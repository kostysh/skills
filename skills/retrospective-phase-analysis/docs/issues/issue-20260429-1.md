## Title

Классифицировать duplicate trace-only review signals при complete stage state

## Skill

`retrospective-phase-analysis` (`skills/retrospective-phase-analysis`)

## Context

Ретроспектива implementation session `F-0028` / `CF-026` показала, что initial retro scan может завысить количество trace-derived non-PASS review signals, когда bounded stage state уже содержит complete review history. Skill уже считает included stage logs и bounded stage state более сильным evidence, чем broad trace mentions, но scan behavior не закрепляет machine-readable classification для duplicate trace-only review signals.

## Problem

Trace-only review mentions остаются полезным fallback evidence. Однако при наличии complete bounded stage state они могут попадать в output как unresolved non-PASS signals, хотя фактически являются historical/superseded относительно structured stage evidence. Это создает шум в scan summary, Markdown reports, `candidateIncidents`, `reviewFindingsTotal` и downstream problem matrix.

## Impact

- Generated reports могут завышать unresolved review problems.
- Problem matrices могут включать noisy trace-only rows после того, как structured stage state уже resolved review history.
- `CandidateIncident` и `reviewFindingsTotal` могут завышаться даже при наличии нового classification field, если фильтрация будет сделана только в rendering.
- Agents тратят время на ручное объяснение evidence-quality differences.
- Suppression без точного contract может скрыть real late review signals, поэтому classification rule должен иметь tight matching и visible source quality.

## Scope

Не входит в scope:

- изменение UDE producer artifacts;
- трактовка trace-only mentions как structured review truth;
- broad-scanning `.dossier/stages/*`;
- добавление нового sidecar validation document;
- замена agent validation of generated Markdown reports.

## Proposed Resolution

Определить complete review history как bounded stage evidence с `rpa_source_quality.review_history_quality: complete`.

Определить duplicate trace-only non-PASS signal как trace-derived signal, scope которого уже представлен complete bounded stage evidence. Matching использует самые сильные доступные поля:

- feature id или backlog item id;
- stage;
- audit class, когда доступен;
- round или artifact identity, когда доступен;
- commit/event commit, когда доступен;
- timestamp/order, подтверждающий, что trace signal не позже complete stage evidence;
- finding count или verdict summary, когда доступен.

Добавить machine-readable classification в `reviewSignals` или adjacent compatible field:

- `classification: active_unmatched | historical | superseded`;
- сохранить `source_quality: trace_derived`;
- сохранить `matching_artifact: false`, если immutable artifact не найден;
- оставить unmatched или uncertain signals видимыми и влияющими на report status.

Обновить actionable filtering:

- `historical`/`superseded` trace-only duplicates остаются в `reviewSignals` как context;
- `historical`/`superseded` duplicates не увеличивают actionable/unresolved `reviewFindingsTotal`;
- `historical`/`superseded` duplicates не создают `CandidateIncident`;
- `historical`/`superseded` duplicates не ухудшают `stageLogs.metrics.sources.candidate_incidents`;
- `historical`/`superseded` duplicates не добавляют blocking `reportStatus.reasons`;
- `active_unmatched`, uncertain, later timestamp/order, different audit class, different round, different commit или ambiguous scope signals продолжают увеличивать unresolved counts, создавать `CandidateIncident`, попадать в problem matrix и влиять на `reportStatus`.

Обновить rendering:

- `scan-summary.json` записывает classification;
- `src/render/report-markdown.ts` и `src/render/logging-review-markdown.ts` показывают historical/superseded trace-only signals отдельно от unresolved unmatched signals;
- `src/render/problem-matrix-markdown.ts` использует unresolved unmatched signals для actionable gaps, а historical/superseded signals оставляет только как context.

Обновить manual stage-log guidance:

- `stage_log_candidates[].next_action` instructs rerun with `--stage-log ... --artifact-evidence ...` для `referenced_only` candidates, которым нужна manual inclusion;
- `src/core/extract-trace-scope.ts`, `reportStatus.reasons` и rendered reports показывают это next action.

## Alternatives Considered

- Drop duplicate trace-only signals entirely. Отклонено: source-quality history остается полезной и может показывать producer gaps.
- Treat every trace-only signal as unresolved. Отклонено: complete bounded stage state является более сильным evidence и должен снижать шум.
- Use only feature/stage matching. Отклонено: это может скрыть later audit, другой audit class, другой round или post-completion regression.
- Put the fix only in UDE producer artifacts. Отклонено: RPA отвечает за consumer-side classification и fallback evidence handling.

## Destructive Side Effects

- Misclassification can hide a real late review. Снижение риска: требовать matching по самым сильным доступным scope, audit class, round, commit и timestamp/order; uncertain signals остаются active unmatched.
- A new field can break downstream consumers. Снижение риска: version the scan-summary contract или keep the field additive and update snapshots/docs.
- Source quality can be lost if historical/superseded signals are removed. Снижение риска: сохранять `source_quality: trace_derived`, `matching_artifact` и rendered context.
- Filtering can become cosmetic only and still overcount metrics/incidents. Снижение риска: test `reviewFindingsTotal`, `CandidateIncident`, `stageLogs.metrics.sources.candidate_incidents`, `reportStatus.reasons` и problem matrix together.
- Manual override guidance can become too broad. Снижение риска: держать его привязанным к `referenced_only` candidates и явному `--artifact-evidence`.
