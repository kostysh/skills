# Issue

`issue-20260428-1`

## Title

Проверять deployed runtime path и identity binding для runtime gates

## Skill

`code-reviewer` (`skills/code-reviewer`)

## Context

Ретроспектива dossier-driven implementation phase для `CF-019` / `F-0027` показала, что runtime-gating code can look correct in isolated units while the deployed runtime path still bypasses the gate. Поздний review также выявил hard-coded deployment identity at an integration boundary.

The general problem is not project-specific. Any runtime gate that authorizes execution must be reviewed through the path actually used in production or the shipped lifecycle.

Self-contained evidence summary:

- isolated service/router logic was not enough to prove production lifecycle wiring;
- tick/request execution path initially did not exercise the gate before invocation;
- hard-coded deployment identity survived until a late code review round;
- adjacent spec/security findings belonged to the same policy/admission risk family.

## Problem

The skill has strong general review guidance, but it does not require a dedicated review block for runtime-gating changes. Reviewers can inspect the service logic and tests while missing whether the deployed construction path actually wires the gate.

Required review dimensions are currently not explicit enough:

- production construction path;
- dependency wiring in deployed lifecycle;
- actual request/tick path that invokes the gate;
- invocation boundary after policy/admission decision;
- idempotency lock scope;
- deployed-path tests rather than only isolated unit tests;
- release/deployment/cell identity binding in integration code.

## Evidence

The originating retrospective found:

- a router/gate integration problem in production lifecycle wiring;
- missing or insufficient deployed-path coverage for runtime gate execution;
- hard-coded deployment identity behavior found after other review dimensions had passed;
- cross-skill policy/admission risks that need coordinated vocabulary but independent review.

Existing skill surfaces likely affected:

- `skill.yaml`
- `fragments/*`
- `references/*`
- `assets/fixtures/*`
- generated `SKILL.md` and `docs/compile-report.md` after regeneration.

Maintenance path:

- This skill is a generated documentation skill. Implementations must update the source bundle first and regenerate generated outputs instead of hand-editing generated `SKILL.md` only.

## Impact

- Code may be approved because isolated units pass while the shipped path bypasses the gate.
- Identity-binding bugs can survive until late integration review.
- Review rerounds increase because construction path, identity binding, and deployed-path evidence are not a standard review shape.

## Scope

In scope:

- active code-review checklist guidance for runtime-gating changes;
- deployed-path test evidence expectations;
- integration identity checks for release/deployment/cell identity;
- optional cross-skill alignment with shared policy/admission risk-family guidance.

Out of scope:

- security-specific replay/authority guidance owned by `security-reviewer`;
- spec traceability owned by `spec-conformance-reviewer`;
- application-specific runtime implementation;
- mandatory dependency on external project files.

## Proposed Resolution

1. Add a mandatory review block `tested path equals deployed path` for runtime-gating changes.
2. Require reviewers to inspect production construction path, dependency wiring, request/tick path, invocation boundary, and idempotency lock scope.
3. Require tests that execute the deployed path. Isolated service/router tests are insufficient when production wiring can bypass the gate.
4. Add integration identity checks:
   - deployment/cell identity is not hard-coded unless the spec explicitly requires it;
   - runtime identity comes from canonical upstream evidence or configuration passed through the deployed path;
   - tests cover non-default identity, mismatch refusal, and absence of silent fallback to default identity.
5. Preserve portability: if a shared policy/admission risk-family reference is added by UDE, this skill may point to it by skill name, but must keep its own checklist understandable inside this skill folder.
6. Implement through the generated-skill maintenance path: update `skill.yaml`, `fragments/*`, `references/*`, and fixtures as needed, then regenerate `SKILL.md` and `docs/compile-report.md`.

## Alternatives Considered

- Keep deployed-path checks as general reviewer judgment. Rejected because runtime-gating failures show this needs an explicit checklist block.
- Move identity binding entirely to security review. Rejected because hard-coded identity and production wiring are code-correctness issues even when they also have security impact.

## Destructive Side Effects

- Runtime-gating reviews may return more blocking findings when deployed-path tests are missing.
- Existing examples or fixtures may need updates to distinguish isolated unit evidence from deployed-path evidence.
- The checklist must stay generic and portable so one project's runtime names do not become mandatory guidance.
