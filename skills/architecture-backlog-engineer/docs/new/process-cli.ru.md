# Утилита скила architecture-backlog-engineer

Описание утилиты и процесса который она поддерживает.

## Этапы процесса использования утилиты

1. Создание беклога
	- Регистрация беклога
	- Регистрация источников
	- Регистрация пакетов
2. Получение информации о состоянии беклога
	- Статус беклога
	- Генерация человекочитаемого беклога
	- Чтение элементов беклога
	- Получение списка gaps всех или по задаче
	- Получение happy-path
	- Получение списка задач на review
3. Изменение беклога
	- Изменение элементов
	- Удаление элементов
	- Удаление беклога
4. Сервис беклога
	- Обновление статуса источников
	- TODO: Какие ще нужны сервисные команды?

Модель взимодействия в проессе:
- Оператор создает и редактирует архитектурные и прочие документы в проекте
- Оператор дает задания агенту и получает от него ответы.
- Агент получает задания у оператора, читает документы, использует утилиту
- Утилита создает артефакты методики

## Создание беклога

### Регистрация версии беклога

Оператор отправляет запрос агенту следующего содержания:
- создай беклог в директории "./backlog"
- Агент получив запрос регистрирует беклог. Для этого он использует команду "init"

#### Пример регистрации беклога:

```bash
./path/to/cli.mjs init --path "./backlog"
```

##### Результат регистрации беклога:

```json
{
	"id": "<uuid>",	
	"path": "<normalized_path>./backlog"
}
```

Идентификатор беклога становится уникальным скопом в котором работают все остальные команды

### Регистрация источников

Оператор отправляет запрос агенту следующего содержания:
- Перечень документов содержащих архитектуру, технических и других решений проекта (список путей к файлам)
- Агент получив этот список изучает файлы и регистрирует их с помощью утилиты, для этого он использует команду "register-source"

#### Пример регистрации источников

```bash
./path/to/cli.mjs register-source --backlog "<backlog_uuid>" --path "./architecture.md" --kind "<source_type>" --authority "<authority_type>" --note "<readable_note>"
```

> `kind` - тип источника (архитектура, ADR, runtime и т.д.), должен быть стандартизован и описан в скиле.
> `authority` - тип доверия источнику (целевая архитектура, текущее фактическое состояние, planning), должен быть стандартизован и описан в скиле.

Результат регистрации источников:
```json
{
	"id": "<uuid>",
	"path": "<normalized_path>./architecture.md",
	"kind": "<source_type>",
	"authority": "<authority_type>",
	"note": "<readable_note>",
	"hash": "<unique_hash>"
}
```

Как видно - утилита регистрирует документ и генерирует для них уникальные идентификаторы и хеш, который впоследствии будет использоваться для детектирования изменений в источнике.

Все источники которые используются в качестве proofs (смотри "Структура пакета") должны быть зарегистрированы.

#### Получение списка источников

В любой момент, агент может запросить у утилиты список зарегистрированных источников командой "list-sources":

```bash
./path/to/cli.mjs list-sources  --backlog <backlog_uuid>
```

или с фильтром по задаче:

```bash
./path/to/cli.mjs list-sources  --backlog <backlog_uuid> --item "<item_id>"
```

Результат запуска утилиты
```json
[
	{
		"id": "<UUID>",
		"path": "<normalized_path>./architecture.md",
		"kind": "<source_type>",
		"note": "<readable_note>",
		"hash": "<unique_hash>"
	}
]
```

### Регистрация пакетов

> Обычно оператор не дает пямого запроса на регистрацию пакетов. Регистрация пакета(ов) - это прямое следствие запроса на создание беклога. Получив такой запрос, агент регистрирует новый беклог или использует уже существующий, если необходимо регистрирует источники и приступает к изучению источников и на их основе создает пакеты задач.

Действия агента:
- Если еще не была создана - создает директирию для хранения пакетов в конексте беклога (стандартное имя: "packets")
- Изучает источники и создает/редактирует пакеты задач в директории "packets"
- Регистрирует пакеты с помощью утилиты, для этого он использует команду "packet"

#### Структура пакета

- `context`: {
	- `glossary`: [
		{
			"term": "<term_title>"
			"definition": "<term_definition>"
			"aliases": [
				"<term_alias>"
			]
		}
	]
	- `id_strategy`:
	- `target_system`: []
	- `as_built`: []
	- `claims`: [
		{
			"claim_id": "<claim_id>"
			"title": "<claim_title>"
			"claim_class": "<claim_class>"
			"commitment": "<claim_commitment>"
			"source_refs": [
				"<source_id>": uuid источника
			]
		}
	]
	- `contracts`: [
		{
			"contract_id": "<contract_id>"
			"title": ""
			"owner": ""
			"versioning_strategy": ""
			"reconciliation_strategy": ""
			"deprecation_window": ""
			"retirement_condition": ""
		}
	]
	- `data_domains`: [
		{
			"domain_id": "<domain_id>"
			"title": ""
			"data_class": ""
			"owners": []
		}
	]
	- `quality_attributes`: [
		{
			"quality_attribute_id": "<quality_attribute_id>"
			"title": ""
			"quality_class": ""
			"target": ""
			"applies_to_refs": []
			"owner_refs": []
			"source_refs": []
			"proof_refs": []
		}
	]
	- `policy_decisions`: [
		{
			"policy_decision_id": "<policy_decision_id>"
			"title": ""
			"policy_surface": ""
			"decision_state": ""
			"owner": ""
			"source_refs": []
			"related_item_refs": []
		}
	]
}	
- `items`: [ // Атомарная задача - одна понятная цель, один внятный результат, можно отдельно описать, спланировать и сделать.
	{
		// Идентификация и описание
		`item_id`: Устойчивый идентификатор задачи
		`title`: Смысл задачи
		`class`: Тип задачи
		// Статус
		`delivery_state`: Технологический статус задачи - defined, specified, planned, implemented
		`readiness_states`: [ // Процессный стутус задачи - 
			"gaps_resulution|deps_changed|proofs_changed|claims_changed|contracts_changed, confirmed"
		]
	    `gaps`: [
	    	"<gap_description>": Описание проблелов в задаче, которые необходимо закрыть перед специфицированием
	    ]
	    // Привязки
	    `depends_on`: [
	    	"<item_id>": зависит от задачи
	    ]
	    `affects`: [
	    	"<item_id>": влияет на задачу (нужно ли??? если есть depends_on, то при формировании графа affects станет известен сам)
	    ]

	    	"test": uuid источника содержащего пруф плана (где тест)
	    }

	    ]

	    	"<contract_id>"
	    ]

	    ]
	    `quality_attributes`: [
	    	"<quality_attribute_id>"
	    ]

	    	"<policy_decision_id>"
	    ]
	    `history`: [
	    	"<iso_date>: <change_description>"
	    ]
	}
]

Что выполняет утилита при регистрации пакета:
- В процессе регистрации утилита читает регистрируемый пакет и строит граф задач на основе привязок элементов items.
- В процессе построения графа задач утилита идентифицирует задачи по их item_id. Если задача уже существует и при этом она изменилась (для определения этого утилита доджна хранить ), то она будет обновлена (upsert значение).
- Если происходит upsert задачи, то у всех depends_on и affects задач, readiness_state устанавливается в состояние deps_changed, а в history добавляется запись о том, что изменилось (например: `auth-core`'s title changed или `auth-core`'s specification changed). При этом, если у задачи которая изменилась есть "дети" в графе задач, то у каждой из них readiness_state и history будут изменены.
- По-умолчанию у добавляемой из пакета задачи readiness_state равняется confirmed
- Если у задачи в пакете массив gaps содержит записи, то readiness_state автоматически устанавливается в gaps_resulution (даже если readiness_state установлен иным)

## Получение информации о состоянии беклога

### Статус беклога

Команда "status" возвращает перечень полезных метрик, которые агент может использовать для работы и информирования оператора.

Например, такие метрики:
- Общее количество задач в беклоге
- Количество задач у которых есть gaps
- Количество задач готовых к специфицированию
- Количество задач в состоянии specified
- Количество задач в состоянии planned
- Количество задач в состоянии implemented
- Количество задач ожидающих ревью - те, у которых `readiness_state !== confirmed` 
- ???

### Генерация человекочитаемого беклога

Команда "report" создает человекочитаемый и наглядный беклог в .md файле по указанному пути.

### Чтение элементов беклога

Команда "item" возвращает объект задачи по его item_id.

### Получение списка gaps всех или по задаче

Команда "gaps" возвращаяет массив "белых пятен" индексированный по задачам, по всему беклогу. При указании параметра "--item <item_id>" массив gaps фильтруется по конкретной задаче.

### Получение happy-path

Команда "happy-path" возвращает индексированный массив `{ "item_id": "<ready_for_what>" }` которые ждут обработки и отсортированных по положению в графе и своим зависимостям. Из массива исключаются те задачи, у которых `delivery_state === implemented` и `readiness_state === confirmed` (по причине того, что такие задачи уже выполнены и не требуют вмешательства).

### Получение списка задач на review

Команда "review" возвращает индексированный массив `{ "item_id": "<why_need_review>" }` которые ждут ревью по причине того, что их `readiness_state !== confirmed` (например, у них изменения в зависимостях или proofs).

## Изменение беклога

### Изменение элементов

Изменение элементов осуществляется путем внесения изменений в элемент задачи в соответствующем пакете с последующей повторной регистрацией пакета. В процессе этой повторной регистрации утилита определит какие задачи изменились и внесет изменения только в них.

### Удаление элементов

Команда "delete-item", удаляет элемент по коду. При удалении элемента утилита обновляет все зависимые задачи, изменяя их readiness_state и дополняет их history.

### Удаление беклога

Команда "delete-backlog" удаляет беклог и его артефакты. Процедура опасная, поэтому агент обязан предупреждать оператора о последствиях и вызывать ее только получив от оператора четкое подтверждение.

## Сервис беклога

### Обновление статуса источников

Команда "refresh" выполняет рекурсивное обновление hash всех зарегистрированных источников. Если указан параметр "--item <item_id>" то refresh применяется только к "proofs" конкретной задачи и ее "детей" в графе.

Если при обновлении hash выявляется, что он изменился, то утилита для всех задач в которых данный источник указан в "proofs" устанавливает readiness_state в статус proofs_changed и также добавляет в history соответствующую запись `<iso_date>: "<item_id>" proof "<origin|specification|plan|implementation|test>" changed`
