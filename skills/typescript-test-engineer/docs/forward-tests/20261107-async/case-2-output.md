> Публичная нормализованная запись ответа: пути рабочего окружения заменены относительными ссылками; решения и результаты сохранены.

Минимальная коррекция: использовать существующий `now` для прикладной проверки, сохранить реальную PostgreSQL-проверку и подписаться на оба события до `start()`. Файлы менять не требуется: ниже дизайн.

1. **Прикладная проверка срока**

   Сохранить TTL 2 секунды. Использовать фиксированный `issuedAt` и три значения логического времени:

   | Логическое время | Ожидаемый результат |
   |---|---|
   | `expiresAt - 1` мс | токен принят |
   | `expiresAt` | токен отклонён |
   | `expiresAt + 1` мс | токен отклонён |

   В каждом случае передать через существующий seam постоянную функцию `now: () => logicalNow`. Создать `operationId` из того же `logicalNow`. Не смешивать его с настоящим `Date.now()`.

   Проверять фактический результат принятия или отклонения через существующий контракт `checkToken`. Формат результата и ошибки в запросе не задан, поэтому новые поля или коды ошибок не вводить. Если тесту нужны сервисы, дождаться их готовности до операции; задержка запуска больше не меняет логическое время.

2. **Интеграционная проверка PostgreSQL**

   Оставить реальную функцию, её SQL, `clock_timestamp()` и самостоятельное соединение с тестовой БД. Удалить утверждение, что подмена `Date.now()` управляет временем БД.

   После готовности сервисов подготовить данные по времени самой БД и вызвать настоящую функцию. Сохранить отдельные случаи принятия действующего и отклонения истёкшего токена. Не ждать истечения TTL и не увеличивать его.

   Время БД до и после вызова позволяет подтвердить сторону границы: для положительного случая весь интервал должен находиться до `expiresAt`, для отрицательного — на границе или после неё. Если интервал пересёк границу, такой вызов не доказывает выбранный сценарий.

   Без управления часами БД нельзя детерминированно попасть в точное равенство или за 1 мс до него. Эти точки проверяет прикладной тест; для реальной PostgreSQL-функции они остаются ограничением доказательства.

3. **Синхронные события**

   Оба ожидания должны существовать до `start()`. Например, следующая схема сохраняет проверки и отменяет ожидания при ошибке запуска или отсутствии события. `eventDeadlineMs` здесь обозначает существующий лимит тестового окружения.

   ```ts
   const controller = new AbortController();
   const readyWait = once(emitter, 'ready', {
     signal: controller.signal,
   });
   const finishedWait = once(emitter, 'finished', {
     signal: controller.signal,
   });
   const settled = Promise.allSettled([readyWait, finishedWait]);
   const watchdog = setTimeout(
     () => controller.abort(),
     eventDeadlineMs,
   );

   try {
     start(emitter);

     const [ready] = await readyWait;
     await finishedWait;
     assert.equal(ready.status, 'ok');
   } finally {
     clearTimeout(watchdog);
     controller.abort();
     await settled;
   }
   ```

   Сохранены получение `ready`, его `status === 'ok'` и получение `finished`. Таймер ограничивает ожидание; он не служит сигналом готовности. Оба обработчика ошибок подключены через `allSettled` до запуска. Для отдельного тестового emitter можно также проверить отсутствие оставшихся слушателей `ready`, `finished` и `error`.

Предложенный патч не устраняет причины: сутки валидности скрывают старение токена, 50 мс не доказывают готовность, а `flushPromises()` после `start()` не возвращает уже потерянные синхронные события.

Очистку сервисов и соединений зарегистрировать до действий, которые могут завершиться ошибкой. Дождаться завершения начатой работы, закрыть соединения и удалить только данные данного теста. Подмена глобальных часов здесь не нужна.
