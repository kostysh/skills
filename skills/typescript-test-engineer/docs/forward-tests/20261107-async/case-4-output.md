> Публичная нормализованная запись ответа: пути рабочего окружения заменены относительными ссылками; решения и результаты сохранены.

Общий запрет async callback в `waitFor` не нужен. Перенос `submitJob()` внутрь callback нарушит контракт: ошибка чтения может вызвать повторную отправку job.

Это проектирование тестов по синтетическому входу. Файлы не изменены.

1. Для unit-теста оставить fake timers, применить асинхронное продвижение времени и дождаться имеющегося Promise завершения:

   ```ts
   vi.useFakeTimers();

   // Фрагмент тела теста; teardown описан ниже.
   scheduleSave();

   await vi.advanceTimersByTimeAsync(99);
   expect(saved).toBe(false);

   await vi.advanceTimersByTimeAsync(1);
   await saveCompleted; // Уже имеющийся Promise полного завершения.
   expect(saved).toBe(true);
   ```

   Проверка на 99 мс обнаружит преждевременное сохранение. Проверка после 100 мс и `await saveCompleted` обнаружит отсутствие результата. Синхронный `advanceTimersByTime` запускает таймер, но не доказывает завершение асинхронной части callback.

   Здесь не нужны polling, настоящий сон или сеть. Поддержка выбранного API задана во входе; менять Vitest не требуется.

2. Интеграционный тест уже правильно разделяет команду и наблюдение:

   ```ts
   await submitJob();

   await waitFor(async () => {
     const state = await readState();
     expect(state).toEqual({ status: 'complete' });
   }, { timeout: 2_000 });
   ```

   Семантика ожидания:

   - Незавершённое состояние вызывает ошибку assertion и следующую попытку чтения.
   - Rejection из `readState()` делает callback отклонённым; `waitFor` повторяет наблюдение в пределах timeout.
   - Пока Promise callback остаётся pending, новый вызов callback не начинается.
   - Возврат `false` или проглоченная ошибка чтения могут завершить ожидание успешно. Они не означают «повтори позже».

   Для переходной ошибки чтения достаточно повторить чтение. Повторять команду нельзя. Если чтение зависнет, должен сработать независимый реальный deadline раннера, который уже предусмотрен контрактом. Сам timeout не отменяет зависший запрос.

   Реальные таймеры и соединение с worker сохраняются: это граница, которую проверяет интеграционный случай. Локальный Promise flush её завершение не доказывает.

3. Очистку зарегистрировать до запуска действия и выполнить на успешном и ошибочном выходе.

   В unit-тесте нужно завершить либо штатно отменить принадлежащую тесту работу и дождаться её Promise. При раннем падении проверки на 99 мс можно асинхронно довести этот локальный одноразовый таймер до выполнения и присоединиться к завершению. Простое удаление таймера может оставить Promise завершения pending. После завершения работы удалить оставшиеся таймеры и восстановить реальные таймеры через вложенный `finally`.

   В интеграционном тесте после окончания наблюдения нужно через поддерживаемый lifecycle отменить незавершённые чтения, дождаться начатой работы и закрыть принадлежащее тесту соединение. Порядок зависит от транспортного API. Если именно закрытие соединения прерывает чтение, оно предшествует ожиданию чтения. Нельзя полагаться только на `Promise.race`: проигравшая операция продолжает работу.

   API отмены и очистки job во входе не указан. Поэтому гарантированную очистку worker/job подтвердить нельзя. Если отмена или присоединение недоступны, это остаётся явным ограничением.

Для этой правки применимы риски повторной отправки, ошибки чтения и незавершённой работы после ошибки. Запрет повторной отправки следует закрепить наблюдаемым числом отправок через существующий seam, сохранив реальный вызов worker. Параллельные команды, конфликты завершения, replay, восстановление stale job, ошибки записи, невалидный вход и восстановление частичного состояния — N/A для данной правки: она не вводит такие переходы. Поведение worker при этих условиях не проверено.
