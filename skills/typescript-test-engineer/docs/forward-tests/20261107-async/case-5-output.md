Причина — незавершённая работа и отсутствие гарантированной очистки. Увеличение TTL, повторные запуски и больший timeout эту причину не устраняют.

Из предоставленного кода следует:

- Когда `first` отклоняется, `Promise.all` и затем `Promise.race` отклоняются. Они **не отменяют `second`**. Он продолжает ждать `gate`.
- Исключение выходит из `await`, поэтому `vi.useRealTimers()` не выполняется. Подмена времени остаётся в общем worker и может влиять на следующие или concurrent-тесты.
- Дедлайн использует подменённый `setTimeout`. Без продвижения fake timers он не сработает. `vi.setSystemTime()` задаёт дату, но не продвигает таймеры.
- Нет пути, который обязательно остановит работу, удалит listener и закроет клиент. Незакрытый клиент может удерживать процесс. Сам ожидающий Promise процесс не удерживает.

Источник позднего `unhandled rejection` **не установлен**. `Promise.all` регистрирует обработчики для обоих участников, а `Promise.race` — для обоих своих входов. Позднее отклонение проигравшего Promise само по себе не становится необработанным. Нужно проверить отделённую async-работу, обработчики событий и ошибки остановки внутри участников. Их реализации не предоставлены.

Минимальная рекомендуемая коррекция — оформить существующий lifecycle в одном scope:

1. Зарегистрировать `finally` или cleanup hook **до запуска** потенциально падающей работы. Сразу наблюдать отклонения каждого запущенного участника.
2. При любом выходе запросить отмену через существующий signal и освободить принадлежащие тесту ожидания. При необходимости освободить `gate`, предварительно запросив отмену, чтобы не продолжить полезную работу случайно.
3. Дождаться завершения всех запущенных участников. `Promise.allSettled` подходит для сбора результатов, но сам заблокированный `gate` не освобождает.
4. После остановки работы удалить принадлежащий ей listener и закрыть клиент в порядке, предусмотренном его API.
5. Убрать собственный таймер дедлайна. Восстановить часы и другие подмены даже при ошибке очистки. Сохранить исходную ошибку; ошибки teardown также отразить в диагностике.

Если тест проверяет только сравнение дат или TTL, достаточно контролировать business clock и оставить execution timers работающими. Если проверяется именно таймерное поведение, нужны управляемое async-продвижение времени и независимый работающий watchdog. Конкретный API зависит от версии Vitest, которой во входе нет. Общую подмену часов необходимо изолировать от concurrent-тестов.

Фокус проверки после отдельного разрешения на исправление:

| Сценарий | Что должно быть доказано |
| --- | --- |
| `second` достиг ожидания `gate`, затем `first` падает | Исходная ошибка сохраняется; cleanup отменяет или освобождает `second`, дожидается его остановки и закрывает ресурсы |
| `second` падает раньше незавершённого `first` | Другой участник также завершается; его поздняя ошибка наблюдается. Способ остановки `first` нужно установить по реализации |
| Assertion падает до освобождения `gate` | Cleanup всё равно выполняется; нет оставленного listener, клиента или подменённых часов |
| Оба участника завершаются успешно | Дедлайн снят, ресурсы закрыты, часы восстановлены |
| Работа зависла при замороженной дате | Независимый watchdog действительно срабатывает, после чего выполняется полная очистка |

Порядок нужно задавать через deferred или существующие сигналы достижения фазы, без `sleep`. После проверки этих путей следует повторно запустить изолированный тест, затем соответствующий suite в общем worker и проверить выход процесса. Повторы нужны для проверки устойчивости исправления; retries не заменяют его.
