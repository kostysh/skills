Добавить admission-gate checklist для replay semantics и authority binding

## Problem

The skill has general security guidance for auth, replay, freshness, and evidence. Admission gates need a more specific security checklist because a stored policy decision can be confused with current executable authority.

The reviewer must explicitly distinguish:

- historical/audit replay of a previous decision;
- current invocable or executable capability;
- conflict replay using the same idempotency key with different inputs;
- caller-controlled timestamps or evidence refs;
- canonical authority for freshness, evidence identity, scope, stage, release, runtime artifact, and deployment identity.

Dangerous pattern: the system records `allowed` once for idempotency or audit, then later treats replay of that record as permission to execute after policy, evidence, identity, or caller authority may have changed.

## Scope

In scope:

- application-specific implementation advice;
- mandatory dependency on external project files.

## Proposed Resolution

1. Add an admission-gate security checklist for any feature where a policy/admission/approval decision can produce executable capability.
2. Require replay semantics checks:
   - replay returns only audit/history status unless fresh invocation is explicitly proven safe;
   - replay does not grant a new invocable capability;
   - conflict replay fails closed;
   - idempotency key scope includes security-relevant dimensions such as actor, operation, target, stage, policy, release, and deployment identity.
3. Require authority questions:
   - who controls the freshness timestamp;
   - which canonical source binds evidence identity;
   - whether caller can select scope, stage, evidence, or release refs;
   - what happens when evidence is absent or stale;
   - which identity binds release to runtime artifact and deployment.
4. Return `FAIL` when replay grants executable capability, conflict replay does not fail closed, or caller-controlled authority lacks protective binding.
5. Preserve portability: if a shared policy/admission risk-family reference is added by UDE, this skill may point to it by skill name, but must keep its own checklist understandable inside this skill folder.
6. Implement through the generated-skill maintenance path: update `skill.yaml`, `fragments/*`, `references/*`, and fixtures/tests as needed, then regenerate `SKILL.md` and `docs/compile-report.md`.

## Alternatives Considered

- Use only general auth/replay guidance. Rejected because admission gates have a specific capability-replay failure mode.
- Treat replay only as correctness. Rejected because replay of stored `allowed` decisions can become authorization bypass.

## Destructive Side Effects

- Reviews may become stricter for approval/admission workflows and return `FAIL` when replay semantics are ambiguous.
- Existing examples may need updates to distinguish historical replay from executable capability.
- Guidance must stay generic so one project's admission terminology does not become mandatory.
