# Issue: extend admission security review to policy-governance gates

Issue ID: `SEC-02`

Primary owner skill: `security-reviewer`

Status: audited

## Проблема

Существующий security issue [improvement-proposal-20260423-1.md](improvement-proposal-20260423-1.md) покрывает auth-admission route concerns. Инцидент `F-0025` показал связанный, но отдельный surface: policy-governance admission before external consultant invocation and policy activation.

В session `019dbf3f` были релевантны такие security-facing branches:

- consultant execution невозможен после explicit DENY;
- conflicting admission replay должен fail closed до any external invocation;
- missing freshness timestamp при age gating должен fail closed;
- active-scope activation должен быть serialized, чтобы две active policies не могли быть admitted concurrently.

Это security-relevant, потому что защищает external side effects, governance state и fail-closed policy enforcement, даже когда это не HTTP route admission problem.

## Почему это важно

Policy-governance admission может контролировать внешние side effects и security-relevant control-plane decisions. Security review должен явно отличать этот surface от route admission и проверять fail-closed behavior, replay и activation races.

## Текущая активная поверхность

- `SKILL.md`: threat model, security review workflow и auth-admission checkpoint.
- `references/methodology.md`: finding confidence и exploitability discipline.
- `references/api-auth-input.md`, если используется: route admission checklist.
- Существующий issue [improvement-proposal-20260423-1.md](improvement-proposal-20260423-1.md): auth-admission early checklist stack.

## Требуемое исправление

Добавить bounded policy-governance admission checkpoint в `security-reviewer`.

Checkpoint срабатывает при review changes, которые affect:

- external consultant или external tool invocation admission;
- policy profile activation или active-scope selection;
- governance/audit persistence used as precondition for action;
- fail-closed policy gates;
- replay/idempotency controls вокруг security-relevant decisions.

## Что должно измениться

Security checklist:

- нет invocation after explicit deny;
- нет invocation after failed или conflicting audit persistence;
- replayed или conflicting request ids не могут reuse stale allow decisions;
- stale или missing freshness evidence fails closed, когда freshness required;
- activation races не могут create simultaneous active security/governance policy;
- audit records достаточны для объяснения refusal and admission decisions;
- mitigations проверены before reporting vulnerability.

## Acceptance Criteria

- `security-reviewer` docs distinguish route auth-admission from policy-governance admission.
- Fast workflow или relevant reference включает bounded checkpoint выше.
- Security review prompts для policy/admission features явно спрашивают про deny/no-invocation, replay conflict, freshness, audit persistence failure и activation races.
- Findings по-прежнему требуют confirmed attacker/control path или security-relevant operator/control-plane impact.
- Tests или examples покрывают one external-invocation admission review and one active-policy activation review.

## Обязательные ограничения для planning и implementation

- Default threat model сохраняется, но policy-governance reviews могут state, когда relevant actor is operator, compromised integration или replay source rather than anonymous web attacker.
- HIGH-confidence default reporting сохраняется.
- Non-security merge risks route back to `code-reviewer`.

## Non-Goals

- Не расширять route-specific auth-admission issue; это отдельная policy-governance admission concern.
- Не report-ить low-confidence theoretical vulnerabilities.
- Не дублировать general code quality findings from `code-reviewer`.
- Не требовать этот checkpoint для features, которые не gate external side effects, authorization или policy activation.
