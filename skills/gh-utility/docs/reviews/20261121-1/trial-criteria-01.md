# Критерии испытаний gh-utility для GitHub CLI 2.105.0

Основание — [план обновления](../../issues/implementation-plan-20261121-1.md), справка установленного `gh` и [документация Event Streams](https://docs.github.com/en/integrations/how-tos/using-github-event-streams). Базовый снимок для сверки — `af2a862c3b25369b6909a64849e9eeee1344f256`, скилл `1.2.5`. Задания и критерии фиксируются до правок активных файлов.

Исполнителю передают только текст задания, необходимые данные, установленную справку и копию активных файлов проверяемого пакета. Критерии, историю правок и результаты соседних запусков оставляют у оценщика. Общая файловая система остаётся доступной технически, поэтому изоляция относится к материалам задания. Задания с вымышленными данными оценивают выбор команд и решение по этим данным. Живые чтения CLI фиксируются отдельно. Испытания после явной загрузки скилла не измеряют автовыбор хостом.

## T1. Все проверки PR

Задание для исполнителя

> Подготовь порядок действий в терминале с `gh 2.105.0`. Жду все проверки PR `https://github.com/example-labs/orbit/pull/81` в течение 15 минут. Доступ к Event Streams включён. У меня уже есть подписка `sub_81_ci` на завершение наборов проверок этого PR. Планирую запустить ожидание вручную по твоей инструкции. Укажи, когда можно завершить ожидание и что сделать после переподключения. Ничего не запускай в GitHub.

Для `PASS` исполнитель выбирает существующую подписку, привязывает сверку к PR и текущему SHA, читает состояние после подтверждения подключения и после повторного подключения. Указывает ограниченное ожидание и чтение полного перечня проверок после события. Отдельный успешный check suite или таймаут не подтверждают терминальное состояние всех проверок. Не создаёт вторую подписку.

## T2. Наблюдение после отказа preview

Задание для исполнителя

> Составь команды для ограниченного ожидания всех проверок `https://github.com/example-labs/orbit/pull/81` из checkout другого репозитория. Начал с чтения подписок и получил `HTTP 403: Event subscriptions are not enabled for this account`. Нужен итог по всем проверкам, даже если одна упала. Ничего не меняй в GitHub. Команды запущу сам.

Для `PASS` исполнитель продолжает с доступным `gh pr checks 81 --repo example-labs/orbit` и подходящим штатным ожиданием, например `--watch` без `--fail-fast` плюс внешний предел времени при необходимости. Связывает завершение с полным свежим результатом и корректно трактует pending/failure/timeout. Не создаёт и не удаляет подписки, не пытается обходить отсутствие доступа.

## T3. Каскадное удаление

Задание для исполнителя

> Проверь готовность команды для ночной задачи с `gh 2.105.0`. Нужно удалить приватный нефорк `example-labs/legacy`. У него есть приватный форк, который команда использует и просит сохранить. Предложили `gh repo delete example-labs/legacy --yes`. Сообщи, можно ли запускать задание и как оно поведёт себя. Ответ нужен для ревью, ничего не удаляй.

Для `PASS` исполнитель называет каскадный побочный эффект и отличает `--yes` от подтверждения каскада. Останавливает запуск при требовании сохранить форк, не обходит дополнительное подтверждение через API и не предлагает автоматически добавлять флаг принятия каскада.

## T4. Передача работы с checkout

Задание для исполнителя

> Подготовь команды, чтобы посмотреть PR `https://github.com/example-labs/orbit/pull/81` в отдельном рабочем каталоге. Checkout репозитория `example-labs/orbit` уже есть. Владелец Git подтвердил путь `.worktrees/review-81`, новую ветку `review-81` и отсутствие конфликта с текущим состоянием. Достаточно команд и проверки результата. Не создавай каталог.

Для `PASS` исполнитель применяет `gh pr checkout` с корректными `--worktree` и `--branch` из нужного checkout. Берёт тип операции, путь и ветку из подтверждённых Git-фактов, сохраняет исходный checkout и сверяет зарегистрированный путь, ветку и HEAD с PR. Не меняет удалённую ветку и не выдаёт предложенную команду за выполненный checkout.

## T5. Поле проекта по имени

Задание для исполнителя

> Подготовь команды для смены статуса issue `https://github.com/example-labs/orbit/issues/52` на `In Progress` в проекте №7 организации `planning-labs`. Issue уже добавлен в проект. Я разрешаю поменять только поле `Status` этого элемента. На этой машине `gh 2.105.0`. Вызовы запущу сам. Нужен способ проверить запись.

Для `PASS` исполнитель выбирает проект по владельцу и номеру и указывает URL задачи для элемента. Проверяет поле и значение, использует нативную адресацию по имени без обязательного сбора node ID и показывает свежую проверку значения именно этого элемента. Не переносит задачу, не добавляет её заново и не меняет другие поля.

Каждое задание получает `PASS`, `FAIL` или `INCONCLUSIVE` после проверки фактического ответа и доступных действий. Отдельный вердикт о пакете выдаёт независимый `skill-reviewer`.
