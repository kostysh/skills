## Замечания и P1-screen

### P1-01. Диагностика может ротировать учётные данные вне запроса

Прямое доказательство. Правила безопасности трактуют PR, repository и Projects reads как операции без дополнительного эффекта и направляют на обычный `gh auth status`. В сценариях HTTP 401 обе таблицы снова предлагают его. Блоки `First checks` и `Fast triage` ставят после `--no-refresh` команды `gh repo view` и `gh api rate_limit` без условия между вызовами. В Projects пример `Auth and target` тоже начинает с обычного `gh auth status`. Абзац об ограничении ротации есть в справке по аутентификации, но эти инструкции его не применяют в точке выбора команды. [Safety rules](/home/kostysh/.codex/skills/custom/.worktrees/gh-utility-2-105/skills/gh-utility/references/safety-rules.md:18) · [Auth and scopes](/home/kostysh/.codex/skills/custom/.worktrees/gh-utility-2-105/skills/gh-utility/references/auth-and-scopes.md:5) · [Troubleshooting](/home/kostysh/.codex/skills/custom/.worktrees/gh-utility-2-105/skills/gh-utility/references/troubleshooting.md:5) · [Projects](/home/kostysh/.codex/skills/custom/.worktrees/gh-utility-2-105/skills/gh-utility/references/projects-playbook.md:5)

Путь ошибки и P1-screen. Оператор просит проверить PR или причины HTTP 401 и исключает изменение учётных данных. Команда `gh auth status` без `--no-refresh` может обменять близкий к истечению OAuth-токен и записать новые данные в keyring или конфигурацию. Без `--active --hostname` проверка охватывает также другие сохранённые аккаунты. Обычный API-вызов после безопасного статуса отдельно запускает автообновление. Поэтому даже предварительная диагностика способна изменить учётные данные вне разрешённого действия, включая аккаунт вне запроса. [Выбор аккаунтов и credential](https://github.com/cli/cli/blob/v2.105.0/pkg/cmd/auth/status/status.go#L314-L359) · [Ветка no-refresh](https://github.com/cli/cli/blob/v2.105.0/pkg/cmd/auth/status/status.go#L536-L553) · [Автообновление в HTTP-клиенте](https://github.com/cli/cli/blob/v2.105.0/api/http_client.go#L203-L223) · [Сохранение и замена credential](https://github.com/cli/cli/blob/v2.105.0/internal/config/refreshable.go#L483-L514)

Закрытие. Оставить единое правило ротации, связать его с классификацией чтений и ссылаться на него в применимых примерах. Для диагностики с запретом ротации выбирать хост и активный аккаунт, использовать `--no-refresh`, если флаг поддерживается, и явно применять условие безопасного источника перед следующим API-вызовом. Проверить исходный путь с близким к истечению токеном и посторонним аккаунтом, а также нормальный путь с подтверждённым источником без автообновления. Для повторной проверки достаточно зафиксированных фактов, справки и кода версии.

### P2-01. Операции с существующей подпиской зависят от хоста по умолчанию

Прямое доказательство. Пример `gh event listen --subscription ID` и команды списка, просмотра и удаления не задают `GH_HOST`. Для слушателя только `--resource` выбирает хост по URL. При ID или списке клиент использует `DefaultHost` и принимает только GitHub.com. [Пример скилла](/home/kostysh/.codex/skills/custom/.worktrees/gh-utility-2-105/skills/gh-utility/references/pr-ci-review-loop.md:84) · [Выбор хоста в listen](https://github.com/cli/cli/blob/v2.105.0/pkg/cmd/event/listen/listen.go#L237-L248) · [Выбор хоста в list](https://github.com/cli/cli/blob/v2.105.0/pkg/cmd/event/subscription/list/list.go#L69-L83) · [Ранний отказ в OpenStream](https://github.com/cli/cli/blob/v2.105.0/pkg/cmd/event/client/client.go#L214-L224)

Путь ошибки и P1-screen. В окружении с `GH_HOST` на Enterprise пользователь сообщает о доступной подписке GitHub.com и просит ждать по ID. Приведённая команда возвращает ошибку хоста ещё до подключения. Ожидание не запускается. Команда при этом явно завершается с ошибкой до запроса к другому сервису. Ложное подтверждение результата или удаление другого ресурса из этого пути не следует.

Закрытие. Показать установку `GH_HOST=github.com` на время отдельного вызова для listener по ID и команд подписок без URL. Проверить выданные команды для действующей подписки в окружении с Enterprise-хостом по умолчанию.

### P2-02. Fallback на watch может пережить общий срок

Прямое доказательство. При недоступном preview справка предлагает `gh pr checks --watch` или `gh run watch` без способа применить к ним общий срок. Ограниченные чтения указаны после досрочного выхода watch и для чтения состояния PR. Реализация `pr checks` опрашивает с интервалом до выхода из pending. `run watch` ждёт `Completed`. [Monitoring и fallback](/home/kostysh/.codex/skills/custom/.worktrees/gh-utility-2-105/skills/gh-utility/references/pr-ci-review-loop.md:59) · [Цикл pr checks](https://github.com/cli/cli/blob/v2.105.0/pkg/cmd/pr/checks/checks.go#L204-L229) · [Цикл run watch](https://github.com/cli/cli/blob/v2.105.0/pkg/cmd/run/watch/watch.go#L173-L203)

Путь ошибки и P1-screen. Пользователь задаёт конечное окно в 15 минут. Preview отдаёт 403, а уже видимая проверка остаётся pending дольше окна. Запуск указанного watch без внешней границы задерживает итоговый снимок и сообщение о неполном результате сверх срока. Правило об ожидаемом наборе остаётся верным, поэтому доказанный дефект относится к сроку и выдаче результата.

Закрытие. Применять один срок к подключению, наблюдению, переходу на запасной способ и итоговому чтению. Для конечного окна или ограничить watch снаружи, или показать повторные отдельные чтения. Проверить выдачу при 403 с известным pending до истечения окна и при раннем выходе watch.
