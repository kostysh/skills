# Issue: require implementation pre-review risk checklist evidence

Issue ID: `ISS-07`

Primary owner skill: `unified-dossier-engineer`

Status: audited

## Проблема

High-risk implementation surfaces могут доходить до external review без author-side pre-review checklist, записанного в dossier artifacts.

В session `019dbf3f` `F-0025` реализовал policy profiles, consultant admission, perception policy decisions и active-scope governance. External reviews поздно нашли существенные edge cases:

- explicit consultant `deny` должен persist как DENY и не должен invoke consultant;
- conflicting consultant admission replay должен fail closed до invocation;
- missing `observedAt` при наличии `maxEvidenceAgeMs` должен fail closed как stale evidence;
- active-scope activation требует serialized read plus insert semantics.

Это не responsibility `implementation-discipline`. Правильный owner — dossier workflow evidence: high-risk features должны declare и check свою risk family до начала external review.

## Почему это важно

External reviewers должны оставаться независимыми, но workflow не должен использовать их как первый механизм обнаружения очевидных high-risk branches. Checklist evidence переносит часть самопроверки до review, не заменяет review и не доказывает correctness.

## Текущая активная поверхность

- `SKILL.md`: implementation workflow и review policy.
- `references/delivery-workflow-layer.md`: stage readiness и handoff semantics.
- `references/telemetry-and-closure.md`: stage state и log frontmatter.
- `references/audit-policy.md`, если active in source bundle: required audit stack и review freshness.

## Требуемое исправление

Добавить generic implementation pre-review checklist evidence mechanism в dossier workflow.

Механизм не hardcode-ит каждый domain в global skill. Feature или stage явно declares one or more bounded risk families, затем runtime/workflow требует checklist evidence до того, как `implementation` можно считать ready for external review.

Начальная risk family:

- `policy-admission-governance`

## Что должно измениться

Для `policy-admission-governance` checklist покрывает:

- explicit allow и explicit deny behavior;
- отсутствие external invocation после deny или failed admission persistence;
- duplicate/conflicting request id replay behavior;
- missing, ambiguous, stale или unsupported evidence handling;
- freshness timestamp requirement, когда age gates существуют;
- active-scope concurrency и transaction/locking model;
- сохранение append-only decision/audit facts;
- regression test paths для каждого accepted high-risk behavior.

Допустимые evidence shapes:

- structured `pre_review_checklists` field в `.dossier/stages/<feature>/implementation.json`;
- mirrored bounded frontmatter в implementation stage log;
- checklist section в dossier со stable ids, referenced by stage state;
- helper command, который записывает checklist entries до `ready_for_close`.

## Acceptance Criteria

- Implementation stage может declare bounded risk family, например `policy-admission-governance`.
- Если risk family declared, `ready_for_close` или pre-review handoff записывает structured checklist evidence.
- Missing checklist evidence блокирует stage или явно помечает implementation как не готовый к external review.
- External reviewers могут читать checklist как author-side evidence, но все равно выполняют independent review.
- Tests или fixtures покрывают один implementation с declared risk family и один implementation без risk family.

## Обязательные ограничения для planning и implementation

- Risk-family declarations остаются explicit; нельзя infer-ить их только из keywords.
- Projects могут добавлять risk families без изменения core runtime behavior.
- Checklist evidence считается readiness artifact, а не proof of correctness.
- Существующие audit policy и review freshness gates сохраняются.

## Non-Goals

- Не менять `implementation-discipline`.
- Не делать policy/admission checklist обязательным для каждого implementation.
- Не превращать dossier workflow в domain-specific reviewer.
- Не заменять external `spec-conformance-reviewer`, `code-reviewer` или `security-reviewer` audits.
- Не блокировать low-risk documentation-only или artifact-only implementation stages нерелевантными checklists.
