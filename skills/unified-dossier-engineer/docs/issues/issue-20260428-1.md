# Issue: добавить явное состояние `intaken` после `feature-intake`

Issue ID: `ISS-10`

Primary owner skill: `unified-dossier-engineer`

Status: audited

## Проблема

После успешного `feature-intake` выбранный backlog item остается в `delivery_state: defined`.
Feature dossier при этом уже создан, `feature-intake` закрыт через verification, independent review и `dossier-step-close`, а `next-step` для dossier корректно указывает на `spec-compact`.

На практике это создает неоднозначность:

- `queue` продолжает показывать выбранный item как обычную backlog-задачу, которую можно брать дальше;
- оператор видит `CF-019` в queue после закрытого intake и ожидаемо воспринимает это как ошибку закрытия;
- агенту приходится объяснять, что "intake уже был, но backlog state еще defined", хотя это не видно в backlog truth layer;
- `feature-intake` оставляет durable dossier handoff, но не оставляет явного backlog-level lifecycle следа;
- current lifecycle reconciliation issue покрывает `spec-compact -> specified`, `plan-slice -> planned`, `implementation -> implemented`, но намеренно задает `feature-intake -> no lifecycle target`.

Наблюдаемый инцидент:

- `CF-019` был выбран в intake и оформлен как `F-0027`.
- `F-0027` получил `process_complete: true` для `feature-intake`.
- `dossier-engineer next-step --dossier ...F-0027...` вернул `spec-compact`.
- `dossier-engineer queue` продолжил показывать `CF-019` рядом с еще не intaken `CF-026`, потому что `CF-019.delivery_state` остался `defined`.

Это не просто UX-шероховатость. Backlog truth layer не умеет отличать "defined and not yet handed off into a feature dossier" от "defined but already intaken into a live feature cycle".

## Почему это важно

`unified-dossier-engineer` специально разделяет backlog truth и delivery workflow. Это правильно, но отсутствие явного post-intake state ломает операторские решения на самой ранней границе workflow.

Риски:

- next-intake selection может повторно выбрать уже intaken item;
- операторы и агенты начинают сверять truth через dossier/index/prose вместо backlog read model;
- `queue` перестает быть достаточно ясным readiness surface для intake decisions;
- feature dossier creation становится видимым только в docs/ssot, но не в backlog lifecycle;
- future drift detection вынуждена реконструировать "уже intaken" через dossier mapping вместо простого backlog state;
- объяснение текущего контракта выглядит как оправдание workflow gap.

Нужен machine-readable state, который говорит: backlog item уже выбран и передан в feature workflow, но еще не прошел `spec-compact`.

- `dossier-step-close` has no target to enforce for `feature-intake`.

- Stage controllers currently do not mutate backlog truth directly; backlog truth mutation is owned by `patch-item` / `refresh + patch`.

## Требуемое исправление

Добавить first-class post-intake backlog state: `intaken`.

Целевой lifecycle order:

`defined < intaken < specified < planned < implemented`

Observable target:

- после truthful close of `feature-intake`, selected backlog item is no longer plain `defined`;
- backlog truth records that the item has been handed off into a feature dossier;
- `queue` and `status` can distinguish not-yet-intaken `defined` work from already-intaken work whose next action is dossier-local `spec-compact`;
- `next-step` remains dossier-local and continues to return `spec-compact`.

Mutation boundary is normative:

- `feature-intake` sets `backlog_lifecycle_target: intaken` and exposes unresolved backlog actualization while the selected item remains `defined`;
- backlog truth mutation remains owned by `patch-item` or `refresh + patch`;
- the agent applies a canonical backlog patch that moves the selected item from `defined` to `intaken`;
- `dossier-step-close --step feature-intake` validates current backlog truth and fails closed while the item remains below `intaken`;
- successful close records the accepted patch artifact through the existing `dossier-step-close --backlog-actualization-artifact <path>` evidence path.

The `feature-intake` stage controller must not mutate backlog truth directly. If future planning wants command-owned mutation, that must be a separate architecture issue because it would change the active stage-controller boundary.

## Что должно измениться

### 1. Backlog lifecycle model

- Add `intaken` as a valid backlog `delivery_state`.
- Update lifecycle ordering and comparators.
- Update packet/patch validation to accept `intaken`.
- Update read models (`status`, `items`, `queue`, `report`, `search`) to handle `intaken`.
- Update queue semantics so `intaken` work is not presented as a fresh intake candidate.

### 2. Feature intake lifecycle reconciliation

- Add a `feature-intake -> intaken` lifecycle target.
- Ensure stage state records the target/current/reconciled fields for `feature-intake`.
- Ensure `dossier-step-close` cannot truthfully close `feature-intake` while selected item remains plain `defined`.

### 3. Backlog truth mutation path

- Preserve explicit backlog truth ownership.
- Require a canonical `patch-item` artifact for `defined -> intaken`.
- Record accepted actualization evidence through `dossier-step-close --backlog-actualization-artifact <path>`, matching the existing lifecycle reconciliation pattern.
- Preserve help/runtime/tests parity for the `--backlog-actualization-artifact` path if any feature-intake-specific validation is added or changed.
- Do not add command-owned backlog mutation to `feature-intake` in this issue.

### 4. Read-model and operator guidance

- `queue` should clearly exclude or separately classify `intaken` items.
- `status` should count `intaken` separately from `defined`, for example with `intaken_count`.
- `next-step` for the mapped dossier remains the canonical source for the next delivery workflow stage.
- Operator-facing text should make it clear that `intaken` means "dossier handoff exists; proceed via dossier-local `spec-compact`", not "requirements are specified".

### 5. Docs / runtime / test parity

- Update active references and generated `SKILL.md` only through the source-bundle workflow.
- Update runtime help/examples if command behavior changes.
- Add tests covering the new state, lifecycle ordering, closure behavior, and queue/status read models.

## Acceptance Criteria

- Backlog `delivery_state` model has an explicit `intaken` state.
- Lifecycle ordering treats `intaken` as strictly after `defined` and before `specified`.
- A closed `feature-intake` for a selected backlog item cannot leave that item indistinguishable from not-yet-intaken `defined` work.
- `dossier-step-close` for `feature-intake` enforces current backlog truth at `intaken`.
- `feature-intake` does not mutate backlog truth directly; actualization uses canonical `patch-item` or `refresh + patch`.
- Accepted actualization evidence is recorded through `dossier-step-close --backlog-actualization-artifact <path>`.
- `queue` no longer silently offers an already-intaken backlog item as ordinary intake-ready work.
- `status` exposes `intaken` counts/readiness clearly enough for next-intake decisions, including a deterministic field such as `intaken_count`.
- `items` shows enough state to distinguish `defined` from `intaken`.
- `spec-compact` closure still requires at least `specified`; `intaken` is not treated as specified.
- Existing lifecycle reconciliation for `spec-compact`, `plan-slice`, and `implementation` continues to work unchanged except for the new lower state in the ordering.
- Dependency readiness and rank ordering handle `intaken` explicitly instead of relying on a stale hard-coded rank set.
- Docs explain that `intaken` is backlog handoff state, not dossier maturity, not requirements specification, and not implementation readiness.
- Tests cover:
  - successful intake path requiring actualized `intaken` before close;
  - queue exclusion or classification for `intaken`;
  - `status` output with `intaken_count` or equivalent deterministic field;
  - dependency readiness/rank ordering involving `intaken`;
  - `spec-compact` cannot close with only `intaken`;
  - no regression for `specified -> planned -> implemented`;
  - report/status/search/items behavior for `intaken`.

## Обязательные ограничения для planning и implementation

- Не сливать backlog lifecycle и dossier `status` в один enum.
- Не считать `intaken` эквивалентом `specified`.
- Не позволять `feature-intake` silently skip durable backlog evidence.
- Не позволять `feature-intake` directly mutate backlog truth.
- Не делать broad queue redesign; менять только поведение, необходимое для `intaken`.
- Не auto-close source-review, dependency attention или downstream readiness из-за `intaken`.
- Не ломать текущие stage names, command names, artifact families, review policy или closure gates.
- Не добавлять prose-only command semantics без runtime/help/tests parity.
- Не ссылаться на абсолютные локальные пути.

## Non-Goals

- Не переводить существующие historical items задним числом без отдельной migration decision.
- Не реализовывать feature-intake/spec/plan/implementation в рамках этого issue.
- Не менять meaning `specified`, `planned`, `implemented`.
- Не удалять requirement for external review and verification artifacts.
- Не решать все возможные queue-ranking вопросы beyond already-intaken visibility.
- Не менять one feature = one backlog item.
