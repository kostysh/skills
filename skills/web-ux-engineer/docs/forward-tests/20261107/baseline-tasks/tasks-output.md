## A. Список → изменение контакта → продолжение обработки

Показанный код может потерять введённый контакт и контекст списка, а после timeout сообщает об отказе, которого могло не быть.

Скил: `react-spa-engineer`. Режим: read-only анализ интегрированного SPA-сценария. Ограниченный анализ выполнен (`completed`); работающий исправленный сценарий не заявляется. Основание — только фрагмент A и заданные условия API. Конфигурация маршрутов и реализация `api.patch` не предоставлены.

Существенные проблемы:

1. **Восстановление списка не определено.** `query` и `page` существуют только в `List`, а оба возврата ведут на голый `/records`. При размонтировании списка его состояние сбросится. По этому фрагменту нельзя доказать, что маршрутизатор сохраняет компонент; передачи контекста возврата здесь нет. Это ставит под угрозу принятое требование продолжить обработку того же списка.
2. **Любая ошибка стирает ввод.** `catch` возвращает `draft` к `record.contact`. Пользователь теряет исправление и не видит серверные ошибки конкретного поля. Нужно сохранять ввод, сопоставлять известные field errors полю `contact`, а остальные ошибки показывать на уровне формы.
3. **Timeout ошибочно объявляется отказом.** Текст `Not saved. Try again.` утверждает, что запись не произошла. По условию сервер мог принять запрос. Повтор PATCH без принятого контракта идемпотентности может повторить эффект операции.
4. **Ожидающая операция не связана с текущим экраном.** Во время PATCH доступны редактирование и Cancel. После ухода старый callback всё ещё может показать toast и выполнить `navigate('/records')`. Новые изменения в поле после начала запроса также могут исчезнуть при успешном возврате. Если `record` изменится без remount, начальный `useState(record.contact)` сам по себе не сменит черновик на данные другой записи. Это условные риски жизненного цикла, которые нужно проверить на реальном устройстве маршрутов.
5. **Обновление отображаемых данных не показано.** После PATCH код сразу сообщает `Saved` и уходит. Нет явного обновления/инвалидации detail и списка. Реализация `api.patch` могла делать это внутри, но фрагмент не позволяет подтвердить такой контракт.

Минимальное изменение контракта:

- Хранить фильтр и страницу в одном владельце, который переживает detail и возврат. Для этого сценария подходит URL списка и сохранённый адрес возврата. Восстанавливать оба параметра после Save и Cancel; не создавать ещё одну изменяемую копию параметров в store.
- Зафиксировать отправляемый снимок контакта отдельно от последующих правок. Определить поведение формы и Cancel во время запроса: закрытие экрана не должно означать отмену записи на сервере. Статус операции должен оставаться доступным в устойчивом владельце, а callback старого экрана не должен менять новый маршрут.
- Разделить состояния: отправка; подтверждённая ошибка поля/отказ; неизвестный исход; проверка результата; ошибка проверки; подтверждённый результат. При восстанавливаемых ошибках сохранять ввод и показывать доступную ошибку рядом с полем либо формой.
- Не считать старый Query cache или любой успешный GET подтверждением записи. После timeout показывать «Результат изменения пока не подтверждён» и давать действие проверки. Повторять PATCH можно лишь по согласованному контракту идемпотентности/статуса операции.
- После принятого условия успеха обновить либо инвалидировать затронутые чтения и вернуть пользователя к сохранённому списку.

Краткая матрица времени жизни для этого предложения:

| Значение | Идентичность и владелец | Уход/remount | Результат и поздний ответ |
| --- | --- | --- | --- |
| Фильтр и страница | URL конкретного списка | Сохраняются для возврата | Ответ записи не меняет параметры списка |
| Черновик | Запись + экземпляр формы; состояние формы | Не сбрасывается из-за ошибки; явная политика при смене записи | Ответ старой записи не переписывает новый черновик |
| Попытка PATCH и статус UI | Запись + маршрут + attempt ID + существующий access scope, если он есть; устойчивый feature-owner использует Query для IO | Переживают закрытие дочернего редактора; на другом экране скрыты/показаны только под исходной идентичностью | Старые callbacks не перенаправляют новый экран и не закрывают новую попытку |
| Проверка исхода | Та же операция + отдельный verification sequence; тот же feature-owner и Query-чтение | Переживает remount редактора | Ошибка чтения видима; stale-данные не закрывают проверку; устаревшие ответы и таймеры ограждены по идентичности |

**Недостающий контракт:** владелец API должен определить, как чтение подтверждает именно эту запись. Например, сервер может дать версию фиксации и чтение с гарантией не ниже этой версии либо статус операции по её идентификатору. Это варианты для согласования, а не свойства существующего API. Без гарантии свежести один повторный GET не позволяет честно завершить неизвестный исход.

Проверки для исправления: фильтр и страница сохраняются после Save/Cancel и навигации назад; field error сохраняет ввод и относится к нужному полю; timeout после фактической записи не показывает ложный отказ и не запускает повтор PATCH; старый cache/устаревший GET не показывают успех; сбой чтения оставляет явное восстановимое состояние; уход, смена записи и поздний ответ не вызывают чужой toast, redirect или перезапись черновика. Для полного пользовательского сценария нужны наблюдения в браузере, а для гарантии чтения и идемпотентности — проверка принятого API-контракта в разрешённой тестовой среде.

## F. PATCH из портала detail: состояние и подтверждение чтением

Нужен контракт, в котором попытка PATCH и проверка её результата переживают портал, но не переносят данные и статус в другую запись или tenant.

Скил: явно запрошенный `react-spa-engineer`. Режим: read-only проектирование технического контракта. Запрошенный перечень требований и проверок подготовлен (`completed`); совместимость с конкретной реализацией не проверялась. Версии библиотек, исходники этого портала и гарантии API не предоставлены.

**Идентичность.** Для операции фиксируются исходный маршрут/его generation, access scope (tenant, user и версия сессии, если они влияют на доступ), entity ID, уникальный attempt ID. Проверка результата получает отдельный verification sequence. Повтор чтения не создаёт новый PATCH. Каждое завершение, обновление UI, cache write, toast и redirect должны проверять соответствующую идентичность, а не брать текущий tenant или текущую запись из изменившегося замыкания.

**Владелец.** Черновик формы остаётся локальным. UI-фазы операции и проверки живут в узком feature-owner выше портала и тех маршрутов, которые операция должна пережить. Он использует TanStack Query для мутаций/чтений и `shared/api` для транспорта. Существующий подходящий владелец предпочтительнее нового глобального store. При смене entity состояние старой операции остаётся связано со старой entity; при потере access scope оно скрывается/очищается и ограждается от поздних эффектов.

| Состояние | Идентичность и writable owner | Переживает портал | Навигация и context loss | Подтверждение/поздние ответы |
| --- | --- | --- | --- | --- |
| Редактируемый черновик | Entity + экземпляр формы; форма | По принятой политике черновиков; отправленный снимок от него независим | Смена entity не переиспользует чужой черновик | Ответ не затирает более новые правки |
| Снимок команды и PATCH | Исходные scope/entity/attempt; Query mutation через `shared/api` | Да | Операция остаётся под исходным ключом; закрытие портала не обещает серверный rollback | Повторная отправка только по принятой идемпотентности; abort не доказывает отсутствие записи |
| Фаза и прогресс UI | Route/scope/entity/attempt; устойчивый feature-owner, использующий состояние Query | Да | На новом маршруте/записи старый статус не выдаётся за текущий | Старый callback не завершает новую попытку, не показывает чужой toast и не перенаправляет пользователя |
| PATCH receipt | Scope/entity/attempt; результат Query mutation | Да | Не преобразуется в данные другого scope | Receipt хранится как receipt, не подставляется как актуальная проекция entity |
| Чтение для проверки | Scope/entity/attempt + verification sequence; Query read, оркестрация у feature-owner | Да | При смене access scope отменить/оградить чтение и его эффекты | Требуется чтение с принятой гарантией свежести; устаревший результат не завершает проверку |
| Ошибка проверки/успех | Та же идентичность; фаза feature-owner | Да | UI доступен только соответствующему контексту | Ошибка остаётся видимой и восстановимой; поздний предыдущий sequence не меняет терминальный результат |
| Retry timers/listeners | Исходный scope/attempt/sequence; создавший их owner | Пока нужна соответствующая проверка | Очистка на завершении/context loss | После очистки они не создают запросы, записи cache или уведомления |

Фазы UI: `idle → submitting → verifying → verified`. Отдельные ветви — подтверждённый отказ/field errors, `outcome-unknown` после неоднозначного transport failure и `verification-failed` после ошибки чтения. При `verifying` пользователь видит, что запрос принят, а результат ещё проверяется. При `verification-failed` доступно действие повторить **проверку**, и старый cache не превращает её в успех. Повторное чтение имеет ограниченную политику retry; оно не должно бесконечно маскировать ошибку.

**Свежесть — отдельный обязательный API-контракт.** Сам факт сетевого GET, `isSuccess`, `invalidateQueries` или `ensureQueryData` не доказывает чтение после записи. Нужно выбрать поддерживаемый сервером механизм: например, receipt с commit version и чтение не ниже неё либо иной гарантированный read-after-write/status API. До его согласования нельзя утверждать, что автоматическое подтверждение реализуемо существующим API. Старую проекцию можно временно показывать как старую, но она не доказывает исход PATCH. Результат, начатый до записи или относящийся к старому verification sequence, не должен перезаписать уже подтверждённые данные.

Query keys включают scope, entity и параметры представления. После подтверждения согласованно обновляются/инвалидируются detail и затронутые списки. При смене tenant/user отменяются либо ограждаются старые запросы, очищается старое scoped состояние, и поздние ответы не возвращают его в новый контекст. Это правило клиентской изоляции; серверная авторизация остаётся обязанностью API. Durable browser storage и сохранение через reload здесь не требуются и не вводятся.

Проверки будущей реализации:

1. PATCH показывает прогресс; receipt переводит в проверку, а не сразу в success. Только чтение, удовлетворяющее принятому критерию свежести, подтверждает результат.
2. Старый cache, устаревший сетевой ответ и ошибка чтения не дают ложного успеха. Retry повторяет чтение и сохраняет восстановимое состояние; данные не откатываются из-за ответа старого sequence.
3. Отдельно проверить field errors, неоднозначный timeout, повторное нажатие и ответы в обратном порядке. Ввод и снимок команды не смешиваются; новый attempt не завершается старым callback.
4. **Один комбинированный сценарий:** заполнить Query cache tenant A старой записью; начать PATCH; закрыть и снова открыть портал во время операции/проверки; убедиться, что прогресс не пропал; завершить PATCH и заставить подтверждающее чтение завершиться ошибкой; увидеть восстановимое состояние; сменить маршрут/запись, затем tenant на B при ещё управляемом retry timer или позднем ответе A; завершить все отложенные ответы и таймеры. У B не появляется ни данных, ни статуса, ни уведомления/redirect от A. Старые timers/listeners очищены, отложенные promise завершены до teardown.
5. Наблюдать этот путь в браузере с управляемыми синтетическими ответами. Такие проверки доказывают клиентский контракт. Гарантии свежести, идемпотентности и авторизации требуют отдельного подтверждения принятого API в разрешённой тестовой среде.

Здесь эти проверки не запускались; реализация и доступ к backend не запрошены. Если механизм свежести отсутствует, блокируется только зависящее от него подтверждение. Основание — [Persistence Architecture](/tmp/web-ux-20261107-xaye7ceb/baseline-active/react-spa-engineer/references/persistence-architecture.md): “If a required backend freshness, idempotency, authorization, or conflict policy is missing or disputed, return `blocked`; do not encode a guess in browser state.”

## H. Визуальная стратегия того же модуля

Улучшить только композицию overview недостаточно для передачи готовой стратегии разработчику.

Скил: явно запрошенный `frontend-design`. Результат: `strategy-only`; готовность стратегии к реализации — `blocked` на неполном покрытии обязательных представлений и недостающих контрактах их использования. Предварительная визуальная направленность определена.

Иерархия источников: принятый стандарт и применимые peer views определяют состав сценария; библиотека определяет повторно используемые компоненты и tokens; overview показывает лишь текущую реализацию. Наличие библиотечных компонентов не доказывает, что они интегрированы в модуль.

| Возможность | Требование/peer | Библиотека | Модуль | План стратегии |
| --- | --- | --- | --- | --- |
| Search | Обязателен/есть | Есть | Нет | Использовать существующий компонент и принятый контракт поиска |
| Detail | Обязателен/есть | Есть | Нет | Использовать существующее представление и явную связь с выбранной записью |
| History | Обязательна/есть | Есть | Нет | Использовать существующий компонент и определить его место в принятом сценарии |

Предварительная стратегия: `product/app`, `system-constrained`, основной визуальный подход — `data-led`. Рабочая поверхность должна помогать искать, сравнивать и открывать записи, затем читать детали и историю. Иерархия строится на принятых таблице, типографике, отступах и навигационных паттернах библиотеки; акценты показывают действие и состояние. Декоративные hero и новая система карточек для этой цели не нужны. Материальные loading/empty/error/permission-состояния каждого представления и переходы между ними должны быть связаны с их действующими владельцами, а не придуманы при оформлении.

**Зависимость результата:** стратегия готова только после описания полного search/detail/history-сценария, его состояний, компонентов, переходов и responsive-поведения. Факт существования компонентов известен из условия; их реальные API, варианты, tokens и примеры использования не предоставлены. Поэтому точное сопоставление и реализационная готовность пока не подтверждены.

**Следующий шаг без реализации:** изучить актуальные компоненты и применимые peer views; составить компактную карту «сценарий → состояние → компонент/владелец», разрешить реальные пробелы, затем закончить визуальную стратегию всего модуля. В ней зафиксировать переходы search → detail → history и возврат, доступность действий, содержимое/ошибки, длинные данные и целевые размеры экрана. После этого передать разработчику стратегию с отдельным планом будущей браузерной проверки. Самой стратегии не требуется выдавать себя за уже работающий модуль.

Причина ограничения — [Strategy To Implementation](/tmp/web-ux-20261107-xaye7ceb/baseline-active/frontend-design/references/strategy-to-implementation.md): “When accepted sources or relevant peer views establish one of them, an unrecorded omission blocks visual polish and implementation-ready status.” Здесь обязательные возможности перечислены, но стратегия их состояний и интеграции ещё не определена. Реализация, макет и runtime-доказательства не создавались.
