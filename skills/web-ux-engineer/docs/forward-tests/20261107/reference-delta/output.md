# Разбор двух запросов

Режим: read-only. Выполнено определение ведущего и поддержанного вклада явно выбранного `react-spa-engineer`. Аудиты приложения не выполнены: исходники, доступный интерфейс, принятые требования и наблюдения не предоставлены. Выводов о качестве приложения или оценок скила здесь нет.

## Запрос 1 — UX-аудит сценария работы с заявкой

**Ведущий: `web-ux-engineer`.** Запрошенный результат — оценка понятности шагов, сохранения рабочего контекста и восстановления после сбоя. В `react-spa-engineer` разделы Overview и Interop priority прямо относят сценарный UX-аудит, continuity и recovery к этому владельцу. Это основание для выбора ведущего; содержимое соседнего скила не исследовано.

**Вклад `react-spa-engineer` сохраняется.** Он может дать технический разбор того, поддерживает ли SPA принятый сценарий:

- Проследить владение фильтрами и навигационным контекстом между списком, редактированием и возвратом: React Router/URL, локальное состояние и состояние данных. Какие именно параметры и позицию должен сохранять интерфейс, определяет принятый UX-контракт.
- Проследить форму контакта, клиентскую проверку, ошибки сервера, состояние сохранения и обновление данных через React Hook Form/Zod, `shared/api` и TanStack Query.
- Проверить, где живут попытка сохранения и проверка её результата; не теряются ли они при закрытии формы или смене маршрута и не переходят ли в другой контекст доступа. Ошибку авторитетного перечитывания нельзя скрывать за сообщением об успешном завершении всего сценария.
- Оценить поддерживающую механику: доступные поля и сообщения, клавиатурное восстановление после ошибки, фокус согласно принятой политике навигации, сохранение уже показанного содержимого при фоновом обновлении.

Это технический вклад в UX-аудит, а не самостоятельное решение о том, какие шаги понятны сотруднику и какой возврат удобен. Без материалов нельзя установить дефект или подтвердить поведение. Для последующего разбора нужны принятый сценарий, соответствующие участки приложения и наблюдаемое выполнение пути «отфильтрованный список → контакт → возврат», включая сбой и восстановление. Интерактивное утверждение потребует наблюдения в браузере; одних типов, снимков или моков недостаточно.

## Запрос 4 — аудит реализации по Web Interface Guidelines

**Ведущий: `web-ui-reviewer`.** Запрошен именно аудит реализации по правилам интерфейса: семантика, имена, клавиатура, фокус и адаптивные состояния. Interop priority закрепляет итог аудита за `web-ui-reviewer`; начало `references/accessibility.md` подтверждает этот маршрут. Это не сценарный UX-аудит.

**Вклад `react-spa-engineer` сохраняется в пределах прочитанного руководства.** При наличии приложения он может собрать технические наблюдения о следующих механизмах:

- Нативная семантика контролов, видимые связанные метки, доступные имена, описания, ошибки и состояния.
- Клавиатурный путь, видимый фокус, порядок переходов; для составных контролов — полнота принятой модели взаимодействия, а не наличие отдельных ARIA-атрибутов.
- Управление фокусом диалогов, доступность фона, закрытие, возврат фокуса и очистка состояния после закрытия.
- Фокус и сообщения при навигации, загрузке, фоновом обновлении, ошибке и пустом результате; наблюдаемое поведение при zoom/reflow и reduced motion.

Эти проверки дают локальные факты и ограничения для ведущего. Они не заменяют полный аудит по Web Interface Guidelines: сами Guidelines и методика соседнего скила не прочитаны. Доступность для экранного диктора и полная модель взаимодействия не доказываются автоматическими правилами, ролями или снимками. Нужно отдельно указать фактически проверенные браузеры, сценарии и покрытие вспомогательных технологий.

Запрос разрешает только аудит. Исправления, интеграция принятых корректировок и переработка адаптивной композиции сейчас не разрешены. Если позднее потребуется изменение переиспользуемого составного контрола, конкретный вопрос его корректности можно адресовать `react-components-engineer`; для текущего определения ведущего его загрузка не нужна.
