## A. Сценарий «список → контакт → тот же список»

**Использованный скил: `web-ux-engineer`. Статус: `findings`.**

В коде есть проблемы, которые мешают оператору сохранить исправление и продолжить работу с тем же списком.

| Место и условие | Основание и последствие | Изменение | Проверка |
| --- | --- | --- | --- |

Оператор должен вводить его заново; при field errors он не видит, какое значение исправить. | Сохранить введённое значение. Связать field errors с полем контакта; дать понятное сообщение и перевод фокуса к ошибке при отправке. | Вернуть ошибку поля и отдельно сетевую ошибку: введённый контакт остаётся, сообщение поля видно, исправление можно отправить повторно в рамках разрешённого API поведения. |

Закрытие формы не отменяет серверную операцию. | Разделить отказ от ещё не отправленных правок и закрытие уже отправленной операции. | Поле контакта при `busy` | Поле остаётся редактируемым. PATCH уже получил прежний снимок `draft`, но оператор может изменить текст, после чего success закроет редактор. Для разрешения неизвестного исхода нужен ответ владельца API: какое свидетельство связывает результат с конкретной попыткой и подтверждает его актуальность. Само наличие GET недостаточно. Чтение без гарантии свежести может вернуть старый контакт и после успешного PATCH. Нельзя объявлять по такому ответу ни отказ, ни безопасный повтор. Возможные механизмы — подтверждённая версия записи либо статус операции; это варианты для согласования, а не существующие гарантии.

Успех следует показывать по однозначному подтверждению принятого API-контракта. Актуальность данных в возвращённом списке также должна опираться на согласованный механизм обновления. По приведённому фрагменту нельзя утверждать, что он уже есть или отсутствует во всём приложении.

Предел: выводы основаны на коде и заданных условиях. Реальные переходы, фокус, доступность, свежесть чтения и сохранение на сервере не проверены. Изменений кода нет.

## F. PATCH из detail-портала: состояние и подтверждение

**Использованный скил: `react-spa-engineer`. Режим: проектирование контракта, read-only. Статус: `partial` для полного контракта внедрения: общий контракт определён, но критерий авторитетной свежести должен подтвердить владелец API.**

Статус отправки и последующей проверки должен переживать закрытие портала. PATCH receipt означает результат транспортного этапа по API-контракту; он не становится актуальной проекцией записи. Старый Query cache также не подтверждает результат.

Идентичность операции: исходный маршрут/контекст навигации, tenant и пользователь при пользовательской области данных, `entityId`, уникальный `attemptId`, номер последовательности проверки `verificationSequence` и поколение контекста доступа. Попытка PATCH и повторные чтения результата имеют разные идентификаторы. Ответ применяется только к совпадающей актуальной последовательности и разрешённому контексту.

| Состояние | Единственный владелец | Что переживает портал | Смена маршрута, записи или tenant | Подтверждение и поздний ответ |
| --- | --- | --- | --- | --- |
| Редактируемый ввод | Локальное состояние формы | Сохранение черновика определяется принятым поведением формы; новый durable storage не нужен по этому заданию | Не переносится в другую запись или tenant | Отправляемый payload фиксируется отдельно от последующих правок |
| Снимок payload и выполняющийся PATCH | Мутация TanStack Query через `shared/api`; UI наблюдает её из устойчивого владельца feature | Попытка и необходимый статус продолжаются при закрытии/повторном открытии | При другой записи статус остаётся связан с исходной; при утрате доступа UI скрывается/сбрасывается, работа отменяется где возможно и обязательно отсекается по идентичности | Закрытие портала и abort транспорта не доказывают отмену серверной операции |
| Pending и recoverable failure | Производное представление состояния операции у ближайшего владельца, который переживает нужные remount и navigation | Статус доступен вне портала и восстанавливается при возвращении | Не показывается как статус новой записи; старый callback не навигирует новый экран | Никакой второй независимой копии сущности/результата в UI store |
| Полученный receipt | Результат той же мутации | Да, пока нужен для проверки | Сохраняет tenant/entity/attempt; не подменяет новую операцию | Не писать receipt в detail cache как полноценную запись |
| Авторитетное перечитывание | Query-адаптер проверки; один координатор последовательности над одноразовым порталом | Да | Новая последовательность или потеря доступа делает старую неактуальной; ответы и таймеры отсеиваются | Успех только после чтения, удовлетворяющего согласованному критерию свежести и связи с попыткой |
| Ошибка перечитывания | Та же последовательность проверки и её устойчивое UI-представление | Да; ошибка не исчезает при remount | Не протекает в другой tenant/запись | Видимое состояние «Запрос принят, результат ещё не подтверждён» и действие повторить проверку; старый кеш не превращает его в success |
| Итоговое подтверждение | Та же операция, после принятого результата проверки | Срок отображения определяется сценарием, а не жизнью портала | Публикуется только в своём действующем контексте | Старый ответ не перезаписывает более новую попытку или проверку |

Базовые переходы: `idle → submitting → verifying → confirmed`. Отдельные ветки: field errors/подтверждённый отказ, `outcome-unknown` после неоднозначного timeout, `verification-failed` после неудачного чтения. HTTP-успех PATCH не переводит напрямую в `confirmed`. Повтор чтения не повторяет PATCH. Повтор PATCH требует отдельного разрешающего API-контракта, в том числе правил идемпотентности.

TanStack Query владеет мутацией, чтением, кешем и invalidation; `shared/api` — транспортом. React Router владеет навигацией. Для представления статуса достаточно существующего Query-состояния и ближайшего устойчивого feature/layout-владельца; глобальный Zustand store не нужен автоматически. Если статусы обязаны пережить смену маршрута, владелец должен находиться выше этого маршрута. Сущность не следует дублировать в Context/Zustand. Переживание reload и Dexie не входят в заданный объём.

Ключи detail/list включают контекст доступа и все параметры представления. После мутации затронутые чтения обновляются или инвалидируются, но факт invalidation, успешный возврат кеша или любое произвольное GET 200 не доказывают свежесть. При смене tenant/user нужно отменить либо отсечь старую работу, удалить данные прежнего доступа и сбросить связанное UI-состояние; поздние ответы и таймеры не должны восстановить его после очистки. Клиентская очистка не заменяет серверную авторизацию.

Недостающий ответ API: какое чтение считается актуальным относительно receipt/попытки. Например, сравнимая версия могла бы служить границей, **если это гарантирует API**. Такой гарантии в задании нет. До её согласования нельзя завершить выбор проверки или обещать достоверное `confirmed`; контракт клиента должен сохранять неопределённость.

Нужны следующие проверки, пока не выполненные:

1. Проверить переходы состояний и идентичности: receipt не даёт terminal success; новый attempt и новая verification sequence отклоняют запоздалые результаты предыдущих.
2. Проверить закрытие/открытие портала во время PATCH и во время GET: прогресс и recoverable failure сохраняются, запрос не дублируется.
3. Проверить смену записи и маршрута: старый результат не меняет текущую запись, не присваивает ей старый статус и не вызывает неожиданную навигацию.
4. Выполнить **один комбинированный сценарий**: заполнить кеш старыми данными tenant A → начать PATCH → закрыть/открыть портал → получить receipt → заставить авторитетное чтение завершиться ошибкой → увидеть явный восстанавливаемый неуспех → запустить повтор проверки с задержанным ответом/таймером → перейти в tenant B → завершить все отложенные ответы и таймеры. В B нет данных или статуса A; очистка не отменена поздней записью; все таймеры, подписки и deferred promises завершены/очищены.
5. На согласованном API-контракте проверить положительный путь и неизвестный исход: устаревшее чтение не завершает проверку, подходящее авторитетное чтение завершает; timeout не превращается в утверждение об отказе или безопасном повторе.

Локальные unit/integration-проверки и браузер с синтетическими ответами доказывают только клиентский контракт. Реальные freshness, idempotency и authorization потребуют отдельной разрешённой интеграционной среды. В этой задаче не запускались ни backend, ни реализация, ни проверки в браузере. Следующий владелец — API-владелец для критерия подтверждения; затем разработчик SPA сможет реализовать и проверить указанный контракт.
