## Issue ID

## Title

Отсутствует переносимая доказательная методика ретроанализа

## Skill

`retrospective-analysis`, `skills/retrospective-analysis`

## Context

Полный ретроанализ `SL-02` в проекте Aequitas ADR оказался полезным, но для его
проведения оператору потребовалось вручную задать большой набор требований:
исчерпывающий разбор сессии, всех `FAIL`-аудитов, причинности, дедупликации,
истории прежних исправлений, итогового remediation plan и безопасного создания
задач. В активном наборе skills нет владельца этого процесса.

## Problem

Без переносимой методики следующий агент может:

- выборочно исследовать источники или пропустить часть `FAIL`-аудитов;
- принять симптомы за первопричины либо ошибочно объединить разные проблемы;
- считать commit subject доказательством устранения исторической проблемы;
- не отличить устранённый occurrence от отсутствующего системного prevention;
- подготовить неполный или неисполняемый план;
- создать дублирующие задачи до стабилизации и одобрения плана;
- применить тяжёлый full-процесс к одной локальной ошибке.

## Evidence

- `Aequitas-ADR/app`:

## Impact

Ретроанализ остаётся зависимым от большого одноразового prompt, а его полнота,
воспроизводимость, proportionality и безопасный handoff в delivery backlog не
защищены общей методикой.

## Scope

В scope:

- новый documentation-only skill с режимами `targeted` и `full evidentiary`;
- evidence/causality/deduplication contract;
- проверка статуса исторических исправлений по первичным evidence;
- Markdown/JSON output contract;
- independently assignable remediation plan;
- operator approval и idempotent task-routing contract;
- blind forward-tests и независимый skill review.

Не входят:

- CLI, runtime, dependency или generic evidence registry;
- автоматическое принятие выводов;
- автоматическое создание задач без operator approval;
- проектно-специфичные paths, branch names или GitHub Project fields;
- восстановление удалённого `retrospective-phase-analysis`.

## Proposed Resolution

Создать компактный source-compiled `retrospective-analysis`: recurring decisions
и stop rules оставить в `SKILL.md`, подробные контракты вынести в три явно
достижимые active references. Использовать существующие инструменты проекта
только как optional evidence aids. Формальный `PASS` поручить независимому
`skill-reviewer`.

## Alternatives Considered

- Восстановить `retrospective-phase-analysis`: отклонено из-за чрезмерного CLI и
  process surface, ранее сознательно удалённого из active skills.
- Оставить правила только в одном проекте: отклонено, потому что причинность,
  дедупликация и проверка истории переносимы.
- Создать обязательный analyzer/registry: отклонено; автоматизация не понимает
  семантическую причинность и создаёт новый поддерживаемый workflow.
- Один всегда полный режим: отклонено как несоразмерный для локальных incidents.

## Destructive Side Effects

- Слишком механический workflow может заменить анализ checklist bureaucracy.
- Слишком широкий trigger может навязать full-retro локальным задачам.
- Task-routing без hard stop может повторить массовое создание дубликатов.
- Project-specific assumptions в portable skill нарушат переносимость.

Mitigations: два режима, complexity gate, explicit stop rules, direct readback,
blind targeted scenario и portability checks.
