## Изменения и приёмка

1. Получить независимый вердикт по этому плану до записи текста кандидата. Поддерживать скил через компактный `skill.yaml` и штатный компилятор. Добавить правила сопровождения, ссылку в каталог и журнал. В поставку входит только `SKILL.md`. Скил не требует отдельных инструментов, скриптов, шаблонов, обязательных ролей или проектных файлов. Исключить названия платформы, частных проектов и ссылки на методику.
2. Описать выбор между прямым выполнением и делегированием, полномочия, одного владельца задания, условия параллельной работы, передачу минимального контекста и проверяемого результата. При изменении входа обновить зависимые задания. Принять общий результат по исходному запросу, соблюдая действующие остановки и независимость там, где она требуется. Проверить текст как автор до генерации, затем выполнить lint, regenerate, check, отдельную компиляцию, проверку метаданных и чтение архива штатного упаковщика.
3. Провести испытания ниже. Зафиксировать ответы, наблюдаемые действия и пределы проверки. Передать неизменный пакет и свидетельства независимому skill-reviewer. При существенной находке сохранить первый результат, исправить источник, проверить исходный сбой и смежную границу, повторить аудит до PASS.
4. Выполнить штатные проверки, проверить состав изменений, создать коммит и PR в master. Проверить опубликованный head и состояние PR. Для отмены достаточно отозвать ветку до слияния. Решение о слиянии и выпуске остаётся оператору.

### Задания и критерии до написания кандидата

Цель испытаний — оценить решения кандидата. Измерение выигрыша над работой без скила в запрос не входит, сравнительных пар нет. Исполнителям доступны только их входы и, для исполнения, установленный файл. Критерии видит оценщик. Изоляция контекста не означает изоляцию общей файловой системы.

- **Выбор из каталога.** По описаниям нового скила и соседних delivery-planner, documentation и code-reviewer выбрать владельца для трёх запросов. Координация уже начатой сверки нескольких исполнителей — orchestrator. Только план поставки — delivery-planner. Простая редактура абзаца — прямое выполнение или documentation. Тела скилов до выбора закрыты.
- **Готовые независимые задания.** Составить расписание из двух утверждённых выписок для организатора. Север: 09:00, зал A, 12 мест. Юг: 10:30, зал B, 8 мест. Оператор поручил двум помощникам независимо прочитать по одной выписке, разрешил делегирование и просит итоговый список с суммой. Проверить реальные поручения, их границы, результаты и общий ответ с обоими залами и 20 местами. Локальная ошибка одного исполнителя требует сверки с источником.
- **Изменение общей основы.** При продолжении задания старая ведомость r1 (12 + 8) заменена утверждённой r2 (9 + 8). Черновик программы и старый итог 20 подготовлены по r1, независимый текст об адресе уже сверен. Только координатор вправе править итоговую сводку. Организатор требует отдельной проверки вместимости перед рассылкой, в текущем сеансе привлекать проверяющего нельзя. Оценить ответ на предоставленные события: сохранить адрес, вернуть затронутую работу к r2, выдать подтверждаемую часть с суммой 17, обозначить отсутствующую независимую проверку и удержать рассылку. Сценарий проверяет решение при возобновлении, а не наблюдение за живой рассылкой.
