# План 20261124-1 — вопросы исполнителей через координатора

## Результат и полномочия

24 ноября оператор сообщил о трёх отдельных сессиях, исполнители в которых задали вопросы ему напрямую. Оператор поручил исправить инструкцию в отдельном ворктри и разрешил слепую проверку. Основание для изменения — его сообщение и действующий пункт выдачи поручения в `orchestrator` 0.1.2. Пункт задаёт результат, права и свидетельства, но не говорит, кому исполнитель направляет вопросы. База — `3f5f3ae5`.

Решение принимает координатор до отправки задания. Он даёт разрешённый способ связи и направляет к себе сообщения исполнителя по задаче. Это действует и для отдельной сессии. Если напрямую связаться нельзя, достаточно общей записи, которую координатор прочитает сам. Координатор отвечает в пределах своих полномочий, передаёт нужный вопрос оператору и возвращает ответ исполнителю. Разрешения на внешние операции остаются у владельца решения. Изменение касается инструкции задания, его не нужно превращать в инфраструктуру связи.

## Изменение и приёмка

1. Независимо проверить этот план. До правки зафиксировать исходную поставку, две задачи, закрытые критерии и назначения. SHA-256 протокола с хешами этих материалов — `a56a942ce6ba8dea9b6998271f41e3abedd4432f73563986dcaa3e8483517347`. Исправить `skill.yaml`, провести авторскую проверку и сгенерировать 0.1.3. Испытать файл из однофайлового архива.
2. Провести два парных сравнения 0.1.3 и 0.1.2 по [правилам слепых испытаний](../../../skill-reviewer/references/forward-testing.md). Четыре запуска получают одну модель и режим, одинаковые данные, инструменты, права и запрос. Каждый запускается без наследования истории, получает только свой пакет и материалы задачи. В первом сценарии сотруднику нужен факт, который может сообщить координатор по штатному каналу субагентов. Во втором сотрудник работает отдельно, прямое сообщение между такими сессиями не разрешено и требуется решение оператора. Для второго есть общая область обмена. Запись вопроса оператору в испытании служит моделью отправки, ответа на неё нет.
3. Проверить текст первого фактического поручения, чтение его исполнителем и то, как прошёл вопрос. В первом случае координатор по коду из запроса находит и возвращает ответ без обращения к оператору. Во втором координатор читает адресованную ему запись, сам готовит вопрос оператору и оставляет зависимое действие в ожидании. Проверка не должна проходить только по словам координатора в итоговом отчёте. Использовать реальных помощников в свежих контекстах и наблюдаемый обмен, без создания пользовательских чатов или обращения к живому оператору. Отдельно указать, что канал между пользовательскими сессиями был представлен условием задачи.
4. Два разных оценщика проверяют одну заранее выбранную работу по одинаковым свидетельствам и рубрике. Первичный оценщик также проверяет остальные работы. Оба фиксируют баллы и основания до раскрытия ключа и другой оценки. При расхождении пара остаётся неопределённой до решения независимого арбитра по тем же материалам. Проверить структуру и побайтовое соответствие пакета, запустить штатные тесты и получить заключение `skill-reviewer` по устойчивому снимку. Записать вердикт, наблюдаемый результат и пределы проверки в журнале. Обновить навигацию.
