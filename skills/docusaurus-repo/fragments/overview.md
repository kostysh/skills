## Interop priority

- This skill owns Docusaurus repository bootstrap, config, routing, plugin and theme selection, search architecture, and deployment constraints.
- `documentation` owns document form, Diataxis decisions, and large-scale content rewrites inside the docs tree.
- `frontend-design` owns custom landing-page visual direction when the site intentionally has a branded homepage beyond the standard docs shell.
- If there is tension, keep Docusaurus architectural constraints from this skill and let companion skills optimize within those constraints.

## Reasonable defaults

- Prefer `pnpm create docusaurus@latest <site> classic --typescript`.
- Prefer the classic preset until there is a concrete reason to hand-assemble plugins.
- Every new Docusaurus repo must include `prettier`, `markdownlint-cli2`, their config files, `AGENTS.md`, and a GitHub Actions docs-quality workflow during bootstrap, not as a later cleanup task.
- Prefer docs-first information architecture over custom React pages.
- Prefer autogenerated sidebars plus explicit `slug` front matter to keep URLs stable.
- Prefer CSS and theme config first, wrapping second, ejecting last.
- Prefer Algolia for public docs, local search for small/private docs, Typesense for self-hosted search.
- Do not add versioning unless the docs really ship against multiple live product versions.

## Deliverables by default

- Required repo files: `.prettierrc.json`, `.prettierignore`, `.markdownlint-cli2.jsonc`, `AGENTS.md`, and `.github/workflows/docs-quality.yml`.
- Required package scripts: `format`, `format:check`, `lint:md`, `lint:md:fix`, and `docs:quality`.
- Required Docusaurus baseline: `docusaurus.config.ts`, `sidebars.ts`, the chosen content roots, and an explicit search decision.
- Deployment baseline: set `url`, `baseUrl`, and `trailingSlash` deliberately when host behavior makes path handling non-trivial.
- If the repo already pins a higher Node version than Docusaurus requires, keep the docs workflow aligned to the repo's chosen runtime instead of silently downgrading CI.

## First pass

1. Identify the site mode:
   - docs-only
   - docs + blog/changelog
   - docs + marketing homepage
   - multi-instance docs
2. Capture constraints:
   - public vs private docs
   - package manager and monorepo vs standalone
   - single vs multi-locale
   - versioned vs unversioned docs
   - OpenAPI/reference generation needs
   - target host, `baseUrl`, and `trailingSlash` behavior
3. Choose the search strategy early. Search affects config, crawler/indexing, and UX.
4. Shape the route map before writing pages. Decide `routeBasePath`, slugs, sidebars, navbar items, and plugin IDs up front.
5. Implement in this order:
   - bootstrap
   - content structure
   - global config
   - search
   - theming and custom UX
   - deployment and verification

## Working rules

- Keep `docusaurus.config.*` authoritative. Avoid scattering site metadata across random files.
- Treat repository operations as first-class work: scripts, config files, CI, and `AGENTS.md` are part of the deliverable, not follow-up chores.
- Bootstrap docs quality tooling immediately: `prettier` for formatting/fixing, `markdownlint-cli2` for Markdown linting/fixable issues, `AGENTS.md` for agent workflow and quality gates, and a GitHub workflow that runs check-only validation.
- Mirror the documentation hierarchy in the filesystem unless there is a real reason not to.
- Set explicit doc `slug`s before large renames or reorganizations.
- Use `src/pages/` only for standalone routes. Pages do not get doc sidebars.
- Use MDX for interactive content, not as an excuse to turn docs into unstructured React blobs.
- Let Prettier own formatting for `.md` and `.mdx`. Use `markdownlint-cli2` as the structural Markdown layer; expand it to `.mdx` only after validating the actual MDX patterns used by the site.
- Keep fix modes local. CI must run check-only commands and must never call `prettier --write` or `markdownlint-cli2 --fix`.
- Pin community plugins carefully and verify compatibility with the current Docusaurus release before adopting them.
- Seed `AGENTS.md` with repo-specific doc rules and mandatory quality gates before handing the site to other agents.
- When production behavior differs from dev mode, verify the built site with `pnpm run serve -- --build` before touching theme internals or routing logic.
- If routing, i18n, or plugin changes produce stale or inconsistent output, run `pnpm exec docusaurus clear` before assuming the config is wrong.
- Validate every major change with docs quality commands and then `pnpm start`, `pnpm build`, and `pnpm run serve -- --build`.

## Decision shortcuts

- Docs-only home at `/`:
  - set the docs plugin `routeBasePath: '/'`
  - remove or replace `src/pages/index.*` so it does not conflict with docs routes
- Separate docs families with distinct release cycles:
  - use docs multi-instance only when the sets belong on one site
  - split into multiple sites if each instance is large or independently operated
- Public open-source docs:
  - default to Algolia DocSearch
- Private, internal, or small docs:
  - default to local search
- Self-hosted search or cross-site search:
  - consider Typesense or a custom SearchBar
- Deep layout customization:
  - start with CSS variables and stable theme class names
  - wrap theme components before ejecting them

## Verification checklist

- No duplicate routes or broken links.
- `pnpm format:check` passes.
- `pnpm lint:md` passes.
- `pnpm build` passes.
- The GitHub Actions docs-quality workflow exists and runs check-only commands.
- `url` and `baseUrl` match the actual deployment.
- `trailingSlash` behavior matches the target host and the local built preview.
- Search works for current docs, older versions, and non-default locales if used.
- Mobile nav, sidebar, TOC, and search modal remain usable.
- Dark and light mode branding stays legible.
- Code blocks, tabs, admonitions, diagrams, and MDX imports render correctly.
- Generated reference docs, if any, live in their own content tree and are not being hand-edited in place.
- Search and docs pages remain performant after adding heavy plugins or large indexes.
