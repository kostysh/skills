Готовность интеграции очереди на ревизии 6 закрывать нельзя. Изолированные тесты подтверждают восстановление заданий, но не согласованное владение долговременными данными по C1. Применимость исключения ADR-9 после изменения роли `state` не обоснована.

Режим: **closure-time re-audit**. Статус оценки: **limited**. Единственный итог режима: **claim-not-demonstrated**. Область: заявленная готовность интеграции `queue` на R6; основание — концепция C1 и принятое архитектурное изменение R6. Потребитель — интегрирующий runtime: после аварии он должен сохранять и восстанавливать задания при определённой, согласованной ответственности за миграции и recovery долговременных данных.

| Элемент | Значение для проверяемого утверждения |
| --- | --- |
| Доставленное поведение | Отдельная очередь восстанавливает задание после аварии с тем же файлом; двойного ack нет — это установлено предоставленными тестами R6. |
| Сохраняемый инвариант | Долговечность очереди подтверждена в проверенном отдельном сценарии. Требуемый C1 инвариант согласованного владения миграциями и recovery всех долговременных данных на интеграционной границе не подтверждён. |
| Обеспечивающая основа | Собственный слой хранения очереди и общий `state` с достаточным API позволяют реализовать решение, но сами по себе не устанавливают распределение ответственности между ними. |
| Свидетельства | Зелёные тесты очереди и `state` относятся к отдельным модулям. PASS ревизии 5 относится к прежней границе; совместное владение миграциями/recovery в R6 не определено и не проверялось. |

Материальное изменение — полномочия `state`, а не технология SQLite или текст ADR. В R5 исключение опиралось на отсутствие у `state` долговременного контракта. В R6 он принят общим владельцем долговременного хранения доменных модулей и предоставляет необходимый очереди API. Поэтому изменившаяся предпосылка возвращает применимость ADR-9 в область re-audit, хотя в ADR, спецификации и коде очереди нет diff. Исторический PASS остаётся результатом для R5; переносить его на эту границу R6 нельзя. Несвязанные проверенные решения пересматривать не требуется.

В полном предоставленном наборе обоснований нет актуального решения владельца архитектуры об исключении. Это предметный пробел при ясных C1 и R6, а не неопределённость источника концепции. Неизменённый ADR и старый PASS не заменяют текущего основания. При этом изменение предпосылки само по себе не отменяет ADR-9 и не доказывает, что очередь обязана использовать `state`.

**Fake-risk: high** — предложенное закрытие может пройти по зелёным функциональным тестам при неопределённой ответственности за миграции и восстановление, то есть без демонстрации существенного требования C1.

**Единственное первичное решение: request authority/evidence.** Следующий владелец — владелец архитектуры (`architecture-engineer`). Минимально требуется актуальное решение по применимости ADR-9 после R6: обосновать исключение либо изменить его и явно установить границы ответственности `queue` и `state` за миграции и recovery. Затем для закрытия интеграции нужны свидетельства совместного сценария в принятой конфигурации, показывающие выполнение этого распределения при миграции и аварийном восстановлении с сохранением заданий. Повторение отдельных тестов этот пробел не закрывает.

Антиутверждения: заключение не устанавливает фактическую потерю данных, конфликт миграций или дефект алгоритма очереди; не отменяет ADR и не предписывает архитектуру. Отдельные БД или файлы сами по себе не означают дублирование ответственности. Оценка основана исключительно на установленных синтетических фактах задания; внешние системы не проверялись.
