Готовность интеграции очереди на ревизии 6 закрывать нельзя. Подтверждённое поведение отдельной очереди сохраняет значение, но актуальное основание архитектурного исключения и согласованное владение миграциями/recovery не установлены.

Режим: `closure-time re-audit`. Область: заявка на закрытие готовности интеграции `queue` на ревизии 6; концептуальный источник — C1, текущий архитектурный контекст — принятое изменение R6. Статус: `limited`; исход: `claim-not-demonstrated`; fake-risk: `high`. Основание ревью достаточно для этого вывода: концепция и заявленная граница известны. Пробел касается обоснования исключения и доказательств интеграции, поэтому весь обзор не является `blocked / not assessable`.

Потребитель заявленной способности — интегрирующий runtime и доменные потребители очереди. После перезапуска задания должны сохраняться, а ответственность за миграции и восстановление всех долговременных данных должна быть согласована согласно C1 либо иметь актуально обоснованное исключение.

Классификация относительно этой границы:

- **Delivered behavior:** в предоставленном сценарии отдельная очередь восстанавливает задание после аварийного завершения с тем же файлом; двойного ack нет.
- **Capability-preserving invariant:** тестами отдельной очереди подтверждены сохранность задания и корректность ack в проверенных условиях. Общесистемная согласованность владения миграциями/recovery ими не подтверждена.
- **Enabling substrate:** принятые обязанности и достаточный API `state`, а также собственные драйвер, миграции и recovery очереди обеспечивают локальную основу работы. Их наличие не определяет согласованную ответственность при интеграции.
- **Verification evidence:** текущие раздельные тесты `queue` и `state` подтверждают только свои проверенные границы. PASS ревизии 5 — историческое свидетельство обоснованности исключения при прежнем контракте `state`.

ADR-9 входит в повторную проверку, несмотря на отсутствие diff. Его основанием в ревизии 5 была ограниченность `state` краткоживущими сессиями. R6 материально меняет именно эту предпосылку: `state` теперь отвечает за долговременное хранение доменных модулей и предоставляет достаточный API очереди. Неизменность SQLite и модели запуска не сохраняет прежнее распределение ответственности. Неизменённые спецификация, код и текст ADR, как и предыдущий PASS, не заменяют актуальное обоснование исключения. Результат ревизии 5 не опровергнут для прежней границы, но автоматически переносить его на R6 нельзя.

Остаются два связанных пробела:

1. В полном наборе текущих обоснований отсутствует решение владельца архитектуры о применимости исключения после R6 и согласованном владении миграциями/recovery. Требуется актуальное обоснование сохранения исключения либо решение об изменении границы ответственности.
2. Нет текущего доказательства работы этой согласованной границы. После её определения нужны результаты интеграционной проверки, показывающие, кто выполняет миграции и восстановление, и сохранение требуемых свойств очереди при перезапуске в принятой конфигурации. Раздельные зелёные тесты допускают успешное прохождение при незакрытом требовании C1 — отсюда высокий риск ложного закрытия.

Anti-claims: не установлены потеря заданий, дефект ack или неработоспособность отдельной очереди. Ревью не отменяет ADR-9, не предписывает обязательное переиспользование `state` и не объявляет отдельные файлы или БД дублированием слоя хранения. Вопрос касается владения ответственностью. Фактические внешние системы не проверялись; вывод основан только на синтетических установленных фактах задания.

Основное решение: `request authority/evidence`. Следующий владелец — владелец архитектуры (`architecture-engineer`): минимально требуется актуальное решение по исключению ADR-9 после R6 с явным распределением ответственности. Затем владелец интеграции предоставляет доказательства на принятой границе. До этого исход для готовности интеграции остаётся `claim-not-demonstrated`; локальные подтверждённые результаты очереди и `state` этим не аннулируются.
