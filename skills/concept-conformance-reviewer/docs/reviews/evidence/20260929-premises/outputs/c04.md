F1 устранён на уровне design-time приёмки: исправленный AC-3 требует восстановления реально сохранённого задания после принудительного завершения процесса. Прохождение проверки только через подставной storage adapter больше не удовлетворяет критерию.

- Режим: **design-time**, повторный аудит ревизии 9.
- Статус оценки: **assessable**.
- Результат: **design-ready**.
- Fake-risk: **low** в проверенной границе.
- Основное решение: **proceed**.

Основание — концепция C1: задания, подтверждённые как сохранённые, доступны после аварийного перезапуска. Граница повторного аудита — F1, заменённый AC-3 и непосредственно затронутая цепочка сохранения и восстановления. Остальные критерии и проверенные в ревизии 8 архитектурные основания приняты как установленные входные данные.

Потребитель — участник системы, сохраняющий и затем получающий задание. Проверяемая возможность: после подтверждённой записи и аварийного завершения задание остаётся доступным при запуске с тем же файлом; AC-3 также требует ровно одного ack.

Исходный путь ложной приёмки закрыт: исправная подстановка при потере реальных данных уже не позволяет выполнить AC-3. Уникальный id связывает проверку с созданным заданием, а новый процесс и тот же файл требуют восстановления через реальную границу хранения. Дополнительных дефектов приёмки на непосредственно затронутой поверхности из предоставленных данных не следует.

Архитектурные решения повторно не открываются: технология, API, ответственность, условия изоляции и основания ADR не изменились, новых противоречащих данных нет. Это относится и к раздельным файлам через общий модуль, отсутствию межфайловых атомарных операций и обоснованному исключению для sandbox. Таймауты API, язык и оформление CLI вне затронутой поверхности.

Анти-claims: заключение не подтверждает фактическое восстановление в реализации, общую надёжность хранилища или межфайловую атомарность. Оно закрывает F1 как дефект проектной приёмки и не подменяет проверку готовой реализации.
