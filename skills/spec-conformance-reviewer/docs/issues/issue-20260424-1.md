# Issue: add bounded policy/admission edge-case matrix to spec reviews

Issue ID: `SCR-01`

Primary owner skill: `spec-conformance-reviewer`

Status: audited

## Проблема

Spec-conformance reviews могут проходить по policy/admission features без явной matrix для mandatory negative и fail-closed branches.

В session `019dbf3f` normative sources `F-0025` требовали explicit consultant admission и structured refusal semantics. Initial implementation review нашел spec blocker: explicit consultant DENY не был смоделирован как first-class persisted deny/no-invocation outcome.

Более поздние blockers касались adjacent branches, которые должны быть видимы в policy/admission matrix, даже если финальный owner конкретной проверки — `code-reviewer` или `security-reviewer`: conflicting admission replay, missing freshness timestamp, active-scope activation conflict.

## Почему это важно

Spec review должен проверять обязательные ветки поведения, которые прямо следуют из normative sources. Без explicit matrix reviewer может подтвердить happy path и пропустить mandatory refusal/fail-closed behavior.

## Текущая активная поверхность

- `SKILL.md`: requirement extraction, traceability и verdict discipline.
- `references/methodology.md`: source priority и extraction workflow.
- `references/reporting.md`: statuses, findings и verdicts.

## Требуемое исправление

Когда normative sources упоминают policy decisions, admission gates, external consultant invocation, fail-closed behavior, activation decisions или refusal semantics, `spec-conformance-reviewer` должен extract и review bounded edge-case matrix.

## Что должно измениться

Минимальные matrix rows, когда применимо:

- explicit allow;
- explicit deny;
- missing admission evidence;
- ambiguous admission evidence;
- stale evidence или missing freshness timestamp, когда age limits normative;
- unsupported или unhealthy downstream path;
- duplicate/conflicting request id, если idempotency/replay semantics normative или implied by persistence contract;
- activation conflict, если single-active-scope behavior normative;
- persistence failure, если spec требует fail-closed auditability.

Docs и fixtures должны закрепить, что matrix включается только по normative trigger, а не для каждого review.

## Acceptance Criteria

- Methodology инструктирует reviewers создавать policy/admission matrix только при наличии normative trigger в sources.
- Findings цитируют и requirement basis, и implementation evidence.
- Missing explicit DENY/no-invocation path classified as spec non-compliance, когда spec requires explicit admission/refusal.
- Missing matrix rows reported as verification gaps или ambiguity, когда normative source недостаточно explicit.
- Tests или review fixtures покрывают consultant admission feature с explicit allow/deny и stale evidence requirements.

## Обязательные ограничения для planning и implementation

- Matrix rows применяются условно, а не universally.
- Ambiguous requirements становятся `ambiguous_spec` или verification gaps, а не invented obligations.
- Skill остается requirement-first: сначала read specs, затем implementation; taste-based findings избегаются.

## Non-Goals

- Не превращать skill в general code reviewer.
- Не report-ить replay, concurrency или persistence concerns без связи с normative requirement или contract.
- Не требовать эту matrix для unrelated CRUD, UI, documentation или non-admission changes.
- Не дублировать security exploitability classification; security-specific findings route to `security-reviewer`.
