Добавить traceability и checklist для policy/admission conformance

## Problem

The skill reviews implementation against normative requirements, but it does not require a dedicated policy/admission conformance checklist. For this class of feature, the reviewer should not rely only on generic spec matching. The review needs explicit evidence that:

- baseline route cannot bypass the gate;
- fallback target is explicitly bound to policy or release evidence;
- current policy identity is the authoritative source;
- upstream evidence comes from canonical sources;
- stage, scope, and task binding are checked before decision and at persistence;
- each relevant acceptance criterion maps to code path, negative test, and evidence source.

Without that shape, conformance depends too much on reviewer inference and can be approved without durable traceability.

- missing `AC -> code path -> negative test -> evidence source` traceability at implementation handoff;
- repeated cross-skill findings around the same policy/admission risk family.

## Impact

- Policy/admission conformance can be approved without explicit bypass-prevention evidence.
- Reviewer output is harder to compare with code/security review because no traceability matrix is required.
- Future agents may repeat ad hoc inference instead of following a clear review contract.

## Scope

In scope:

- active checklist guidance for policy/admission, release-policy, governance, and runtime-gating conformance;
- review-output requirement for `AC -> code path -> negative test -> evidence source`;
- optional cross-skill alignment with a shared policy/admission risk-family reference.

Out of scope:

- changing application-specific specs or code;
- adding dossier runtime commands;
- replacing independent review with shared reviewer conclusions;
- requiring non-portable external files.

## Proposed Resolution

1. Add an active checklist section for admission/release-policy conformance. The reviewer verifies baseline bypass prevention, fallback/release binding, authoritative policy identity, canonical evidence source, and stage/scope/task binding at decision and persistence.
2. Require a traceability matrix in review output for governance/admission features: `AC -> code path -> negative test -> evidence source`.
3. Return `FAIL` when implementation evidence does not allow the reviewer to confirm every required mapping.
4. If the reviewer reconstructs the matrix from checked artifacts, mark source quality per row.
5. Preserve portability: any shared policy/admission risk-family reference must be referenced by skill name or copied into this skill's active surface during implementation; the issue must not make external project files mandatory.
6. Implement through the generated-skill maintenance path: update `skill.yaml`, `fragments/*`, `references/*`, and fixtures as needed, then regenerate `SKILL.md` and `docs/compile-report.md`.

## Alternatives Considered

- Keep relying on generic spec conformance review. Rejected because policy/admission gates have recurring failure modes that need named checks.
- Trust implementation notes without independent traceability verification. Rejected because conformance review must validate evidence, not only summarize claims.

## Destructive Side Effects

- Reviews for governance/admission features may return more `FAIL` verdicts when traceability evidence is missing.
- Existing examples or fixtures may need updates to distinguish ordinary spec review from policy/admission gate review.
- If the shared risk-family reference is introduced, portability must be protected by avoiding absolute paths and mandatory external dependencies.
