## Issue ID

## Title

Сделать Phase 2: single-writer runtime safety для mutating dossier commands

## Skill

`dossier-engineer` (`skills/dossier-engineer`)

## Context

Анализ `docs/dossier-engineer-problem-analysis-and-proposals.ru.md` выявил runtime race: параллельные mutating CLI-команды могут читать один и тот же старый artifact и перетирать изменения друг друга.

Phase 2 из roadmap отвечает за runtime safety:

- exclusive single-writer lock для всех mutating commands;
- temp+rename writes;
- re-read affected artifacts after lock acquisition;
- stale write detection;
- lock conflict output with next actions.

## Problem

Текущий runtime пишет Markdown artifacts через обычную запись файла после read-modify-write цикла. Нет single-writer protection, atomic write envelope и stale-read detection.

Это означает, что два агента или два процесса могут:

- одновременно прочитать один artifact;
- подготовить разные изменения;
- последняя запись silently перетрёт часть изменений первой;
- runtime продолжит считать состояние валидным, хотя semantic updates lost.

Методика не может решить этот класс дефекта: даже дисциплинированный агент не видит race внутри filesystem write path.

## Evidence

Основной источник: `docs/dossier-engineer-problem-analysis-and-proposals.ru.md`.

Релевантные причины:

- `3.10. Причина J`: runtime race не устранён методикой.
- `3.11. Причина K`: нельзя полагаться только на память агента.
- `3.12. Причина L`: runtime implementation слабее ожидаемого process contract.

Релевантное предложение:

- `P0. Ввести single-writer lock для mutating runtime-команд`.

В анализе указано, что `src/infra.ts` использует обычный `writeFile`, а `updateArtifact` читает, меняет frontmatter и пишет файл обратно без:

- single-writer lock;
- atomic temp+rename write;
- stale-read check;
- compare-and-swap по previous hash;
- transaction envelope для multi-file commands.

## Impact

- Acceptance criteria, anti-claims, review records, stage transitions или hygiene state могут быть потеряны без явной ошибки.
- Параллельные agents могут создать dossier state, который выглядит валидным структурно, но не содержит всех semantic updates.
- Work item может закрыться с неполным набором evidence или gates.
- Оператор получает ложное чувство безопасности от Markdown/YAML canonical state, хотя write path не сериализован.

## Scope

Входит в scope:

- Добавить exclusive ephemeral dossier write lock для всех mutating commands.
- Read-only commands оставить параллельными.
- После lock acquisition заново читать affected artifacts.
- Выполнять preconditions после re-read.
- Писать artifacts через temp file + atomic rename.
- Добавить stale write detection по previous file hash, `updated_at`, или эквивалентному runtime-owned compare signal.
- Для lock conflict возвращать no-write result, holder info when available, и `Next actions`.
- Не держать write lock во время long-running external commands.
- Использовать один primary lock path: `<repo-root>/.dossier-runtime/write.lock/`.
- Освобождать lock через finally/defer cleanup path.
- Добавить lock diagnostic interface или обязательный lock conflict output with lock path, holder metadata and age.
- Обновить active guidance wording around runtime concurrency.
- Обновить runtime tests.

Не входит в scope:

- Добавление отдельной базы данных.
- Создание committed lock files или canonical lock artifacts under `docs/dossier/`.
- Per-file locks на первой итерации.
- Долгоживущие locks, которые блокируют обычную разработку кода.
- Изменение business semantics stage gates; это Phase 1 и Phase 3.
- Добавление новых обязательных artifact families. Prefer strengthening existing work item body contracts and existing verification/review artifacts over adding new mandatory artifact families.

## Proposed Resolution

1. Ввести coarse-grained lock на dossier root.

   Primary lock location:

   ```text
   <repo-root>/.dossier-runtime/write.lock/
   ```

   Lock не является canonical dossier state и не должен коммититься.
   The directory is ephemeral runtime metadata and must be gitignored.
   Do not place runtime locks under `docs/dossier`.
   Do not rely on `.git` being a directory.

   Runtime or setup guidance must ensure `.dossier-runtime/` is ignored by git. The lock directory must never appear in changesets or generated dossier reports.

2. Atomic acquisition через `mkdir(lock_dir)`.

   Если `mkdir` успешен, команда получила lock. Если директория существует, mutating command должен завершиться без изменений и вывести:

   - что lock held;
   - holder metadata when available;
   - how to retry;
   - stale lock recovery guidance;
   - `Next actions`.

3. Все mutating commands должны использовать общий mutation envelope:

   1. Acquire write lock.
   2. After lock, re-read all affected artifacts.
   3. Check preconditions.
   4. Prepare changes in memory.
   5. Write files via atomic temp+rename.
   6. Run post-write validation for affected artifacts.
   7. Release lock.

   The mutation envelope MUST release the write lock in a finally/defer cleanup path after every command, including validation failure, write failure, thrown error, or external interruption that reaches runtime cleanup.

4. Long-running external commands MUST NOT hold the dossier write lock while the external process is running.

   For commands such as `verify run`:

   1. read the intended verification scope;
   2. run the external command without the write lock;
   3. acquire the write lock;
   4. re-read affected artifacts;
   5. verify that material scope is still current;
   6. record verification artifact or report stale scope.

5. Active guidance должна использовать формулировку:

   ```md
   Mutating runtime commands MUST acquire an exclusive ephemeral dossier write lock before reading and writing artifacts.
   The lock is not canonical dossier state and must not be committed.
   If the lock is held, the agent MUST stop the mutation and follow the runtime lock recovery instructions; it MUST NOT bypass the lock by manually editing artifacts.
   ```

6. Уточнить старое правило про lock files:

   ```md
   Do not use committed lock files or lock files as canonical dossier state.
   Ephemeral runtime write locks are required for mutating commands and are not dossier artifacts.
   ```

7. Classify commands.

   Read-only commands may run without write lock:

   - `status`;
   - `attention`;
   - `queue`;
   - `next`;
   - `lint`, if it does not write;
   - `capability check`;
   - `guardrail check`, if without `--record`;
   - `source impact`.

   Mutating commands must serialize, including:

   - `source add/refresh/review resolve`;
   - `capability create/claim/anti-claim/demo`;
   - `baseline create/capability add`;
   - `guardrail add/resolve`;
   - `work create/acceptance/demo/anti-claim/challenge/support/dependency/blocker/risk/amend/split/retire`;
   - `stage start/ready/close/reopen/log`;
   - `verify run/record`;
   - `review record`;
   - `hygiene run`;
   - `changeset create`;
   - `report create`;
   - `retro create`.

   `verify run` is logically mutating because it may record verification results, but its external execution phase MUST run outside the write lock.

   Only the final record phase uses the mutation envelope:

   ```text
   acquire lock -> re-read -> validate scope freshness -> write verification artifact -> release lock
   ```

8. Add lock diagnostics.

   Preferred minimal interface:

   ```bash
   dossier-engineer lock status
   dossier-engineer lock break --reason "<reason>"
   ```

   If the first implementation does not add lock commands, lock conflict output MUST include the lock path, holder metadata, age, and manual safe-removal guidance.

9. Document read-only mixed-view limitation.

   ```md
   Read-only commands may run without write lock and may observe a transient mixed view during a concurrent mutation. Closure decisions must not rely on such a view; mutating closure commands re-read under the write lock.
   ```

## Alternatives Considered

- Добавить database. Отклонено: анализ прямо указывает, что Markdown/YAML model остаётся правильной; race решается lock + atomic write.
- Добавить per-file locks сразу. Отклонено: first version должна быть one dossier root, one writer at a time, чтобы избежать deadlocks и lock ordering complexity.
- Полагаться на инструкции "не запускать параллельно". Отклонено: это не runtime protection и не покрывает несколько агентов/процессов.
- Использовать committed lock artifact under `docs/dossier/`. Отклонено: lock не должен стать canonical truth или merge-conflict source.

## Destructive Side Effects

- Concurrent mutating commands начнут fail/retry вместо silent overwrite. Это намеренное изменение; mitigation: lock-held output должен давать clear next actions.
- Stale lock может заблокировать работу после crash. Mitigation: holder metadata, timestamp, stale recovery command/guidance, and conservative refusal to auto-delete fresh locks.
- Temp+rename может вести себя по-разному на filesystems. Mitigation: tests and clear fallback for unsupported atomic rename semantics.
- Coarse lock может сериализовать больше команд, чем строго нужно. Mitigation: CLI commands are short; parallel code work remains unaffected; per-file locks explicitly out of scope for first iteration.
- Long-running verification could block all dossier writes if the lock is held during external tests. Mitigation: `verify run` and similar commands run external processes outside the lock and record results only after re-reading under the lock.
- Read-only commands may observe transient mixed multi-file state during concurrent mutation. Mitigation: read-only output is advisory; mutating closure commands re-read and validate under the lock before changing canonical state.

## Verification

Функциональная проверка должна включать runtime acceptance tests из анализа:

- Two concurrent mutating commands cannot both write the same artifact; one must wait or fail with lock-held output.
- A mutating command writes via temp+rename and does not leave half-written Markdown after simulated crash.
- Mutating command re-reads affected artifacts after acquiring lock.
- `verify run` or another long-running external command does not hold the write lock while the external process is running; it re-acquires the lock only to record results.
- The write lock is released through cleanup on validation failure, write failure and thrown runtime errors.
- Primary lock path is `<repo-root>/.dossier-runtime/write.lock/`; runtime does not rely on `.git` being a directory.
- Runtime or setup guidance ensures `.dossier-runtime/` is ignored by git; the lock directory never appears in changesets or generated dossier reports.
- Lock conflict output includes lock path, holder metadata, age, and safe recovery guidance, or `lock status` / `lock break` commands provide that interface.
- Read-only commands can run without lock and are documented as potentially observing transient mixed views.

Также проверить:

- read-only commands run without acquiring write lock;
- every known mutating command goes through the mutation envelope;
- lock conflict output includes `Next actions`;
- stale lock recovery is documented and tested;
- active guidance says ephemeral locks are required and not canonical state;
- generated `SKILL.md` regenerated from source bundle, if active wording changed;
- `scripts/dossier-engineer.mjs` rebuilt from `src/*`;
- instruction-quality audit from `skill-source-compiler` passes after substantial active guidance changes.
- The issue-level independent audit does not replace implementation review after changes are made.
