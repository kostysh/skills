## Issue ID

`issue-20260502-1`

## Title

Добавить session-forensics слой в ретро-анализ process misses

## Skill

`dossier-engineer` (`skills/dossier-engineer`)

## Context

Текущий `retrospective` workflow строится от canonical dossier artifacts: sources, capabilities, baselines, guardrails, work items, source reviews, stage events, verification artifacts, review artifacts, hygiene artifacts и changesets. Active reference прямо фиксирует, что `retro create` не использует JSONL session index или database.

Это защищает `dossier-engineer` от hidden telemetry, центрального mutable state и merge-conflict-heavy глобальных индексов. Но в обсуждении методики ретро возник важный пробел: реальные причины process misses часто видны только в raw session log. Именно в сессионном логе можно увидеть, где агент столкнулся с ambiguity, tool failure, stale context, ignored blocker, weak evidence или неверной классификацией capability/substrate, но не записал это в canonical dossier artifacts.

Нужная observable capability: retrospective workflow должен уметь восстанавливать доказуемую причинную цепочку process miss по bounded session-log context и переводить найденные причины в canonical dossier actions: `process_misses`, `skill_feedback`, guardrails, follow-up work, source/work item updates или explicit `no_action`.

Substrate, который сам по себе не решает проблему:

- raw `jsonl` parser;
- event index;
- timeline summary;
- enriched retro report;
- цитаты из сессионного лога;
- счетчики tool calls, failures или message counts;
- большая forensic appendix без canonical follow-up action.

Anti-claim: `dossier-engineer` не должен превращать raw session logs в новый canonical dossier state, hidden telemetry layer, committed JSONL index, database или обязательную глобальную историю всех агентских действий.

## Problem

Текущий retrospective protocol видит только проблемы, которые уже были записаны в canonical artifacts. Это оставляет несколько failure modes:

- process miss произошел в сессии, но агент не записал его в work item, changeset, verification, review или guardrail;
- `retro create` показывает симптом, но не помогает понять источник: skill rule gap, weak methodology, runtime friction, stale context, operator ambiguity, tool failure или ignored instruction;
- отчет может зафиксировать `missing_demo` или `infrastructure_masquerade`, но не показать, где именно агент принял substrate за capability;
- repeated tool failures, warnings, blocker outputs или rejected assumptions могут остаться только в session log;
- final answer или stage close могли завысить claim относительно фактического evidence, но это не всегда видно из dossier artifacts;
- большие raw logs невозможно надежно анализировать простым "прочитай все и сделай вывод";
- без формальной методики агент может придумать post-hoc causal story вместо evidence-backed root cause.

Ожидаемое поведение: session log используется как bounded forensic evidence для исследования конкретных retrospective problems и обнаружения незаписанных process misses.

Нежелательное фактическое поведение: session log становится неограниченным новым источником истины, а успешным результатом считается сам факт парсинга или суммаризации лога.

## Evidence

Active reference `references/retrospective.md` сейчас говорит:

- retrospective reports derive from canonical artifacts;
- `No JSONL session index or database is used`;
- process misses are stored in changeset frontmatter or work item body, then summarized by `retro create`;
- `retro create` scans canonical artifacts and creates a derived `RETRO-*.md` report.

Это правильно для canonical state, но не закрывает forensic need:

- session context может объяснить, почему process miss не был записан;
- session context может показать первичный момент, где existing gate должен был сработать;
- session context может различить "rule absent" и "rule existed but was ignored";
- session context может доказать, что причина лежит в runtime feedback, skill wording, review workflow или operator ambiguity.

Связанная discussion source: операторская постановка от 2026-05-02 о необходимости отдельного слоя анализа raw session logs для выявления проблемных ситуаций, с которыми сталкивался агент и которые стали причиной process misses.

## Impact

Без session-forensics слоя:

- ретро может быть слишком поздним и поверхностным: оно видит только уже записанные проблемы;
- скрытые или незаписанные process misses не попадают в improvement loop;
- recommendations могут исправлять симптомы, а не причины;
- skill changes могут добавлять еще больше инструкций там, где нужен runtime gate или clearer Next action;
- repeated agent failures могут выглядеть как одноразовые ошибки;
- оператор получает отчет, но не получает доказательства, что root cause действительно найден;
- большие сессионные логи остаются практически непригодными для методического анализа.

Если слой реализовать плохо:

- возникнет privacy/security risk из-за сохранения raw logs или больших excerpts;
- появится non-portable dependency на конкретный agent runtime;
- отчеты станут тяжелыми и конфликтными;
- agents начнут считать "log summary" доказательством process improvement;
- `dossier-engineer` потеряет merge-safe Markdown/YAML модель canonical state.

## Scope

Входит в scope:

- Добавить в active guidance `Session Forensics Pass` как optional/triggered layer после canonical retrospective pass.
- Определить, что raw session log является forensic input, а не canonical dossier state.
- Определить bounded input packet для анализа конкретной retro problem.
- Определить методику анализа больших logs:
  - mechanical event normalization;
  - relevant window selection;
  - claim/evidence/gap separation;
  - root-cause classification;
  - countercheck against post-hoc causality;
  - forensic finding output;
  - canonical promotion.
- Определить minimal evidence block для forensic findings.
- Добавить discovery mode для незарегистрированных process misses, которые не попали в initial `retro create`.
- Определить redaction/privacy expectations для цитат из сессии.
- Определить allowed canonical actions after forensics:
  - add/update `process_misses`;
  - add/update `skill_feedback`;
  - open issue for skill/runtime change;
  - add/update guardrail;
  - update active methodology;
  - create follow-up work;
  - record explicit `no_action` with rationale.
- Уточнить, что enriched retrospective report remains derived and cannot become closure evidence.
- Уточнить, какие acceptance criteria являются misleading и должны отклоняться.

Не входит в scope:

- Делать raw session logs обязательным входом для каждого retrospective.
- Коммитить raw JSONL logs в `docs/dossier/`.
- Создавать committed JSONL session index, database, глобальный event store или mutable hidden state.
- Делать runtime-specific session discovery универсальным portable CLI contract.
- Требовать от `retro create` читать произвольные локальные agent runtime logs на Phase 1.
- Строить полную observability/telemetry платформу.
- Использовать hidden reasoning или private scratchpad как доказательство root cause.
- Заменять existing canonical retrospective pass анализом raw logs.
- Считать цитату из лога достаточной без interpretation, root-cause classification и canonical action.

## Proposed Resolution

### 1. Add `Session Forensics Pass` to retrospective methodology

Новая методика должна описывать трехслойный retrospective process:

1. `Canonical Retro Pass`: выполнить текущий `retro create` по canonical dossier artifacts.
2. `Session Forensics Pass`: исследовать bounded session-log context для проблем из retro report и, при необходимости, выполнить discovery scan для незарегистрированных process misses.
3. `Canonical Promotion`: перенести доказанные выводы в canonical dossier artifacts or explicit `no_action`.

Normative constraint:

```md
Session logs are forensic inputs. They are not canonical dossier state.

Session forensics may enrich retrospective analysis only when findings are traceable to bounded log evidence and result in a canonical dossier action or explicit no-action rationale.
```

### 2. Define bounded forensic input packet

Агент не должен получать задание "проанализируй весь лог". Для каждой known problem нужен bounded packet:

```yaml
retro_problem:
  kind: missing_demo | infrastructure_masquerade | stale_evidence | runtime_friction | other
  affected_artifacts:
    - WI-...
    - CAP-...
  observed_symptom: "<what canonical retro reported>"
  expected_gate: "<rule/check/stage that should have prevented or recorded the miss>"
session_logs:
  - ref: "<path/hash/session id>"
scope:
  since: "<timestamp or event index>"
  until: "<timestamp or event index>"
active_rules:
  - references/retrospective.md
  - references/workflow.md
```

Если границы неизвестны, агент начинает с lightweight discovery pass, но обязан затем сузить анализ до relevant window.

### 3. Normalize log into neutral event timeline

Первый проход должен быть mechanical and non-interpretive. Агент извлекает только значимые события:

```yaml
event:
  index: 1842
  timestamp: "<if available>"
  type: user_message | assistant_claim | tool_call | tool_result | file_edit | test_run | failure | warning | review | verification | final_response
  summary: "<neutral one-line summary>"
  refs:
    tools:
      - exec_command
    files:
      - "<relative path>"
    artifacts:
      - WI-...
```

Для больших logs event timeline должен быть временным рабочим материалом. В canonical dossier попадают только selected evidence snippets and interpreted findings.

### 4. Select relevant window for each problem

Для каждой retrospective problem агент ищет first relevant point where the miss became possible:

- user intent or scope was interpreted;
- capability/substrate classification was chosen;
- source/capability/work item was selected or skipped;
- acceptance or demo evidence was defined;
- tool output exposed warning/blocker/failure;
- review/verification result was interpreted;
- final answer/stage close made a claim.

Окно расширяется назад до последнего material change of intent/scope/source and вперед до момента проявления miss. Агент должен объяснить, почему окно достаточно, и явно отметить, если evidence outside the window may matter.

### 5. Separate claims, evidence and gaps

Внутри окна агент строит causal timeline, разделяя:

- `claim`: что агент заявил или считал выполненным;
- `evidence`: что фактически было подтверждено tool output, file diff, verification, review или user-visible demo;
- `gap`: что осталось непроверенным;
- `miss_trigger`: где workflow/rule/runtime должен был остановить, предупредить или записать проблему.

Минимальная структура:

```yaml
causal_timeline:
  - event: 1762
    role: claim
    summary: "Agent treated API-level test as behavioral proof."
  - event: 1774
    role: evidence
    summary: "Test output proves repository behavior only."
  - event: 1781
    role: gap
    summary: "No live-app or user-visible demo was executed."
  - event: 1790
    role: miss_trigger
    summary: "Implementation closure should have required behavioral-demo evidence."
```

### 6. Classify root cause with countercheck

Root cause classification must be evidence-backed:

```yaml
root_cause:
  class: skill_rule_gap | weak_methodology | runtime_friction | ignored_instruction | stale_context | operator_ambiguity | tool_failure | insufficient_evidence | unknown
  rationale: "<why this is cause, not only symptom>"
  failed_prevention:
    expected_rule: "<rule/gate/check>"
    outcome: rule_absent | rule_weak | rule_existed_but_not_applied | runtime_did_not_expose_blocker | operator_decision_required | unknown
```

Перед выводом агент обязан выполнить countercheck:

- Есть ли более ранняя причина, чем найденный симптом?
- Видел ли агент нужную информацию в момент ошибки?
- Существовало ли правило, которое должно было предотвратить miss?
- Это проблема методики, runtime feedback, operator ambiguity или конкретного agent execution?
- Можно ли подтвердить вывод только visible log/tool outputs, без hidden reasoning?
- Есть ли evidence против выбранной причины?

Если evidence недостаточен, finding должен иметь `root_cause.class: insufficient_evidence` или `unknown`.

### 7. Emit forensic finding

Для каждой investigated problem агент создает compact finding:

```yaml
session_forensic_finding:
  problem_ref: "RETRO-...#missing-demo-1"
  session_ref: "<session log ref or hash>"
  window:
    start_event: 1740
    end_event: 1895
  evidence:
    - event: 1762
      excerpt: "<redacted short quote>"
      proves: "Agent accepted API test as behavioral proof."
  context_summary: "<what was happening>"
  root_cause_class: weak_methodology
  failed_prevention: "Behavioral demo gate existed but was applied too late."
  confidence: high | medium | low
  recommended_canonical_action: process_miss | skill_feedback | guardrail | issue | follow_up_work | no_action
```

Evidence excerpts должны быть короткими, redacted where needed, and scoped to what they prove.

### 8. Promote findings into canonical dossier actions

Forensic finding не должен быть конечным результатом. После анализа агент выбирает одно действие:

- record/update `process_misses`;
- record/update `skill_feedback`;
- open a skill/runtime issue;
- create/update guardrail;
- update active methodology/reference;
- create follow-up work item;
- record `no_action` with explicit rationale.

`retro create` может быть rerun after canonical promotion, чтобы итоговый derived report отражал promoted findings.

### 9. Add misleading acceptance criteria guidance

Следующие acceptance criteria должны считаться substrate-only and rejected:

- "JSONL parser handles session logs";
- "event timeline is generated";
- "retro report contains excerpts from logs";
- "agent summarized the whole session";
- "N process misses were detected";
- "large log was processed without error";
- "report includes root cause labels".

Достаточные acceptance criteria должны требовать observable methodological effect:

- every finding has bounded log evidence, context summary, root-cause classification, countercheck and confidence;
- every high/medium-confidence finding has canonical action or explicit `no_action`;
- enriched report remains derived and does not become closure evidence;
- raw logs and generated indexes are not committed as canonical dossier state;
- discovery scan can identify at least one unrecorded miss in a fixture where canonical artifacts omit it;
- insufficient evidence produces `unknown` / `insufficient_evidence`, not invented causality.

## Alternatives Considered

### Keep current retrospective only

Rejected because current `retro create` cannot inspect unrecorded session-level failures and may only summarize symptoms already present in canonical artifacts.

### Make raw session logs canonical dossier state

Rejected because it violates merge-safe Markdown/YAML dossier design, creates privacy/security risk, and conflicts with the rule against JSON/JSONL/database canonical state.

### Add a mandatory `retro create --session-log <path>` command immediately

Deferred. A runtime command may be useful later, but the first needed change is methodology: input bounds, root-cause discipline, privacy limits, and canonical promotion rules. Adding a command too early risks making parser success look like process improvement.

### Let agents freely inspect full logs and enrich reports

Rejected because large logs encourage post-hoc causality, selective quoting, context overreach and unbounded token usage.

### Store full forensic annexes as derived reports only

Insufficient because derived reports do not affect primary truth. Findings must be promoted into canonical dossier actions or explicitly marked `no_action`.

## Destructive Side Effects

Risks:

- Sensitive user/project data from raw session logs could be copied into dossier artifacts.
- Large excerpts can make dossier history noisy and conflict-prone.
- Runtime-specific log layout assumptions can break skill portability.
- Agents can overfit to session transcript and invent intent that is not supported by durable sources.
- Forensic analysis may become expensive and slow for large logs.
- Operators may mistake enriched reports for closure evidence.
- Session logs may include hidden or non-shareable context that should not be stored.
- Too much mandatory forensic process can reintroduce the heavy workflow that earlier issues intentionally avoided.

Required mitigations:

- Store only short redacted excerpts needed to prove a finding.
- Treat raw logs and event indexes as temporary forensic inputs.
- Keep runtime-specific discovery as optional agent-side guidance, not portable CLI contract.
- Require confidence and `unknown` / `insufficient_evidence` outcomes.
- Require canonical promotion or explicit `no_action`.
- Keep session forensics triggered by retrospective problems, suspicious gaps, operator request, or high-risk work, not mandatory for every small task.
- Keep enriched retro reports derived and non-closure evidence.

## Verification

Expected verification for implementation:

- Active guidance documents `Canonical Retro Pass`, `Session Forensics Pass`, and `Canonical Promotion`.
- `references/retrospective.md` explains session logs as forensic inputs, not canonical state.
- The methodology defines bounded packets, event normalization, relevant window selection, claim/evidence/gap separation, root-cause taxonomy, countercheck, finding output, and canonical promotion.
- The guidance explicitly rejects substrate-only acceptance criteria.
- Privacy/redaction and portability constraints are explicit.
- Any new runtime command or flag, if added, is reflected in help output, tests, and docs/runtime parity.
- If the change is documentation-only, no runtime command is documented as shipped.
- Instruction quality audit passes after substantial skill guidance changes.
- Portability check confirms no absolute local paths or required external files are introduced.

Behavioral verification examples:

- Given canonical artifacts that contain a `missing_demo` problem and a fixture log where the agent accepted API tests as behavioral proof, session forensics produces bounded evidence, root cause, countercheck, confidence and canonical action.
- Given a fixture log with ambiguous evidence, session forensics returns `insufficient_evidence` instead of inventing a root cause.
- Given a fixture where the process miss exists only in session log and not in canonical artifacts, discovery mode can produce a candidate finding that must be promoted before it affects final retrospective reporting.
