# Issue

## Language

Русский.

## Issue ID

`issue-20260501-3`

## Title

Сделать Phase 3: integration correctness, live-app evidence и negative falsifiers

## Skill

`dossier-engineer` (`skills/dossier-engineer`)

## Context

Анализ `docs/dossier-engineer-problem-analysis-and-proposals.ru.md` показал, что behavioral verification не всегда доказывает production integration. В ретро-сценарии ранние tests/reviews проверяли bridge, tools, prompt routing, selection handling, IPC/security boundaries, но реальное пользовательское поведение стало доказанным только после live Electron demo.

Phase 3 из roadmap должна закрыть риск "фича реализована, но не интегрирована в действующее приложение":

- обязательный `Integration Path` в `Plan Slice`;
- `AC -> surface -> evidence -> falsifier` matrix;
- live-app behavioral evidence для UI/editor/user-facing capability;
- testable anti-claims as negative AC/falsifier.

## Problem

Текущий `behavioral-demo` profile слишком общий. Агент может доказать внутренний substrate:

- mock;
- headless store;
- schema;
- prompt/tool wrapper;
- contract test;
- bridge availability;

и принять это за доказательство user-visible capability. Для UI/editor/operator behavior это недостаточно: closure evidence должно проходить через actual running application path and production entrypoint.

Anti-claims также могут остаться prose boundary. Если anti-claim описывает observable forbidden behavior, но не превращён в negative acceptance criterion или falsifier, implementation может забыть его проверить.

- `3.6. Причина F`: concept conformance приходит слишком поздно, если plan не назвал production path.

- `P2. Stage Quality Rubric`, особенно questions about production entrypoint, AC proof, substrate-only false positive, and change-proposal trigger.

## Impact

- Work item может закрыть implementation на substrate evidence и не дать оператору наблюдаемого поведения.
- Automated tests могут пройти, но production renderer/main/preload/UI path не будет интегрирован.
- Falsifiers не проверяются, и негативные границы scope остаются только в prose.
- Capability claims могут выглядеть выполненными, хотя actual actor entrypoint не работает.

## Scope

Входит в scope:

- Обновить `Plan Slice` body contract для capability work, чтобы `Integration Path` и AC/evidence/falsifier matrix были обязательными.
- Для user-visible capability work требовать production entrypoint and runtime path.
- Для UI/editor/operator capabilities требовать at least one closure evidence through actual running application path.
- Добавить structural support for negative/falsifier acceptance criteria or an equivalent explicit falsifier linkage.
- Добавить minimal structured fields for live-app verification evidence.
- Зафиксировать границу Phase 1 vs Phase 3, чтобы не дублировать plan-section presence checks.
- Обновить verification contract/body expectations: before, action, after, continuity/save/retry where applicable.
- Требовать, чтобы testable anti-claims были represented as negative AC or falsifier before `spec-compact` close.
- Обновить runtime stage close checks, capability checks, lint/dedicated checks, references and tests.

Не входит в scope:

- Требовать live-app evidence для purely internal support work.
- Запрещать unit/mock/contract/headless tests как supporting evidence.
- Добавлять новую базу данных или отдельный evidence artifact type.
- Возвращать тяжёлый workflow с большим числом stage artifacts.
- Review noise policy; это Phase 4.
- Добавление новых обязательных artifact families. Prefer strengthening existing work item body contracts and existing verification/review artifacts over adding new mandatory artifact families.

## Proposed Resolution

1. Сделать `Integration Path` обязательным для user-visible capability work.

   Требуемая формулировка:

   ```md
   For user-visible capability work, the plan MUST name the production entrypoint and runtime path through which the capability will be observed.
   Implementation closure evidence must exercise that path, not only mocks, schemas, internal stores, or headless tools.
   ```

   Required fields in `Plan Slice`:

   ```markdown
   ### Integration path

   - Actor entrypoint:
   - Runtime path:
   - Production components touched:
   - UI/API/agent path:
   - State/effect path:
   - Continuity path:
   - What would prove this is integrated:
   - What would prove this is only substrate:
   ```

   User-visible default:

   ```md
   For `delivery.kind=capability`, assume user-visible/operator-visible unless the work item explicitly records `non-user-visible` rationale in the Plan Slice.
   ```

2. Добавить минимальную matrix:

   ```markdown
   | AC | Observable behavior | Implementation surface | Evidence method | Falsifier |
   |---|---|---|---|---|
   ```

   Matrix должна быть обязательной для capability work before `plan-slice` close. Она должна связывать каждый acceptance criterion с observable behavior, implementation surface, evidence method and falsifier.

3. Clarify Phase 1 / Phase 3 boundary.

   ```md
   Phase 1 introduces and validates the presence of `Integration Path` and `AC -> evidence` sections at plan-slice close.

   Phase 3 upgrades their semantics:
   - production entrypoint must be specific;
   - user-visible capability must have live-app closure evidence;
   - evidence must exercise the named production path;
   - testable anti-claims must become negative AC/falsifiers.
   ```

4. Усилить `behavioral-demo` для UI/editor/operator capabilities.

   Closure evidence должно явно содержать:

   - actual app entrypoint;
   - production path;
   - observed UI/app state before;
   - actor action;
   - observed UI/app state after;
   - continuity/save/retry path where relevant;
   - checked falsifiers showing evidence is not only mock/headless/schema/prompt substrate.

   Mock/headless/unit evidence can support closure but cannot be the only passing closure evidence for UI/editor/user-facing capability.

   Minimal structured support for `verify record` should not require a new artifact type. Preferred minimum:

   ```bash
   dossier-engineer verify record \
     --work <id> \
     --stage implementation \
     --profile behavioral-demo \
     --evidence-class live-app \
     --entrypoint "<actual app entrypoint>" \
     --runtime-path "<production path>" \
     --evidence <path>
   ```

   CLI flags use kebab-case. Stored frontmatter fields use snake_case:

   - `--evidence-class` -> `evidence_class`;
   - `--runtime-path` -> `runtime_path`.

   `before`, `action`, `after`, `continuity/save/retry` and checked falsifiers may remain body-contract fields in the verification artifact.

5. Превратить testable anti-claims в negative acceptance or falsifier.

   Rule:

   - If an anti-claim describes observable forbidden behavior, `spec-compact close` must require a negative AC or falsifier that can be checked.

   Preferred and Phase 3 target behavior: runtime supports both acceptance kinds: `negative` and `falsifier`.

   ```bash
   dossier-engineer work acceptance add --work <work-id> --kind negative --text "<forbidden observable behavior>"
   dossier-engineer work acceptance add --work <work-id> --kind falsifier --text "<condition that would prove the capability is not integrated>"
   ```

   Fallback explicit storage is acceptable only if implementation constraints make new acceptance kinds impractical, and it must still be machine-checkable. For example, runtime may define `demonstration.falsifiers` linked to AC IDs. Do not leave falsifiers only as unstructured prose.

   Example:

   Anti-claim:

   ```text
   Do not route ordinary human comments to Codex without explicit operator intent.
   ```

   Negative AC:

   ```text
   When an ordinary human comment is added without agent-authored thread context or explicit operator intent, the app must not route it to Codex.
   ```

6. Добавить stage quality rubric checks without new artifacts.

   `plan-slice` close should require answers to:

   - which production entrypoint is used;
   - which files/interfaces/components are touched;
   - how each AC is proven;
   - where substrate-only false positive may appear;
   - when change-proposal is required.

## Alternatives Considered

- Считать `behavioral-demo` достаточным без additional live-app class. Отклонено: analysis shows behavioral-demo can pass through substrate-only tests.
- Запретить mock/headless evidence. Отклонено: such evidence is useful as supporting verification; it is only insufficient as sole closure evidence for user-visible capability.
- Создать новый artifact type для integration proof. Отклонено: roadmap asks minimal model; existing work item and verification artifacts are enough.
- Оставить anti-claims only as scope boundaries. Отклонено: testable anti-claims are negative behavior requirements and must enter verification.

## Destructive Side Effects

- UI/editor capabilities станут сложнее закрывать. Mitigation: requirement applies to closure evidence, not every test; supporting automated tests remain allowed.
- Heuristic for "user-visible" may be ambiguous. Mitigation: default to requiring Integration Path for `delivery.kind: capability`; allow explicit non-user-visible rationale.
- Agents may write vague `Integration Path` boilerplate. Mitigation: stage close checks must reject missing actor entrypoint/runtime path and internal-API-only descriptions for user-visible scope.
- Negative AC extraction from anti-claims may produce over-testing. Mitigation: only testable, observable anti-claims must become negative AC/falsifier.

## Verification

Функциональная проверка должна включать runtime acceptance tests из анализа:

- `stage close --stage plan-slice` blocks if plan lacks integration path for user-visible capability.
- `stage close --stage plan-slice` blocks if AC-to-evidence matrix is absent.
- `stage close --stage implementation` blocks if behavioral-demo evidence does not declare actual app entrypoint for UI/editor capability.
- Testable anti-claim must be represented as negative AC or falsifier before spec close.
- `capability check` distinguishes support evidence from actual live-app behavioral evidence.
- For capability work with user-visible/operator-visible scope, mock/headless evidence may be recorded and may satisfy supporting verification, but mock/headless evidence alone must not satisfy implementation closure.
- `verify record --profile behavioral-demo --evidence-class live-app` requires at least structured `entrypoint` and `runtime_path`.
- CLI flags use kebab-case and stored frontmatter uses snake_case for live-app evidence fields: `--evidence-class` -> `evidence_class`, `--runtime-path` -> `runtime_path`.
- Capability work is treated as user-visible/operator-visible unless `Plan Slice` records an explicit `non-user-visible` rationale.
- Runtime supports `negative` and `falsifier` acceptance kinds as the Phase 3 target behavior, or documents a machine-checkable fallback only if new kinds are impractical.

Также проверить:

- unit/mock/headless evidence can still be recorded as supporting evidence;
- non-user-visible capability can close with explicit rationale and appropriate evidence;
- generated `SKILL.md` regenerated from source bundle, if active guidance changed;
- `scripts/dossier-engineer.mjs` rebuilt from `src/*`;
