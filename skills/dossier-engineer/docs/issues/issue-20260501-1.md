# Issue

## Language

Русский.

## Issue ID

`issue-20260501-1`

## Title

Сделать Phase 1: честный `queue`, содержательные `Spec Compact`/`Plan Slice` и терминальный handoff

## Skill

`dossier-engineer` (`skills/dossier-engineer`)

## Context

Анализ `docs/dossier-engineer-problem-analysis-and-proposals.ru.md` показал, что текущий `dossier-engineer` хорошо запрещает явный substrate-only closure на уровне принципов, но слабо защищает содержательность `spec-compact`, `plan-slice` и завершение lifecycle.

Phase 1 из roadmap должна дать быстрые исправления без возвращения тяжёлого старого workflow:

- заменить misleading `Ready work items` на honest actionable queue output;
- добавить обязательные body-блоки `Spec Compact` и `Plan Slice` в work item;
- закрывать `spec-compact` и `plan-slice` только при непустом, project-specific content;
- требовать current concept-conformance review до закрытия `plan-slice` для capability work;
- запретить handoff как "готово", пока `status` и `next` не показывают terminal state;
- исправить `next` для already-hygiened closed work.

## Problem

Текущий runtime и skill позволяют агенту пройти protocol surface без достаточного содержательного handoff-контракта:

- `queue` пишет `Ready work items`, хотя item может быть готов только к старту `feature-intake`, а не к implementation.
- `spec-compact` и `plan-slice` проверяются через presence checks: behavior AC, demo scenario, anti-claim, challenge. Это ловит пустоту, но не качество спецификации и плана.
- `stage close --stage plan-slice` фактически может пройти на одном challenge summary, хотя challenge отвечает "как план может быть неверным", а не "какой именно план выполняется".
- Stage event body может оставаться scaffold-only, а work item body перегружен ролями и не отделяет summary от spec/plan contracts.
- Implementation может быть сделан в коде, но dossier lifecycle остаётся `planned`/`implementation: in_progress`; handoff может выглядеть завершённым без terminal state.
- `next` может повторно предлагать hygiene для уже закрытого и hygiened work item.

Это substrate risk: можно получить артефакты и зелёный `lint`, но не получить реальную готовность к implementation или closure.

- `3.12. Причина L`: CLI specification and runtime implementation diverge.

Релевантные предложения:

- `P0. Сделать spec-compact и plan-slice ... обязательными body-блоками work item`.
- `P0. Перенести concept-conformance review на plan-slice`.
- `P1. Упростить terminal lifecycle`.

## Impact

- Агент и оператор могут принять "ready" за "implementation-ready".
- Weak spec/plan могут пройти `lint`, `status` и `capability check`.
- Work item может начать implementation без production path, sequence, surface и evidence mapping.
- Длинные сессии чаще заканчиваются lifecycle drift: код готов, dossier не закрыт.
- Generated reports или textual summaries могут выглядеть как готовность, хотя runtime truth state не terminal.

## Scope

Входит в scope:

- Обновить source bundle `skill.yaml`, `fragments/*`, активные `references/*` и generated `SKILL.md` через regeneration, если меняется активная инструкция.
- Обновить runtime в `src/*` и built artifact `scripts/dossier-engineer.mjs`.
- Изменить `queue` output semantics: `queue` показывает actionable next work, not implementation readiness.
- Добавить `Spec Compact` и `Plan Slice` в scaffold capability work item.
- Добавить stage close gates для непустого, non-placeholder `Spec Compact` и `Plan Slice`.
- Применить Body Completion Gate к `Spec Compact` и `Plan Slice`, включая operator-language requirement for semantic body content.
- Перенести mandatory concept-conformance review gate на `plan-slice close` для capability work.
- Обновить `review required --work <id>` или эквивалентный runtime output, чтобы required reviews могли показываться для `plan-slice`, не только для implementation.
- Добавить final/handoff terminal rule: нельзя говорить "готово" без implementation closure, hygiene pass, clean `status` и no actionable `queue` entry for the work item.
- Исправить `next`, чтобы already-hygiened closed work не получал повторный hygiene next action.
- Добавить короткую stage quality rubric в active guidance и, где уместно, в stage close blocker text.
- Обновить runtime tests.

Не входит в scope:

- Возврат полного старого тяжёлого workflow.
- Добавление отдельных stage dossiers как новых обязательных артефактов.
- Создание базы данных, global state snapshot, committed mutable index или canonical lock artifact.
- Решение write concurrency; это Phase 2.
- Полная integration evidence policy; это Phase 3.
- Review noise policy; это Phase 4.
- Добавление новых обязательных artifact families. Prefer strengthening existing work item body contracts and existing verification/review artifacts over adding new mandatory artifact families.

## Proposed Resolution

1. Изменить `queue` wording и grouping.

   Требуемая формулировка для active guidance:

   ```md
   `queue` shows actionable next work, not implementation readiness.
   A queued work item may be ready only to start the next protocol stage.
   The agent MUST inspect `next --work <id>` before treating any queued item as implementation-ready.
   ```

   Runtime output должен больше не использовать общий label `Ready work items`. Минимально достаточный формат должен явно показывать readiness type:

   ```text
   Next actionable work:
   - WI-... | next_action=start_stage | stage=feature-intake | implementation_ready=false
   - WI-... | next_action=close_stage | stage=plan-slice | implementation_ready=false
   - WI-... | next_action=start_stage | stage=implementation | implementation_ready=true
   ```

2. Усилить work item body как carrier для stage contracts.

   Capability work scaffold должен включать:

   ```markdown
   ## Spec Compact

   ### Behavior statement

   ### Acceptance criteria matrix

   ### Negative acceptance / falsifiers

   ### Anti-claims and non-goals

   ### Open questions and gaps

   ## Plan Slice

   ### Implementation target

   ### Integration path

   ### Files, interfaces, and components

   ### Sequence

   ### AC to evidence matrix

   ### Risks and fallback/change-proposal triggers
   ```

   Требуемая формулировка для `Spec Compact`:

   ```md
   Before `spec-compact` close, capability work MUST have a completed `Spec Compact` body section in the work item.
   It must include behavior statement, acceptance criteria matrix, negative/falsifier criteria, anti-claims, and open gaps.
   Frontmatter presence alone is not sufficient.
   ```

   Требуемая формулировка для `Plan Slice`:

   ```md
   Before `plan-slice` close, capability work MUST have a completed `Plan Slice` body section in the work item.
   It must include implementation target, integration path, files/interfaces/components, sequence, AC-to-evidence matrix, risks, and change-proposal triggers.
   A challenge alone is not a plan.
   ```

   Body Completion and language requirement:

   ```md
   Spec Compact and Plan Slice body sections are subject to the Body Completion Gate.
   They must be written in the operator's working language and must not remain empty, placeholder-only, template-only, or heading-only at stage close or handoff.
   Spec Compact and Plan Slice semantic body content MUST be written in the operator's working language. Protocol keys, CLI commands, enum values and file paths remain in English.
   ```

3. Закрытие `spec-compact` и `plan-slice` должно блокироваться при scaffold-only content.

   Минимальные runtime checks:

   - section exists;
   - section is not empty;
   - section is not placeholder-only, TODO-only, or repeated template headings only;
   - required subsections have at least one project-specific bullet, row, or paragraph;
   - `Plan Slice` contains at least one concrete file/interface/component, or explicitly states `non-code` with rationale.

   Because Phase 1 already introduces `Integration path` and `AC to evidence matrix` into the `Plan Slice` body contract, it must also enforce their presence at plan close. Full closure evidence semantics remain Phase 3, but the plan must already name the user-visible production path.

   Required wording from the integration proposal:

   ```md
   For user-visible capability work, the plan MUST name the production entrypoint and runtime path through which the capability will be observed.
   Implementation closure evidence must exercise that path, not only mocks, schemas, internal stores, or headless tools.
   ```

   Phase 1 should enforce the first sentence at `plan-slice close` and document the second sentence as the upcoming closure-evidence rule completed by Phase 3.

4. Для capability work `plan-slice close` должен требовать current PASS `concept-conformance-reviewer`.

   For Phase 1, `stage close --stage plan-slice` must block capability work unless a current PASS `concept-conformance-reviewer` review is recorded for `plan-slice`.

   Implementation start must therefore be impossible unless the plan-slice concept gate has already passed. Phase 4 уточнит freshness/re-review noise policy.

5. Сделать terminal handoff rule явным и enforceable in guidance.

   Требуемая формулировка:

   ```md
   A work item is not handoff-complete until implementation closure and post-close hygiene both pass, status has no closure violations, and queue no longer presents the work item as actionable.
   ```

   Terminal lifecycle model must be explicit:

   ```md
   Implementation stage close produces `lifecycle=implemented`.
   It is not terminal handoff completion.
   Successful post-close hygiene is the terminal handoff gate and sets the work item to closed/handoff-complete state.
   ```

   Нельзя, чтобы handoff выглядел завершённым после одного textual close.

6. Исправить `next` для closed/hygiene state.

   Если `post_close_hygiene.implementation: closed` и lifecycle terminal, `next` должен показывать отсутствие required next action или только optional changeset/report hint, но не повторный `hygiene run`.

   Runtime test contract:

   ```md
   If lifecycle is closed and post_close_hygiene.implementation is closed/pass, `next --work <id>` returns no required next action.
   It may return optional changeset/report hints only.
   ```

7. Обновить required-review flow для `plan-slice`.

   Runtime help/next output should support stage-specific required review guidance:

   ```bash
   dossier-engineer review required --work <work-id> --stage plan-slice
   dossier-engineer review required --work <work-id> --stage implementation
   ```

   If the exact command surface is different, `next` and `stage close` blocker output must still print the exact `review record --stage plan-slice` command needed to satisfy the gate.

8. Добавить short Stage Quality Rubric без новых артефактов.

   `spec-compact` close должен заставлять ответить:

   - какое observable behavior создаётся или меняется;
   - какие positive AC доказывают поведение;
   - какие negative AC/falsifiers предотвращают самообман;
   - какие anti-claims ограничивают scope;
   - какие implied expectations учтены;
   - какие gaps остаются.

   `plan-slice` close должен заставлять ответить:

   - какой production entrypoint задействован;
   - какие files/interfaces/components изменяются;
   - какая sequence implementation steps;
   - как каждый AC будет доказан;
   - где возможен substrate-only false positive;
   - когда нужен change-proposal.

## Alternatives Considered

- Вернуть полный старый workflow с большим числом stage artifacts. Отклонено: анализ прямо требует не возвращать тяжёлый протокол; проблема находится в нескольких слабых gates.
- Сделать stage event body главным stage contract. Отклонено для Phase 1: предпочтителен вариант A из анализа, где stage events остаются events, а содержательный spec/plan живёт в одном work item.
- Оставить `queue` как есть и обучить агента помнить `next`. Отклонено: анализ показывает, что нельзя полагаться только на память агента; runtime signal должен быть честным.
- Добавить новую команду вместо изменения `queue`. Отклонено: minimal roadmap просит не плодить новую модель, а изменить label/grouping существующей команды.

## Destructive Side Effects

- Более строгие stage close gates могут заблокировать существующие work items с бедным body. Mitigation: добавить понятные blocker messages и recovery path через manual body edit + lint.
- Template section checks могут породить формальное заполнение. Mitigation: требовать project-specific content, matrix row/bullet и concrete file/interface/component or explicit non-code rationale.
- Concept-conformance before plan-slice может добавить ранний review overhead. Mitigation: Phase 4 должна переиспользовать fresh review на implementation closure и не требовать повторный review без material scope change.
- Изменение `queue` output может сломать snapshot tests или операторские привычки. Mitigation: tests должны проверять новый contract; docs/help должны явно описать `Actionable work items`.

## Verification

Функциональная проверка должна включать runtime acceptance tests из анализа:

- `queue` does not label `feature-intake:not_started` items as implementation-ready.
- `stage close --stage spec-compact` blocks if `Spec Compact` body section is missing/placeholder.
- `stage close --stage plan-slice` blocks if `Plan Slice` body section is missing/placeholder.
- `stage close --stage spec-compact` blocks when `Spec Compact` body is heading-only, placeholder-only, or copied template text.
- `stage close --stage plan-slice` blocks when `Plan Slice` body is heading-only, placeholder-only, or copied template text.
- Body content is written in the operator's working language while protocol keys, enum values, CLI commands and paths remain in English.
- `stage close --stage plan-slice` blocks capability work unless a current PASS `concept-conformance-reviewer` review is recorded for `plan-slice`.
- `stage close --stage plan-slice` blocks if plan lacks integration path for user-visible capability.
- `stage close --stage plan-slice` blocks if AC-to-evidence matrix is absent.
- `stage close --stage implementation` sets lifecycle to `implemented` and does not mark the work item handoff-complete.
- After successful `hygiene run`, the work item becomes terminal closed/handoff-complete.
- `next --work <id>` reports hygiene exactly once after implementation close and does not report hygiene again after successful hygiene.
- Already hygiened closed work returns no hygiene next action.
- If lifecycle is closed and `post_close_hygiene.implementation` is closed/pass, `next --work <id>` returns no required next action and only optional changeset/report hints.
- `lint` or dedicated stage close check detects scaffold-only stage/spec/plan sections.
- `review required --work <id> --stage plan-slice` or equivalent blocker output reports the required concept-conformance review before `plan-slice close`.
