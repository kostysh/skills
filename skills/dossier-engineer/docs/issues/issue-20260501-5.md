# Issue

## Language

Русский.

## Issue ID

`issue-20260501-5`

## Title

Сделать required audits независимыми external reviewer agent checks

## Skill

`dossier-engineer` (`skills/dossier-engineer`)

## Context

`dossier-engineer` уже использует review/audit gates: `concept-conformance-reviewer`, `spec-conformance-reviewer`, `code-reviewer`, `security-reviewer` and related review classes. Phase 1 переносит concept-conformance на `plan-slice`, Phase 3 усиливает integration/live-app evidence, Phase 4 уточняет freshness and consolidated review policy.

Однако сама модель исполнения review остаётся недостаточно жёсткой: агент-разработчик может подготовить, выполнить и записать review в одном и том же агентском контексте. Это снижает ценность audit gates, особенно для проблем, ради которых создавался `dossier-engineer`:

- substrate/infrastructure masquerade;
- weak spec/plan;
- отсутствие реальной интеграции в действующее приложение;
- stale review reuse;
- self-confirming implementation closure.

Среда разработки поддерживает spawning independent agents. Поэтому required audits должны выполняться независимыми внешними reviewer agents, а implementing agent должен только подготовить bounded review packet, запросить review, записать неизменённый verdict/findings и исправить найденные проблемы.

## Problem

Текущий review protocol может создать иллюзию независимого контроля, но фактически допустить self-review:

- implementing agent может сам выдать PASS по своему work item;
- review может выполняться в том же conversation/thread/context, где агент только что реализовал изменение;
- PASS может быть основан на summary разработчика, а не на bounded packet with artifacts/evidence;
- FAIL/BLOCKED findings могут быть перефразированы, ослаблены или скрыты при записи;
- closure может принять review artifact с `verdict=PASS`, не проверяя provenance and independence;
- concept-conformance review может стать формальностью, если его делает тот же агент, который сформулировал слабый plan;
- consolidated review policy из Phase 4 может снизить noise, но без external provenance не даст настоящего независимого сигнала.

В результате `dossier-engineer` может иметь правильные gates на бумаге, но audit signal останется self-confirming.

## Evidence

Основания из текущего анализа и roadmap:

- `issue-20260501-1`: concept-conformance review становится обязательным до `plan-slice close` для capability work. Этот gate особенно нуждается в независимом reviewer, иначе агент сам подтверждает собственный plan.
- `issue-20260501-3`: live-app evidence и integration path должны защищать от implementation без интеграции. Внешний reviewer лучше проверяет, что evidence действительно exercises production path.
- `issue-20260501-4`: consolidated review is timing/scope policy, not a new review class. Для сохранения качества consolidated bundle должен быть fresh and independently reviewed.
- Наблюдение оператора: Codex умеет spawning agents, и independent external audits должны быть полезнее самопроверки implementing agent.
- Общий failure mode: агент может убедительно закрывать собственную работу, пропуская слабые места, которые внешний reviewer заметил бы лучше.

## Impact

Без external review execution model:

- review artifacts могут пройти formal closure, но не повысить доверие;
- concept-conformance может подтверждать слабую спецификацию вместо исправления drift;
- code/security/spec reviews могут быть biased by implementer context;
- FAIL findings могут не сохраняться как immutable audit history;
- operator видит `PASS`, но не знает, был ли PASS независимым;
- Phase 1/3/4 improvements дают меньший эффект, потому что final review signal остаётся self-authored.

## Scope

Входит в scope:

- Обновить active skill guidance, source bundle fragments, references and regenerated `SKILL.md` where applicable.
- Обновить review/audit policy так, чтобы required review gates satisfied only by eligible independent external reviews.
- Определить роли: implementing agent, reviewer agent, operator.
- Ввести bounded review packet contract for external reviewer agents.
- Расширить review artifact/provenance model: reviewer kind, reviewer identity, launch mode, isolation level, implementer identity, packet/scope reference, raw findings/report reference.
- Обновить closure eligibility: required review PASS eligible only if external independence and freshness are valid.
- Обновить runtime commands/help where needed:
  - generate/print review packet;
  - record review with provenance;
  - report required reviews with external-review expectation;
  - block closure on ineligible self/same-thread/unknown provenance for required reviews.
- Разрешить one external reviewer agent to cover multiple review classes only if verdict/findings are separated by class.
- Preserve immutable FAIL/BLOCKED attempts.
- Update tests.

Не входит в scope:

- Добавление новой обязательной delivery stage.
- Возврат тяжёлого старого workflow.
- Требование отдельного reviewer process for every tiny micro-fix; Phase 4 consolidated review policy still applies.
- Требование всегда использовать три разных reviewer agents для spec/code/security; one external reviewer may cover multiple classes if output is separated and eligible.
- Автоматическое исправление code/dossier reviewer agent-ом. Reviewer agents are read-only.
- Создание базы данных, global review registry, committed mutable review index, or new heavy artifact family.
- Замена required review classes одним новым `external-review` class.
- Полная orchestration implementation for spawning agents if environment integration is unavailable; skill/runtime must at least support packet/provenance/eligibility.

## Proposed Resolution

1. Add active guidance: required audits are external.

   ```md
   Required review gates are satisfied only by eligible independent reviews.

   The implementing agent MUST NOT author required PASS review verdicts for its own work.
   It prepares a bounded review packet and requests a spawned, operator-provided,
   or manual external reviewer agent.

   The reviewer agent is read-only. It reviews the packet and returns a verdict:
   PASS, FAIL, or BLOCKED, with findings and rationale.

   The implementing agent records the returned review result without rewriting the
   verdict, hiding findings, or converting FAIL/BLOCKED into PASS.
   ```

2. Define roles.

   ```md
   Implementing agent:
   - performs implementation and dossier maintenance;
   - prepares review packet;
   - requests external review;
   - records returned review artifact;
   - applies fixes after FAIL/BLOCKED.

   Reviewer agent:
   - receives bounded packet or readonly repository context;
   - does not modify code, dossier artifacts, runtime state, or review packet;
   - returns verdict, findings, rationale, and reviewed scope.

   Operator:
   - may spawn/provide reviewer agents;
   - may resolve disputed findings;
   - must not manually convert FAIL into PASS.
   ```

3. Define eligible independent review.

   Eligible for required closure gates:

   - reviewer is not the implementing agent;
   - `launch_mode` is `spawned`, `operator-provided`, or `manual-external`;
   - `isolation_level` is `bounded-packet` or `repository-readonly`;
   - reviewer has read-only role for reviewed scope;
   - review artifact records reviewer identity and implementer identity;
   - verdict/finding text is preserved from reviewer output;
   - review is fresh for current material scope hash;
   - review class matches required gate.

   Not eligible for required closure gates:

   - `self-review`;
   - `same-thread`;
   - `unknown` launch mode;
   - same agent as implementer;
   - review based only on implementer summary without artifacts/evidence;
   - reviewer modified the implementation while reviewing;
   - reviewer output was rewritten materially before recording.

4. Add bounded review packet contract.

   Runtime should provide a command or derived output:

   ```bash
   dossier-engineer review packet \
     --work <WI-id> \
     --stage <stage> \
     --class <review-class>
   ```

   The packet is derived, not canonical truth. It may be printed to stdout or saved under a non-canonical generated location.

   Minimum packet content:

   - work item ID and title;
   - stage;
   - review class;
   - operator language;
   - source refs and relevant source excerpts/paths;
   - capability claim;
   - anti-claims;
   - acceptance criteria, including negative/falsifier criteria;
   - `Spec Compact` material sections;
   - `Plan Slice` material sections;
   - integration path;
   - AC/evidence/falsifier matrix;
   - live-app evidence obligations where applicable;
   - changed files or implementation surface;
   - verification artifacts;
   - demo artifacts;
   - known gaps/blockers;
   - material scope hash;
   - explicit review questions for the class.

5. Define review class prompts/checklists.

   `concept-conformance-reviewer` must check:

   - capability advances project concept;
   - work is not infrastructure masquerading as feature;
   - observable behavior is clear;
   - anti-claims are honest and not hiding the main expected capability;
   - demo scenario can falsify false completion;
   - integration path is concrete;
   - core value is not deferred to unspecified future work.

   `spec-conformance-reviewer` must check:

   - implementation matches acceptance criteria;
   - negative/falsifier criteria are respected;
   - anti-claims are not violated;
   - source requirements are still represented;
   - change-proposal exists when scope/source interpretation changed.

   `code-reviewer` must check:

   - correctness;
   - integration with existing app;
   - maintainability;
   - edge cases;
   - error handling;
   - regression risk;
   - lifecycle/status consistency.

   `security-reviewer` must check:

   - authentication/authorization;
   - data exposure;
   - secrets;
   - input handling;
   - persistence safety;
   - external integrations;
   - runtime boundaries;
   - fail-closed behavior.

6. Extend review artifact provenance.

   Review artifacts should record at least:

   ```yaml
   reviewer_kind: external-agent
   reviewer_id: codex-reviewer-20260501-a
   implementer_id: codex-implementer-20260501-b
   launch_mode: spawned
   isolation_level: bounded-packet
   readonly: true
   packet_hash: sha256:...
   material_scope_hash: sha256:...
   raw_report_ref: docs/dossier/reviews/.../raw-report.md
   verdict: PASS
   ```

   CLI flags may use kebab-case while frontmatter uses snake_case:

   ```bash
   --reviewer-kind external-agent
   --reviewer-id <id>
   --implementer-id <id>
   --launch-mode spawned
   --isolation-level bounded-packet
   --packet-hash <hash>
   --report <path>
   ```

7. Closure eligibility update.

   Required review gate passes only when review artifact is:

   - required class;
   - verdict PASS;
   - fresh for material scope;
   - independent/eligible;
   - not superseded by later material change;
   - not invalidated;
   - preserving reviewer findings.

   Ineligible review artifacts may remain in history but must not satisfy closure.

8. Multiple review classes by one external agent.

   Allow one external reviewer agent to cover multiple review classes only if output has separate sections and verdicts:

   ```text
   concept-conformance: PASS/FAIL/BLOCKED
   spec-conformance: PASS/FAIL/BLOCKED
   code: PASS/FAIL/BLOCKED
   security: PASS/FAIL/BLOCKED
   ```

   Runtime may record them as separate review artifacts or as one multi-class artifact only if closure can validate each required class independently.

   Consolidation must not replace required review classes.

9. FAIL/BLOCKED attempts are immutable.

   Required guidance:

   ```md
   FAIL and BLOCKED external review attempts MUST be recorded and preserved.
   The implementing agent may fix findings and request a new external review, but
   must not delete, rewrite, or hide failed attempts.
   ```

10. External review workflow.

    Required operational sequence:

    ```text
    implementation or plan reaches review point
    -> implementing agent generates review packet
    -> external reviewer agent reviews packet read-only
    -> reviewer returns verdict/findings
    -> implementing agent records review artifact with provenance
    -> if FAIL/BLOCKED: implementer fixes and repeats review
    -> if PASS and fresh: closure may use review
    ```

11. Runtime output and next actions.

    `review required`, `next`, and failed `stage close` output should identify when an external review is required:

    ```text
    Missing required eligible external review:
    - class: concept-conformance-reviewer
    - stage: plan-slice
    - required launch_mode: spawned|operator-provided|manual-external
    - required isolation_level: bounded-packet|repository-readonly

    Next actions:
    1. Run: dossier-engineer review packet --work WI-... --stage plan-slice --class concept-conformance-reviewer
    2. Spawn external reviewer agent with the packet.
    3. Record returned review with: dossier-engineer review record ...
    ```

12. Interaction with existing phases.

    - Phase 1: `plan-slice close` requires fresh eligible external concept-conformance review for capability work.
    - Phase 3: implementation closure requires external review to consider live-app evidence where applicable.
    - Phase 4: consolidated review remains timing/scope policy. Required classes still need fresh eligible external PASS artifacts.
    - Phase 2: review record and review packet writes follow mutation envelope/write-lock rules where they write files.

## Alternatives Considered

- Allow implementing agent self-review. Отклонено: this preserves self-confirming closure and weakens audit gates.
- Require operator to manually perform every review. Отклонено: too much operator burden; spawned agents should handle routine audit when available.
- Require a separate reviewer agent for every required class. Частично отклонено: safer but more expensive; one external reviewer can cover multiple classes if verdicts/findings are separated.
- Add a new delivery stage for external review. Отклонено: adds process weight; existing review gates are enough if execution/provenance is fixed.
- Add a new canonical review packet artifact family. Отклонено for Phase 5: packet can be derived/generated; review artifact remains canonical.
- Treat any PASS review as valid if class matches. Отклонено: provenance and freshness are required for meaningful audit.
- Let reviewer agents modify code while reviewing. Отклонено: this blurs reviewer/implementer roles and breaks independence.

## Destructive Side Effects

- More overhead for required reviews. Mitigation: only required gates need eligible external reviews; Phase 4 consolidated review reduces micro-fix review churn.
- Reviewer spawning may be unavailable in some environments. Mitigation: allow `operator-provided` and `manual-external` launch modes; if none available, closure should report missing eligible review rather than self-pass.
- One external reviewer covering multiple classes may be shallow. Mitigation: require separate verdict/findings per class and allow stricter project policy later.
- Review packet may omit important context. Mitigation: packet contract includes material scope, evidence, sources, AC/falsifiers, integration path, and explicit class questions.
- Raw reviewer findings may contain noisy or imperfect text. Mitigation: preserve raw findings or report reference; implementer may add summary but not rewrite verdict/findings materially.
- Runtime may misclassify eligible provenance. Mitigation: explicit enums for reviewer kind, launch mode, isolation level, readonly status, implementer identity, material scope hash.
- Additional CLI fields may make `review record` longer. Mitigation: use sensible defaults only when safe; do not default to eligible external review without explicit provenance.

## Verification

Functional tests and acceptance checks should include:

- `stage close --stage plan-slice` blocks capability work when concept-conformance review is missing.
- `stage close --stage plan-slice` blocks when concept-conformance review exists but `launch_mode=self-review` or `same-thread`.
- `stage close --stage plan-slice` accepts fresh PASS concept-conformance review with eligible external provenance.
- Implementation closure blocks when required spec/code/security review artifacts are PASS but ineligible due to self/same-thread/unknown provenance.
- Implementation closure accepts required review bundle when each required class has fresh eligible external PASS artifact.
- Review artifact with FAIL remains visible and is not overwritten by later PASS.
- A later PASS review supersedes earlier FAIL only when fresh and eligible.
- `review packet --work <id> --stage <stage> --class <class>` includes capability claim, anti-claims, ACs, negative/falsifier criteria, Spec Compact, Plan Slice, integration path, evidence/demo refs, material scope hash, and class-specific review questions.
- `review required --work <id> --stage plan-slice` reports external concept-conformance review requirement.
- `review required --work <id> --stage implementation` reports required external review classes and acceptable provenance.
- One external reviewer covering multiple classes is accepted only if each class has distinct verdict/findings and closure can validate classes independently.
- Review becomes stale when material scope hash changes after packet/review.
- Review becomes stale when demo scenario or falsifier set changes.
- Reviewer artifact with `readonly=false` or missing isolation metadata does not satisfy required closure gate.
- Ineligible review artifacts remain in history but are not selected for closure.
- Runtime/help text instructs implementing agent to spawn or request external reviewer rather than self-review.

Also verify non-regression:

- Non-required advisory self-review can still be recorded as non-eligible history if project wants it.
- Existing review artifacts without provenance are reported as ineligible for new required gates unless migration/compatibility policy explicitly marks them accepted.
- Phase 4 micro-fix consolidation still works: note-only micro-fixes do not require full review until consolidated closure review, unless material trigger fires.
- No new mandatory artifact family is required beyond existing review artifacts and derived review packets.
