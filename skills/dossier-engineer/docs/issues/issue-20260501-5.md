# Issue

## Language

Русский.

## Issue ID

`issue-20260501-5`

## Title

Required audits must be executed by fresh independent reviewer agents spawned by the implementing agent

## Skill

`dossier-engineer` (`skills/dossier-engineer`)

## Context

`dossier-engineer` relies on review/audit gates to prevent false completion:

- `concept-conformance-reviewer` protects the product concept and prevents infrastructure masquerading as capability;
- `spec-conformance-reviewer` checks that implementation matches normative requirements, specifications, contracts, ADRs, tickets, and acceptance criteria;
- `code-reviewer` checks code correctness, maintainability, integration, regressions, and implementation quality;
- `security-reviewer` checks security-sensitive behavior, vulnerabilities, permission boundaries, secrets, workflows, webhooks, configuration, and runtime boundaries.

The current and planned improvements strengthen stage gates, live-app evidence, review freshness, and material scope tracking. However, those gates remain weaker than intended if the implementing agent can satisfy required reviews by reviewing its own work or by continuing the same implementation context.

The environment can spawn additional agents. Required audits should therefore be executed by fresh independent reviewer agents spawned by the implementing agent at the moment an audit gate is reached.

Important clarification:

- the operator does not normally launch audits;
- the operator does not choose reviewers during normal workflow;
- the operator does not author, approve, override, or waive audit verdicts;
- the operator's only standard audit-related role is granting permission to spawn reviewer agents when the execution environment requires explicit permission for agent spawning.

## Problem

The existing review model can still allow self-confirming audit behavior:

- the implementing agent may author a required PASS verdict for its own work;
- review may run in the same conversation/session/thread that produced the implementation;
- a reviewer may inherit or fork the implementing session context instead of receiving a bounded review packet;
- PASS may be based on the implementer's summary instead of source, dossier artifacts, evidence, demos, and changed files;
- FAIL/BLOCKED findings may be softened, rewritten, hidden, or omitted when recorded;
- closure may accept a review artifact because it says `PASS`, without validating independence provenance;
- concept-conformance review can become meaningless if the same agent that wrote a weak plan also approves it;
- consolidated review can reduce noise but still be self-confirming without independent execution;
- the implementing agent may not know which reviewer role is required for the actual change type;
- after one review class fails and another passes, the implementing agent may rerun either too few audits or all audits unnecessarily because rerun rules are not explicit.

This is especially harmful for the known `dossier-engineer` failure modes:

- weak `spec-compact` and `plan-slice` artifacts;
- infrastructure mistaken for product capability;
- implementation not integrated into the actual app;
- stale or overly broad review reuse;
- completed work items whose lifecycle/status/evidence are internally inconsistent.

## Evidence

Relevant surrounding issues and findings:

- `issue-20260501-1`: `plan-slice` for capability work requires current PASS `concept-conformance-reviewer`. This gate must be independent; otherwise the implementing agent validates its own concept alignment.
- `issue-20260501-3`: implementation closure requires live-app/integration evidence. External reviewers are better positioned to challenge whether the evidence exercises the real production path.
- `issue-20260501-4`: consolidated review is timing/scope policy, not a replacement for required review classes. Freshness and material scope hash are only useful if the review signal is independent.
- Operational observation: Codex can spawn agents. Required audits can be performed by fresh external reviewer agents instead of same-thread self-review.
- Safety observation: due to execution-environment policy, the implementing agent may need operator permission before spawning reviewer agents. This permission is not an audit verdict and is not normal review participation.

## Impact

Without a required external reviewer execution model and reviewer-role selection matrix:

- review artifacts can satisfy formal closure while adding little real assurance;
- `concept-conformance` can approve a weak plan instead of catching concept drift;
- `spec/code/security` reviews can inherit the implementing agent's assumptions and miss integration gaps;
- implementing agents may skip required code/security reviews after code changes;
- implementing agents may rerun reviews that are still fresh, increasing overhead and review noise;
- operator sees `PASS` but cannot tell whether the audit was independent or whether the right reviewer role was used;
- FAIL/BLOCKED attempts can disappear from the dossier history;
- Phase 1/3/4 improvements become less effective because final audit remains self-authored or mismatched to the change type;
- agents learn that review gates are paperwork rather than an actual second opinion.

## Proposed Resolution

### 1. Default audit policy: implementing agent launches required audits

Required review gates are executed by fresh independent reviewer agents.

The implementing agent MUST NOT author required PASS review verdicts for its own work.

When a required audit gate is reached, the implementing agent MUST:

1. determine required reviewer roles using the auditor-role selection matrix;
2. prepare a bounded review packet for each required role or a combined packet with role-specific sections;
3. spawn a fresh independent reviewer agent with the required reviewer role;
4. ensure the reviewer agent does not inherit or fork the current implementation session context;
5. pass only the bounded review packet and allowed readonly repository context;
6. receive PASS, FAIL, or BLOCKED verdict with findings and rationale;
7. record the reviewer result without rewriting verdict or hiding findings;
8. fix issues after FAIL/BLOCKED;
9. rerun only the failed review class and any previously PASS review classes whose scope was materially affected by the fix.

Required audit gates are not satisfied by same-thread review, self-review, or unverifiable internal reasoning.

### 2. Operator role: spawn permission boundary only

The operator is not part of normal audit execution.

The operator's only standard audit-related role is to grant or deny permission for the implementing agent to spawn reviewer agents when the execution environment requires explicit permission for agent spawning.

The operator does not normally:

- launch audits manually;
- select reviewers;
- decide which audit class is required;
- author review verdicts;
- approve PASS results;
- convert FAIL/BLOCKED into PASS;
- waive required audit gates;
- edit review findings.

If reviewer spawning is blocked by execution-environment policy, the implementing agent stops at the audit gate and asks for spawn permission.

Required request format:

```text
Required external audit is blocked because spawning reviewer agents requires operator permission.

Requested permission:
- spawn a fresh independent reviewer agent;
- reviewer role: <review-class>;
- context mode: bounded review packet;
- no fork or inheritance of the current implementation session context;
- reviewer is read-only and will return PASS/FAIL/BLOCKED with findings.

After permission is granted, the implementing agent will run the external audit and record the result.
```

Permission to spawn is not permission to pass the audit. It only allows the implementing agent to launch the reviewer.

### 3. Requirements clarification is not audit override

If the reviewer returns BLOCKED because the review packet is incomplete, the implementing agent fixes the packet and reruns the audit.

If the reviewer returns BLOCKED because a product/domain decision is missing, the implementing agent may ask the operator for the missing requirement decision.

That operator response is a requirements clarification, not an audit override. After clarification, the implementing agent updates the dossier as needed and reruns the external review.

### 4. Reviewer agent isolation

A required reviewer agent MUST be fresh and independent.

Required properties:

- launched as a fresh agent/session;
- no fork of the implementing agent's current conversation/session context;
- no inherited hidden scratchpad or private reasoning from the implementing session;
- receives bounded review packet;
- may receive readonly repository context if allowed;
- read-only role;
- does not modify code, dossier artifacts, runtime state, review packets, or stage status;
- returns verdict, findings, rationale, and reviewed scope.

Not acceptable for required gates:

- same-thread review;
- self-review;
- reviewer spawned by forking current implementation context;
- reviewer with write access to reviewed artifacts during review;
- reviewer that only sees implementer's summary without packet/evidence;
- unknown launch mode;
- unknown isolation level.

### 5. Auditor-role selection matrix

The implementing agent MUST select reviewer roles from the actual work performed, not from the agent's intuition.

Runtime/help output SHOULD provide an explicit `review required --work <id> --stage <stage>` result that lists required review classes and reasons.

#### Reviewer role definitions

`concept-conformance-reviewer`:

Review feature ideas, backlog/work items, specifications, plans, acceptance criteria, or implementations against a higher-level product or system concept. Use when a task may create infrastructure, mocks, metadata, wrappers, tests, or documentation that looks like progress but does not deliver the claimed observable capability; when separating capability from substrate; when checking whether acceptance criteria can be satisfied without real behavior; or before implementing complex agent, runtime, platform, self-development, cognition, workflow, or product features whose wording may drift from the original concept.

`spec-conformance-reviewer`:

Review code and implementation evidence against normative requirements from specs, contracts, ADRs, tickets, sources, and acceptance criteria. Use when checking whether an implementation matches a specification, API contract, PRD, RFC, migration requirement, negative/falsifier criteria, or when producing a requirement-to-code traceability matrix and implementation-versus-spec verdict.

`code-reviewer`:

Systematic code review for pull requests, diffs, and local branch changes. Use for code, tests, build logic, runtime logic, application integration, maintainability, correctness, regressions, edge cases, lifecycle consistency, and high-signal implementation feedback.

`security-reviewer`:

Systematic security review for vulnerabilities in application code, CI workflows, permission models, webhooks, secrets, configuration, auth, RLS, OWASP-style risks, persistence boundaries, external integrations, fail-closed behavior, and runtime/security-sensitive configuration.

#### Required reviewer matrix

| Change / stage condition | Required reviewer roles | Reason |
| --- | --- | --- |
| New capability, changed capability claim, changed concept interpretation, changed observable behavior, changed delivery kind, changed `Spec Compact`, changed `Plan Slice`, changed integration path, changed demo scenario, changed falsifier set, or high concept-drift risk | `concept-conformance-reviewer` | Prevent infrastructure/substrate from masquerading as capability and ensure the slice advances the concept. |
| `plan-slice` close for capability work | `concept-conformance-reviewer` | Implementation must not start until the plan has external concept conformance. |
| Implementation closure for capability, support, maintenance, or fix work with normative requirements or acceptance criteria | `spec-conformance-reviewer` | Verify implementation against sources, spec, AC, negative criteria, falsifiers, and anti-claims. |
| Any code-bearing change, including application code, runtime code, tests, build scripts, CI logic, configuration that affects execution, integration glue, or generated runtime script changes | `code-reviewer` | Check correctness, maintainability, regressions, edge cases, and integration quality. |
| Any code-bearing change | `security-reviewer` | Security risks may appear even in ordinary code; required security audit is the safe default for code changes. |
| Any change touching auth/authz, permissions, user data, persistence, external input, webhooks, secrets, encryption, CI permissions, package/scripts, release/deploy workflow, sandboxing, policy/admission, runtime boundary, IPC, plugin/tool execution, or configuration with security impact | `security-reviewer` | Security-sensitive surface requires explicit threat/vulnerability review even if change is not typical product code. |
| Pure documentation/source/dossier text change with no capability/spec/plan/evidence/security implication | No required external reviewer by default; optional advisory review may be recorded | Avoid review noise for non-material text-only changes. |
| Source-only change that changes requirements, concept, acceptance criteria, or scope | `concept-conformance-reviewer` and/or `spec-conformance-reviewer` depending on affected material | Source interpretation can invalidate concept and/or implementation conformance. |
| Source-only formatting or typo change with explicit source-review `no_change` verdict | No required external reviewer by default | Avoid review noise for non-material source updates. |
| Change-proposal accepted for concept/capability/scope/spec/plan | `concept-conformance-reviewer`; add `spec-conformance-reviewer` if requirements/AC/spec changed | Accepted changes may invalidate planning and implementation conformance. |
| Live-app evidence path, production entrypoint, or runtime path changed | `concept-conformance-reviewer`, `spec-conformance-reviewer`; add `code-reviewer`/`security-reviewer` if code changed | Integration proof and scope changed. |
| Security fix after failed security review | `security-reviewer`; also rerun `code-reviewer` if code changed; rerun `spec-conformance-reviewer` only if behavior/spec/contract/AC changed | Rerun affected scopes, not all scopes blindly. |
| Micro-fix inside same material scope and trust boundary with no code change | No new full review required; record note per Phase 4 | Avoid micro-fix review noise. |
| Micro-fix with code change but same spec/concept/security posture | `code-reviewer`; `security-reviewer` if production code/config/runtime behavior changed | Code review scope changed; security review may be affected by code/config changes. |

Conservative default:

- if code changed, require `code-reviewer` and `security-reviewer`;
- if spec/AC/contract changed, require `spec-conformance-reviewer`;
- if capability/concept/plan/demo/falsifier/integration path changed, require `concept-conformance-reviewer`;
- if unsure whether a role is required, include the reviewer role and record the reason.

### 6. Review class prompts/checklists

`concept-conformance-reviewer` checks:

- capability advances the project concept;
- work is not infrastructure masquerading as feature;
- observable behavior is clear;
- anti-claims are honest and do not hide the main expected capability;
- demo scenario can falsify false completion;
- integration path is concrete;
- core user/operator value is not deferred to unspecified future work.

`spec-conformance-reviewer` checks:

- implementation matches acceptance criteria;
- negative/falsifier criteria are respected;
- anti-claims are not violated;
- source requirements are represented;
- change-proposal exists when source/scope interpretation changed;
- evidence maps to ACs and falsifiers.

`code-reviewer` checks:

- correctness;
- maintainability;
- integration with existing app;
- edge cases;
- error handling;
- regression risk;
- lifecycle/status consistency.

`security-reviewer` checks:

- authentication/authorization;
- data exposure;
- secrets;
- input handling;
- persistence safety;
- external integrations;
- runtime boundaries;
- fail-closed behavior.

### 7. Bounded review packet contract

The implementing agent prepares a bounded review packet before spawning the reviewer.

Runtime should provide a command or derived output:

```bash
dossier-engineer review packet \
  --work <WI-id> \
  --stage <stage> \
  --class <review-class>
```

The packet is derived review context, not canonical truth. It may be printed to stdout or saved under a generated non-canonical location.

Minimum packet content:

- work item ID and title;
- stage;
- review class;
- operator language;
- reviewer instructions for that class;
- reason why this reviewer role is required;
- source refs and relevant source paths/excerpts;
- capability refs and capability claim;
- anti-claims;
- acceptance criteria, including `negative` and `falsifier` criteria;
- `Spec Compact` material sections;
- `Plan Slice` material sections;
- integration path;
- AC/evidence/falsifier matrix;
- live-app evidence obligations where applicable;
- changed files or implementation surface;
- verification artifacts;
- demo artifacts;
- known gaps and blockers;
- material scope hash;
- explicit review questions.

The packet must not include the implementing agent's hidden chain of thought, private scratchpad, or unbounded conversation context.

### 8. Review artifact provenance

Review artifacts should record at least:

```yaml
reviewer_kind: spawned-agent
reviewer_role: code-reviewer
reviewer_id: codex-reviewer-20260501-a
implementer_id: codex-implementer-20260501-b
launch_mode: spawned
isolation_level: bounded-packet
context_inheritance: none
readonly: true
packet_hash: sha256:...
material_scope_hash: sha256:...
required_reason: "code-bearing change"
raw_report_ref: docs/dossier/reviews/.../raw-report.md
verdict: PASS
```

CLI flags may use kebab-case while frontmatter uses snake_case:

```bash
--reviewer-kind spawned-agent
--reviewer-role code-reviewer
--reviewer-id <id>
--implementer-id <id>
--launch-mode spawned
--isolation-level bounded-packet
--context-inheritance none
--packet-hash <hash>
--required-reason "code-bearing change"
--report <path>
```

Allowed `launch_mode` for required gates:

- `spawned`.

Optional non-standard modes may be recorded as history, but do not satisfy required gates unless explicitly supported by a future policy:

- `manual-external`;
- `same-thread`;
- `self-review`;
- `unknown`.

Allowed `isolation_level` for required gates:

- `bounded-packet`;
- `repository-readonly`.

Allowed `context_inheritance` for required gates:

- `none`.

### 9. Closure eligibility update

A required review gate is satisfied only when the review artifact is:

- required class;
- verdict PASS;
- fresh for current material scope hash and reviewer-class scope;
- produced by a spawned independent reviewer agent;
- recorded with `context_inheritance=none`;
- recorded with eligible `isolation_level`;
- read-only;
- not same-thread;
- not self-review;
- not unknown provenance;
- not superseded by later material change relevant to that review class;
- not invalidated;
- preserving reviewer findings or raw report reference.

Ineligible review artifacts may remain in history but must not satisfy closure.

### 10. Rerun policy after FAIL/BLOCKED and fixes

Required reviews are rerun by affected reviewer class, not blindly all-or-nothing.

After any FAIL/BLOCKED review:

1. record the failed review artifact unchanged;
2. fix the findings or clarify missing requirements;
3. classify the fix impact;
4. rerun the failed review class;
5. rerun any previously PASS review class whose reviewed scope was materially affected by the fix.

Previously PASS review artifacts remain eligible only if the fix does not affect their scope.

Examples:

- `spec-conformance-reviewer` PASS, `security-reviewer` FAIL. A security fix that changes internal validation code but does not change spec, contract, AC, observable behavior, integration path, or evidence matrix does not require rerunning `spec-conformance-reviewer`. It does require rerunning `security-reviewer`. It also requires rerunning `code-reviewer` if code changed after code review PASS.
- `spec-conformance-reviewer` PASS, `security-reviewer` FAIL. A security fix that changes public API behavior, contract, negative AC, falsifier, or acceptance semantics makes the spec review stale and requires rerunning `spec-conformance-reviewer`.
- `concept-conformance-reviewer` PASS at `plan-slice`. A later change to capability claim, demo scenario, integration path, falsifier set, or Plan Slice material sections requires rerunning concept conformance.
- `code-reviewer` PASS. Any subsequent code change in the reviewed scope stales that code review unless explicitly classified as non-material generated/comment-only change outside reviewed production/test/build surface.
- `security-reviewer` PASS. Subsequent changes to production code, config, CI, auth, persistence, external input, permissions, runtime boundary, package scripts, or security posture stale the security review.

Runtime/help output SHOULD explain which classes are stale and why:

```text
Review freshness after fixes:
- spec-conformance-reviewer: still fresh; no spec/AC/contract/observable behavior change detected.
- code-reviewer: stale; code changed after PASS review.
- security-reviewer: stale; security finding fixed in production validation path.

Next actions:
1. Spawn fresh code-reviewer.
2. Spawn fresh security-reviewer.
```

The implementing agent MUST NOT reuse a PASS review when the fix potentially affects that reviewer's scope.

### 11. Multiple review classes by one reviewer agent

One spawned reviewer agent may cover multiple required review classes only when the reviewer output has separate sections and verdicts per class:

```text
concept-conformance-reviewer: PASS/FAIL/BLOCKED
spec-conformance-reviewer: PASS/FAIL/BLOCKED
code-reviewer: PASS/FAIL/BLOCKED
security-reviewer: PASS/FAIL/BLOCKED
```

Runtime may record them as separate review artifacts or as one multi-class artifact only if closure can validate each required class independently.

Consolidation is timing/scope policy. It does not replace required review classes.

### 12. FAIL/BLOCKED attempts are immutable

FAIL and BLOCKED external review attempts MUST be recorded and preserved.

The implementing agent may fix findings and request a new external review, but must not:

- delete failed attempts;
- rewrite failed verdicts;
- hide findings;
- summarize away blocking details;
- replace external FAIL with self-authored PASS.

### 13. Required external review workflow

Required operational sequence:

```text
stage reaches required review gate
-> implementing agent computes required reviewer roles
-> implementing agent generates bounded review packet(s)
-> implementing agent spawns fresh independent reviewer agent(s)
-> reviewer audits read-only without inherited implementation context
-> reviewer returns verdict/findings/rationale
-> implementing agent records review artifact(s) with provenance
-> if FAIL/BLOCKED: implementer fixes or clarifies, then requests new external review for affected classes
-> if PASS and fresh: closure may use review
```

### 14. Runtime output and next actions

`review required`, `next`, and failed `stage close` output should identify when a fresh spawned external review is required:

```text
Missing required eligible external review:
- class: concept-conformance-reviewer
- stage: plan-slice
- required launch_mode: spawned
- required context_inheritance: none
- required isolation_level: bounded-packet|repository-readonly
- reason: capability plan-slice requires concept conformance

Next actions:
1. Run: dossier-engineer review packet --work WI-... --stage plan-slice --class concept-conformance-reviewer
2. Spawn a fresh external reviewer agent with the packet.
3. Record returned review with: dossier-engineer review record ...
```

For implementation after code changes:

```text
Required external reviews:
- spec-conformance-reviewer | reason: implementation closure against acceptance criteria
- code-reviewer | reason: code-bearing change
- security-reviewer | reason: code-bearing change
```

If spawn permission is required:

```text
External review cannot proceed because spawning reviewer agents requires operator permission.
Request permission to spawn reviewer agent for class <review-class>.
Self-review and same-thread review are not acceptable substitutes.
```

### 15. Interaction with existing phases

- Phase 1: `plan-slice close` requires fresh eligible spawned `concept-conformance-reviewer` PASS for capability work.
- Phase 2: `review record` writes follow mutation envelope/write-lock rules. Reviewer spawning/external review execution itself does not hold dossier write lock.
- Phase 3: implementation closure requires external review to consider live-app evidence and integration path where applicable.
- Phase 4: consolidated review remains timing/scope policy. Required review classes still need fresh eligible external PASS artifacts. Rerun only failed/stale affected classes after fixes.

## Alternatives Considered

- Allow implementing agent self-review. Rejected: preserves self-confirming closure.
- Let operator manually launch all audits. Rejected: operator should start the dossier process, not operate every review gate.
- Let operator select reviewers in normal workflow. Rejected: unnecessary operator involvement and inconsistent process.
- Let operator waive required audit gates. Rejected for normal workflow: creates escape hatch and weakens audit guarantees.
- Fork current implementation context into reviewer. Rejected: reviewer would inherit implementer assumptions and hidden context.
- Require a separate reviewer agent for every required class. Partially rejected: safer but more expensive; one fresh spawned reviewer can cover multiple classes if verdicts/findings are separated.
- Rerun every previously PASS review after every fix. Rejected: creates review noise and conflicts with Phase 4.
- Never rerun previously PASS reviews after fixes. Rejected: unsafe when fix affects that reviewer class scope.
- Add a new delivery stage for external review. Rejected: existing review gates are enough if execution/provenance is fixed.
- Add a new canonical review packet artifact family. Rejected for this phase: packet can be generated/derived; review artifact remains canonical.
- Treat any PASS review as valid if class matches. Rejected: provenance, independence, freshness, role selection, and scope are required.
- Let reviewer agents fix code while reviewing. Rejected: blurs reviewer/implementer roles and breaks independence.

## Destructive Side Effects

- More overhead for required reviews. Mitigation: only required gates need eligible spawned reviews; Phase 4 consolidated review reduces micro-fix review churn.
- Code-bearing changes now require both code and security reviewers. Mitigation: this is an intentional safety default; support/advisory tests and docs-only changes do not trigger it unless material.
- Spawn permission may be unavailable. Mitigation: implementing agent stops at audit gate and asks operator for spawn permission; self-review is not used as fallback.
- Reviewer spawning may not be supported in some environments. Mitigation: closure reports missing eligible review; future environment-specific integrations can provide the spawn mechanism without changing review semantics.
- One reviewer covering multiple classes may be shallow. Mitigation: require separate verdict/findings per class.
- Review packet may omit important context. Mitigation: packet contract includes source refs, capability claim, ACs, falsifiers, integration path, evidence, demos, material scope hash, role-selection reason, and explicit class questions.
- Raw reviewer findings may be noisy. Mitigation: preserve raw report or report reference; implementer may add a separate summary but must not rewrite verdict/findings materially.
- Additional provenance fields make `review record` longer. Mitigation: use explicit fields for required reviews; do not infer eligibility from prose.
- Operator permission requests may interrupt automation in restricted environments. Mitigation: permission is requested only when spawning is blocked by environment policy.

- `stage close --stage plan-slice` blocks capability work when concept-conformance review is missing.

- Code-bearing implementation closure blocks when `code-reviewer` is missing.
- Code-bearing implementation closure blocks when `security-reviewer` is missing.
- Implementation closure blocks when required spec/code/security reviews are PASS but ineligible due to self/same-thread/unknown provenance.
- Implementation closure accepts required review bundle when each required class has fresh eligible spawned external PASS artifact.
- Security-sensitive non-code/config changes require `security-reviewer`.
- Pure docs-only non-material change does not require code/security review.
- Source/spec/AC changes require spec and/or concept reviewers according to the role matrix.
- Review artifact with FAIL remains visible and is not overwritten by later PASS.
- A later PASS review supersedes earlier FAIL only when fresh and eligible.
- `review packet --work <id> --stage <stage> --class <class>` includes capability claim, anti-claims, ACs, negative/falsifier criteria, Spec Compact, Plan Slice, integration path, evidence/demo refs, material scope hash, class-specific review questions, and role-selection reason.
- Review packet does not include current implementation session transcript, hidden scratchpad, or unbounded conversation context.
- `review required --work <id> --stage implementation` reports required spawned external review classes and acceptable provenance.
- One spawned reviewer covering multiple classes is accepted only if each class has distinct verdict/findings and closure can validate classes independently.
- Review becomes stale when material scope hash changes after packet/review.
- Review becomes stale when demo scenario or falsifier set changes.
- Review artifact with `readonly=false` or missing isolation metadata does not satisfy required closure gate.
- Ineligible review artifacts remain in history but are not selected for closure.
- Runtime/help text instructs implementing agent to spawn a fresh reviewer agent rather than self-review.
- If spawn permission is required by environment policy, the agent stops and asks the operator for spawn permission without performing self-review.
- Operator permission grant is not recorded as review verdict and does not satisfy any audit gate.
- After `security-reviewer` FAIL and `spec-conformance-reviewer` PASS, a security fix that does not change spec/AC/contract/observable behavior keeps spec review fresh.
- After `security-reviewer` FAIL and `spec-conformance-reviewer` PASS, a security fix that changes public API, contract, negative AC, falsifier, or observable behavior stales spec review.
- After `code-reviewer` PASS, a subsequent code change in reviewed scope stales code review.
