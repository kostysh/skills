# Issue

## Language

Русский.

Английскими оставлены только команды, enum/frontmatter keys, имена review classes и точные формулировки, которые предполагаются как будущая prose/contract surface скила.

## Issue ID

`issue-20260501-5`

## Title

Сделать required reviews независимыми: provenance, bounded review packet и eligibility gates

## Skill

`dossier-engineer` (`skills/dossier-engineer`)

## Context

`dossier-engineer` уже усилил ключевые gates в Phase 1-4:

- Phase 1: `Spec Compact` / `Plan Slice` стали содержательными, `plan-slice` требует concept review, `queue` больше не выдаёт misleading implementation readiness;
- Phase 2: mutating runtime commands проходят через write lock / mutation envelope / atomic writes;
- Phase 3: user-visible capability work требует live-app evidence, production integration path и `negative` / `falsifier` acceptance;
- Phase 4: review freshness считается по normalized material scope, final closure требует fresh review bundle, consolidated review является timing/scope policy, а не новым review class.

Но эти улучшения всё ещё могут быть ослаблены, если required review фактически является self-review того же implementing agent, выполняется в той же беседе/контексте или записывается без проверяемого reviewer provenance.

Нужная observable capability: оператор и runtime должны отличать fresh eligible independent review от self-review / same-thread / unknown-provenance review. Закрытие work item должно принимать только review artifacts, которые одновременно fresh по material scope и eligible по provenance.

Substrate, который сам по себе не решает проблему:

- просто добавить ещё один `PASS` artifact;
- добавить новый generic `external-review` class;
- заставить оператора вручную проводить audit;
- создать тяжёлое новое семейство canonical review-packet artifacts;
- полагаться на обещание агента “я проверил независимо” без machine-readable provenance.
- запускать required audit на заведомо слабой модели или low reasoning level только ради формального прохождения gate.

## Problem

Текущая review model может оставлять self-confirming audit path:

- implementing agent может записать required `PASS` verdict для собственной работы;
- review может выполняться в той же conversation/session/thread, где была сделана implementation;
- reviewer может быть запущен с inherited thread history / forked context вместо clean context и bounded review packet;
- reviewer может быть запущен на модели или reasoning effort, не соответствующих review class, risk, ambiguity and blast radius;
- `PASS` может основываться на summary implementer-а, а не на source artifacts, dossier artifacts, evidence, demos и changed files;
- `FAIL` / `BLOCKED` findings могут быть смягчены, переписаны или исчезнуть из истории;
- closure может принять review artifact только потому, что у него `verdict: pass`, без проверки independence provenance;
- concept-conformance review может стать бессмысленным, если тот же агент, который написал слабый план, сам его одобряет;
- consolidated review снижает micro-fix noise, но без independent execution остаётся self-confirming;
- после `FAIL` одного review class и `PASS` другого агент может либо перезапустить слишком мало reviews, либо перезапустить все без необходимости.

Это особенно опасно для уже выявленных failure modes:

- weak `spec-compact` / `plan-slice`;
- infrastructure masquerading as capability;
- implementation не интегрирована в реальный app/runtime path;
- stale или overly broad review reuse;
- закрытые work items с внутренне несогласованными lifecycle/status/evidence.

## Evidence

Связанные уже реализованные issues:

- `issue-20260501-1`: `plan-slice` для capability work требует current PASS `concept-conformance-reviewer`; этот gate слаб, если concept review является self-review.
- `issue-20260501-3`: implementation closure требует live-app evidence; independent reviewer должен проверять, что evidence действительно проходит production path.
- `issue-20260501-4`: consolidated review не заменяет required review classes; freshness meaningful только если review signal независим.

Текущее состояние skill/runtime:

- `review required --work <id> --stage plan-slice` и `review required --work <id> --stage implementation` уже возвращают required classes и freshness.
- `review record` уже создаёт immutable `REV-*.md`, но не хранит достаточный provenance для проверки independence.
- `reviewFresh` / `reviewFreshForStage` уже учитывают normalized material scope, но не проверяют reviewer execution eligibility.
- Runtime не должен полагаться на hidden conversation state: eligibility должна быть выражена в review artifact frontmatter.

Execution environment caveat:

- Некоторые среды позволяют spawn fresh reviewer agents, но правила могут требовать явного разрешения оператора в текущей задаче.
- Навык не должен предполагать универсальный Codex-specific spawn API внутри portable CLI.
- Если spawn недоступен или запрещён, workflow должен fail closed at audit gate вместо self-review fallback.

## Impact

Без external/independent provenance gates:

- review artifacts могут формально удовлетворять closure, но не добавлять реальной assurance;
- `concept-conformance-reviewer` может одобрить weak plan вместо обнаружения concept drift;
- `spec/code/security` reviews могут унаследовать assumptions implementer-а и пропустить integration gaps;
- оператор видит `PASS`, но не видит, был ли audit независимым;
- `FAIL/BLOCKED` attempts могут исчезать из dossier history;
- Phase 1/3/4 становятся менее эффективными, потому что final review остаётся self-authored или mismatched to change type;
- agents получают стимул воспринимать review gates как paperwork.

## Scope

Входит в scope:

- Обновить active guidance, source bundle, references и regenerated `SKILL.md`.
- Определить required review execution model:
  - implementing agent готовит bounded review packet;
  - implementing agent запускает fresh independent reviewer agent, если среда это поддерживает и есть требуемое permission;
  - если spawn недоступен или permission не дан, implementing agent останавливается на audit gate;
  - reviewer работает read-only и возвращает verdict/findings/rationale;
  - implementing agent records returned result without rewriting verdict or hiding findings.
- Определить role boundaries:
  - implementing agent owns orchestration and recording;
  - reviewer agent audits read-only;
  - operator only grants spawn permission when required by current execution environment.
- Определить bounded review packet contract.
- Добавить review provenance fields.
- Добавить reviewer compute policy: model/reasoning selection must fit review class, risk, ambiguity and blast radius.
- Добавить review eligibility checks для required gates.
- Уточнить auditor-role selection matrix с учётом текущей risk-weighted policy, Phase 1-4 freshness и no-heavy-workflow constraint.
- Определить rerun/freshness rules after `FAIL` / `BLOCKED` and subsequent fixes.
- Обновить `review required`, `review record`, `stage close`, `lint` / closure checks и help output where needed.
- Preserve immutable `FAIL` / `BLOCKED` attempts.
- Allow one spawned reviewer agent to cover multiple required review classes only if separate verdicts/findings are returned per class and runtime can validate each class independently.
- Добавить tests.

Не входит в scope:

- Добавлять новый delivery stage.
- Требовать, чтобы оператор вручную запускал audits.
- Делать оператора normal reviewer selector.
- Позволять оператору author/approve/override/waive audit verdicts в normal workflow.
- Делать reviewer agents writable.
- Требовать separate reviewer process для каждого tiny micro-fix; Phase 4 consolidated review policy remains valid.
- Заменять required review classes одним generic `external-review` class.
- Создавать тяжёлое новое canonical review-packet artifact family; packets are derived/generated.
- Создавать database, global review registry, committed mutable review index или hidden canonical state.
- Встраивать конкретный Codex spawn API в portable CLI. Runtime должен определить packet/provenance/eligibility contracts и blocked-spawn behavior.
- Хардкодить vendor-specific model names в portable runtime.
- Переписывать уже существующие committed review artifacts. Compatibility for older records must be explicit and limited.

## Proposed Resolution

### 1. Default audit policy: implementing agent orchestrates independent required audits

Новая normative формулировка для active guidance:

```md
Required review gates are satisfied by fresh eligible independent reviews, not by implementer self-review.

The implementing agent MUST NOT author required PASS review verdicts for its own work.

When a required review gate is reached, the implementing agent prepares a bounded review packet, launches a fresh independent reviewer agent when the environment allows it and required operator permission has been granted, records the returned verdict/findings without rewriting them, and reruns only failed or stale affected review classes after fixes.

If the environment cannot provide an eligible independent reviewer, the implementing agent stops at the audit gate. Same-thread review, self-review, and unverifiable internal reasoning do not satisfy required gates.
```

### 2. Operator role: spawn permission boundary only

Оператор не является участником normal audit execution.

Стандартная роль оператора:

- grant/deny permission to spawn reviewer agents when the current environment requires explicit permission.

Оператор не должен обычно:

- manually launch audits;
- choose reviewers;
- decide required review classes;
- author review verdicts;
- approve `PASS`;
- convert `FAIL/BLOCKED` into `PASS`;
- waive required audit gates;
- edit review findings.

Если spawning требует permission, agent-side guidance должна использовать такую форму запроса:

```text
Required independent review is blocked because spawning reviewer agents requires operator permission in the current environment.

Requested permission:
- spawn a fresh independent reviewer agent;
- reviewer role: <review-class>;
- context mode: bounded review packet;
- launch context: fresh session, no current-thread fork, no inherited thread history;
- reviewer is read-only and will return PASS/FAIL/BLOCKED with findings.

Permission to spawn is not permission to pass the review.
```

### 3. Requirements clarification is not audit override

Если reviewer возвращает `BLOCKED`, потому что packet неполный, implementing agent исправляет packet и перезапускает review.

Если reviewer возвращает `BLOCKED`, потому что отсутствует product/domain decision, implementing agent может спросить оператора о недостающем requirement decision.

Ответ оператора является requirements clarification, а не audit override. После clarification implementing agent обновляет dossier as needed and reruns independent review.

### 4. Reviewer isolation contract

Required reviewer execution должен быть fresh and independent.

Правильная терминология для agent-side launch contract:

- **fresh reviewer session** — новый reviewer session/thread, созданный специально для audit;
- **no context fork / no current-thread fork** — reviewer не запускается через fork текущей implementation session;
- **no inherited thread history** — reviewer не получает transcript/history текущей беседы implementer-а;
- **bounded review packet only** — reviewer получает только packet и явно разрешённый readonly repository context.

В средах, где spawn API имеет параметр вроде `fork_context`, required review launch должен использовать эквивалент `fork_context: false`. Это agent-side requirement, а не portable CLI dependency.

Required properties:

- fresh reviewer session when spawning is available;
- no context fork / no current-thread fork;
- no inherited thread history, hidden scratchpad, or private reasoning from implementing agent;
- bounded review packet only;
- optional readonly repository context;
- read-only role;
- no code/dossier/runtime/stage mutations;
- returns verdict, findings, rationale, reviewed scope.

Not acceptable for required gates:

- same-thread review;
- self-review;
- reviewer spawned with forked context / inherited thread history from current implementation session;
- reviewer with write access to reviewed artifacts during review;
- reviewer that only sees implementer's summary without packet/evidence;
- unknown launch mode;
- unknown isolation level;
- missing provenance.

Runtime не может проверить hidden conversation context. Поэтому runtime должен fail closed на machine-readable provenance fields: если provenance отсутствует или ineligible, review не satisfies required gate.

### 5. Auditor-role selection matrix

Implementing agent выбирает reviewer roles по фактически выполненному change type, а не по intuition.

Runtime/help output SHOULD provide:

```bash
dossier-engineer review required --work <id> --stage <stage>
```

Output должен показывать required review classes, freshness, eligibility status and reasons.

#### Reviewer role definitions (role === skill)

`concept-conformance-reviewer`:

> Review feature ideas, backlog items, specifications, plans, acceptance criteria, or implementations against a higher-level product or system concept. Use when a task may create infrastructure, mocks, metadata, wrappers, tests, or documentation that looks like progress but does not deliver the claimed observable capability; when separating capability from substrate; when checking whether acceptance criteria can be satisfied without real behavior; or before implementing complex agent, runtime, platform, self-development, cognition, workflow, or product features whose wording may drift from the original concept.

`spec-conformance-reviewer`:

> Review code against normative requirements from specs, contracts, ADRs, tickets, and acceptance criteria. Use when checking whether an implementation matches a specification, API contract, PRD, RFC, migration requirement, negative/falsifier criteria, or when producing a requirement-to-code traceability matrix and implementation-versus-spec verdict.

`code-reviewer`:

> Systematic code review for pull requests, diffs, and local branch changes. Use for code, tests, build logic, runtime logic, application integration, maintainability, correctness, regressions, edge cases, lifecycle consistency, and high-signal implementation feedback.

`security-reviewer`:

> Systematic security review for vulnerabilities in application code, CI workflows, permission models, webhooks, secrets, configuration, auth, RLS, OWASP-style risks, persistence boundaries, external integrations, fail-closed behavior, and runtime/security-sensitive configuration.

#### Required reviewer matrix

| Change / stage condition | Required reviewer roles | Reason |
| --- | --- | --- |
| `plan-slice` close for capability work | `concept-conformance-reviewer` | Implementation must not start until the plan has external concept conformance. |
| New capability, changed capability claim, changed concept interpretation, changed observable behavior, changed delivery kind, changed `Spec Compact`, changed `Plan Slice`, changed integration path, changed demo scenario, changed falsifier set, or high concept-drift risk | `concept-conformance-reviewer` | Prevent infrastructure/substrate from masquerading as capability and ensure the slice advances the concept. |
| Implementation closure for capability, support, maintenance, or fix work with normative requirements or acceptance criteria | `spec-conformance-reviewer` | Verify implementation against sources, spec, AC, negative criteria, falsifiers, and anti-claims. |
| Any code-bearing change, including runtime code, tests, build scripts, generated runtime script changes, CI logic, configuration that affects execution, or integration glue | `code-reviewer` | Check correctness, maintainability, regressions, edge cases, lifecycle consistency, and integration quality. |
| Production/runtime/config code with security impact, or code touching external input, persistence, execution boundary, dependency loading, package scripts, auth/privacy/network, permission boundaries, fail-closed behavior, or security-sensitive configuration | `security-reviewer` | Security-sensitive surface requires explicit threat/vulnerability review. |
| Pure documentation/source/dossier text change with no capability/spec/plan/evidence/security implication | No required external reviewer by default; optional advisory review may be recorded | Avoid review noise for non-material text-only changes. |
| Source-only change that changes requirements, concept, acceptance criteria, or scope | `concept-conformance-reviewer` and/or `spec-conformance-reviewer` depending on affected material | Source interpretation can invalidate concept and/or implementation conformance. |
| Source-only formatting or typo change with explicit source-review `no_change` verdict | No required external reviewer by default | Avoid review noise for non-material source updates. |
| Change-proposal accepted for concept/capability/scope/spec/plan | `concept-conformance-reviewer`; add `spec-conformance-reviewer` if requirements/AC/spec changed | Accepted changes may invalidate planning and implementation conformance. |
| Live-app evidence path, production entrypoint, or runtime path changed | `concept-conformance-reviewer`, `spec-conformance-reviewer`; add `code-reviewer` / `security-reviewer` if code/security-sensitive surface changed | Integration proof and scope changed. |
| Security fix after failed security review | `security-reviewer`; also rerun `code-reviewer` if code changed; rerun `spec-conformance-reviewer` only if behavior/spec/contract/AC changed | Rerun affected scopes, not all scopes blindly. |
| Micro-fix inside same material scope and trust boundary with no code change | No new full review required; record note per Phase 4 | Avoid micro-fix review noise. |
| Micro-fix with code change but same spec/concept/security posture | `code-reviewer`; add `security-reviewer` if production code/config/runtime behavior or security-sensitive surface changed | Code review scope changed; security review may be affected by code/config changes. |

Conservative default:

- if code changed, require `code-reviewer`;
- if code affects production/runtime/config/security-sensitive surface or the impact is unclear, require `security-reviewer`;
- if spec/AC/contract changed, require `spec-conformance-reviewer`;
- if capability/concept/plan/demo/falsifier/integration path changed, require `concept-conformance-reviewer`;
- if unsure whether a role is required, include the reviewer role and record the reason.

### 6. Reviewer compute policy

Required reviews must be run with a reviewer model and reasoning effort appropriate to the review class, risk, ambiguity, and blast radius.

Новая normative формулировка для active guidance:

```md
Required reviews must be run with a reviewer model and reasoning effort appropriate to the review class, risk, ambiguity, and blast radius.

The implementing agent must not downshift required audits to a weaker model or low reasoning level merely to satisfy the gate cheaply.

For required gates, reviewer model capability should be at least comparable to the implementing agent's model for the reviewed domain. High-risk reviews should use a stronger model or higher reasoning effort than the implementation pass.

Do not use low reasoning effort for required reviews that can block or permit implementation closure.
```

Runtime must not hardcode specific vendor model names. It should store model/reasoning provenance and, where possible, validate declared policy class rather than a fixed model list.

High-risk required reviews must use `high` or `xhigh` reasoning effort, not merely "not low". High-risk conditions include:

- `security-reviewer`;
- broad, novel, agent/runtime/platform/capability concept work;
- runtime lifecycle, concurrency, locking, closure, provenance, or source-of-truth semantics;
- many acceptance criteria, `negative` / `falsifier` criteria, contracts, or source ambiguity;
- previous `FAIL` / `BLOCKED` in the same review class;
- high blast radius across multiple capabilities, stages, commands, or generated runtime artifacts.

Recommended default policy:

| Review class / condition | Model choice | Reasoning effort |
| --- | --- | --- |
| `concept-conformance-reviewer` for broad, novel, agent/runtime/platform/capability work | strongest available reviewer model | `high` or `xhigh` |
| `concept-conformance-reviewer` for narrow routine capability plan | strong model | `high` |
| `spec-conformance-reviewer` with many ACs, falsifiers, contracts, or source ambiguity | strong model | `high` |
| `spec-conformance-reviewer` for small unambiguous docs/spec match | strong or standard model | `medium` minimum |
| `code-reviewer` for runtime/app logic, lifecycle, concurrency, generated scripts, tests | strong coding-capable model | `high` |
| `code-reviewer` for trivial localized code diff | strong or standard coding-capable model | `medium` minimum |
| `security-reviewer` | strongest available security-capable model | `high` or `xhigh` |
| Any review after previous `FAIL` / `BLOCKED` | same or stronger than failed review | same or higher |

The runtime/help surface should require or recommend these provenance fields for required review artifacts:

```yaml
reviewer_model: default
reviewer_reasoning_effort: high
model_selection_policy: required-review-risk-weighted
model_selection_reason: "security-sensitive runtime change"
```

Missing model/reasoning provenance should make a new required review ineligible unless a future compatibility policy explicitly accepts a non-model-specific external reviewer kind.

### 7. Bounded review packet contract

Runtime should provide derived output:

```bash
dossier-engineer review packet \
  --work <WI-id> \
  --stage <stage> \
  --class <review-class>
```

Packet is derived review context, not canonical truth. It may be printed to stdout or saved under a generated non-canonical location.

Minimum packet content:

- work item ID and title;
- stage;
- review class;
- operator language;
- reviewer instructions for that class;
- reason why this reviewer role is required;
- source refs and relevant source paths/excerpts;
- capability refs and capability claim;
- anti-claims;
- acceptance criteria, including `negative` and `falsifier` criteria;
- `Spec Compact` material sections;
- `Plan Slice` material sections;
- integration path;
- AC/evidence/falsifier matrix;
- live-app evidence obligations where applicable;
- changed files or implementation surface;
- verification artifacts;
- demo artifacts;
- known gaps and blockers;
- material scope hash;
- explicit review questions.

Packet must not include implementing agent hidden chain of thought, private scratchpad, or unbounded conversation transcript.

### 8. Review artifact provenance

Review artifacts should record:

```yaml
reviewer_kind: spawned-agent
reviewer_role: code-reviewer
reviewer_id: codex-reviewer-20260501-a
implementer_id: codex-implementer-20260501-b
launch_mode: spawned
isolation_level: bounded-packet
context_inheritance: none
readonly: true
packet_hash: sha256:...
required_reason: "code-bearing change"
reviewer_model: default
reviewer_reasoning_effort: high
model_selection_policy: required-review-risk-weighted
model_selection_reason: "security-sensitive runtime change"
raw_report_ref: docs/dossier/reviews/.../raw-report.md
```

Existing required fields remain:

```yaml
audit_class: code-reviewer
verdict: pass
material_scope_hash: sha256:...
```

CLI flags may use kebab-case while stored frontmatter uses snake_case:

```bash
--reviewer-kind spawned-agent
--reviewer-role code-reviewer
--reviewer-id <id>
--implementer-id <id>
--launch-mode spawned
--isolation-level bounded-packet
--context-inheritance none
--readonly true
--packet-hash <hash>
--required-reason "code-bearing change"
--reviewer-model default|<model-id-or-family>
--reviewer-reasoning-effort medium|high|xhigh
--model-selection-policy required-review-risk-weighted
--model-selection-reason "<reason>"
--report <path>
```

Eligible values for new required gates:

- `launch_mode: spawned`;
- `isolation_level: bounded-packet` or `repository-readonly`;
- `context_inheritance: none`;
- `readonly: true`;
- `reviewer_kind: spawned-agent` or another explicitly supported independent reviewer kind in a future policy.
- `reviewer_model`, `reviewer_reasoning_effort`, `model_selection_policy`, and `model_selection_reason` recorded for required reviews.
- high-risk required reviews use `reviewer_reasoning_effort: high` or `xhigh`.

Ineligible for new required gates:

- `same-thread`;
- `self-review`;
- `unknown`;
- missing provenance;
- `context_inheritance` other than `none`;
- `readonly: false`.
- missing reviewer model/reasoning provenance for a new required review.

Non-standard modes may be recorded as history, but must not satisfy new required gates unless a future explicit policy makes them eligible.

### 9. Closure eligibility update

A required review gate is satisfied only when the review artifact is:

- required class;
- `verdict: pass`;
- fresh for current material scope hash and reviewer-class scope;
- produced by eligible independent reviewer execution;
- recorded with `context_inheritance: none`;
- recorded with eligible `isolation_level`;
- read-only;
- not same-thread;
- not self-review;
- not unknown provenance;
- model/reasoning provenance present and appropriate under the declared model selection policy;
- not superseded by later material change relevant to that review class;
- preserving reviewer findings or raw report reference.

Ineligible review artifacts may remain in history but must not satisfy new closure gates.

Existing review artifacts that predate provenance fields must not be rewritten. For new required gates they are ineligible unless an explicit compatibility policy accepts them for historical already-closed work only. They may still appear in reports as legacy review history.

### 10. Rerun policy after `FAIL` / `BLOCKED` and fixes

Required reviews are rerun by affected reviewer class, not blindly all-or-nothing.

After any `FAIL` / `BLOCKED` review:

1. record failed/blocked review artifact unchanged;
2. fix findings or clarify missing requirements;
3. classify fix impact;
4. rerun failed/blocked review class;
5. rerun any previously `PASS` review class whose reviewed scope was materially affected by the fix.

Previously `PASS` review artifacts remain eligible only if the fix does not affect their scope.

Examples:

- `spec-conformance-reviewer` PASS, `security-reviewer` FAIL. A security fix that changes internal validation code but does not change spec, contract, AC, observable behavior, integration path, or evidence matrix does not require rerunning `spec-conformance-reviewer`. It does require rerunning `security-reviewer`. It also requires rerunning `code-reviewer` if code changed after code review PASS.
- `spec-conformance-reviewer` PASS, `security-reviewer` FAIL. A security fix that changes public API behavior, contract, negative AC, falsifier, or acceptance semantics makes the spec review stale and requires rerunning `spec-conformance-reviewer`.
- `concept-conformance-reviewer` PASS at `plan-slice`. A later change to capability claim, demo scenario, integration path, falsifier set, or Plan Slice material sections requires rerunning concept conformance.
- `code-reviewer` PASS. Any subsequent code change in the reviewed scope stales that code review unless explicitly classified as non-material generated/comment-only change outside reviewed production/test/build surface.
- `security-reviewer` PASS. Subsequent changes to production code, config, CI, auth, persistence, external input, permissions, runtime boundary, package scripts, or security posture stale the security review.

Runtime/help output should explain stale reasons:

```text
Review freshness after fixes:
- spec-conformance-reviewer: still fresh; no spec/AC/contract/observable behavior change detected.
- code-reviewer: stale; code changed after PASS review.
- security-reviewer: stale; security finding fixed in production validation path.

Next actions:
1. Generate review packet for code-reviewer.
2. Spawn fresh independent code-reviewer when allowed.
3. Generate review packet for security-reviewer.
4. Spawn fresh independent security-reviewer when allowed.
```

### 11. Multiple review classes by one reviewer agent

One spawned reviewer agent may cover multiple required review classes only when output has separate sections and verdicts per class:

```text
concept-conformance-reviewer: PASS/FAIL/BLOCKED
spec-conformance-reviewer: PASS/FAIL/BLOCKED
code-reviewer: PASS/FAIL/BLOCKED
security-reviewer: PASS/FAIL/BLOCKED
```

Runtime may record them as separate review artifacts or one multi-class artifact only if closure can validate each required class independently.

Consolidation is timing/scope policy. It does not replace required review classes.

### 12. `FAIL` / `BLOCKED` attempts are immutable

`FAIL` and `BLOCKED` external review attempts MUST be recorded and preserved.

Implementing agent may fix findings and request a new independent review, but must not:

- delete failed attempts;
- rewrite failed verdicts;
- hide findings;
- summarize away blocking details;
- replace external `FAIL` with self-authored `PASS`.

### 13. Runtime output and next actions

`review required`, `next`, and failed `stage close` output should identify when a fresh eligible independent review is required:

```text
Missing required eligible independent review:
- class: concept-conformance-reviewer
- stage: plan-slice
- required launch_mode: spawned
- required context_inheritance: none
- required launch_context: fresh-session-no-fork
```

### 14. Interaction with existing phases

- Phase 1: `plan-slice close` requires fresh eligible independent `concept-conformance-reviewer` PASS for capability work.
- Phase 2: `review record` writes follow mutation envelope/write-lock rules. Reviewer spawning/external review execution itself does not hold dossier write lock.
- Phase 3: implementation closure requires independent review to consider live-app evidence and integration path where applicable.
- Phase 4: consolidated review remains timing/scope policy. Required review classes still need fresh eligible independent PASS artifacts. Rerun only failed/stale affected classes after fixes.

## Alternatives Considered

- Allow implementing agent self-review. Rejected: preserves self-confirming closure.
- Let operator manually launch all audits. Rejected: operator should start the dossier process, not operate every review gate.
- Let operator select reviewers in normal workflow. Rejected: unnecessary operator involvement and inconsistent process.
- Let operator waive required audit gates. Rejected for normal workflow: creates escape hatch and weakens audit guarantees.
- Fork current implementation context into reviewer. Rejected: reviewer would inherit implementer assumptions and hidden context.
- Require a separate reviewer agent for every required class. Partially rejected: safer but more expensive; one fresh independent reviewer can cover multiple classes if verdicts/findings are separated.
- Rerun every previously PASS review after every fix. Rejected: creates review noise and conflicts with Phase 4.
- Never rerun previously PASS reviews after fixes. Rejected: unsafe when fix affects that reviewer class scope.
- Add a new delivery stage for external review. Rejected: existing review gates are enough if execution/provenance is fixed.
- Add a new canonical review packet artifact family. Rejected for this phase: packet can be generated/derived; review artifact remains canonical.
- Treat any PASS review as valid if class matches. Rejected: provenance, independence, freshness, role selection, and scope are required.
- Let reviewer agents fix code while reviewing. Rejected: blurs reviewer/implementer roles and breaks independence.
- Require `security-reviewer` for every code change unconditionally. Rejected: too heavy and conflicts with Phase 4 review-noise reduction. Keep risk/security-sensitive triggers and conservative fallback when impact is unclear.
- Hardcode exact model names in portable runtime. Rejected: model availability is environment-specific; runtime should store and validate policy/provenance, while agent-side guidance selects the strongest suitable available model.

## Destructive Side Effects

- More overhead for required reviews. Mitigation: only required gates need eligible independent reviews; Phase 4 consolidated review reduces micro-fix review churn.
- Spawn permission may be unavailable. Mitigation: implementing agent stops at audit gate and asks operator for spawn permission; self-review is not used as fallback.
- Reviewer spawning may not be supported in some environments. Mitigation: closure reports missing eligible review; future environment-specific integrations can provide the spawn mechanism without changing review semantics.
- One reviewer covering multiple classes may be shallow. Mitigation: require separate verdict/findings per class.
- Review packet may omit important context. Mitigation: packet contract includes source refs, capability claim, ACs, falsifiers, integration path, evidence, demos, material scope hash, role-selection reason, and explicit class questions.
- Raw reviewer findings may be noisy. Mitigation: preserve raw report or report reference; implementer may add a separate summary but must not rewrite verdict/findings materially.
- Additional provenance fields make `review record` longer. Mitigation: use explicit fields for required reviews; do not infer eligibility from prose.
- Reviewer compute policy may increase cost. Mitigation: require suitable model/reasoning only for required gates and keep Phase 4 consolidation to avoid micro-fix audit churn.
- Legacy review artifacts may become ineligible for new required gates. Mitigation: do not rewrite history; define compatibility for historical already-closed work only.

## Verification

Functional tests and acceptance checks should include:

- `stage close --stage plan-slice` blocks capability work when concept-conformance review is missing.
- `stage close --stage plan-slice` blocks when concept-conformance review exists but `launch_mode=self-review`, `same-thread`, `unknown`, missing provenance, or `context_inheritance` is not `none`.
- `stage close --stage plan-slice` accepts fresh PASS concept-conformance review with eligible independent provenance.
- `review required --work <id> --stage plan-slice` reports `concept-conformance-reviewer` for capability work.
- `review required --work <id> --stage implementation` reports required classes, freshness, eligibility, and reasons.
- Code-bearing implementation closure blocks when required `code-reviewer` is missing or ineligible.
- Security-sensitive implementation closure blocks when required `security-reviewer` is missing or ineligible.
- Implementation closure blocks when required spec/code/security reviews are `PASS` but ineligible due to self/same-thread/unknown provenance.
- Implementation closure accepts required review bundle when each required class has fresh eligible independent PASS artifact.
- Security-sensitive non-code/config changes require `security-reviewer`.
- Pure docs-only non-material change does not require code/security review.
- Source/spec/AC changes require spec and/or concept reviewers according to the role matrix.
- Review artifact with `FAIL` remains visible and is not overwritten by later `PASS`.
- A later `PASS` review supersedes earlier `FAIL` only when fresh and eligible.
- `review packet --work <id> --stage <stage> --class <class>` includes capability claim, anti-claims, ACs, negative/falsifier criteria, `Spec Compact`, `Plan Slice`, integration path, evidence/demo refs, material scope hash, class-specific review questions, and role-selection reason.
- Review packet does not include current implementation session transcript, hidden scratchpad, or unbounded conversation context.
- One spawned reviewer covering multiple classes is accepted only if each class has distinct verdict/findings and closure can validate classes independently.
- Review becomes stale when material scope hash changes after packet/review.
- Review becomes stale when demo scenario or falsifier set changes.
- Review artifact with `readonly=false` or missing isolation metadata does not satisfy required closure gate.
- Required review with missing model/reasoning provenance is ineligible for new required gates.
- Required review with `reviewer_reasoning_effort=low` is ineligible for closure-blocking/closure-permitting gates.
- Security-sensitive required review records strongest-available/security-capable model selection reason and `high` or `xhigh` reasoning effort.
- Ineligible review artifacts remain in history but are not selected for closure.
- Runtime/help text instructs implementing agent to use a fresh independent reviewer rather than self-review.
- If spawn permission is required by environment policy, the agent stops and asks the operator for spawn permission without performing self-review.
- Operator permission grant is not recorded as review verdict and does not satisfy any audit gate.
- After `security-reviewer` FAIL and `spec-conformance-reviewer` PASS, a security fix that does not change spec/AC/contract/observable behavior keeps spec review fresh.
- After `security-reviewer` FAIL and `spec-conformance-reviewer` PASS, a security fix that changes public API, contract, negative AC, falsifier, or observable behavior stales spec review.
- After `code-reviewer` PASS, a subsequent code change in reviewed scope stales code review.
- After `concept-conformance-reviewer` PASS, a change to capability claim, demo scenario, integration path, falsifier set, or Plan Slice material sections stales concept review.
- `review required` or equivalent freshness output explains which classes are stale or ineligible and why.

Non-regression checks:

- Non-required advisory self-review can still be recorded as non-eligible history if project wants it.
- Existing review artifacts without provenance are reported as ineligible for new required gates unless a separate compatibility decision explicitly marks them accepted for historical already-closed work only.
- Phase 4 micro-fix consolidation still works: note-only micro-fixes do not require full review until consolidated closure review, unless material trigger fires.
- No new mandatory artifact family is required beyond existing review artifacts and derived review packets.
