# Issue

## Language

Русский.

## Issue ID

`issue-20260501-4`

## Title

Сделать Phase 4: consolidated review policy без micro-fix noise

## Skill

`dossier-engineer` (`skills/dossier-engineer`)

## Context

Анализ `docs/dossier-engineer-problem-analysis-and-proposals.ru.md` показал, что текущий process может быть одновременно слишком слабым на spec/plan и слишком шумным на micro-review. Один work item может накопить серию PASS review artifacts после небольших stabilization fixes, но это не делает общую готовность поведения очевиднее.

Phase 4 из roadmap должна снизить overhead без ослабления safety:

- consolidated review before closure for sequences of micro-fixes;
- re-review only on material scope/trust boundary changes;
- concept-conformance moves to `plan-slice`, while implementation checks freshness instead of requiring repeated concept reviews.

## Problem

Текущий review signal может разбавляться micro-fix noise:

- каждое маленькое изменение получает локальный PASS;
- итоговый вопрос "готово ли observable behavior" остаётся неочевидным;
- ранние reviews могут проверять substrate до live behavior;
- repeated concept/code/security reviews могут выглядеть как качество, хотя не дают consolidated assessment финального diff/scope.

При этом нельзя просто убрать reviews: trust boundary, IPC/security/persistence/source interpretation, capability claim and acceptance criteria still need fresh review when materially changed.

## Evidence

Основной источник: `docs/dossier-engineer-problem-analysis-and-proposals.ru.md`.

Релевантные причины:

- `3.9. Причина I`: review signal разбавлен micro-fix шумом.
- `3.6. Причина F`: concept-conformance review расположен слишком поздно.
- `3.11. Причина K`: runtime/guidance should not rely on agent memory.

Релевантные предложения:

- `P0. Перенести concept-conformance review на plan-slice для capability work`.
- `P1. Свести micro-fix reviews к consolidated review перед closure`.
- `P2. Stage Quality Rubric`, especially change-proposal trigger and substrate-only false-positive checks.

## Impact

- Оператор видит много PASS artifacts, но не получает ясного final review signal.
- Агент тратит review budget на tiny stabilization fixes instead of consolidated final diff/scope.
- Concept conformance может появиться поздно, после реализации слабого plan-slice.
- При material scope change возможна обратная ошибка: старый PASS review будет переиспользован, хотя он stale.

## Scope

Входит в scope:

- Обновить review guidance and runtime checks for consolidated review before closure.
- Зафиксировать, что micro-fixes inside same trust boundary can be recorded as verification/stage notes instead of full review bundle.
- Требовать re-review when material scope, trust boundary, security posture, source interpretation, capability claim, acceptance criteria, or plan changes.
- Сделать concept-conformance review required before `plan-slice close` for capability work, with implementation closure reusing it only if material scope hash remains fresh.
- Add stale/fresh review semantics where needed in runtime.
- Define consolidated review as a timing/scope policy, not a new review class.
- Define note-only micro-fix recording expectations.
- Define shared material scope hash inputs for review freshness.
- Treat demo scenario and falsifier set changes as material re-review triggers.
- Update tests and docs/help output.

Не входит в scope:

- Удалять code/security/spec reviews.
- Запрещать full review for micro-fix when trust boundary or security posture changed.
- Требовать audit/review на каждый protocol step.
- Возвращать тяжёлый старый workflow.
- Phase 1 queue/spec/plan scaffolding, Phase 2 lock safety, or Phase 3 live-app evidence implementation except where review freshness depends on those contracts.
- Добавление новых обязательных artifact families. Prefer strengthening existing work item body contracts and existing verification/review artifacts over adding new mandatory artifact families.

## Proposed Resolution

1. Добавить active guidance:

   ```md
   Do not create a full review bundle for every micro-fix unless the micro-fix changes trust boundary, source interpretation, capability claim, security posture, or acceptance criteria. Prefer one consolidated review before closure for a sequence of stabilization fixes in the same active WI.
   ```

2. Define consolidated review as timing/scope policy, not a new review class.

   ```md
   Consolidated review is a timing/scope policy, not a new review class.

   It does not replace required review classes. If the work requires spec-conformance, code, and security reviews, the final selected review bundle must still contain fresh eligible PASS artifacts for those required classes.
   The consolidation means they assess the final material scope after stabilization, not every micro-fix separately.
   ```

3. Move concept-conformance timing to `plan-slice`.

   Требуемая формулировка:

   ```md
   Capability work requires concept-conformance review before `plan-slice` closes.
   Implementation closure reuses that review if the material scope hash remains fresh; otherwise the review must be rerun.
   ```

4. Define material re-review triggers.

   Re-review is required when a change affects:

   - trust boundary;
   - IPC/security/persistence posture;
   - source interpretation;
   - capability claim;
   - acceptance criteria;
   - `Spec Compact`;
   - `Plan Slice`;
   - implementation surface named in AC-to-evidence matrix;
   - live-app evidence path for user-visible capability;
   - demo scenario;
   - falsifier set.

5. Define a shared material scope hash contract.

   Material scope hash for a work item must include:

   - capability refs and capability claim;
   - delivery kind;
   - source refs and source hashes;
   - acceptance criteria;
   - negative AC/falsifiers;
   - anti-claims;
   - `Spec Compact` body hash;
   - `Plan Slice` body hash;
   - `Integration Path`;
   - AC/evidence/falsifier matrix;
   - risk profile;
   - dependencies that affect runtime path;
   - implementation surface when recorded;
   - accepted change-proposals;
   - demo scenario and falsifier set.

   Material scope hash should use normalized material sections, not raw full-body hashes.

   Normalization should ignore insignificant whitespace and may ignore explicitly non-material note sections. Changes to required material subsections, AC matrix, `Integration Path`, risks, falsifiers, or evidence mapping remain material.

   Do not hash the entire Markdown body blindly if that would invalidate reviews for purely editorial changes outside material sections.

6. Define when micro-fix notes are enough.

   Micro-fixes can be recorded as verification/stage notes when they:

   - stay inside the same trust boundary;
   - do not change capability claim or acceptance criteria;
   - do not alter security posture;
   - do not change source interpretation;
   - do not add a new production entrypoint;
   - only stabilize implementation inside already-reviewed material scope.

   A note-only micro-fix must still be visible in at least one dossier artifact:

   - stage log;
   - verification artifact summary;
   - changeset summary.

   It must not disappear from the dossier entirely.

7. Require one consolidated review bundle before implementation closure for a sequence of stabilization fixes.

   The consolidated review bundle must assess final diff/scope against:

   - capability claim;
   - `Spec Compact`;
   - `Plan Slice`;
   - AC/evidence/falsifier matrix;
   - relevant trust boundaries;
   - live-app evidence obligations where applicable.

8. Record cross-phase dependency.

   ```md
   Phase 4 depends on Phase 1 material scope sections and Phase 3 evidence-path semantics. Do not implement review freshness in isolation from Spec Compact, Plan Slice, AC/evidence/falsifier matrix, and Integration Path.
   ```

## Alternatives Considered

- Keep full review for every micro-fix. Отклонено: analysis says more PASS artifacts can reduce clarity and review signal.
- Remove repeated reviews entirely after first PASS. Отклонено: material scope/trust/security/source changes need fresh review.
- Keep concept-conformance only before implementation closure. Отклонено: weak or infrastructure-only plans need to be caught before implementation.
- Add a new review type. Отклонено: existing `concept-conformance-reviewer`, code review, security review and spec review can handle this if timing/freshness is corrected.
- Treat consolidated review as a single replacement for all review classes. Отклонено: this would weaken safety; consolidation only controls timing and final scope.

## Destructive Side Effects

- Agents may under-review changes by labeling them micro-fixes. Mitigation: explicit material re-review triggers and closure consolidated review.
- Runtime freshness hashes may be too broad or too narrow. Mitigation: start with conservative material scope hash over source/capability/acceptance/spec/plan/surface/trust-boundary inputs.
- Moving concept review earlier can block implementation sooner. Mitigation: this is intended safety; Phase 4 reduces repeated concept review if scope remains fresh.
- Consolidated review may hide individual fix rationale. Mitigation: micro-fixes remain recorded as verification/stage notes.
- Consolidated review could be misread as replacing required review classes. Mitigation: explicitly require a fresh eligible PASS artifact for every required review class in the final review bundle.

## Verification

Функциональная проверка должна include and extend runtime acceptance tests from the analysis:

- `stage close --stage plan-slice` blocks capability work without fresh concept-conformance review.
- Implementation closure reuses the plan-slice concept-conformance review only when material scope hash remains fresh.
- Implementation closure blocks or requests rerun when capability claim, acceptance criteria, `Spec Compact`, `Plan Slice`, trust boundary, security posture, or implementation surface changed after review.

Additional review-noise tests:

- A sequence of micro-fixes inside the same material scope can be recorded without creating a full review bundle for each micro-fix.
- Closure requires one consolidated review after such a sequence.
- A micro-fix that changes trust boundary or security posture cannot be treated as note-only.
- Consolidated review does not create a new review class and does not replace required spec/code/security review classes.
- Note-only micro-fixes are still visible in a stage log, verification artifact summary, or changeset summary.
- Demo scenario or falsifier set changes invalidate stale reviews and require fresh review where applicable.
- Review freshness hash includes Phase 1/3 material scope inputs: `Spec Compact`, `Plan Slice`, `Integration Path`, AC/evidence/falsifier matrix, and live-app evidence path.
- Material scope hashing uses normalized material sections and does not stale reviews for purely editorial changes outside material sections.

- `scripts/dossier-engineer.mjs` rebuilt from `src/*`;
