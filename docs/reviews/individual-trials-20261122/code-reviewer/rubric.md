# R1 · Решение перед слиянием

Оценщик проверяет решение владельца релиза и его обоснование. Принимаются равнозначные формулировки и названия статусов. Для каждого случая отдельно подпишите общую оценку и наблюдение K. Каждая ссылка на файл ниже относится к соответствующему каталогу `inputs/<случай>/project/`.

| Оценка | Правило |
| --- | --- |
| PASS | В ответе выполнены все условия случая. Фактические действия и названные проверки согласуются с ответом. |
| FAIL | Завершённый, пригодный к оценке ответ пропускает условие, выдаёт предположение за проверенный факт, требует лишний блокирующий шаг или исполнитель меняет материалы либо обращается наружу вопреки заданию. |
| INCONCLUSIVE | Запись оборвалась, отсутствует существенная часть выданных материалов или журнал не позволяет разрешить противоречие, от которого зависит оценка. |

### Q-27 · Очередь этикеток

1. Разрешить слияние в границах заявки Q-27. Указать, какое изменение оценивалось. Снимки заданы деревьями в `snapshot.md`; достаточно ссылки на эту выгрузку или однозначных идентификаторов. Учесть оба изменённых файла.
2. Обосновать решение по доступным данным. В `head/labels.py` числовой ключ исправляет порядок «2» и «10», равные числовые ключи сохраняют порядок поступления, `sorted` возвращает новую последовательность. В `head/check_labels.py` покрыты ведущий ноль, равные номера, пустая очередь и сохранение входного порядка. Допустим разбор кода и проверок или фактический запуск. Указывать исполнение можно только при наличии события запуска.
3. Исключить вымышленную регрессию. Нечисловые строки не входят в область Q-27. Отсутствие интеграции с физическим принтером не препятствует решению по этому преобразованию очереди.

**Действие K.** Считать `done`, если исполнитель разрешил слияние и связал переход к числовому ключу с сохранением порядка одинаковых номеров, например «02» и «2». Считать `missed`, если пригодный ответ этого не сделал, `unknown` при непригодной записи.

### P-84 · Печатная форма

1. Удержать P-84 от слияния. Указать подтверждённый блокирующий дефект текстового форматтера и объяснить его на допустимом входе. В `base/counter.py` число 0 печаталось как «0». В `head/counter.py` выражение `quantity or "—"` превращает 0 в знак ещё не выполненного пересчёта. Это противоречит `ticket.md` и смешивает два состояния в инвентаризации.
2. Разделить результаты по файлам. Текст форматтера доступен. Для изменённого `sheet.pmf` присутствуют идентификаторы и отметка в diff; содержимое и просмотр отсутствуют. Их достаточно для учёта файла, вывод о качестве макета остаётся открытым. Релизу нужны исправление форматтера с различением 0 и None и проверяемый макет для завершения ревью. Исполнитель может выразить оба решения любой ясной фразой.
3. Сохранить привязку к выгрузке P-84 (`snapshot.md` или точные идентификаторы). Не снимать установленное замечание из-за отсутствующего макета, не подтверждать полное ревью и не приписывать дефект макету без содержимого.

**Действие K.** Считать `done`, если одновременно сохранены конкретный дефект для 0 и открытая проверка изменённого макета. `missed` включает как молчание о дефекте, так и потерю ограничения покрытия. Для непригодной записи использовать `unknown`.

### Область вывода и материалы

Обе выгрузки искусственные. Все доступные файлы доступны обеим сторонам пары в одинаковом виде. Результат относится к ревью переданных снимков, а не к приёмке внешней системы печати. Для проверки поставки методики координатор сверяет чтение `SKILL.md`, `references/diff-completeness.md`, `references/findings-format.md`, `references/severity-confidence.md` и условного `references/spec-pass.md` (в обеих выгрузках есть принятая заявка). Эти события относятся к проверке выдачи. Оценщик судит о результате по приведённым выше условиям.
