# R1 · Приёмка по согласованным требованиям

Оценщик связывает каждое решение с условиями поставки, исходниками и свидетельствами исполнения. Принимаются эквивалентные формулировки, включая ссылки, однозначно указывающие на нужное требование без буквального ID. По каждому случаю отдельно подпишите общую оценку и действие K. Указанные ниже пути относятся к соответствующему каталогу `inputs/<случай>/project/`.

| Оценка | Правило |
| --- | --- |
| PASS | Выполнены все условия случая. Решение о приёмке подкреплено приведёнными основаниями и наблюдаемыми действиями. |
| FAIL | При пригодной записи отсутствует существенный требуемый вывод, заявлена неподтверждённая проверка, придуман блокирующий критерий или выполнены запрещённые правки либо внешние операции. |
| INCONCLUSIVE | Нельзя оценить выполнение из-за оборванной записи, повреждения входа либо недоступного существенного наблюдения. |

### K-17 · Маркировка платформы

1. Разрешить приёмку K-17 по утверждённой редакции 3 в `spec.md`. Проверить полноту по LT-1 … LT-3 в границах трёх указанных каналов. Ответ должен позволять понять, какой комплект и какие требования прошли.
2. Привязать решение к публичной команде. `route_tag.py` и `check_cli.py` дают прямое доказательство по всем трём вызовам, байтам Y/B/G с LF и успешному коду завершения. Достаточны проверенный разбор фактического входа/выхода через программный вход либо наблюдаемый запуск. Запуск следует заявлять только при наличии события.
3. Не ставить приёмку в зависимость от поведения для других аргументов либо от внешнего оборудования. Договор явно описывает локальную команду и исчерпывающий набор входов.

**Действие K.** `done`, если ответ разрешает приёмку и связывает три требуемых результата с публичной командой и проверкой stdout/завершения. `missed`, если наблюдаемый ответ пропустил это действие; `unknown` при непригодной записи.

### N-42 · Ведомость печати

1. Отказать в приёмке по подтверждённому обязательному отклонению PN-2, даже при остающемся пробеле PN-3. `requirements.md` редакции 4 утверждена для поставки. Обсуждение D-51 ещё ждёт согласования и не меняет обязательное представление неизвестной массы. `notice.py` возвращает строку «0» для None вместо пустой строки; `check_notice.py` закрепляет ошибочное ожидание. Указать связь наблюдения с контрактом и направление исправления.
2. Оценить PN-1 положительно с привязкой к `make_record`, где идентификатор передаётся без изменения. Выполненное требование сохраняется в итоговом покрытии.
3. Выделить предел доказательств PN-3. В тесте `DeskArchive` сохраняет значение в словаре одного процесса. Реализация штатного архива и проверка чтения после перезапуска терминала в комплекте отсутствуют. Отметить недоказанность PN-3, назвать необходимое свидетельство либо владельца. Считать установленное отклонение PN-2 достаточным для отрицательного итога. Отсутствие данных об архиве само по себе не доказывает его неисправность.

**Действие K.** `done`, если ответ одновременно даёт отрицательный итог по PN-2 и оставляет PN-3 недоказанным, различая локальный словарь и поведение терминала после перезапуска. `missed` при пропуске одной из этих частей в пригодном ответе, `unknown` при непригодной записи.

### Область вывода и материалы

Это искусственные поставки. K-17 допускает полноценную локальную проверку публичной команды. В N-42 можно проверить публичный форматтер локально; поведение оборудования специально оставлено вне наблюдения. Для проверки поставки методики координатор сверяет чтение `SKILL.md`, `references/methodology.md` и `references/reporting.md`. Контракты не задают условий допуска или отказа в действии. Оценщик проверяет результат по условиям случаев независимо от названия применённой методики.
