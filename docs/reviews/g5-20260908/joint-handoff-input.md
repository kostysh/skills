# J1 — потребление фактической передачи approval в PRD

Дополнительная проверка прямого межскиллового контракта по принятому плану; подготовлена после source freeze, не является baseline/candidate сравнением. Исполнителю передаётся только раздел «Задание», без критериев.

## Задание

Используй prd-engineer. Обнови короткий черновик PRD в ответе, без записи в репозиторий или tracker и без передачи в разработку. Продуктовый владелец поручил отразить принятый ответ заказчика; одобрения новой редакции ещё нет. Текущий черновик: сотрудник получает готовый отчёт в кабинете; канал уведомления Q-17 пока TBD; срок хранения Q-18 пока TBD. Прочих требований нет. Вход от requirements-approval — фактический результат проверки предоставленного ответа:


Проверка предоставленного ответа завершена: **Q-17 решён по содержанию; Q-18 остаётся без выбранного срока. Общий workflow: `partial`.**

| Код | Источник и полномочия | Answer | Workflow | Принятое обязательство и остаток |
| --- | --- | --- | --- | --- |
| Q-17 | Предоставленный полный действующий ответ уполномоченного заказчика: «Только в кабинете, email не нужен» | `complete` | `partial` | Уведомлять о готовом отчёте только в кабинете, без email. В PRD ещё не внесено; follow-up не назначен. |
| Q-18 | Предоставленный ответ того же заказчика: «О сроке хранения сообщу позже» | `non-answer` | `partial` | Срок хранения не выбран; обещание ответить позже не задаёт ни срок хранения, ни дату ответа. Следующий владелец решения — заказчик. |

Передача владельцу PRD (`prd-engineer`), подготовленная к использованию:

> Q-17: основание — текущий ответ уполномоченного заказчика «Только в кабинете, email не нужен». Отразить в требованиях уведомление о готовом отчёте только в кабинете и отсутствие email. Связать изменение с Q-17 и вернуть ссылку на точное изменение и версию документа с соблюдением правил её одобрения. Если внесение отложено, оформить связанный follow-up с точным обязательством, владельцем, модулем, условием активации, ожидаемым подтверждением выполнения, маршрутом возврата доказательств и обратной ссылкой на решение Q-17. Этот текст передачи сам по себе ещё не такой follow-up.
>
> Q-18: сохранить срок хранения как нерешённый вопрос за заказчиком; не подставлять значение. Получение Q-18 не является условием отражения независимого решения Q-17.

Исследование ограничено предоставленными сообщениями; их полномочия и актуальность заданы условием, а не проверены через почту. Внешних действий и правок документов не выполнено, состояния GitHub не наблюдались. Q-17 нельзя объявить `verified`: пока нет устойчивого внесения решения или назначенного связанного follow-up. Q-18 требует последующего содержательного ответа; это не мешает завершённой проверке сообщений и передаче Q-17. **Общий результат: `partial`.**


## Критерии (исполнителю не передавать)

Q-17 отражён только как кабинет без email, trace к точному принятому ответу сохранён; Q-18 остаётся открытым, независимый Q-17 не блокирован; новая редакция draft-only/non-authoritative, нет ложного approval или verified closure, нет внешних действий. Это наблюдение consumer usability одного handoff, не доказательство реального согласования/публикации.
