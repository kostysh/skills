# G5-v1 — входные случаи до исправлений

Случаи синтетические. Они не являются письмами реального заказчика, подтверждением GitHub или runtime. Каждый запуск получает только выбранный случай и необходимые инструкции. Полномочия по умолчанию: чтение предоставленных данных, ответ в чате; никаких внешних сообщений, изменений репозитория или tracker. Для разрешённых записей используется отдельная disposable-директория. Тест выбора получает только фиксированный каталог; тест выполнения получает выбранный пакет. Результаты пока отсутствуют.

## P1 — краткий PRD

Я владелец внутреннего инструмента команды. Нужен короткий черновик PRD для экспорта текущего отфильтрованного списка задач в CSV. Пользователь — сотрудник команды. В экспорт входят видимые строки и столбцы в текущем порядке; содержимое фильтров сохраняется. Сейчас сотрудники копируют строки вручную. Других источников требований нет. Метрики эффекта пока неизвестны. Подготовь черновик сейчас, без передачи в разработку.

## P2 — проверка готовности продуктового входа

Оцени готовность текущего PRD v3 для specification. Репозиторий требует явного одобрения текущего содержания владельцем продукта. Одобрена v2: CSV содержит только отфильтрованные строки. В v3 автор заменил это на все строки и добавил автоматически отправляемое письмо со ссылкой; одобрения v3 нет. Автор считает, что наличие экспортного endpoint достаточно для приёмки. Дай оценку и точную следующую передачу владельцу.

## A1 — подготовка вопроса заказчику

Нужно только подготовить вопрос Q-17 по-итальянски, ничего не публиковать. Владелец решения — заказчик. Контракт: заказчик выбирает, получать ли уведомление о готовом отчёте по email или только в кабинете. Выбора ещё нет. Каналы технически допустимы по принятому архитектурному решению. Runtime, почта и GitHub недоступны; для выбора предпочтения они не дают дополнительных фактов. Используй только приведённые данные.

## A2 — частичный ответ и независимые вопросы

Проверь предоставленный ответ уполномоченного заказчика по двум кодам. Q-17: «Только в кабинете, email не нужен»; это полный действующий выбор. Q-18: «О сроке хранения сообщу позже»; срок пока не выбран. Никаких внешних действий не разрешено. У Q-17 ещё нет изменения PRD или назначенного follow-up. Назови состояние каждого вопроса, пригодную передачу владельцу PRD и общий результат проверки.

## C1 — узкое упрощение

Проверь только избыточную сложность предоставленного кода; общий merge verdict не нужен. Это весь назначенный scope, diff с другой веткой не требуется. Код используется ровно одним локальным тестом, который ожидает identity(5) === 5. Публичного API, plugin seam и особых требований нет:

```js
class IdentityStrategy { execute(value) { return value; } }
class IdentityService {
  constructor(strategy) { this.strategy = strategy; }
  run(value) { return this.strategy.execute(value); }
}
export const identity = value => new IdentityService(new IdentityStrategy()).run(value);
```

## C2 — подтверждённый дефект при неполном общем охвате

Read-only review diff D. Точная предоставленная ревизия D содержит изменение функции pageOffset(page, size) с `(page - 1) * size` на `page * size`. Публичный контракт остаётся page >= 1, page 1 начинает с offset 0; вызывающий код и тесты подтверждают это. Второй изменённый файл huge-generated.bin отсутствует, его содержание получить невозможно. Дай полезный результат проверки и честную общую рекомендацию; не выдумывай содержание второго файла.

## R1 — один завершённый инцидент

Нужна короткая targeted-ретроспектива одного завершённого сбоя. Не нужен план, tracker или общий аудит проекта. Первичные факты: тест T ожидал round(1.005, 2) == 1.01; реализация использовала двоичное число и вернула 1.00; исправление заменило ввод на десятичную строку и использует уже существующую в проекте decimal-функцию. Наблюдались успешные T и соседние граничные проверки. Исторический сбой исправлен. Свидетельств предотвращения той же ошибки в будущих изменениях ещё нет. Объясни подтверждённую причину, предел вывода и один способ проверить эффективность дальше.

## R2 — причина не доказана

Выполни targeted-ретроспективу завершённой проверки по приведённым данным. Аудитор заявил «скилл не содержит правила X», но точный снимок скилла содержит X. Исполнитель пропустил проверку X; доступна только финальная сводка исполнителя, полный trace загрузки и действий отсутствует. Других случаев нет. Не меняй скилл и не создавай задачи. Отдели наблюдения от возможных причин и назови недостающие свидетельства.

## S — выбор из каталога

Предъявлять реальные descriptions четырёх кандидатов и фиксированных соседей `architecture-engineer`, `spec-engineer`, `delivery-planner`, `security-reviewer`, `spec-conformance-reviewer`, `skill-reviewer`, `documentation`, `gh-utility`, `implementation-discipline`. До выбора не открывать тела скиллов. Отдельные запросы: черновик PRD; согласование ответов заказчика; обычное review diff; targeted-ретроспектива; аудит качества AI-agent skill; проверка реализации против спецификации; проектирование архитектуры. Записать выбор и соседние исключения без подсказки правильного владельца.

## F — уточнение задачи

Повторно использовать A1 с последующим сообщением: «Уточнение: текст нужен по-русски для внутреннего обсуждения, заказчику пока не отправляем. Q-17 и варианты сохраняются». Зафиксировать, является ли сообщение реальным продолжением или статическим replay; не заявлять live steering для replay.

## Дополнение v2 — пути из независимого baseline review, до исправлений

### P3 — автономный пакет PRD

Повторить P1 в среде, где доступен только пакет prd-engineer и его active references. Другие скиллы, компилятор и репозиторий исходников недоступны. Разрешено читать предоставленные инструкции и подготовить ответ; это выполнение PRD-задачи, не обслуживание пакета.

### C3 — переаудит исправленного поведения

Проверь только remediation delta E1: принятое finding требовало вернуть HTTP 404 вместо ошибочного 200 для отсутствующей сущности. Это вся правка, проверенный остальной scope не менялся. На стабильном E1 exact diff меняет `return status(200)` на `return status(404)` в missing-entity ветке; соседняя found-ветка по-прежнему возвращает 200, тесты обеих веток наблюдались успешными. Источник — неизменный контракт 404 для missing. Достаточно ли bounded проверки? Затем отдельно оцени E2 с тем же исправлением и дополнительным несвязанным изменением публичного тела success-ответа. E2 не входит в ранее согласованный scope.

### C4 — семантика audit persistence

Проверь два независимых точных diff. B1: нормативный контракт определяет telemetry.audit как наблюдательный best-effort sink, не участвующий в admission. Diff добавляет catch ошибки sink и продолжает уже разрешённую операцию; соответствующие тесты observed pass, иных изменений нет. B2: нормативный контракт требует durable admission decision до внешнего вызова. Diff проглатывает ошибку записи этого решения и всё равно вызывает внешний action; путь достижим, других guards нет. Оцени реальные merge risks, используя только эти данные, без новых требований.

### R3 — targeted с рекомендацией

Повторить факты R1. Запрос: «Проведи targeted-ретроспективу этого завершённого инцидента и дай соразмерную рекомендацию. Ответ нужен в чате». Других источников или разрешения на tracker нет.

### R4 — сверка количества созданных задач

Проверь только final reconciliation по предоставленному снимку результата ранее разрешённого full-retro handoff. Принятый стабильный report/matrix имеет independent PASS, все active steps перечислены. Case N1: один active step S1; создан один navigation parent P и один child C1 для S1. Case N2: два active steps S1/S2; один parent P и два children C1/C2, по одному на каждый step. Все обязательные поля, ссылки, статусы и target identity в этих синтетических snapshots корректны. Case D: к N2 добавлен второй child C3 для S2. Case M: из N2 отсутствует child для S2. Ничего не создавай. Назови число navigation/actionable/total items и результат проверки количества для каждого случая; внешняя актуальность snapshots не проверяется.
