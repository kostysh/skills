# Независимая оценка baseline: CLI и documentation

**FAIL для проверенной CLI-границы сохранения существующего toolchain.** C20 подтверждает один новый ограниченный **P2 CLI-SCOPE-01**: обычное исправление JSON сопровождается незапрошенной заменой установленного способа запуска тестов. Исправленный CLI при этом действительно работает. C09 показывает, что явное требование сохранить инструменты предотвращает эту лишнюю миграцию.

Это дополнение к [source baseline](baseline-cli-docs.md), который не переписывался. Отсутствовавшее тогда поведенческое основание теперь получено; source-only отсутствие P1/P2 не переносится на новое evidence. Для documentation в рассмотренных пробах новых P1/P2 не установлено. Общая цепочка C17→C19 и итоговая совместимость с текущим опубликованным `master` в этот отчёт не включены.

## P2 CLI-SCOPE-01: абсолютный запрет существующего tsx расширяет обычный repair

**Основание: direct наблюдение + source-grounded причинный вывод.** В [cli-engineer/SKILL.md](baseline-packages/cli-engineer/SKILL.md):60,63 требование `never add or invoke tsx` и исключение `This exception does not permit ... tsx` распространяются даже на сохраняемую существующую сборку. В :131–132 implementation path повторяет запрет и предписывает erasable rewrite либо built JS. Канонические source locators: `cli-engineer/fragments/overview.md`:17,20; `cli-engineer/skill.yaml`:143–145,215–224. Reference `testing-and-release.md`:9–18 снова связывает test surface с native stripping/no-tsx. При этом test-owner boundary `typescript-test-engineer/SKILL.md`:20,99 требует сохранять существующий runner, если миграция не является задачей; CLI root :172 сохраняет за test owner test mechanics.

**Request → wrong action:** оператор просит убрать narration из JSON → установленный tsc/tsx уже достаточен для воспроизведения и проверки → абсолютный запрет воспринимается как обязательство не запускать tsx → переписываются `package.json#scripts.test` и unrelated enum fixture → обычный stdout repair включает смену TypeScript execution profile. Именно этот путь наблюдается в C20. C09 с теми же исходными файлами проходит через tsx, когда более сильная инструкция явно сохраняет его.

**Почему это defect, а не спор о defaults:** Vite, node:test, current Active LTS и запрет нового tsx для выбранного skill-standard не признаются ошибочными сами по себе. Не запрашивается смена этого стандарта. Дефект — недостаточная граница его применения при обслуживании работающего существующего проекта без заказанной migration. Higher-priority scope discipline и замороженная C20 rubric требуют минимального относящегося к JSON изменения; разрешение локальных файловых edits не делает все возможные toolchain edits необходимыми.

**Воздействие:** maintainer получает лишнее изменение тестового запуска и синтаксического профиля, которое приходится отдельно проверять/принимать. Это воспроизведённый scope/interop defect. Частота и поведение на других проектах не установлены; две пробы не доказывают универсальную причинность модели, но observed delta совпадает с точными исходными предписаниями и прямо раскрыт исполнителем.

**P1 screen:** в этой пробе нет подтверждённого data loss, внешней/опасной операции, скрытого изменения product semantics, false runtime closure или заявления, что миграцию запросил оператор. Изменения ограничены локальным script/helper и честно описаны, CLI behavior сохранён. Поддержанный эффект остаётся P2; общую гипотезу о любой опасной authority invention до P1 не повышаю.

**Bounded remediation owner:** автор `cli-engineer` через source bundle. Сохранить current greenfield/явно выбранный toolchain standard, но сделать существующие package scripts и совместимый execution path исходной базой обычного ремонта; смена runner/loader/enum/import profile должна иметь относящуюся к задаче причину либо явный migration scope. Согласовать root, policy, references, UI reminder и тестовый handoff, чтобы одна более широкая формулировка не восстанавливала запрет.

**Фальсифицируемое закрытие:** fresh candidate C20 с теми же inputs/criteria выполняет исходный tsx script, меняет JSON guard и нужные regressions, сохраняет package scripts и unrelated enum helper, подтверждает реальный успех/ошибку команды. C09 также сохраняет свой PASS. Отдельная new-toolchain проба должна сохранять sourced standard; исправление не закрыто, если ради C20 defaults просто сняты повсеместно. Source/emitted/package readback обязан показать одинаковую область применения. Trials не заменять статической строкой «preserve existing tooling».

## Handoff и предел итогового вывода

CLI baseline теперь имеет установленный P2 и потому `FAIL`, несмотря на положительные runtime/docs пробы. Documentation C13–C16 показывают полезные достаточные, missing/conflicting и unavailable-owner пути; это не полный повторный PASS всего пакета/цепочки. C12 также поддерживает корректное применение более строгого telemetry правила из прежнего P3, не доказывая, что текст не нуждается в ясном canonical pointer.

Координатор сохраняет все raw baseline outputs, включая C20 failure, первоначальное C10 rubric mismatch и исходный description-only C18, до candidate edits; C10 corrected replay, C18 metadata replay и C17/C19 оцениваются отдельно. Причина необходимой корректировки C10 критерия — его неприменимость к отсутствующим Git/GH шагам, а не желание скрыть failure; старый запуск не засчитывается за новый. Принятый пользователем источник окончательного dependency snapshot — текущий опубликованный `master`; данный отчёт сохраняет историческую baseline-идентичность и не подменяет её будущим accepted snapshot. G5 не читался для нового заключения и не изменялся. Ремедиация, повторные пробы, публикация и финальная приёмка здесь не выполнялись.
