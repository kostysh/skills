# Протокол сравнительных испытаний

Зафиксирован до правок target sources, 2026-09-08. Основание — принятый план и стандарт, критерии не выводятся из будущего candidate. [Закрытые критерии](closed-criteria.json), [хэш критериев](criteria.sha256), [снимок исходных случаев](cases-snapshot.json).

19 случаев: C01–C04 TypeScript, C05–C08 Node, C09–C12 CLI, C13–C16 documentation; для каждого четыре состояния sufficient/missing/conflicting/unavailable. C17 — совместный исполняемый сценарий, C18 — отдельный catalog-only выбор 13 владельцев, C19 — потребление результата C17 соседями. C19 оценивает естественно различающиеся выходы upstream C17 по одинаковому запросу/критериям; одинаковый исходный вход гарантируется на уровне всей цепочки C17→C19, а не байтов produced handoff.

Все исполнители: назначены GPT-6 Astra, high, fork=none. Назначенные параметры сохраняются в run-index; независимая телеметрия фактически выбранной backend-модели не доступна. Автор случаев/будущего candidate — root; executor — новый агент для каждого случая/варианта; root сохраняет результаты и предварительную оценку, независимый reviewer проверяет критерии, raw evidence и side effects. Executor не присваивает себе независимую приёмку.

Исполнителю доступны task.md, app и нужные активные инструкции. Trial copies исключают source bundles, supporting history, evals/answer keys; включают SKILL.md, references, assets, agents и scripts при наличии. File hashes и список исключений записаны в run-index. При каталожном выборе тела не копируются. В missing-dependency случаях runtime catalog ограничен явно. Остальные соседи взяты из frozen baseline.

Общий filesystem технически доступен агентам: ограничения чтения — явные инструкции, не hard sandbox. Корневой каталог нейтрален и не содержит baseline/candidate в имени; исполнителям запрещены другие runs, repository history, memory и ожидаемые ответы. Общие higher-priority правила среды остаются фактором поведения, одинаковым для обеих версий.

Для raw command evidence используется одноразовый Python subprocess recorder в каждом временном task root: command/cwd/stdout/stderr/exit/time/timeout сохраняются непосредственно из subprocess результата. Это временный сборщик вывода, не новый shipped runtime или постоянный испытательный framework. Чтение/редактирование может выполняться напрямую; before/after product files проверяются отдельно. RESULT.md — ответ исполнителя, не доказательство команд вместо commands.jsonl.

Shared preinstalled fixture tooling: TypeScript5.9.3, tsx4.20.5, ts-node10.9.2, @types/node24.0.0. Точный package-lock сохраняется как setup evidence. Source snapshot исключает node_modules, которые подключены read-only по назначению из общего временного toolchain. Проверяемая фактическая Node — v24.15.0; остальные версии подтверждаются только явно указанными источниками, а не фиктивными запусками.

Сохранить все результаты, включая FAIL и INCONCLUSIVE. Непредвиденная ошибка самого fixture/recorder требует отдельной записи причины и симметричного исправления сравнения; не менять продуктовую рубрику под ответ. Более узкое source-level воспроизведение найденных примеров и structural checks отмечаются отдельно от blind trials.

## Исправление двух ограничений подготовки до candidate

C10 первоначально требовал именовать Git/GH owners даже в npm-only handoff, который не предлагает этих действий. Независимый assessor отметил отсутствие этих имён; это не source-дефект и не основание расширять каждый npm-only ответ. По owning task и правилу условного interop рубрика v3 требует сохранить границу полномочий и маршрутизировать владельцев только при предложении соответствующих шагов. v2 и исходный run сохранены. C10 повторяется до candidate по неизменному task input; все остальные критерии неизменны. C19 сохраняет явную проверку всех9 владельцев.

C18 первый run проверил только descriptions (13/13 primary choices), без UI metadata. Он сохранён как descriptions-only, не как полный catalog+metadata claim. Исправлен временный input collector: теперь в каталог включаются существующие skill metadata и agents/openai.yaml, тела по-прежнему отсутствуют. C18 повторяется до candidate с теми же13 запросами/критериями и той же моделью; одинаковый collector используется для candidate. Это исправление полноты input, не подгонка ответов.


## C19: ошибка сбора фактических producer artifacts

Первый candidate C17 корректно сохранил tarball и установленный bin в `artifacts/`, указал их в HANDOFF и выполнил README. Сборщик C19 копировал только каталог с буквальным именем `installed`, поэтому потребитель не получил реально существовавший артефакт. Исполнитель C19 обнаружил отсутствие и удержал claim. Это дефект collector, не отсутствие результата C17 и не finding навыка. Неполный C19 сохраняется отдельно как INCONCLUSIVE для сравнения end-to-end; полезное обнаружение gap не скрывается.

Исправление временного collector копирует все producer output directories, кроме отдельно скопированного app и active skills, сохраняя относительные пути. Никакого предписанного имени каталога результата в task C17 не было. Одинаковый collector и пояснение rel-path применяются в fresh baseline/Candidate C19 повторах. Критерии v3 не меняются, active packages неизменны; оригиналы коллектора и все runs сохраняются. Другие случаи не затронуты.
