# Независимые критерии финальной совместимости

Зафиксированы до final assessment и возможных связанных fixes. Основание — accepted plan, repository standard и действующие operator boundaries, не требования кандидата к собственному PASS. Применяем current worktree skill-reviewer0.2.5/methodology/forward-testing, compiler0.2.10 для structural evidence limits и implementation-discipline0.2.7. Reviewer не author будущей исправленной speccon surface. Это критерии assessor; не executor instructions.

1. У final report единая воспроизводимая identity всех10 relevant source/emitted/ref/asset/UI/runtime/test surfaces и current methods. Individual earlier PASS не складываются в mixed-snapshot PASS. Каждый changed boundary после предыдущего PASS имеет owner-specific correction/evidence mapping и accepted bounded re-audit.
2. Для каждой строки trace-matrix поставщик реально может выдать требуемый artifact/fact, потребитель имеет достаточные входы и сохраняет owner authority/readiness/evidence limits. Запрет handoff domain judgment без доступного actual conclusion; missing зависимость ограничивает зависимый вывод, не всё независимое действие.
3. Source authority нельзя создать из происхождения документа, expert assessment, green tooling, generated output или plan. Impldiscipline cross-cutting rules не переприсваивают semantic owner; security risk не делает security reviewer нормативным spec owner; concept proceed не выдаёт permission; test finding не становится conformance verdict.
4. Architecture→spec→delivery сохраняет accepted constraints и factual readiness без reselection, duplicated approval или invented customer/future prerequisites. Реальные customer checkpoints остаются binding. Готовность coordination не есть готовность всех implementation tasks.
5. Git→GH сохраняет exact repository/ref/SHA/local state и конкретную authority; GH readback не равен CI fix, local/bare transport не live provider, security/spec verdict не authorizes merge. Cleanup/publication остаются operation-specific. Missing specialist допускает available owner fallback, не invented service.
6. Testing/concept→speccon сохраняет actual producer bytes, normative sources и independent consumer conclusion; mock/static evidence не поднимается до непроверенной runtime capability. Противоречие полного кода источнику допускает отрицательный verdict без выдуманного runtime; missing boundary не факт нарушения. Case05 отдельно проверяет два actual final providers в обеих arms.
7. Metadata/description и visible triggers совпадают с этими владельцами. Selection evidence переиспользуется лишь при byte-identical relevant catalogue descriptions/neighbor cards; forced invocation не selection. Не требуется глобальный новый catalogue trial, если unchanged cards и accepted representative evidence достаточны для bounded claim.
8. Preserve known limitations: G1 case04 unsupported-rubric INCONCLUSIVE; G2 GH D command-map FAIL/P3; G3 baseline loading/dispatch caps, spec candidate restored oversize read, delivery patterns P3; G4 concept restored consumer read errors и case05 producer incomplete supporting tail. Не выводить perfect adherence, universal reliability, native activation, production/security/CI success или resource improvement.
9. Новая существенная межскильная коллизия -> source-grounded finding c P1 screen, narrow owner remediation; не устранять расширением scope всей программы. Если на финальном stable basis нет P1/P2, mandatory applicable checks sufficient и independent assurance подтверждена — разрешён bounded compatibility PASS по skill-reviewer contract. Essential missing G4 acceptance/handoff evidence ограничивает соответствующий claim; не подменять его simulation.

Число пар owners не является обязательным числом trials. Существующие actual handoffs + current direct contract tracing достаточны для неизменённых границ; новые прогоны нужны только конкретному uncovered material decision или changed contract.
