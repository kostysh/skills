# Предложения слепых испытаний: Payload и миграция

Статус: критерии предложены до candidate; исполнение НЕ проводилось. Автор случаев и будущий оценщик независим от автора исправлений; этим контекстом нельзя пользоваться как слепым исполнителем. Root должен зафиксировать окончательные raw tasks, закрытую rubric, payload-lockfile/fixtures и их SHA256 до изменения candidate и выдавать исполнителю только raw task и необходимые исходные файлы. Все случаи используют gpt-6-astra; назначенную модель и фактически доступные настройки записать отдельно от наблюдаемой runtime identity. Предлагаемые файлы fixture ниже пока не существуют.

## Нейтральные raw tasks для выборки из каталога

1. «После добавления собственного `/api/posts/related` обычный пользователь видит больше записей, чем в стандартном API. Найди причину в приложенном коде и исправь в временном проекте. Все нужные исходники приложены».
2. «Есть Contentful export, утверждённые коллекции Payload и разрешение на импорт в эту пустую локальную БД. Перенеси статьи, переводы, авторов и изображения; проверь результат в API и на существующей странице Next».
3. «Нужно убрать CLS у обычной страницы Next без CMS. Исправь работу изображения».
4. «Объясни ошибку условного типа TypeScript; Payload в проекте отсутствует».
5. «Спланируй перенос Strapi 5 в Payload по приложенным схемам и данным. Выполнять импорт пока нельзя».

Каталог: тестируемые описания, стабильные прямые соседи `nextjs`, `typescript-engineer`, `typescript-test-engineer`, `security-reviewer`; без тел скиллов до решения выбора. Отдельно зафиксировать естественный выбор и принудительно загруженное выполнение.

## Нейтральные raw tasks для выполнения

### P01 — обычная достаточная задача

«В приложенном локальном Payload-проекте добавь поле `subtitle` к Posts и верни его на существующей публичной странице. Установленные версии и команды бери из package.json и lockfile. Можно менять временный проект, запускать имеющиеся проверки. После сохранения документа проверь страницу при новом открытии».

### P02 — запросный доступ

«Временный проект содержит Posts с правилом чтения и endpoint `/related`. Реализуй endpoint, чтобы посетители получали те же допустимые записи, что стандартный API. Есть anonymous, user-A, user-B и admin; разрешено использовать только эту локальную БД. Докажи результат запросами для каждого пользователя».

### P03 — tenant и изменение ролей

«В проекте пользователи работают в своих организациях и могут создавать контент. Реализуй создание документов в организации текущего пользователя и администрирование ролей по приложенным требованиям. Проверь API, включая неподходящие входные данные».

### P04 — атомарность и сбой

«Создание Order должно обновлять Inventory и сохранять Audit. Временная SQLite БД разрешена. В приложенном hook после обновления Inventory можно включить контрольный сбой. Обеспечь заявленное поведение и покажи состояние БД после успешной и неуспешной операции».

### P05 — версии и старое приложение

«Исправь кастомную upload collection в приложенном приложении Payload 2.32.3. Обновление major и переписывание Next-интеграции не разрешены. Сохрани поведение для этой установленной версии».

Отдельная вариация с текущим 3.88.0 проектом и перенесённым старым `staticURL`: «Подключи эту upload collection и проверь выдачу файла по публичному URL. Исходник и версии приложены».

### P06 — несовместимые peers и defaults

«Собери plugin fixture из приложенного package.json и подключи его в Payload fixture. Определи совместимый набор в разрешённой временной среде и проверь импорт установленного пакета. Нельзя обновлять исходный продуктовый проект».

Fixture должен содержать Payload/@payloadcms 3.88.0, Next 15.4.10, React 19.2.1, старое описание SQLite atomic-by-default и R2-конфигурацию; raw task не называет диагнозы. Не запускать удалённый R2; если проверить его реально невозможно, требуется честная граница.

### P07 — jobs и plugin composition

«В fixture добавь двухшаговую фоновую задачу и plugin, который сужает доступ существующих коллекций до организации пользователя. Существующий read-access бывает синхронным, асинхронным и запрещающим. Все требуемые изменения разрешены локально; покажи очередь, выполнение и результат API».

### M01 — импорт с подтверждённой моделью

«Модель уже согласована: Authors, Media и Posts, локали en/it. Приложены Contentful export, изображения и mapping; можно импортировать в пустую локальную Payload БД и обновить существующий Next frontend. Выполни перенос, проверь данные в Payload API и публичную страницу после перезапуска».

Fixture: минимум 3 статьи, 2 автора, 2 изображения, nullable optional fields, 2 локали, одна статья со ссылкой на другую, богатый текст с форматированием, внутренней ссылкой и встроенным media; одна связная группа с циклическими ссылками. Source identity включает CMS/space/environment/content type/source ID и locale где требуется. Не выдавать fixture ключи диагностики.

### M02 — частичный сбой и повтор

Использовать тот же raw M01 с обычным дополнительным требованием: «Импорт должен поддерживать повторный запуск, включая прерывание процесса и временную недоступность одного изображения. Прогони эти ситуации и сравни с полным источником». Подготовить управляемый локальный HTTP fixture для 503 на первом media fetch и interruption после записи части документов. Запуск только после выдачи root свободного runtime слота.

### M03 — разные source shapes

«Подготовь точные mapping-функции для приложенных независимых примеров WordPress REST v2, WordPress export/database rows, Strapi 5, Contentful и Sanity. Примеры содержат даты, автора, rich text, файлы и локализации. Не делай импорт. Покажи сохраняемое значение Payload для каждого поля и укажи данные, которых не хватает».

Варианты фиксируются до candidate: WordPress `publish`/`private`/`future` и `date`/`date_gmt`; Strapi `documentId`, richtext Markdown и blocks JSON; Contentful `sys` links и locale objects; Sanity Portable Text с custom block и `_ref`; Unix seconds рядом с milliseconds. Не выдавать список ожидаемых преобразований.

### M04 — неполные и конфликтующие входы

«Нужно перенести данные в Payload; у меня пока только один пример статьи. Подготовь то, что уже можно определить, и назови необходимые уточнения». Отдельная вариация даёт два противоречивых owner mapping для taxonomy. Follow-up как реальное второе сообщение: «Зафиксируй status как enum согласно приложенной принятой схеме; авторов пока не переносим. Можно продолжить подготовку и проверку локального import script, запуск production запрещён».

## Закрытые критерии для оценщика — НЕ выдавать исполнителю

| Случай | Наблюдаемое поведение / falsifier |
| --- | --- |
| Selection 1/2/5 | Выбран Payload для endpoint и payload-migration для переноса; при Next presentation подключён nextjs с ясным handoff. Не считать forced execution доказательством activation. |
| Selection 3/4 | Не включать Payload/migration без его API; выбрать соответствующего владельца. |
| P01 | Использует installed version, existing scripts, конфиг загружается, запись читается через API и новая загрузка страницы показывает subtitle. Генерация types/сборка без наблюдения не закрывает страницу. Лишнее schema approval при достаточном входе — FAIL. |
| P02 | Local API с req и `overrideAccess:false`; anon/user A/user B не получают запрещённые строки. Само наличие req.user не доказательство авторизации. Нельзя заменить inherited policy allow-all. |
| P03 | Create проверяет boolean/data либо присваивает tenant сервером; клиент не может подменить tenant или создать администратора через role field. Update/self-creation/unauth denied для запрещённых случаев. Where на create, только update-защита roles и truthy bypass — FAIL. |
| P04 | Явно устанавливает поддержку транзакций adapter; SQLite включает `transactionOptions:{}`; передаёт тот же req и await. При искусственном сбое нет Order/Audit и Inventory не изменён. Переданный req без поддерживаемой транзакции не PASS. |
| P05 | Старый поддерживаемый snapshot сохраняет свою API ветку без самовольного upgrade; новый v3 исправляет удалённый staticURL по official migration guide. Утверждение о поддержке старого релиза ограничено доступными точными источниками. |
| P06 | Выявляет реально несовместимый peer, не принимает ^15.4.10 как гарантию совместимости при разрешённом 15.5; проверяет exact installed packages. Различает stable 3.88 / canary 4 и док-минимум Node от package engine. R2 binding и S3 endpoint не смешаны. Компиляция не доказывает удалённое хранилище. |
| P07 | Jobs зарегистрированы/queued/run/complete; API использует inlineTask stable signature. Access wrapper awaits original; false остаётся false, true получает tenant Where, Where объединяется с tenant. Никаких Promise/boolean элементов внутри and. Сохранены предшествующие hooks/config. |
| M01 | Переходит к разрешённой работе без повторного подтверждения уже принятой модели. Все исходные records/locales/media/relations учтены; rich text преобразован в соответствующий editor JSON и реально отображён. Source IDs не принимаются за Payload IDs без evidence. Reads c fallbackLocale:false отделяют переводы от fallback. |
| M02 | После fail статус partial с точными failed/skipped; durable identity map/checkpoint выживает restart. Повтор не дублирует records/media/relations; сравнение полных source ID sets с target, counts, missing/unexpected/duplicate IDs и representative content. Exit0 при swallowed exceptions не success. Транзакция БД не объявляется rollback внешних upload. |
| M03 | Каждому source shape соответствует явная conversion branch; нет «HTML напрямую в richText». WordPress статусы/часовой пояс, Strapi id/documentId и Markdown/blocks, Contentful assets/links/locales, Sanity Portable Text/refs обработаны или явно unverified. Unix seconds преобразуются с *1000; locale и nullable не выдуманы. |
| M04 | Поддержанная подготовка продолжается; реальные missing/conflicting facts названы. Не запускает production и не создаёт новые обязательные content types. Уточнение владельца сохраняется, не заставляет relationship вместо принятого enum. |

Для каждого исполнения нужны raw task, активная поверхность пакета, model/settings, exposure, actual tool trace, diff, durable artifacts, результат PASS/FAIL/INCONCLUSIVE и границы DB/API/browser/remote. Baseline и candidate используют одни и те же входы/rubric. API без browser readback не закрывает совместный migration→Payload→Next случай; browser без DB/ID reconciliation тоже недостаточен.
