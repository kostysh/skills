Доработай `hono-engineer`, `nextjs`, `electron-engineer`, `docusaurus-repo`, `supabase-engineer`, `payload` и `payload-migration`. Результат — корректное выполнение принадлежащих им задач, актуальные технические инструкции и согласованная передача ответственности смежным скиллам.

Обязательные источники: [стандарт скиллов](/home/kostysh/.codex/skills/custom/docs/skill-standard.md), `skill-reviewer` с методологией и правилами слепых испытаний, [GPT-6 Astra — Prompting best practices](https://developers.openai.com/api/docs/guides/latest-model#prompting-best-practices), официальная документация соответствующих фреймворков, платформ и используемых ими инструментов.

**1. Зафиксировать исходное состояние и проверить техническую актуальность**

- До изменений создать отдельный worktree через `git-engineer`; сохранить базовую ревизию и версии семи скиллов.
- Провести независимую baseline-оценку исходников, generated-инструкций, активных references, примеров, шаблонов, метаданных, команд и прямых межскилловых контрактов.
- До исправлений определить реалистичные входные случаи и критерии оценки; сохранить фактические baseline-результаты.
- Вести один журнал реализации со ссылками из документации каждого затронутого скилла. Различать подтверждённые дефекты, гипотезы и непроверенные утверждения.

**Для этой группы обязательна полная сверка технических аспектов с официальными источниками, а не только проверка изменяемых строк.**

Для каждого скилла:

- Инвентаризировать технические утверждения, API, команды и flags, настройки, defaults, примеры кода, зависимости, ограничения runtime, способы сборки, тестирования и deployment.
- Проверить их по актуальной официальной документации, release notes, changelog, deprecation notices и migration guides. Не ограничиваться поисковыми выдержками, сторонними статьями или памятью модели.
- Зафиксировать дату проверки, рассматриваемые версии и release channels. Различать актуальный stable, prerelease/experimental и версии существующего проекта.
- Проверить совместимость применимых зависимостей и инструментов: runtime, framework, SDK, CLI, адаптеров и поддерживаемых окружений.
- Найти удалённые и deprecated API, изменённые defaults, breaking changes, новые ограничения и замены прежних рекомендуемых подходов. Существенные новые возможности учитывать там, где они меняют выполнение уже принадлежащих скиллу задач.
- Составить компактную карту покрытия: **аспект → версия → официальный источник → результат проверки → необходимое изменение**. Для N/A указать основание; отсутствие проверки не обозначать как актуальность.
- Устаревшие рекомендации убрать из основного пути. Если они нужны для поддерживаемых старых проектов, оставить явную версионную ветку с ограничениями и корректным путём миграции.
- Не превращать актуализацию скилла в требование автоматически обновлять существующий проект. Рекомендации для нового проекта и работа с установленной версией должны быть явно различимы.

Если официальные источники расходятся с доступной средой, установить версионную причину и ограничить соответствующий вывод. Недостаток доказательств нельзя заменять предположением об актуальности.

**2. Исправить инструкции и согласовать ответственность**

Использовать `skill-creator`, `skill-source-compiler` и `implementation-discipline`. Изменять объявленные источники, затем регенерировать выходные файлы и обновлять версии.

| Скилл | Основной результат доработки |
|---|---|
| `hono-engineer` | Корректные routing, middleware, Context, validation и error handling; совместимость с заявленными runtime и адаптерами; проверка фактического HTTP-поведения. |
| `nextjs` | Актуальные инструкции для App Router, server/client boundaries, rendering, caching, navigation, Server Actions и Route Handlers; явные версионные ограничения и проверка production-поведения там, где оно существенно. |
| `electron-engineer` | Корректные process boundaries, IPC, permissions, lifecycle, packaging и updates; различение возможностей разработки и проверенных результатов на конкретных ОС. |
| `docusaurus-repo` | Актуальные configuration, MDX, plugins, themes, routing, versioning и i18n; работоспособные build и deployment инструкции с проверяемым конечным результатом. |
| `supabase-engineer` | Согласованные schema, migrations, Auth, RLS, API и применимые сервисы; актуальные SDK/CLI и платформенные ограничения; различение локальных проверок и реальной удалённой границы. |

Устранить подтверждённые противоречия, устаревшие рекомендации, неверную маршрутизацию, скрытые обязательства, необоснованные остановки и ложные заявления о готовности. Согласовать исправления во всех затронутых активных поверхностях, включая примеры и шаблоны.

Сокращение текста само по себе не считается улучшением. Не расширять назначение скиллов ради перечисления всех возможностей платформы.

**3. Проверить поведение и получить независимый PASS**

- Выполнить авторскую проверку качества, затем зафиксировать стабильный снимок для независимого `skill-reviewer`.
- Проверить достаточные запросы, отсутствующие и конфликтующие входы, смежные задачи, уточнения пользователя, недостаточные полномочия и частичные свидетельства.
- Добавить случаи с устаревшим API или командой, изменившимся default, несовместимыми версиями и проектом на старой поддерживаемой версии. Проверить корректную реакцию без выдуманного API и без незапрошенного upgrade.
- Отдельно проверить выбор скилла из каталога и выполнение после загрузки. Для слепых испытаний использовать свежие контексты без диагнозов и ответов; baseline и candidate сравнивать по одинаковым критериям.
- Выполнить фактические проверки затронутых API, команд и пользовательских сценариев в безопасной временной среде. Проверка документации подтверждает техническое основание инструкции, но не заменяет наблюдаемое выполнение.
- Проверить естественные прямые взаимодействия между владельцами. Не строить искусственный сценарий, заставляющий использовать все семь платформ одновременно.
- Для runtime, browser, database, packaging и внешних сервисов указывать реально проверенную границу. Mock, локальная эмуляция или успешная сборка не доказывают работу удалённого сервиса либо другой ОС.
- Использовать GPT-6 Astra для соответствующих испытаний; фиксировать назначенную модель, доступные настройки, экспозицию и ограничения.
- Выполнить compiler lint/check/isolated compile, проверки ссылок и переносимости, применимые пакетные проверки и `pnpm test:ci` с ограниченными ресурсами. Не создавать постоянный испытательный runtime.
- Исправлять P1/P2 до независимого PASS. Повторный отказ требует RCA исходного пути; повторные проверки ограничивать изменённой поверхностью и обоснованными последствиями.

**Границы и координация**

Изменяются только семь названных скиллов и общие supporting-записи. Смежные скиллы читать для необходимых прямых контрактов; совместимость проверять с их стабильными принятыми версиями. Их изменение, миграция продуктовых проектов и обновление глобальной среды в задание не входят.

Активные инструкции сохранять на английском, журнал и отчёты — на русском. Делегирование выполнять в пределах отдельно предоставленного разрешения. Коммит, push, PR и merge — по отдельному разрешению.

**Приёмка:** семь независимых PASS, полное покрытие технической сверки официальными источниками, подтверждённые прямые взаимодействия и завершённые обязательные проверки. Нет неразобранных deprecated/removed рекомендаций в основном пути и существенных технических утверждений, выданных за актуальные без проверки. Итог предъявляется оператору с точным снимком, версиями, источниками, результатами и пределами доказательств.
