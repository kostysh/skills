## Issue ID

## Title

Расширить production guidance для native OS integration, lifecycle, permissions и diagnostics

## Skill

`electron-engineer` — `skills/electron-engineer`

## Context

После создания `electron-engineer` и выделения canonical build process был выполнен повторный обзор доступных Electron skills-примеров. Задача обзора была не в копировании API-справочника, а в поиске production-тем, которые уже заявлены в `electron-engineer`, но пока покрыты слишком общо.

Текущее состояние скила уже покрывает архитектуру, IPC/preload security, project structure, build process, renderer integration, data/native modules, testing/observability, packaging/release/updates, source protection и review playbooks. Однако несколько важных Electron-областей остаются распределенными по общим формулировкам без отдельного decision guidance.

## Problem

`electron-engineer` заявляет поддержку native OS integration, multi-window flows, debugging, observing, migrations, packaging and release behavior, но агенту пока не хватает явных production-правил для следующих областей:

- native OS integration: menus, tray, dock/taskbar, shortcuts, dialogs, clipboard, downloads, drag-and-drop, notifications, desktop capture, screen/power APIs, dark mode, accessibility;
- app lifecycle and activation: `whenReady`, single-instance behavior, `second-instance`, macOS `open-file` / `open-url` / `activate`, tray-only quit semantics;
- session permissions and remote content: deny-by-default permission handling, permission/origin scoping, cookies/storage cleanup, desktop capture and media access review;
- web embeds: choosing between sandboxed `iframe`, main-controlled `WebContentsView`, and exceptional `<webview>` usage;
- diagnostics knobs: command-line switches, environment variables, net logging, content tracing, debugger/CDP, dev-only versus production-safe diagnostics;
- heavy-work isolation: utility processes, workers, MessagePort handoff, and interaction with Electron fuses;
- store-specific release targets: MAS/MSIX/Windows Store constraints, sandbox/capabilities/entitlements, updater strategy differences;
- app data migrations: pre-upgrade checks, backup, rollback/recovery, idempotency and partial-failure handling;
- embedded backend boundaries: local HTTP/WebSocket servers, localhost binding, auth, CORS, lifecycle shutdown;
- performance and security verification: project-specific budgets, packaged profiling, manual security scenarios, app metadata/assets release checks.

Expected behavior: when an agent uses `electron-engineer` for a production Electron app, these areas should be discoverable through focused references and checklists without forcing the agent to load or recreate a broad Electron API encyclopedia.

Actual behavior: many of these topics are only indirectly mentioned in existing references, which increases the chance that agents under-specify native integration, permission boundaries, diagnostics, release-store constraints, and migration safety.

## Evidence

Current active references show the gap by broad ownership:

- `references/architecture.md` owns process boundaries, window ownership, sessions, custom protocols, crash boundaries, offline-first behavior, and multi-window architecture, but does not yet provide full lifecycle and OS activation guidance.
- `references/security-ipc-preload.md` owns BrowserWindow security, IPC, preload, CSP, navigation, and external URL handling, but does not yet explicitly own session permission policy, desktop capture/media permission scoping, or web embed selection.
- `references/data-storage-native.md` owns app paths, config files, secrets, SQLite, file import/export, and native modules, but does not yet define upgrade/migration backup and rollback policy.
- `references/testing-observability.md` owns test layers, logs, crash reporting, diagnostics export, and performance budgets, but does not yet include a concrete diagnostics knob matrix or security scenario checklist.
- `references/packaging-release-updates.md` owns signing, notarization, distribution targets, auto-updates, release channels, provenance, SBOM, and rollback policy, but store-specific release constraints are still high level.

The reviewed example skills also highlighted useful topic gaps:

- `hairyf__skills__electron` contains a broad generated API topic map including app lifecycle, accessibility, downloads, desktop capture, power APIs, web embeds, fuses, store packaging, net logging, content tracing, and utility processes.
- `Tomlord1122__tomtom-skill__electron-architect` contributes useful requirements framing around system resources, sensitivity, app pattern, data persistence, and platform matrix.
- `chrisvoncsefalvay__claude-skills__electron-scaffold` contributes native UI, post-scaffold, security-test, error-handling, and platform checklist ideas.
- `claude-dev-suite__claude-dev-suite__electron` contributes backend boundary, SQLite migrations, updater UX, and performance metric ideas.
- `partme-ai__full-stack-skills__electron-skills` contributes mostly API/examples material; the only broadly reusable concept is upgrade discipline: backup, test first, rollback plan.

## Impact

Without this enrichment, agents may:

- implement native OS features as renderer conveniences instead of main-owned capabilities;
- omit permission request handlers or overgrant media, notification, geolocation, or screen-capture permissions;
- choose `<webview>` or remote content patterns without enough isolation and validation;
- debug production issues only through dev mode instead of packaged diagnostics;
- miss store-specific constraints for MAS/MSIX/Windows Store targets;
- perform local data migrations without backup, idempotency, or recovery strategy;
- create local HTTP/WebSocket backends that trust localhost implicitly;
- ship without explicit performance/security scenarios for desktop-specific behavior.

## Proposed Resolution

1. Add `references/native-os-integration.md` with production rules for:
   - menus, context menus, tray, dock, taskbar, recent documents, launcher actions;
   - local and global shortcuts, accelerator portability, cleanup;
   - dialogs, clipboard, downloads, drag-and-drop as main-owned capabilities;
   - notifications, desktop capture, screen/display, power monitor/save blocker, dark mode, accessibility;
   - per-feature ownership: main service, preload facade, renderer UI, validation, cleanup, and tests.

2. Update `architecture.md` with app lifecycle and OS activation guidance:
   - create windows after `app.whenReady()`;
   - use `requestSingleInstanceLock()` when deep links, file opens, tray apps, or singleton state require it;
   - normalize `second-instance`, macOS `open-file` / `open-url` / `activate`, and launch argv before sending route commands to renderer;
   - define tray-only quit behavior explicitly.

3. Update `security-ipc-preload.md` with session permissions and web embed policy:
   - deny-by-default `setPermissionRequestHandler`;
   - allow permissions only by session, origin, window role, and permission type;
   - treat notifications, media, geolocation, desktop capture, and remote content as permissioned features;
   - prefer sandboxed `iframe` for ordinary embeds and `WebContentsView` for main-controlled embedded contexts;
   - allow `<webview>` only as reviewed exception with `will-attach-webview` validation.

4. Update `testing-observability.md` with diagnostics and verification:
   - matrix for command-line switches, environment variables, net logging, content tracing, CDP/debugger, crash reports, heap/performance traces;
   - classify dev-only diagnostics versus production-safe diagnostics;
   - add manual security scenarios: renderer `require()` denial, malicious navigation, unsafe `shell.openExternal`, invalid IPC payload, CSP inline-script block, arbitrary file path denial;
   - make performance budgets project-specific instead of hard-coded global thresholds.

5. Update `data-storage-native.md` with migration and embedded backend boundaries:
   - migration idempotency, backups before destructive upgrades, rollback/recovery path, partial-failure behavior;
   - local HTTP/WebSocket server guidance: bind to loopback, random port when feasible, capability token/auth, strict CORS, lifecycle shutdown, no privileged unauthenticated localhost API.

6. Update `packaging-release-updates.md` with store target constraints:
   - MAS/MSIX/Windows Store as explicit product decisions, not incidental makers;
   - sandbox/capability/entitlement review;
   - `process.mas` / `process.windowsStore` compatibility checks;
   - store-specific updater strategy and release smoke.

7. Update `review-playbooks.md` with review red flags and release checks for the new areas:
   - unchecked permission handlers;
   - unmanaged global shortcuts/power blockers;
   - unsafe web embeds;
   - local server without auth;
   - migrations without backup/recovery;
   - missing icon/metadata/assets and store target checks.

8. Keep all additions portable:
   - no absolute local paths;
   - no mandatory dependency on external example skills;
   - external docs remain optional and version-sensitive.

## Alternatives Considered

- Copy the generated API-topic skill into `electron-engineer`.
  - Rejected: it would make the skill too large, dilute production guidance, and increase stale API risk.

- Add many small API-specific references.
  - Rejected: it would harm progressive disclosure. A focused native OS integration reference plus targeted updates is easier for agents to select.

- Leave current skill as-is and rely on official Electron docs when needed.
  - Rejected: agents need stable production decision guidance before deciding which official docs to fetch.

- Add implementation scripts for security scans or package audits now.
  - Rejected: useful later, but this issue is about normative guidance, not runtime tooling.

## Destructive Side Effects

Potential risks:

- The skill may become too broad if the new reference copies API details instead of guidance.
- Duplicate guidance may conflict with existing `architecture.md`, `security-ipc-preload.md`, `testing-observability.md`, or `packaging-release-updates.md`.
- Store and permission guidance may become version-sensitive if it embeds too many exact API claims.
- Adding a new optional reference requires `skill.yaml`, `SKILL.md`, and `docs/compile-report.md` to stay in sync through `skill-source-compiler`.

Mitigations:

- Keep `SKILL.md` lean and put detail in one focused optional reference plus targeted existing references.
- Use decision tables, anti-patterns, and verification checklists rather than long code snippets.
- Link to `Build Process` for build/package/make/publish ordering instead of duplicating it.
- Run compiler checks and portability checks after implementation.
