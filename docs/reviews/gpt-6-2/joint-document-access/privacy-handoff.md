# «Мои документы» — заключение для контролёра и инженера учебной базы

**Итог.** Условия чтения, четыре учебные записи и результат инженера по безопасности согласуются. Для каждой из трёх учётных записей статически определены два доступных и два недоступных отчёта. Фактическое соблюдение этого правила в учебной базе предстоит проверить. Тестовый контролёр утвердил цель и группы получателей. Ему ещё нужно утвердить срок хранения отчётов и событие, с которого этот срок отсчитывается. [Условия](sources/case.md) · [Передача инженера по безопасности](security-handoff.md) · [Статическое наблюдение](role-observation.json)

## Обработка и пределы оценки

| Операция | Данные и получатели | Условие доступа и состояние |
| --- | --- | --- |
| Хранение коротких отчётов сотрудников | В учебном наборе есть ID отчёта, ID сотрудника-владельца, заголовок и признак разрешения поддержке. Текст отчёта и сведения об обращении в набор не входят. | Четыре строки в локальном JSON доступны для статической сверки. Состояние хранения и обработки в учебной базе неизвестно. Срок хранения, начало отсчёта и исполнение удаления не установлены. |
| Чтение своего отчёта | Сотрудники `worker-a` и `worker-b` | ID текущего сотрудника должен совпадать с `owner`. Фактическое исполнение неизвестно. |
| Чтение для поддержки по обращению | Учётная запись поддержки и отчёты, на чтение которых владелец дал явное разрешение | В учебном наборе разрешение обозначено `supportConsent: true`. Связь с конкретным обращением, выдача и отзыв разрешения, а также фактическое исполнение неизвестны. |

ID владельца и отметка о разрешении связаны с сотрудником в модели. Для реального использования контролёру нужно установить применимость GDPR и документировать правовое основание обработки. Учебный флаг описывает условие доступа по сценарию. Вопрос о правовом основании остаётся открытым. При необходимости юрист даёт правовую оценку, а DPO консультирует независимо. Решение принимает контролёр. [Условия](sources/case.md) · [Учебные данные](sources/documents.json) · [Контроли C1, C2, C3 и C6](references/control-catalog.md)

Сведения о сервисных и административных учётных записях, журналах, трассировке и метриках, копиях, резервном хранении, экспорте, индексах, кэшах, очередях, внешних поставщиках, регионах и передачах отсутствуют. Материалы также не описывают отдельную аналитику, AI-обработку или рабочие процессы реализации прав сотрудников. Эти вопросы остаются за пределами проверки четырёх строк. Правовая оценка актуальности норм и вывод о соответствии GDPR в объём поручения не входят. [Условия](sources/case.md) · [Методика оценки](references/audit-methodology.md)

## Установленный результат и открытые вопросы

| Учётная запись | Полный ожидаемый набор ID | Должны быть недоступны |
| --- | --- | --- |
| `worker-a` | `amber`, `cedar` | `birch`, `dune` |
| `worker-b` | `birch`, `dune` | `amber`, `cedar` |
| Поддержка | `birch`, `cedar` | `amber`, `dune` |

Наборы пересчитаны по исходным записям и совпали с передачей инженера по безопасности и структурированным наблюдением. Сверка также подтвердила SHA-256 и права доступа двух файлов в `sources/` по данным наблюдения. [Учебные данные](sources/documents.json) · [Передача инженера по безопасности](security-handoff.md) · [Статическое наблюдение](role-observation.json)

- **P2 · C4/C9 · `missing_evidence`.** Для четырёх учебных записей подтверждено ожидаемое разграничение. Исполнение через клиент, API и на уровне базы не наблюдалось. Политики доступа на уровне строк (RLS) и права ролей не предоставлены. Ошибка здесь может открыть сотруднику чужой отчёт или дать поддержке доступ без разрешения владельца. До закрытия вывода нужны фактические наблюдения из учебной базы по критериям ниже. [Передача инженера по безопасности](security-handoff.md) · [Каталог контролей](references/control-catalog.md)
- **P2 · C8 · `accountable_or_specialist_decision_needed`.** Тестовый контролёр определяет срок или объективный критерий хранения и событие начала отсчёта. После решения инженер сможет проверить, что по истечении срока отчёт перестаёт быть доступен для обычного чтения и что применяется согласованное удаление или необратимое обезличивание, включая связанные копии, если они есть. Без решения нельзя задать момент такой проверки. [Условия](sources/case.md) · [Каталог контролей](references/control-catalog.md)
- **C3/C6 · `accountable_or_specialist_decision_needed` для реальных данных.** В материалах зафиксированы цель и получатели. Правовое основание не указано. Если поток будет работать с реальными данными сотрудников, контролёр определяет и документирует основание до начала такой обработки. Для доступа поддержки также потребуется определить, как разрешение связано с обращением и когда прекращает действовать. Булево поле само по себе показывает только состояние учебной записи. [Условия](sources/case.md) · [Учебные данные](sources/documents.json) · [Каталог контролей](references/control-catalog.md)

**Статус оценки** — `COMPLETE_FOR_STATED_SCOPE` для документарной сверки предоставленного учебного случая. Статус исполнения ограничений чтения в учебной базе остаётся открытым.

## Передача инженеру учебной базы

**Задача.** Проверить разграничение чтения на четырёх предоставленных учебных записях. Использовать только выданные ресурсы случая и соответствующие учётные записи. Результат нужен для повторной оценки C4/C9. [Условия](sources/case.md) · [Передача инженера по безопасности](security-handoff.md) · [Границы проверки](references/implementation-evidence.md)

1. Выполнить обычное чтение списка в клиенте базы отдельно под `worker-a`, `worker-b` и учётной записью поддержки. Для каждой учётной записи сравнить полный набор фактически возвращённых ID с таблицей без учёта порядка. Если клиент поддерживает чтение отдельного отчёта, проверить, что каждый из двух недоступных ID не выдаёт содержимое.
2. Для штатного API и прямого чтения базы повторить ту же матрицу там, где эти пути выданы для случая. Подтвердить, что используются фактические права каждой роли. Если база использует RLS, указать, какие политики применяются к чтению и какие права выданы ролям. Для каждого недоступного пути указать, почему его проверка осталась открытой.
3. Вернуть протокол с датой, отметкой об учебной среде, способом чтения и ролью для каждого наблюдения. Приложить фактические наборы ID, результаты проверок недоступных записей и расхождения с ожиданием. Для проверки достаточно ID и результатов доступа. Исключить содержимое отчётов и секреты учётных записей из протокола.

**Критерий приёмки.** На каждом проверенном пути все три полных набора совпадают с таблицей, а прямое чтение отдельного отчёта, если предусмотрено этим путём, не раскрывает ни один из двух запрещённых отчётов для соответствующей роли. Успешное наблюдение в клиенте закрывает только клиентский путь. При расхождении указать роль, путь, ожидаемые и фактические ID. После исправления в рамках отдельного поручения повторить матрицу на затронутых путях. Проверку срока хранения назначить после решения контролёра.
