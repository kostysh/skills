# Проверка публичного типа после изменения схемы

На снимке `2835b7574b06a6210b2b2d96465c7e46e7c60d97` формальный аудит дал FAIL/P2. Ранее исполнитель получал готовое выражение `Extract<ReturnType<…>, …>["value"]`. Его работа показывала, что он вернул правильное значение. Ручная копия исходного типа тоже проходила прежнее наблюдение. Повтор на первичном приложении подтвердил оба зелёных компиляционных контура и правильные ответы CLI с ручным типом. После добавления поля `scanned` и обращения к нему от клиента та же реализация получила TS2339. При восстановлении зависимого типа тот же клиент собрался. [Исходный FAIL/P2](../independent-audit.md) · [Повтор прежнего ложного успеха](prior-false-success.json)

## Наблюдаемое решение

Каждый новый `src/public.ts` содержит только функцию, которая принимает `unknown`, возвращает `unknown` и отдаёт сырой вход. Ни одного клиентского типа ещё нет. Исполнитель сам выбирает, какое статическое представление опубликовать, как связать его с принятым схемным API и как выдать результат парсера в исполнении. Клиент уже требует именованный тип для передачи разобранных значений, а также вызывает публичный вход. Склад отдельно сообщает владельца решения о новом формате. Календарь имеет разных потребителей для сырой заявки и разобранного результата. [Исходные адаптеры и хеши](frozen-snapshot.json) · [Поручения и полные исходники](research-inputs.tar.gz)

Для опытов на Linux с Node 24.15.0 установлены полные npm-пакеты `typescript@5.9.3` и `valibot@1.2.0`. У каждой рабочей сессии физические копии обоих пакетов. Штатный `npm run typecheck` запускает локальный CLI, а `npm run --silent read` вызывает обычный публичный вход в отдельном процессе. Valibot получает внешний `unknown` в `safeParse` и отдельно предоставляет типы допустимого входа и разбора. Вывод из фактического результата парсера также может сохранить связь с его типом. [Valibot, вывод типов](https://valibot.dev/guides/infer-types/) · [Valibot, safeParse](https://valibot.dev/api/safeParse/)

## Внешние проверки

| Проект | Текущая наблюдаемая операция | Новая принятая редакция на копии |
| --- | --- | --- |
| Журнал приборов | Строковый уровень от прибора превращается в число, имя станции — в верхний регистр | В нормализованную запись добавлен `padded: boolean`. Новый потребитель обращается к нему через `Reading` и непосредственно через результат импорта. |
| Складские этикетки | Из `N-042` получаются зона north и позиция 42. `{"deferred":true}` отвергается по действующей договорённости. | Добавлено `scanned: boolean`. Оба пути чтения клиента исходно вызывают TS2339 для ручной копии. Это исходный пример отказа аудитора. |
| Календарь | Заявка с днём-строкой и необязательным числом смен превращается в `Date` и конкретное число смен | Для авторов заявок добавлен необязательный `desk`, для экрана — нормализованное поле `roster`. Новый шаблон передаёт `reserve`, экран читает его после реального разбора. |

В первой фазе наблюдатель проверяет текущую программу с настоящим потребителем, открытый вход с типом `unknown`, невозможность принять `any` как тип результата и реальные ответы CLI. Во второй меняются только схема и новый клиент в одноразовой копии. Публичный модуль исполнителя остаётся байт в байт тем же. Базовый клиент, новый клиент, внешние проверки типов и CLI выполняются повторно. Тип и его реальное значение проверяются для исходного и обновлённого форматов. В исходном рабочем проекте сравниваются права и байты файлов. [Заранее закрытые критерии](trial-criteria.md)

До рабочего сравнения проведены 18 контрольных проверок — шесть вариантов в каждом из трёх проектов. Исходный вариант обнаруживает отсутствие клиентских типов. Оба допустимых решения прошли обе версии. Ручной структурный тип прошёл все исходные проверки и сохранил правильное исполнение при обновлении схемы, но свежий клиент во всех трёх случаях получил TS2339. Использование типа входа вместо выхода обнаруживается уже в исходном приложении. Широкий `any` пропускает обращения к неизвестным свойствам, его отдельно обнаруживают внешние проверки типов. [Команды, ошибки и результаты контрольных вариантов](preflight.json)

Проверяются прежние A, B, C и точный архив 0.2.3. Их одиннадцать файлов для каждой редакции совпадают с ранее зафиксированными хешами. Данные новой отложенной задачи, обновления схем и рубрика закрыты до выдачи A/B и до нового решения о применимости уже существующей C. В исходном учебном приложении нет этих обновлений, готового типа или решения. Архив позволяет восстановить зависимости по байтам и правам из официального реестра. SHA-256 архива — `fe855c0ea34a30bc7559ddf2b5532cacebb4ed50df92c45da4d12e34e0e5f281`. Остальные первичные предметные проверки и принятые на себя роли Tally этот опыт не переизмеряет. ## Проверка воспроизводимости

После фиксации распакован новый экземпляр исследовательского архива. Из реестра восстановлены все 132 файла TypeScript и девять файлов Valibot с записанными SHA-256 и правами в каждой рабочей копии. На восстановленном стенде ручная декларация снова дала 0 в исходной версии и 2/TS2339 после добавления `scanned`. Вывод из фактического парсера дал 0 в обеих версиях. [Воспроизведение из архива](fresh-archive-replay.json)

Три дополнительные мутации локализуют проверяемую ошибку. Когда только именованный `Parcel` скопирован вручную, новое поле недоступно через имя. Когда только возвращаемый тип функции скопирован вручную, оно недоступно через вызов. Когда у календаря выведен правильный результат, но скопирован входной `PeriodRequest`, новый шаблон получает TS2353 для `desk`. Все три проходят исходные проверки типов и продолжают правильно работать при исполнении. Это проверка свойств заранее закрытого наблюдателя. Условия выданных задач и оценивания не менялись. [Раздельная проверка трёх границ](split-contract-controls.json)

## Повтор точной поставки на календаре

При слепом оценивании точной 0.2.3 все проверки типов и исполнения календаря прошли. В журнале `b7c2c8` оценщик обнаружил отдельное событие `web_search` с запросом о Valibot. В поручении работа ограничена предоставленным каталогом. Проверка путей оболочки такого обращения не показывает. Общий исход этой работы — FAIL. После подписи заключения назначен один новый исполнитель на идентичные условия точной поставки и календаря. Третьему оценщику передаются под новыми перемешанными кодами три календарных решения — этот повтор, исходная работа с внешним поиском и работа C из подтверждающей серии. Оба контрольных решения сохраняют прежнюю оценку. [Подписанная подтверждающая оценка](assessment-confirm.md) · [Исходное действие исполнителя](results/b7c2c8.json)
