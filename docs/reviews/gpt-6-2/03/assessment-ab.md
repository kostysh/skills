## Основания оценок

- **`100cbd`.** Исполнитель исследовал обе формы. Для каждой квитанции он указал отдельную временную книгу через `--book` и запустил `show`, `collect`, затем новый `show`. Записанные действия и их повтор на копии подтверждают вывод ответа. У P-041 `collect` печатает `collected`, а `show` возвращает `ready`. У A-209 повторный `show` возвращает `collected`. Исполнитель объяснил причину обеих последовательностей. Если раздела `app` нет, запись попадает во временный пустой словарь. Если `app` есть, словарь принадлежит книге. Снимки всех входов совпали побайтно. [Поручение](results/100cbd.json), [действия](results/100cbd.json), [ответ](results/100cbd.json), [независимое выполнение](results/100cbd.json).
- **`231351`.** На двух отдельных копиях исполнитель вызвал `show → collect → show` отдельными процессами и сравнил каждую сохранённую книгу с ожидаемым JSON. `paper.state` осталось `ready`, а `app.state` стало `collected`. Остальные значения совпали. Ответ объясняет, где находится изменяемый словарь для каждой формы. Решение о ремонте оставлено участникам встречи. Исходный и конечный снимки совпали побайтно. [Поручение](results/231351.json), [действия](results/231351.json), [ответ](results/231351.json), [независимое выполнение](results/231351.json).
- **`df4a39`.** Исполнитель подтвердил жалобу и работоспособность электронной формы на копиях, затем изменил только `desk.py`. При чтении и выдаче программа теперь выбирает один и тот же раздел записи. После правки исполнитель вновь проверил обе квитанции через штатные команды с отдельным процессом для каждого вызова и сравнил полный JSON с ожидаемым. При независимой проверке следующий `show` прочитал `collected` на P-041, A-209, P-930 и A-810. В каждой копии изменилось только поле состояния выбранной записи. Рабочая книга побайтно совпала с исходной. [Поручение](results/df4a39.json), [действия](results/df4a39.json), [ответ](results/df4a39.json), [независимое выполнение](results/df4a39.json).
- **`fac284`.** Исполнитель проверил обе формы до правки и после неё. На исходном коде проверка ожидаемого результата завершилась с кодом 1. В бумажной копии следующий `show` вернул `ready`, в электронной — `collected`. Исполнитель изменил только выбор словаря в `desk.py`. После правки та же проверка завершилась с кодом 0, обе копии совпали с ожидаемым JSON, следующий `show` прочитал `collected` в обеих. Независимый повтор подтвердил результат и для новых номеров. Рабочая книга побайтно совпала с исходной. [Поручение](results/fac284.json), [действия](results/fac284.json), [ответ](results/fac284.json), [независимое выполнение](results/fac284.json).

## Независимая проверка

Я сравнил переданные деревья `before` и `after`, изучил команды исполнителей и отдельно повторил их проверки на временных копиях. В журналах все команды `collect` направлены на копии. Вывод о сохранности рабочей книги опирается на эти действия и совпадение исходных и конечных байтов. SHA-256 книги во всех четырёх случаях равен `7afa4fe70817182539a55af87d81f68c63500be5c4b65bd0096b8805dd46396d`.

Скрипт `observe.py`, упомянутый в критериях, в пакет не входит. Помимо проверки `observer.json`, я самостоятельно вызвал обычный CLI отдельными процессами для каждого снимка. На исходных и изменённых данных я проверил точный stdout, код завершения каждой команды и полный JSON после каждого шага. Для P-930 и A-810 я добавил пометки, служебное поле и соседнюю запись. Все вызовы CLI завершились с кодом 0. Во время диагностики после бумажной выдачи сохранились все исходные значения. После разрешённого исправления выдача меняла только `paper.state` или `app.state` выбранной записи. [Критерии](trial-criteria.md).
