# Предметная сверка spec-engineer

На 18 ноября 2026 года скил составляет Markdown-спецификацию для названного инженера или планировщика. Исполнитель наследует принятые требования, выбирает представление и описывает наблюдение, которое опровергнет выполнение. В этом исследовании вопрос об архитектуре уже имел владельца. Для действия было достаточно назвать, кому его передать. Остальные решения сверены по действующим источникам. [Манифест](../../../../skills/spec-engineer/skill.yaml) · [Методика](../../../../skills/spec-engineer/references/methodology.md)

| Указание и решение | Почему точность важна для работы |
| --- | --- |
| Сократить позднее напоминание о нерешённой архитектуре. | В P-75 принятый сценарий таблицы диспетчера можно передать. Анна решает, нужно ли межстанционное поведение, а Олег затем выбирает необходимый способ. Предложение команды о Redis не имеет полномочий владельцев. Правило `Start here`, раздел архитектурных границ и исходные материалы уже направляют эти решения владельцам. В отдельном P-83 внешний формат согласован и обязателен. После сокращения он сохранён. [Наблюдения](study-evidence.json) |
| Сохранить условия готовности, право на запись и адресата передачи. | Задание позволяет создать документ. Согласование продукта, реализация и внешняя поставка имеют собственные основания. В учебном «Кабинете 1» новая реплика владельца соотнесена с прочитанной редакцией PRD 0.3. Она разрешает спецификацию Q-17 и условный старт двух работ. Заместить отсутствующее решение по Q-18 этим разрешением нельзя. [Привязка решения](../joint-cabinet/owner-condition-binding.json) |
| Сохранить источник материального требования и проверку того, что теряется при его удалении. | Поле `starred` и совместимость старого читателя в P-61 обязательны по принятому ADR-08. В P-83 принимающая сторона задаёт UTF‑8, заголовок `site;sector`, порядок полей и разделитель. Для внутреннего способа хранения этих полномочий нет. Задания проверяют обе стороны границы. [Выданные документы](research-inputs.tar.gz) |
| Сохранить выбор формы контракта, проверку наблюдаемого эффекта и отрицательное условие. | Применяются пользователь, событие, результат и критерий, выявляющий частичную работу. Для файла важны фактически принятые значения при импорте, для кабинета нужен показ адресату и отсутствие отправки о том же отчёте. Для приложения важно различить прямой ответ базы и нормальный HTTP-вход. Эти принципы согласуются с проверкой требований на уровне заявленного результата в руководстве NASA. [NASA, Systems Engineering Handbook, Appendix C](https://www.nasa.gov/reference/appendix-c-how-to-write-a-good-requirement/) |
| Сохранить модальность и обусловленное чтение ссылок. | `MUST`, `MUST NOT`, `SHOULD` и `MAY` имеют определённый смысл в принятом стиле спецификаций. BCP 14 различает регистр для документов, которые используют это соглашение. Он не решает, какие требования вправе утвердить владелец продукта. Два обязательных справочника имеют разные условия чтения. Четыре остальных помогают выбрать представление, обнаружить пропуск или увидеть пример. [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174.txt) · [Матрица высокорискового backend-контракта](../../../../skills/spec-engineer/references/high-risk-backend-contract.md) |
| Сохранить маршрутизацию смежных ролей. | 23 формализует принятый запрос. 28 отвечает за HTTP-обработчик. 21 измеряет выдачу под фактическими ролями. Для T03 уже есть контракт локального каталога, и 33 самостоятельно оценивает соответствие реализации каждой его части. Спецификатор не может принять новое продуктовое требование по одному наблюдению в коде. [Вход 21](../21/hono-input/contract.md) · [Передача T03](catalog-handoff.md) |

Руководство OpenAI задаёт вопросы к подсказке о результате, свободе выбора, полномочиях и завершении. Здесь результатом служит применимый документ, а выбор допустимого метода остаётся у инженера. Сведения о поведении Astra сами по себе не устанавливают эффект на Sol. Поведение Sol medium измерено на трёх заданиях. [OpenAI, Prompting best practices](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-6.2-astra#prompting-best-practices) · [Сырые результаты и условия доступа](study-evidence.json)

Предметный источник формы ответа для `GET /documents/:id` — документ учебного владельца API. HTTP Semantics допускает скрытие существования запрещённого ресурса через 404. Конкретное одинаковое тело ответа, форма 200 и роли базы следуют из материалов владельцев 21 и 23. Указания для SDK не добавлены в активный скил. [RFC 9110, §15.5.4](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5.4) · [Контракт владельца](document-access/sources/web-contract.md)

В `spec-engineer` нет собственной CLI, исполняемых программ или зависимостей от API. Восемь файлов выпуска включают точку входа, метаданные выбора и шесть справочников. Проверена авторская выдача из манифеста и полученная распаковка. Испытание выполнялось по заданию с явным подключением скила. Выбор из каталога в этой строке не измерялся.
