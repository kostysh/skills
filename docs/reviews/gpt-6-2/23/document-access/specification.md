# Чтение документа в учебном кабинете Hono

**Статус передачи.** `ready for команда 28` для реализации утверждённых веток `GET /documents/:id` для сотрудников и запросов без действительного сеанса, включая подключение публичного клиента. Сквозная приёмка `blocked` до сборки Hono и выдачи действующего сокета оператором. Открытые решения ниже ограничивают только зависимые от них ветки и выводы.

В кабинете «Мои документы» вошедший сотрудник читает карточку своего отчёта. Запрос чужого отчёта даёт тот же статус и тело, что и запрос отсутствующего. Критичность высокая для контроля доступа: ошибка может раскрыть название или подтвердить существование чужого отчёта. Объём работы ограничен чтением одной карточки по HTTP и проверкой доступа к четырём синтетическим записям на стыке с базой.

| [Доступность стенда](readback/availability.md) | Оператор запускает отдельный комплект и выдаёт команде 28 адрес сокета. Команда 28 собирает приложение и проверяет HTTP. |

Действительный сеанс здесь означает тестовый сеанс, который проверило приложение. `principal` — идентичность из этого сеанса. `:id` — идентификатор запрошенного документа из пути. Карточка — JSON-объект с `id` и `title`. Скрытая запись существует в базе, но недоступна текущему `principal`. `missing` — отсутствующий учебный ID.

Путь чтения — HTTP Hono → проверка сеанса → `readDocument(principal, id)` → Unix-сокет из `DOCUMENT_DESK_SOCKET` → выборка Data API под действующей ролью БД → HTTP-карточка или статус из таблицы ниже. Команда 28 использует [выданный клиент](public/desk-client.mjs), который опирается на встроенные модули Node.js. `listDocuments(principal)` нужен для контроля Data API. Публичный маршрут списка и операции записи вне объёма. Комплект оператора и создаваемые на стенде тестовые ключи остаются в контуре оператора.

## Утверждённый контракт

| ID | Условие | Требование | Основание |
| --- | --- | --- | --- |
| R1 | Чтение карточки в кабинете | Hono MUST предоставлять `GET /documents/:id`. | Явно · [23](sources/web-contract.md) |
| R2 | Нет действительного сеанса | Hono MUST вернуть `401`. Форма тела в источнике не задана. | Явно · [23](sources/web-contract.md) |
| R3 | Hono передаёт запрос на чтение в Data API | Hono MUST передать в `readDocument` идентичность из проверенного сеанса и ID из пути. | Явно · [21](readback/contract.md), [23](sources/web-contract.md) |
| R4 | Вошедший сотрудник читает свой документ | Hono MUST вернуть `200` с JSON-объектом ровно из `id` и `title` этой записи. | Явно · [23](sources/web-contract.md), проекция · [21](readback/contract.md) |
| R5 | Вошедший сотрудник запрашивает чужой или отсутствующий документ | Hono MUST вернуть одинаковые `404` и `{"error":"not_found"}`. На стыке это отображение успешной пустой выборки `status=200, data=[], error=null`. | Ответ явно · [23](sources/web-contract.md), отображение следует из контракта [21](readback/contract.md) |
| R6 | Прямое чтение через Data API под ролью сотрудника | Data API MUST ограничивать видимость записями этого сотрудника. | Явно · [цель проекта](sources/case.md), [21](readback/contract.md) |
| R7 | Прямое чтение через Data API под ролью поддержки | Data API MUST ограничивать видимость записями с явным разрешением владельца на поддержку. | Явно · [цель проекта](sources/case.md), [21](readback/contract.md) |
| R8 | Прямое чтение через Data API скрытого или отсутствующего ID | Data API MUST возвращать `status=200, data=[], error=null`. | Явно · [21](readback/contract.md) |

R2 и R3 задают порядок допуска: без действительного сеанса у запроса нет идентичности для вызова клиента. Клиентский ввод идентичности не даёт доступа к записи. Ошибка адаптера или базы лежит за пределами условия R5.

### Ожидаемая видимость на Data API

| `principal` / действующая роль БД | Полный набор видимых пар | Известные скрытые ID |
| --- | --- | --- |
| `worker-a` / `desk_employee` | `amber` — Апрель, `cedar` — Июнь | `birch`, `dune` |
| `worker-b` / `desk_employee` | `birch` — Май, `dune` — Июль | `amber`, `cedar` |
| `support` / `desk_support` | `birch` — Май, `cedar` — Июнь | `amber`, `dune` |

Каждый возвращённый элемент `data` содержит ровно `id` и `title`. Служебные поля ответа адаптера, включая действующую роль и номер запроса, служат проверке стыка. Порядок списка контрактом не задан. [Контракт команды 21](readback/contract.md)

## Сквозная приёмка

1. **Оператор и команда 28.** Оператор запускает свой комплект и выдаёт адрес действующего Unix-сокета. Команда 28 задаёт `DOCUMENT_DESK_SOCKET` в окружении собранного Hono и использует выданные действительные тестовые сеансы. SHA-256 локального [публичного архива](readback/public-client.tar.gz) сверена с описанием передачи. Файл адаптера в архиве совпадает с рабочим файлом. Архив запуска находится у оператора, его состав и SHA-256 приведены по [описанию передачи](readback/availability.md).
2. **Data API · 21 и оператор · R6–R8.** Через выданный клиент сверить действующие роли и наборы пар из таблицы. Для каждой из трёх идентичностей проверить список, четыре отдельных известных ID и `missing`. Для доступного ID ожидается `200`, одна точная пара и `error=null`. Для скрытого ID и `missing` ожидается `200`, пустой массив и `error=null`. Чужая пара, лишнее поле элемента, неверная роль или доступ поддержки к `amber` либо `dune` опровергают контракт. Исторический [отчёт 21](readback/title-readback.json) содержит 18 таких ответов и прежний контроль чтения только ID. Прежний контейнер завершён и удалён.
3. **HTTP · команда 28 · R1–R5.** Вызвать фактический маршрут Hono с сеансами `worker-a` и `worker-b` по всем четырём ID и `missing`. Для каждого собственного ID сверить `200` и точную пару с таблицей. Для каждого чужого ID сверить статус и тело с ответом на `missing`. Выполнить запрос известного документа без сеанса и с недействительным тестовым сеансом. Ожидается `401` без чтения через адаптер. При проверке привязки идентичности к сеансу ввод клиента не должен менять доступную запись. Чужой `200`, различие статуса или тела двух видов `404`, неверный заголовок карточки, лишнее поле успеха или вызов адаптера без действительного сеанса означают провал приёмки.
4. **Сквозное доказательство · команда 28.** Подтвердить на одном действующем стенде путь от проверенного сеанса и ID через роль и чтение сохранённой записи до внешнего ответа Hono. Повторить чтение той же записи под второй идентичностью и сверить его с отсутствующим ID. Проверка рабочей привязки к клиенту вместе с фактическими ответами исключает приёмку маршрута, который выдаёт зашитые данные. Для фиксации стыка доступны номера запросов Data API. Записи уже загружены оператором, поэтому создание, миграция и восстановление записей в прогон не входят. Отчёт 21 и проверки с подменённым клиентом покрывают свои интерфейсы. Сквозной результат дают ответы собранного Hono с реальным стендом.

## Проверка границ высокорискового контракта

| Граница | Применимость и доказательство |
| --- | --- |
| HRB-01 · Идемпотентность | `not_applicable`. [23](sources/web-contract.md) задаёт чтение без команды записи, ключа идемпотентности или фиксируемого результата. |
| HRB-02 · Блокировки | `not_applicable`. [23](sources/web-contract.md) и [21](readback/contract.md) задают выборку существующих записей без изменения канонического состояния. |
| HRB-03 · Разграничение в базе | `applicable`. 21 отвечает за видимость под действующей ролью. R6–R8 и шаг 2 задают проверку запрещённых выборок. Точные grants, RLS, `SECURITY DEFINER` и исключения привилегированных ролей не описаны публичной передачей. Вывод о внутреннем устройстве ACL зависит от свидетельства 21 или оператора. |
| HRB-04 · Допуск | `applicable`. 23 и 21 задают R2–R3, команда 28 проверяет на шаге 3 отказ без сеанса и привязку запроса к проверенной идентичности. Формат и выпуск сеанса остаются у владельцев. |
| HRB-05 · Ошибки зависимости | `applicable`. 21 определяет ошибки стыка, 23 владеет публичным отображением. R5 и шаги 2–3 покрывают успешную пустую выборку. Для отдельного прогона с отказом зависимости нужен утверждённый ответ. Выдача сбоя за успешную пустую выборку нарушает границу R5. |
| HRB-06 · Отсутствие и потеря связи | `applicable`. 23 и 21 задают отсутствие действительного сеанса и успешную пустую выборку. Шаги 2–3 различают `401`, HTTP `404` и Data API `200` с `[]`. Тайм-аут, ошибка транспорта и политика восстановления остаются в вопросе о сбоях. |
| HRB-07 · Числа и деньги | `not_applicable`. [23](sources/web-contract.md) и [учебные записи](sources/documents.json) задают строковые ID и названия, без денежной арифметики. |
| HRB-08 · Целостность запроса | `not_applicable` к дополнительным требованиям. [23](sources/web-contract.md) задаёт GET и проверку сеанса, покрытую HRB-04. Подпись тела, Origin и другие условия не заданы. |
| HRB-09 · Аудит | `not_applicable` к событиям приложения. [21](readback/contract.md) предоставляет номер запроса для проверки стыка. [23](sources/web-contract.md) не задаёт аудит чтения. Срок хранения отчётов вынесен владельцу политики. |
| HRB-10 · Жизненный цикл | `applicable` к чтению. 23 и 21 задают терминальный ответ для каждой утверждённой ветки на шагах 2–3. Вопросы хранения и восстановления при сбое вынесены владельцам. Сценарии создания и очистки вне текущего GET. |
| HRB-11 · Инвариант доступа | `applicable`. Правило контролёра проходит через R3–R8. Шаги 2–4 должны выявить выдачу чужой карточки и чтение поддержкой отчёта без разрешения. |
| HRB-12 · Публичная форма | `applicable`. 23 владеет HTTP-маршрутом и его ответами, 21 — интерфейсом клиента и выборки. Шаги 2–3 выявляют подмену формы, статуса или значения на соответствующей границе. |
