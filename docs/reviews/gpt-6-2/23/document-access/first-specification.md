# Чтение документа в учебном кабинете

**Статус передачи — `draft` для команды Hono, инженер 28.** Владелец API 23 утвердил HTTP-контракт для сотрудника. Его можно использовать для реализации. Команда базы 21 подтвердила выборку на своём стенде. Сквозная приёмка Hono открыта. В текущем комплекте есть отчёт базы, но отсутствуют приложение Hono, клиентский архив и работающий сокет.

## Область и источники

Кабинет «Мои документы» показывает сотруднику его отчёт. Поддержка может читать отчёт по явному разрешению владельца. Критичность высокая на границе доступа. Ошибка может раскрыть заголовок или выдать существование чужого документа.

| Источник | Что он определяет |
| --- | --- |
| [Цель учебного случая](sources/case.md) | Тестовый контролёр утвердил цель и группы получателей. Согласие владельца ограничивает доступ поддержки. |
| [HTTP-контракт](sources/web-contract.md) | Владелец 23 определяет маршрут и ответы приложения для сотрудника. |
| [Четыре учебные записи](sources/documents.json) | Исходные ID, владельцы, заголовки и признаки разрешения поддержки для прогона. |
| [Стык команды базы](readback/contract.md) и [результаты прогона](readback/title-readback.json) | Команда 21 определяет интерфейс выданного клиента и подтверждает наблюдаемую выдачу Data API. Инженер 28 отвечает за выполнение маршрута на Hono. |

**Термины.** Сеанс — проверенный приложением тестовый сеанс. `principal` — идентификатор из этого сеанса. Скрытый ID принадлежит существующей записи, которую текущий `principal` не вправе читать. `missing` обозначает отсутствующую запись. Порядок элементов при сверке списка несущественен.

## Контракт запроса и стык

Точка входа — `GET /documents/:id`. `id` поступает из пути запроса. Тело запроса контрактом не предусмотрено.

| ID | Условие и обязательство | Основание и признак нарушения |
| --- | --- | --- |
| SPEC-R1 | При действительном сеансе сотрудника и чтении своего документа Hono MUST вернуть HTTP `200` с одним JSON-объектом из ровно двух строковых полей `id` и `title` со значениями выбранной записи. | HTTP-контракт 23 и проекция базы 21. Массив, чужой заголовок, пропущенное или лишнее поле нарушают контракт. |
| SPEC-R2 | При действительном сеансе сотрудника и чтении чужого или отсутствующего документа Hono MUST вернуть одинаковый HTTP `404` с JSON `{"error":"not_found"}` для обоих случаев. | HTTP-контракт 23. Различие статуса или JSON раскрывает, существует ли чужой документ. |
| SPEC-R3 | При отсутствии действительного сеанса Hono MUST вернуть HTTP `401`. | HTTP-контракт 23. Выдача карточки или ответ `404` вместо `401` нарушают контракт. Тело ответа `401` владелец не задал. |
| SPEC-R4 | При обращении к клиенту чтения Hono MUST передать `principal` из проверенного сеанса. | Контракт стыка 21. Если личность запроса заменяется другой или общей привилегированной личностью, проверка доступа выполняется для другого субъекта. |
| SPEC-R5 | Data API MUST ограничивать список и чтение по ID документами текущего владельца для сотрудника и документами с явным разрешением владельца для поддержки. | Цель тестового контролёра. Любая строка вне разрешённого набора нарушает границу доступа, даже если Hono затем её скроет. |

Инженер 28 использует выданный `public/desk-client.mjs`, вызывая `readDocument(principal, id)` через отдельный Unix-сокет, заданный в окружении приложения как `DOCUMENT_DESK_SOCKET`. `listDocuments(principal)` служит для контроля Data API. HTTP-маршрут списка в эту спецификацию не входит. Команда 21 и оператор обеспечивают работу базы и сокета из комплекта оператора. Инженеру 28 выдаются публичный клиент и адрес сокета. Развёртывание использует предусмотренные комплектом тестовые ключи, созданные при старте внутри контейнера.

Успешная выборка с одной строкой даёт карточку. Успешная пустая выборка на прямом интерфейсе — `status=200`, `data=[]`, `error=null` для скрытого и для отсутствующего ID. На HTTP-маршруте сотрудника оба результата дают ответ SPEC-R2. Сбой соединения или ошибка базы не подтверждают успешную пустую выборку. Владелец 23 не задал публичный ответ для этих сбоев.

## Приёмка на локальном стенде

Стенд использует четыре исходные записи и выданные локальные тестовые сеансы. Оператор поднимает отдельную базу из своего комплекта и предоставляет сокет. Инженер 28 подключает выданный клиент и запускает приложение со штатной проверкой сеанса. Для нового прогона нужны выданные 21 архивы с контрольными суммами из описания стыка. Сейчас происхождение архивов и запуск стенда по ним проверить нельзя, поскольку в каталоге есть только описание и журнал. Наблюдения на каждом интерфейсе фиксируются с указанием сеанса, ID, статуса и тела ответа. Для прямого прогона база дополнительно фиксирует действующую роль и номер запроса.

| Сеанс и роль Data API | Полный видимый набор `id — title` | Скрытые ID |
| --- | --- | --- |
| `worker-a` / `desk_employee` | `amber` — Апрель, `cedar` — Июнь | `birch`, `dune` |
| `worker-b` / `desk_employee` | `birch` — Май, `dune` — Июль | `amber`, `cedar` |
| `support` / `desk_support` | `birch` — Май, `cedar` — Июнь | `amber`, `dune` |

| Проверка и ответственный | Условие прохождения и основание для отказа |
| --- | --- |
| AC-1 · Data API, команда 21 · SPEC-R5 | Для каждого из трёх сеансов выполнить список, четыре чтения известных ID и запрос `missing`. Во всех ответах ожидаются `200`, `error=null` и роль из таблицы. Каждый список совпадает с таблицей. Каждая видимая точечная выборка содержит одну строку с точной парой `id` и `title`. Каждая скрытая и отсутствующая выборка содержит `data=[]`. Неверная роль, лишняя строка, лишнее поле, отсутствующая разрешённая строка, несовпадение заголовка или различные результаты для скрытого и отсутствующего ID означают отказ. Для предыдущего чтения только ID разрешённые наборы должны совпадать. |
| AC-2 · HTTP Hono, инженер 28 · SPEC-R1, R2, R4 | Через запущенный маршрут под каждым из двух сеансов сотрудника запросить четыре известных ID и `missing`. Для видимых ID получить точные объекты из таблицы. Для двух чужих ID и `missing` в рамках каждого сеанса сравнить статус и JSON с SPEC-R2. Запрос одного и того же `amber` под `worker-a` и `worker-b` должен дать соответственно карточку и `404`. Одинаковая выдача карточки для обоих сеансов, раскрытие заголовка или различие ответов для чужого и отсутствующего ID означают отказ. |
| AC-3 · HTTP Hono, инженер 28 · SPEC-R3 | Запросить `/documents/amber` без сеанса и с недействительным тестовым сеансом. Оба запроса получают `401` без карточки. Иной статус или данные документа означают отказ. |
| AC-4 · Путь данных, инженер 28 и команда 21 · SPEC-R1, R2, R4, R5 | При AC-2 проверить путь от тестового сеанса и ID через штатную проверку сеанса в Hono, клиент 21, реальную выборку из четырёх записей и HTTP-ответ. Подтвердить использование выданного сокета и клиента при прогоне. Ответ из заглушки, фикстуры приложения или отдельного вызова клиента не закрывает AC-2. У этого GET нет этапа записи или перезагрузки созданного объекта. |

В переданном журнале AC-1 покрыта 18 ответами, полученными для трёх сеансов, и контрольным чтением только ID. После прогона в базе остались четыре записи. Контейнер из этого прогона удалён. Для AC-2–AC-4 нужен новый прогон после предоставления локального комплекта и маршрута. Результаты ограничены учебным стендом и четырьмя записями.

## Границы готовности

| Граница | Решение, доказательство и ответственный |
| --- | --- |
| HRB-03 и HRB-11 · Доступ и инвариант выдачи | Контролёр определил получателей. AC-1 проверяет прямую выборку под назначенными ролями, включая поддержку без согласия. AC-2 проверяет доступ на HTTP для сотрудника. Отчёт 21 подтверждает наблюдаемую выдачу. Точные grants, RLS, наличие `SECURITY DEFINER` и исключения для повышенных ролей в отчёте не описаны. Если потребуется подтвердить эти механизмы или иные пути прямого доступа, доказательство предоставляет 21 по конфигурации выданного стенда и проверкам на соответствующей границе. |
| HRB-04 · Сеанс и субъект | 23 владеет HTTP-контрактом, 28 проверяет сеанс при входе и использует его субъект для чтения. AC-2–AC-4 проверяют смену субъекта и отказ без действительного сеанса. |
| HRB-05 и HRB-06 · Различия исходов | AC-1 и AC-2 проверяют скрытый ID, отсутствие строки и различие контрактов двух интерфейсов. AC-3 проверяет отсутствие действительного сеанса. Для полного контракта обработки сбоев 21 должен описать ошибки клиента, а 23 — утвердить HTTP-ответы и правила повторов, если они нужны. До этого выводы ограничены описанными ответами. |
| HRB-10 · Стенд и чтение | Команда 21 и оператор отвечают за запуск и завершение учебной базы. 28 отвечает за выполнение GET на работающем стенде. Наличие отчёта о завершённом контейнере не подтверждает готовность нового прогона. Жизненный цикл документа выходит за рамки чтения. |
| HRB-12 · Имена и формы | 23 владеет `GET /documents/:id`, статусами HTTP и JSON ответа. 21 владеет символами клиента и формой прямой выборки. AC-1 и AC-2 обнаруживают подмену объекта карточки массивом, утечку полей клиента в HTTP и замену одного статуса статусом другого интерфейса. |
| HRB-01, HRB-02, HRB-07, HRB-08 и HRB-09 · `not_applicable` в пределах утверждённого среза | HTTP-контракт задаёт чтение без записи и числового представления данных. Владелец задал проверку сеанса, но не задал подписанное тело, отдельные требования целостности запроса или журнал событий приложения. Номер запроса в отчёте 21 относится к доказательству выборки. |

- **Поддержка в HTTP.** Цель и право чтения поддержки подтверждены для Data API. Для включения поддержки в приёмку Hono владелец 23 должен подтвердить, распространяется ли утверждённый маршрут на её сеанс, и определить ответы для разрешённого, скрытого и отсутствующего документа.
- **Срок хранения.** У тестового контролёра нужно получить решение о сроке хранения учебных документов и моменте его отсчёта либо подтверждение, кто уполномочен принять это решение. Приёмка описанного GET может идти без этого решения. Правила удаления и истечения срока в этом контракте отсутствуют.
