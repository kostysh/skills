# Предметная проверка 18 ноября 2026

**Две версии Workers требуют разного решения.** В активной справке 0.1.11 имя прежнего npm-пакета подавалось как текущий выбор для нового проекта. npm пометил `@cloudflare/vitest-pool-workers@0.23.0` как переименованный. Его peer-диапазон для Vitest равен `^4.1.0`. Попытка разрешить его вместе с Vitest 5.1.1 в пустом проекте завершилась `ERESOLVE`. Cloudflare описывает новый `@cloudflare/vitest-plugin` и функцию `cloudflareTest()`. У проверенной версии 1.8.4 peer-диапазон равен `^4.1.0 || ^5.0.0`. Сам пример в руководстве использует Vitest 4.1. Новая строка активной справки направляет к версии плагина, совместимой с проектом, и сохраняет действующую установку при отсутствии поручения на миграцию. [Инструкция Cloudflare](https://developers.cloudflare.com/workers/testing/vitest-integration/write-your-first-test/) · [Новый манифест](https://registry.npmjs.org/@cloudflare%2Fvitest-plugin/1.8.4) · [Прежний манифест](https://registry.npmjs.org/@cloudflare%2Fvitest-pool-workers/0.23.0) · [Ошибка разрешения](legacy-peer-mismatch.json)

Один и тот же тест вызвал обработчик через `exports.default.fetch`, прочитал заданную в конфигурации строку из привязки и проверил 404 для другой страницы. Он прошёл на `workerd 2026-08-15` с Vitest 4.1.9 и старым пакетом, а также на `workerd 2026-11-17` с Vitest 5.1.1 и новым плагином. Первая связка выдала предупреждение о переименовании. Вторая с `nodejs_compat` и согласованным рабочим каталогом прошла с пустым stderr. При первом запуске без этого флага сам тест также прошёл, но зависимость Vitest обратилась к недоступному `node:inspector`. Все запуски относятся к локальному workerd. Развёрнутый Worker и пользовательский аккаунт не требовались. [Рабочие команды и потоки](runner-evidence.json) · [Входные файлы с lockfile](runner-probes.tar.gz)

**Node.** Рабочая станция использует Node 24.15.0. Корневое требование репозитория — `>=22.22.0`, CI выбирает ветку 24. Отдельный тест вызвал `t.mock.module` и проверил значение реального импорта. На Node 22.22.0 прежняя форма `namedExports` дала ожидаемое значение, а новая `exports` дала `undefined` и падение теста. Новая форма прошла на 24.15.0, 24.22.3 и 26.13.1. Каждая версия сообщила об экспериментальном модульном мокировании. Совместимость формы уже учитывалась в справке 0.1.11. Отдельная оговорка о типизации также сохраняется. Tally использует enum в исходном тесте и объявленный tsx 4.20.5 для тестов. [Node 22.22.0](https://nodejs.org/download/release/v22.22.0/docs/api/test.html#mockmodulespecifier-options) · [Node 24.15.0](https://nodejs.org/download/release/v24.15.0/docs/api/test.html#mockmodulespecifier-options) · [TypeScript в Node 26](https://nodejs.org/download/release/v26.13.1/docs/api/typescript.html) · [Измерения runner](runner-evidence.json)

**Vitest и React.** В корне checkout, в CLI и в самом скиле `vitest/package.json` не разрешается. Документационные контракты самого пакета запускаются штатным `node --test test/docs-contract.test.mjs`. В расходном проекте действительно установлен Vitest 5.1.1. Его манифест требует Node `^22.12.0 || ^24.0.0 || >=26.0.0`. На Node 24.15.0 проверены React/React DOM 19.3.1, Testing Library React 16.3.3, DOM 10.4.2 и user-event 14.6.12. В jsdom 31.0.1 новый счётчик показал `1` после нажатия. Синхронный возврат `false` завершил `waitFor` после одного вызова, а отклонённый Promise вызвал вторую попытку. Эти же два теста прошли в Vitest Browser Mode с локальным Chrome 158.0.8127.36. Третий тест в браузере измерил отрисованную ширину 32 px. Для установленного Playwright-провайдера 5.1.1 параметр пути к Chrome называется `launchOptions.executablePath`. Первый запуск с неверным именем не нашёл стандартный Chromium, его вывод сохранён. Поставляемая справка разделяет имитацию DOM, Browser Mode и выборочный browser smoke. Справка Vitest по-прежнему помечает `typecheck` как экспериментальный. Эти проверки дали основания сохранить правила о React и Node. **Формулировка.** Руководство OpenAI для Astra рекомендует обозначать результат, разрешённые самостоятельные решения и фактическую проверку завершения. Здесь результатом служит тест, который обнаруживает нарушенный пользовательский контракт и допускает эквивалентную реализацию. Исполнитель выбирает способ запуска. Авторитет контракта, режимы, ограничения на изменение файлов и требования к чувствительным границам заданы в скиле и проекте. Отдельные сессии Sol medium проверяют перенос этого принципа на три локальные задачи. Они не устанавливают эффективность для всех раннеров, выбор скила из каталога или эффект одной удалённой фразы вне остального текста.
