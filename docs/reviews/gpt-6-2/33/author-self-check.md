Инженер исправления и автор ретроспективы получают вердикт на тех же ревизиях. Скил требует установить, что демонстрирует тест, и привязать подтверждённое нарушение как к допустимости проверенного входа, так и к ожидаемому поведению. В исходном прогоне C модель увидела реальное изменение двух записей, признала отсутствие требования к повторяющимся ID и всё же заблокировала рабочую версию. Исправлено только напоминание в `fragments/overview.md`. Метод проверки по-прежнему выбирает рецензент. Две обязательные ссылки уже разделяют подтверждённое несоответствие, неясность нормы и пробел свидетельств. Методика разрешает выводимые требования с явно указанным основанием. Применимость конкретного тестового примера может прямо следовать из источника или быть обоснованно выведена из него. Решения о требованиях остаются у их владельца, вывод о соответствии — у рецензента. Исполнитель проверяет расходные копии реализации. Модуль каталога и принятый README находятся вне области редактирования. Проверка может опровергнуть изменение в любом направлении. Сбой сохранения и нарушение при двух разных ID с одинаковым заголовком требуют отказа. Дополнительный случай с совпадающими ID проверяет одно и то же измеримое поведение на входе от службы поддержки. При принятой норме об ошибке нужно отклонить поставку. Если владелица ещё не приняла это обязательство, разработчик узнаёт о наблюдении отдельно от итогового вердикта по обычным данным. Очередной повтор C на исходной «Сосне» измеряет разброс между сессиями. Эти проверки ограничены локальными примерами.
