# Предметная сверка · 18 ноября 2026 года

Для обычного ревью нужна воспроизводимая рекомендация по заявленному изменению. Рецензент должен проверить доступное поведение, объяснить пропуски и сохранить исходные файлы. Способ добрать свидетельства зависит от входа. Например, когда отсутствует hunk, достаточно сравнить доступные версии файла. Когда отсутствует сам файл, сохраняются как подтверждённая регрессия, так и ограничение охвата. Точная инструкция остаётся в читаемых при каждом ревью ссылках. [Охват](../../../../skills/code-reviewer/references/diff-completeness.md) · [Рекомендации](../../../../skills/code-reviewer/references/findings-format.md)

| Указать результат и границы полномочий | Руководство OpenAI для Astra предлагает задать конечное состояние, решения оператора и проверить выполненную работу. Для ревью это конкретное заключение по неизменному снимку. Рецензент выбирает между чтением, сравнением и проверкой на расходной копии. Исправление, публикация отзыва и слияние требуют соответствующих полномочий. Перенос на Sol проверялся отдельными опытами. [OpenAI, Task completion](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-6.2-astra#task-completion) |
| Зафиксировать область изменения | Git 2.53.0 различает сравнение концов и сравнение с общим предком. GitHub использует для PR три точки. Имя основной ветки, GitHub state и merge commit по отдельности не задают точный состав изменений. В PR #35 merge-base совпал с предоставленной базой. Восьми blob ID соответствуют обе версии всех четырёх изменённых файлов, а полный Git diff совпал с переданными байтами. | Проверить полноту | GitHub допускает скрытие diff из-за размера или правил отображения. REST-список файлов по умолчанию разбит по 30 и ограничен 3000 файлами. У `gh pr view` есть поля `baseRefOid`, `headRefOid`, `changedFiles`, `files` и `mergeCommit`. Вход 08 снят с GitHub через CLI 2.96.0. Сверка с входом 07 дала четыре пути и полные неизменные OID. Точные полномочия, база и граница статуса остаются существенными условиями. [GitHub, PR files](https://docs.github.com/en/rest/pulls/pulls#list-pull-requests-files) · [GitHub CLI](https://cli.github.com/manual/gh_pr_view) · [Вход 08](../08/pr35-git-github-handoff.json) |
| Обосновать замечание и статус | `approve` требует достаточных свидетельств по доступной области. Для `request changes` нужен подтверждённый блокер. `limited` сохраняет уже установленный блокер при недоступной части. `blocked` применяется при отсутствии необходимого основания ревью. Большой diff, новая зависимость или зелёный smoke сами по себе не определяют серьёзность. В T03 обычные тесты прошли на двух ревизиях, а сохранение с новым чтением выявило потерю пользовательских данных на одной. Проверка отдельно запрошенной сложности, полного соответствия спецификации, рисков безопасности и исполняемого пути имеет разные области. Успех опытов по полноте diff не обосновывает удаление их триггеров. В T03 17 даёт риск слияния, 24 проверяет цель пользователя, 33 — требования, 30 — диагностику или разрешённое исправление. CLI из PR #35 использует `@inquirer/checkbox@5.2.7` через `@inquirer/prompts@8.7.4`. Параметр `loop: false` ограничивает курсор границами списка. В приложенном lockfile зафиксированы зависимости, а все 1024 файла 29 пакетов для локальных тестов совпали с официальными npm-архивами после проверки их SRI. На Node 24.15.0 новый тест падает на предыдущей реализации и проходит в изменённой. Проверка использует имитацию нажатий клавиш в Inquirer. Исторический журнал упоминает также Linux PTY и планы проверки CI. В этой проверке граница — модуль и интерактивный тест.
