# План работ по Q-17 для двух команд

Команда источника передаёт факт готовности отчёта и его адресата. Команда кабинета показывает уведомление этому сотруднику. После сверки контракта команды работают параллельно на изолированных учебных копиях. Закрывают обе задачи по одному сквозному сценарию с общим тестовым отчётом.

## Основание и границы

Объём `unchanged` относительно учебного поручения для R2 ↔ Q-17 в PRD 0.3. План готов для координации двух команд. Самый короткий путь — использовать существующую передачу готовности и штатный вход кабинета. Минимальная проверка проходит от фактической готовности до экрана адресата и выхода отправки. Добавлений к объёму нет. [Условие владельца](./owner-scenario-condition.md) · [Спецификация](./specification.md#материал-для-планирования)

Повторное чтение PRD 0.3 подтвердило условия владельца. R2 требует уведомления только в кабинете и исключает email о готовности, Q-18 открыт. Ответ уполномоченного заказчика по Q-17 имеет статус `complete` по записке согласования. Первичный экспорт, редакция 0.2 и реестр отсутствуют в пакете. Учебное решение владельца снимает прежний блокер AHI-01 на подготовку спецификации только для этого участка. Запуск реализации на копиях зависит от согласования контракта. PRD остаётся `draft`, `non-authoritative`, `draft-only`. Для обычной передачи требуются утверждение конкретной редакции владельцем продукта и ссылка от владельца PRD с R2 ↔ Q-17. [PRD 0.3](./product-draft.md) · [Q-17](./decision-intake.md#q-17--канал-уведомления-о-готовности-отчёта) · [Условие владельца](./owner-scenario-condition.md) · [AHI-01](./architecture-handoff.md#передача-следующей-сессии)

## Работы и зависимости

| Работа | Владелец и готовность | Результат и передача |
| --- | --- | --- |
| **J0. Сверить общую границу** · средний риск | `ready for обе команды` для сверки по условию владельца | На общем тестовом отчёте обе команды подтверждают, где источник фиксирует готовность, как различаются отчёт и адресат, что именно читает кабинет и где видны применимые отправки, включая отложенные. Сверить штатные выход и вход и подтвердить, что выход покрывает предусловия входа. Зафиксировать ссылку на существующий контракт и согласованные точки проверки. Если нужна новая граница, зависимость или владелец контракта, вернуть вопрос `architecture-engineer`. После определения границы недостающую сигнатуру или детали поведения уточняет `spec-engineer`. [Контракт уведомления](./specification.md#контракт-уведомления) |
| **J1. Передать готовность** · средний риск | Команда источника, `blocked` до J0 | На своей копии передать по согласованному выходу факт готовности того же отчёта и его адресата. Проверить свой выход на фактическом событии и применимые пути отправки на своём участке. Передать второй команде наблюдение выхода для AC-1 и сведения о путях для AC-2–AC-3. [SPEC-R1–R3](./specification.md#контракт-уведомления) |
| **J2. Показать уведомление** · средний риск | Команда кабинета, `blocked` до J0 | На своей копии принять готовность по согласованному входу, сохранить связку до показа и показать уведомление в кабинете адресата. Проверить вход, фактический экран и применимые пути отправки на своём участке. Передать наблюдения для AC-1–AC-3 и отдельно проверить открытие отчёта по AC-4. [SPEC-R1–R3 и карта проверок](./specification.md#общая-приёмка-и-карта-проверки) |

- `start` J0 → J1 и J2. Обе команды подтверждают совместимость по каноническому контракту на реальной границе копий. До сверки точная форма интерфейса неизвестна. После сверки команды меняют только свой участок и не ждут реализации друг друга.
- `acceptance` J1 + J2 → закрытие обеих работ. Команды совместно подключают свои результаты на согласованной границе. Команда источника собирает общий протокол, команда кабинета добавляет наблюдения входа и экрана, обе подтверждают решение. Отдельный порядок слияния источниками не задан. [Порядок общей приёмки](./specification.md#материал-для-планирования)

## Общая приёмка

Довести общий тестовый отчёт до готовности штатным путём источника. В протоколе связать запуск, событие, отчёт и адресата. Использовать фактический выход источника, штатное чтение кабинета и наблюдение на границах отправки. Если путь включает преобразование, сохранение или повторное чтение, пройти эти переходы в том же сценарии. [Карта проверки](./specification.md#общая-приёмка-и-карта-проверки)

| Проверка | Что должно быть видно в протоколе |
| --- | --- |
| **AC-1 / SPEC-R1** | Источник и кабинет наблюдают ту же связку. Адресат видит уведомление именно об этом отчёте. Подмена отчёта или адресата и отсутствие показа при полном наблюдении означают провал. `edge_ack`, мок и запись в журнале сами по себе показ не подтверждают. |
| **AC-2 / SPEC-R2** | Полный вывод отправки по событию до завершения применимой обработки, включая существующий отложенный путь, если он есть. Писем о готовности этого отчёта адресату — ноль. Любое такое письмо означает провал. Письма по другим причинам вне проверки. |
| **AC-3 / SPEC-R3** | Обе команды сверили маршруты. На выходе каждого применимого существующего канала вне кабинета подтверждено отсутствие доставки по тому же событию. Если таких путей нет, зафиксировать результат сверки. |
| **AC-4 / смежный сценарий PRD** | Адресат отдельно открывает тот же готовый отчёт в кабинете. Если открыть его не удаётся, команда кабинета передаёт сбой владельцу PRD. Изменение механизма открытия вне Q-17. |

Обе команды закрывают Q-17 только при подтверждённых AC-1–AC-3 для одного события. При неполном наблюдении результат остаётся неподтверждённым. При провале команды возвращают наблюдение владельцу участка, устраняют дефект в согласованном объёме и повторяют общий сценарий. AC-4 фиксируется отдельно и определяет, подтверждено ли открытие отчёта. [Спецификация](./specification.md#общая-приёмка-и-карта-проверки)

## Отдельные передачи

- **AHI-02 / Q-18** · `blocked` до решения заказчика. 90 дней остаются предложением поддержки. Владелец PRD после ответа фиксирует решение и критерии доступности, затем передаёт утверждённое требование `architecture-engineer` для пересмотра жизненного цикла. Хранение, удаление и миграции не входят в задания команд. [Q-18](./decision-intake.md#q-18--срок-хранения-отчёта) · [AHI-02](./architecture-handoff.md#передача-следующей-сессии)
- **AHI-03 / PD-LAB-1** · `ready for delivery-planner` для отдельного задания инженеру стенда. Для D72 на `common` подтверждены два показа в срок и ноль `report_ready` в полном окне по тройке. Для h83/e46 показ к 13510 мс неизвестен. `edge_ack` и кадры D70 этот пробел не закрывают. Инженеру нужно клиентское доказательство из того же запуска или, при его отсутствии, отдельно разрешённый прогон D72 на `common`. Контракт замера — три разных отчёта за ≤ 20 мс, полный клиентский и почтовый охват по `(run, report, employee)`, показ каждого к его `ready + 1500 мс` включительно и ноль `report_ready`. Доказанный пропуск срока даёт основание сравнить `separate` в тех же условиях. Письмо означает сбой канала. Неполное наблюдение оставляет выбор открытым. Инженер возвращает данные `architecture-engineer`, хозяин стенда решает вопрос профиля и слота. Это отдельная стендовая работа без зависимости для Q-17. [AHI-03](./architecture-handoff.md#передача-следующей-сессии) · [Условия D72](./lab/request.md)

План ограничен учебными копиями. Внешняя поставка, продуктовый срок показа и новая топология вне поручения. Сверка границы и сквозной сценарий ещё не выполнены.
