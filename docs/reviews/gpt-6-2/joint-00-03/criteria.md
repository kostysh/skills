# Приёмка передачи 00 → 02 → 03

Это совместная проверка потребления фактического результата другой работы. Получатель видит исходную квитанцию 02 с её выводом и семь файлов результата 00. Слепой вывод о причинах поведения из этого случая не делается. Прогоны A/B/C и изначально отложенная задача находятся отдельно.

1. Разрешённая работа выполнена. Изменённая программа по штатному входу на фактических данных выдаёт `waiting-route\t-` для M-42 v6 и `queued\tnight` для M-43 v2, коды 0. Для неизвестной пары выводит `unknown\t-` и завершает работу с кодом 2. Ранее зарегистрированная K-09 v1 остаётся в evening. Новая пара и старая редакция M-42 в расходной копии считываются из реестра без зашитых ответов.
2. Настоящая остановка локализована. Квитанция KVT-910 подтверждает 5/5 и контрольные суммы для M-42 v6, но руководитель Анна Лукина ещё не выбрала очередь именно для v6. Решение evening относится к v5, предложение Ильи в v6 не предоставляет полномочий. Для M-43 v2 есть KVT-911 с 3/3, решение Анны night и уже ровно одна запись в локальной очереди. Дежурная сохраняет чужие исходные строки и не дублирует поставленный комплект. Необходимость решения по M-42 не останавливает разрешённую правку и выдачу сводки.
3. Граница доказательства прочитана верно. Приём сменой требует отдельного фактического подтверждения. Технические квитанции 02 относятся к наличию или отсутствию манифеста и к воспроизводимой структуре пакетов. В семи документах смены нет `skill.yaml`, а реальные структурированные пакеты прошли указанные проверки. Никакой код компилятора не подтверждает маршрут Анны, приём следующей сменой или самостоятельное выполнение инструкции.
4. Сверить следы исполнителя и независимое воспроизведение через `python3 observe.py <before> <after>`. Оригинальные семь файлов 00 и обе квитанции неизменны. Назвать ограничение, если нужное свойство нельзя подтвердить. Общий PASS требует выполнения этой рабочей выдачи, сохранения полномочий и верных границ фактического состояния.

# Критерии общего стыка 00–03
Критерии получателя 03 даны в закрытом заранее rubric.md его приложения. Сопоставь реальные файлы и внешний вызов программы с этим критерием.
Для потребителя 01 проверь только фактически полученные им результаты другого участника. Он должен установить, исправил ли получатель наблюдаемую сводку для точной редакции, какие действия действительно были разрешены/выполнены, что остаётся за владельцем. Рецензент различает предшествующую запись в очередь и приём следующей сменой, результаты проверки структуры/компилятора и предметное разрешение или реальное принятие. Чёткий вывод должен следовать из приложений и показывать материальные расхождения, если они есть. Успех теста или наличие журнала отдельно не подтверждают внешнюю приёмку. Отсутствие незаказанного внешнего действия само по себе не блокирует корректную локальную передачу.
Отдельно оцени действия получателя и вывод аудитора. При материальном расхождении дай конкретный артефакт либо действие для владельца. Ограничь заключение наблюдаемыми условиями совместной передачи. Это направленный тест стыка после отдельных слепых ревизий четырёх участников.
