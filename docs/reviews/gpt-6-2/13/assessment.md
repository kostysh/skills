# Как дежурный проходит новую инструкцию Tally

На пакете `documentation` 0.2.3 четыре отдельных исполнителя в роли дежурных выполнили новые записки в чистых каталогах. У каждого были только архив Tally и `guide.md` назначенного автора. Для 1.0.0 и 1.1.0 они получили нужную сумму и распознали неправильное число. На неисправной 1.0.1 читатель штатной процедуры воспроизвёл отказ и назвал условие замены выпуска. Другой читатель выполнил разрешённый на смену обход. ## Почему изменили правило

В исходном скиле A позднее замечание повторяло уже действующее правило о пределах зелёной сборки документации. В B изъяли только это замечание. На 1.0.0 обе версии прошли. На 1.0.1 оба автора нашли работающий внутренний обработчик. Для штатного bin оба запустили только правильный ввод. Исходная строгая рубрика присвоила **FAIL** обеим запискам. Отсутствие эффекта от удаления одной строки показывает достаточность остальной выдачи только для рабочего случая. [Исходная поставка и случаи](research-inputs.tar.gz) · [Изъятие](A-B.patch) · [Оценка A/B](assessment-ab.md)

Первая короткая редакция C потребовала проверить успех и ошибку через штатный путь и обозначить временное решение. В подтверждении A и C прошли 1.0.0 и заранее отложенный 1.1.0. На 1.0.1 C действительно проверила оба исхода штатного bin. Записка предложила фактически работающий внутренний вызов и пропустила условие восстановления штатного пути. Исходный **FAIL** остался. Чтобы отделить цель дежурного от ожидания рубрики, на одной и той же 1.0.1 заранее назначили два явных поручения. Для C разрешённый разовый обход получил **PASS**. Штатная процедура получила **FAIL** по конкретному пробелу в записке о восстановлении команды. [Текст C](A-C.patch) · [Оценка A/C](assessment-confirm.md) · [Фиксация двух поручений](scope-freeze.json) · [Оценка двух поручений](assessment-pair.md)

В окончательном правиле C2 автор проверяет штатный путь для успеха и существенных ошибок. Если путь неисправен, он сообщает читателю, что должно измениться для его работы. Автор может дать подходящий проверенный обход с указанием его пределов. Все пять последующих авторов получили точные байты распакованной 0.2.3. Для двух явных поручений и двух работающих выпусков получен **PASS**. [Единственное изменение C → C2](C-C2.patch) · [Отличие метаданных поставки](trial-to-release.patch) · [Архив 0.2.3](documentation-0.2.3.tar.gz) · [Оценка пяти авторов](assessment-final.md)

**Прежнее широкое поручение по строгой рубрике всё ещё получило FAIL.** Автор проверил правильный и ошибочный ввод через штатный `tally`, описал фактический отказ и дал рабочий внутренний вызов. В записке нет требования получить проверенный исправленный выпуск и нет явного условия возврата к штатному пути. Текст поручения допускает достигнутый результат через обход. Требование к самой поставке было зафиксировано в рубрике. В паре явных поручений изменилось разрешение читателю при одинаковых байтах пакета. Эта разница определяет, допустимо ли назначить внутреннюю команду оператору. Дополнительный запрет для всех широких задач не обоснован. Этот опыт также показывает предел финального указания, когда автор считает цель достигнутой через обход. [Задание, записка и операции](results/d4260f.json) · [Исходная рубрика](trial-criteria.md) · [Формальная оценка](assessment-final.md)

## Свежая проверка частично работающей команды

Для первой C выпуск 1.1.0 был отложен заранее. При выборе C2 результаты его испытания уже были известны. После фиксации байтов конечного архива поэтому подготовили отдельный учебный выпуск 1.0.2 с ранее выпущенным кодом из строки 05. В его манифесте `tally` указывает прямо на этот файл. Одна ветвь работает, другая выдаёт результат непригодного для приёмника формата. Задачу, рубрику, входные хеши и наблюдения пакета зафиксировали до выдачи новому автору. [Входы и исходный код](fresh-freeze.json) · [Комплект](fresh-inputs.tar.gz)

Автор пропустил весь stdout обычного вызова через `JSON.parse`. Баннер `Calculating` перед объектом делает весь вывод непригодным для JSON-приёмника, несмотря на код 0. Неверное число уже правильно даёт пустой stdout, stderr `Invalid number` и код 2. Автор отдельно задокументировал эту рабочую ветвь и условие приёмки исправленного вывода суммы. Независимый оценщик присвоил **PASS** всем четырём аспектам. [Записка и исполнение](results/f8f969.json) · [Заключение](assessment-fresh.md)

## Что именно проверено

A/B дали четыре свежие сессии. Подтверждение C добавило четыре сессии, включая A на отложенном выпуске. Два прежних наблюдения A независимо переоценены с новыми кодами. Затем последовали два автора C на явных поручениях, пять авторов точной 0.2.3, четыре заранее назначенных читателя и отдельный автор нового частично неисправного выпуска. Все участники — `gpt-6.2-sol`, reasoning `medium`. Оценщики были другими сессиями, работали в режиме read-only и получали критерии, обезличенные действия, файлы и записи наблюдений. Их исходные подписи и SHA-256 журнала событий сохранены до сведения кодов с вариантами. У всех участников долговременная память отключена. Рабочие каталоги отдельные, физический хост общий. Два первоначальных старта завершились до первого события модели из-за базы локального сервиса только для чтения. Они исключены из счёта, новые сессии стартовали с пустого состояния.
