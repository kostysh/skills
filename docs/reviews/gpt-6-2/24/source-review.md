# Предметная сверка пункта 24

Сверка 18 ноября 2026 года. Задача рецензента — определить, достигает ли заявленный пользователь результата в пределах принятой концепции, и передать следующий шаг названному владельцу. Принятая версия 04 определяет полномочия автора продуктового решения. Версия 15 оставляет архитектурные решения архитектору. Скил 24 использует эти результаты как основание для проверки готовности конкретного заявления. [План](../../../plans/implementation-plan-20261118-1.md) · [Принятая версия 04](../04/independent-audit.md) · [Принятая версия 15](../15/recovery/independent-audit.md)

В руководстве OpenAI примеры по завершению долгой работы отнесены к Astra. Руководство предлагает задавать конечный результат и указывать решения, для которых нужен оператор. В этом случае рецензент сам выбирает порядок чтения и способ проверки, а принятие цели и изменение поставки остаются у соответствующих владельцев. Действия Sol на конкретных входах измерены отдельно. Британское руководство по проектированию услуг предлагает явно связывать потребность, роль пользователя, критерии приёмки и свидетельства. Оно даёт независимое методическое основание для такой связи. Полномочия Камиллы и ожидаемое поведение каталога задают документы самого упражнения. [OpenAI, Task completion](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-6.2-astra#task-completion) · [GOV.UK, Writing user stories](https://www.gov.uk/service-manual/agile-delivery/writing-user-stories)

| Существенное правило | Решение и предметное основание |
| --- | --- |
| Владелец, предмет, цель и граница полномочий | Сохранить. Владелец продукта принимает пользовательское требование. Заявка реализации и заключение о коде — свидетельства о поставке. Конфликт с нижестоящей заявкой можно оценить. Неразрешённое равное полномочие или отсутствие самой цели ограничивает предмет оценки. |
| Режим проектирования и режим закрытия | Сохранить. В проекте рецензент ищет реализацию, способную пройти критерий без нужного результата. При закрытии он устанавливает эффект у конкретного получателя. Тест каталога проверяет память процесса. Чтобы принять обещание непрерывности, требуется результат следующего открытия. |
| Пользователь, граница заявления и классификация | Сохранить. Одному локальному оператору важен список закреплённых после открытия. Файл и команды позволяют выполнить запрос. Вывод отдельного процесса показывает результат. Для клиента самого API предоставленный интерфейс может составлять заявленную возможность. Полезная работа по инфраструктуре допускает собственную более узкую приёмку. |
| Перечень видов артефактов в шаге проверки свидетельств | Заменить кратким положительным указанием C. Отдельные определения и соседние шаги всё ещё требуют определить границу, реально проверить эффект и отметить пробелы. B показал правильный итог открытий в обоих случаях. Вывод относится к полным испытанным инструкциям и предоставленным источникам. |
| Согласованность статуса, риска, исхода и решения | Сохранить точные значения, приоритет решений и условия. Положительная оценка возможности требует `assessable`, низкого риска и текущего результата у потребителя. Отказы и недостаток полномочий различаются. При `blocked` контракт исключает вымышленную классификацию. Прямое опровержение цели при достаточных данных допускает сочетание `assessable`, `high`, `claim-not-demonstrated` и `reject`. Выбор одной рекомендации делает передачу однозначной. Отсутствие этого контракта у оценщика оставило шесть строгих оценок открытыми. [Общий фрагмент](formal-verdict-contract.md) · [Первичное ограничение оценщика](assessment-confirm.md) |
| Повторная проверка предпосылок и исправлений | Сохранить. Изменившийся компонент или зона ответственности может затронуть старое обоснование при неизменном тексте ADR. Аудитор устанавливает зависимость и передаёт выбор архитектору. Если связанный блокер повторяется, владелец исследует причину перед очередной правкой. Нынешний опыт с каталогом не измерял все эти решения повторно. [Ранее проверенное изменение основания](../../../../skills/concept-conformance-reviewer/docs/reviews/evidence/20260929-premises/final-audit.md) |
| Разделение ролей | Сохранить. 17 сообщает о дефекте и риске слияния. 24 наблюдает цель пользователя. 33 проверяет все принятые требования. Право исправить код получает отдельный исполнитель по своему поручению. Оценка не требует публикации или изменения ADR. [Заключение 17](../17/catalog-review.md) · [Передача источника 23](../23/catalog-handoff.md) · [Выход 24](catalog-review.md) |

Исходные материалы каталога извлечены из контролируемого Git bundle. Код R2 совпадает с историческим исходным файлом. Для R1 организатор взял сохранение признака из исторического исправления. Направление R1 → R2 создано для исследования. README обеих ревизий совпадает с историческим контрактом по SHA-256 `a61923dbfb54a07bfaa42ecd38cf4b114787c3b29e48dac6d33887a1cf7b1cc8`. Упражнение добавляет один и тот же CLI-адаптер и запись цели от имени владельца. Адаптер вызывает `loadCatalog`, `setPinned` и `saveCatalog` исходного модуля. Тесты поставки и пользовательский путь выполнены на Linux с Node 24.15.0. Скил поставляется без программ и требований к Node. Команды принадлежат учебному приложению.
