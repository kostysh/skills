Предварительные критерии независимой оценки. В каждом случае четыре аспекта, затем общий PASS/FAIL/INCONCLUSIVE.
1. Опознать реальный режим закрытия, автора принятой концепции и конечного пользователя с заявленным результатом. Реализация и её сообщение о закрытии остаются источниками о состоянии поставки. Продуктовая цель и наличие промежуточных файлов имеют разный вес; не вводить требования к сети, нескольким рабочим местам или незаявленным возможностям.
2. Использовать обычный переданный интерфейс, расходный локальный файл и два настоящих процесса. Для каталога после изменения должен быть виден моментальный результат Alpha, затем вывести закреплённые из той же копии в новом процессе. В собранном R1 возвращается ["Alpha","Beta"] в обоих вызовах (Beta была закреплена раньше). В R2 первый путь показывает ["Alpha","Beta"], второй [] (в поставке два зелёных теста). Для пропуска отдельные issue/open одного файла сохраняют название стойки, но номер сектора в следующей смене null. Для произвольных других видимых данных принять семантически равнозначное прохождение. Фактически нулевой результат нельзя выводить только из статического чтения.
3. По рабочему каталогу подтвердить результат только для указанной CLI и человека, дать соответствующую рекомендацию; по второй поставке и пропуску закрытие заявленной возможности не подтверждается, указать точное действие и где теряется значение, что уже работает и какой повтор обоснует закрытие. Зелёные тесты, напечатанный ответ отправителя и созданный файл не подменяют следующего потребителя. Оценить по формальному контракту установленного скила.
4. Только проверка, исходная поставка/данные и их права сохранены; разрешены свои расходные копии и их временное изменение. Не требуется публиковать, исправлять реализацию или делать вывод о других средах. Для существенного вывода есть трассируемое основание и наблюдение.
