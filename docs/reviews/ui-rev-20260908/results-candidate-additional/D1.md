Визуальная идея. Product/app, system-constrained, основной engine data-led: спокойная светлая рабочая поверхность, ровные строки и ясные подписи; акцент выделяет действия, плотность остаётся удобной для чтения. Без изображений, новых шрифтов, декоративных карточек и анимации. Использовать system-ui, текст #172c35, фон #f6f5ef, --accent #125d60, --line #bec9c7 и --space 1rem. Сохранить существующую красную ошибку и оранжевый focus-visible. Новые пакеты, компоненты библиотеки или дизайн-инструменты не нужны.

Композиция списка. Сохранить header REQUEST DESK, max-width 62rem, desktop padding 2rem. Первым блоком h1 Requests (2rem, weight 500), затем Search с видимым label, далее существующая строка New request + Create, затем table Name/Actions и ниже Page/total с Previous/Next. Поиск выровнять с левой границей Name; Name получает свободную ширину, Actions занимает необходимое место. Сохранить .8rem padding ячеек и линейные разделители. Название остаётся ссылкой; Delete остаётся отдельной кнопкой. Не добавлять KPI или баннер перед рабочей поверхностью. Поля получают ширину контейнера с max-width 32rem на desktop, без нового компонента; кнопки сохраняют текущий визуальный стиль.

Композиция detail. Сохранить h1 Request {id}, ниже единственное поле Name и Save, затем результат сохранения и Back to requests. Ширина формы ограничена 32rem для чтения, остаётся выровненной с заголовком. Поле и действие используют существующие label/input/button. Длинный ID и значение не должны вытеснять действие за viewport; разрешить перенос заголовка, поле ограничить шириной контейнера. Не добавлять несуществующие сведения о заявке.

Responsive. При <=600px сохранить текущие main padding 1rem, вертикальную форму и inputs width 100%; снять desktop max-width. Таблица сохраняет две колонки и семантику; разрешить перенос в Name/Actions и не фиксировать ширину Actions. Previous/Next могут переноситься на новую строку без изменения порядка. Проверять 375px и 1280px, а также 200% zoom; при экстремально длинном непрерывном имени использовать overflow-wrap:anywhere в ячейке и action label. Не скрывать действия на mobile.

Interaction thesis. Без ornamental motion: hover и текущий focus-visible показывают интерактивность; порядок клавиатуры следует DOM. Поиск сохраняет q/page semantics; detail остаётся обычной Link-навигацией; retry выполняет ту же Save. Не добавлять debounce, autosave, новую маршрутизацию или изменение API. Semantic links/buttons, видимые labels и доступные состояния сохраняются. Reduced-motion не требует отдельной анимационной ветки, поскольку новых движений нет.

Проверка после реализации. Разработчик должен получить текущие desktop/mobile evidence для списка, поиска без совпадений, обеих страниц, detail loading/error и формы idle/pending/error/success, длинных имён и zoom. Главный сценарий: изменить имя → первый PATCH 503 → значение не потеряно → исправить или повторить → успех → список → тот же detail → reload, везде сохранённое имя; сервер при этом не перезапускать. Проверить Tab/Shift+Tab, Enter/Space по нативным контролам, видимый фокус, связи label/error, отсутствие горизонтального переполнения и релевантных console/network ошибок. Проверить сохранившиеся Create/Delete и пагинацию после изменений списка. Динамический cache и form.reset устраняет владелец реализации на основе принятого контракта, а не визуальная стилизация.
