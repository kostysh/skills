Результат: визуальная стратегия в пределах supplied brief; код и требования не изменены. Формат — strategy-only, потребитель — разработчик страницы списка и карточки заявки. Полная готовность к реализации ограничена отсутствием фактических контрактов компонентов, полей и состояний.

Источники: принятый brief определяет поиск и отдельную карточку заявки; действующая библиотека определяет таблицу, токены и drawer в пределах своих контрактов; макет с summary cards даёт визуальный ориентир, но не отменяет функции brief. Runtime, peer views, Storybook, значения токенов и API компонентов не предоставлены и не проверены. Новые примитивы не предлагаются.

| --- | --- | --- | --- |
| Поиск | Принятый brief | Компонент поиска и точная семантика не представлены | Обязательная область над таблицей; использовать текущий системный паттерн. Не подменять summary cards. |
| Список заявок | Задача и существующая таблица | Наличие таблицы подтверждено входом; API не исследован | Переиспользовать таблицу и её поддерживаемые состояния. |
| Карточка заявки | Принятый brief | Drawer есть в библиотеке, но само наличие не определяет маршрут | Обязательная детальная поверхность; контейнер определяется уполномоченным решением. |
| Summary cards | Только макет | Поведение и источники показателей не определены | Не считать основным списком или новой обязательной функцией. Если показатели уже приняты, оставить компактным вторичным контекстом; до подтверждения не задавать данные и формулы. |
| История | Во входе не установлена | Нет свидетельств | N/A для этой стратегии; не добавлять новую функцию. |

Предлагаемая визуальная теза: спокойная рабочая поверхность, где поиск и ровные строки позволяют быстро найти заявку, а системный акцент показывает доступное действие. Классификация — product/app, system-constrained; основной visual engine — data-led.

Порядок списка: системная навигация, заголовок «Заявки», поиск с постоянной видимой подписью, таблица. Основное пространство первого экрана занимает таблица. Использовать существующие семейства шрифтов, размеры, интервалы, границы, фоны, состояния focus/hover и семантические цвета без новых hex-значений или шрифтов. Не добавлять hero, декоративные градиенты, новую карточную сетку и анимацию появления. Заголовки и данные таблицы берутся из принятого контракта; новые колонки, сортировки, фильтры, экспорт и создание заявки этой стратегией не вводятся.

Адаптивность: на широком экране поиск находится перед таблицей в общей сетке выравнивания. На узком — занимает доступную ширину, заголовок и управляющие элементы переносятся без наложений. Использовать уже принятый мобильный режим таблицы; не скрывать данные или менять её на карточки без проверки текущего контракта. Длинный текст должен оставаться доступным через поддерживаемое компонентом раскрытие или перенос, а не обрезаться без способа чтения. Точный breakpoint и плотность — существующие системные значения.

Состояния для отображения и проверки, когда они предусмотрены текущим контрактом: загрузка в рабочей области с сохранением её геометрии; пустой список отдельно от отсутствия результатов поиска; ошибка в области соответствующей операции с сохранением контекста; длинные значения; существующие ограничения доступа. Использовать текущие state-компоненты и утверждённую копию. Не придумывать retry, permissions, backend-состояния или новое success-уведомление. Поля поиска, момент запуска, правила сопоставления и очистки, набор полей карточки и доступные действия во входе не заданы — их владелец продуктового контракта, а не визуальная стратегия.

Независимый вход с конфликтом спецификаций: до уточнения контейнер карточки имеет статус blocked. Равная дата и наличие drawer не дают приоритета одной спецификации. Основание supplied frontend-design/SKILL.md, Source-authority policy: “stop rather than silently resolve equal-authority conflicts”. Требуемая недостающая информация — выбор владельца между drawer и отдельной страницей. Поиск, таблица, токены, информационная иерархия и описанные адаптивные ограничения остаются подготовленными независимо от этого решения.

Продолжение после supplied conversation replay: сообщение «Выбрана отдельная страница карточки. Продолжай стратегию в этом варианте» принимается как предоставленное решение владельца; это не самостоятельно полученное уточнение в текущем запуске. Конфликт контейнера снят. Переход к карточке ведёт на отдельную страницу через системный доступный элемент навигации заявки. Drawer не используется для этого сценария и не удаляется из библиотеки. Карточка сохраняет shell приложения: системный путь возврата к списку, заголовок из принятого идентификатора, затем утверждённые группы данных; действия только из существующего контракта, с его порядком и доступностью. На мобильном группы располагаются одной колонкой, на широком экране — по системной сетке; данные не теряются. Возврат и сохранность контекста поиска требуют следования текущему маршрутизационному контракту; новый контракт сохранения состояния здесь не объявляется. Декоративная анимация перехода не нужна.

Проверка стратегии: поиск и отдельная карточка явно сохранены; роли brief, библиотеки и макета разделены; page-вариант продолжен после supplied решения; неподтверждённые поля, действия и семантика не изобретены. Визуальное направление и размещение готовы; полный strategy-ready для handoff не заявлен до сопоставления с реальными контрактами поиска, таблицы, detail и состояний. Это ограничение конкретного входа, а не требование менять продукт.

После реализации нужны текущие rendered checks на desktop и mobile: поиск → результат → отдельная карточка → возврат, предусмотренные пустые/error/loading/access состояния, длинные данные, клавиатурная навигация и focus, контраст, размеры целей, отсутствие потерь данных при адаптации. При наличии системной анимации — reduced motion; по необходимости — console/network. В этом задании runtime, макет и код не создавались и не проверялись; стратегия не доказывает рабочий пользовательский сценарий.
