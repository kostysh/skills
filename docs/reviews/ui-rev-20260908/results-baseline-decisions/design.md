# Стратегия списка заявок

Deliverable: strategy-only, для разработчика. Основа — supplied описание brief и системы; сами спецификации, runtime, токены и API компонентов не предоставлены. Поэтому ниже готова композиционная часть стратегии; полная implementation-ready стратегия ограничена недостающими контрактами, runtime не проверен. Код и требования не менялись.

## Основной запрос

Принятый brief задаёт поиск и отдельную карточку заявки. Существующая библиотека задаёт таблицу, токены и drawer. Макет с одними summary cards — визуальная подсказка, которая не отменяет поиск и detail journey. Наличие drawer само по себе не доказывает, что карточку требуется открывать именно в нём. Слово «карточка» здесь обозначает представление заявки, а не обязательный декоративный card-контейнер.

| Возможность | Основание | Повторное использование и границы |
| --- | --- | --- |
| Поиск | Принятый brief | Отдельная видимая область перед таблицей. Компонент поля, поисковые поля, момент запуска и обработка ошибок должны следовать существующему контракту; он не supplied. |
| Список | Существующая таблица | Переиспользовать таблицу и её принятые варианты; столбцы, сортировки, пагинацию и массовые действия не изобретать. |
| Карточка заявки | Принятый brief | Сохранить доступ к отдельному представлению; механизм открытия требует авторитетного решения, не вывода из доступности drawer. |
| Summary cards | Только макет | Не делать их заменой рабочей поверхности; смысл и источник метрик не заданы, поэтому не добавлять выдуманные показатели. |
| История заявки | Основания нет | В эту стратегию не добавляется; отсутствие требования не означает отсутствия функции в продукте. |

Peer views и runtime не supplied: их возможности не объявляю отсутствующими или проверенными.

Визуальная гипотеза: спокойная рабочая поверхность с сильным выравниванием, где поиск и сканирование заявок занимают первый экран. Классификация: product/app, system-constrained, основной engine data-led.

Порядок экрана: существующая навигация → компактный заголовок «Заявки» → поиск → таблица. Таблица занимает доступную ширину контента. Заголовок ориентирует, поиск сужает выдачу, таблица позволяет находить нужную заявку. Не добавлять hero, декоративные иллюстрации, новые шрифты, градиенты или параллельный набор токенов. Иерархию создавать существующими типографическими уровнями, отступами и разделителями. Применять семантические цвета системы, не переназначая значения статусов.

На мобильном поиск располагается отдельной строкой над списком. Использовать штатный адаптивный режим таблицы; не скрывать значимые поля и не заменять таблицу набором карточек без проверки существующего паттерна. Длинные значения должны оставаться доступны способом, который поддерживает система. Конкретные breakpoints, плотность и поведение переполнения берутся из текущих компонентов, не назначаются новыми числами.

Состояния следует выразить существующими компонентами: загрузку — принятым индикатором в области данных; отсутствие заявок и отсутствие результатов поиска — различимыми сообщениями по существующим контрактам; ошибку — штатной ошибкой с только разрешёнными действиями. Разрешения, видимость недоступных записей и success-состояния не заданы: не придумывать их. Для каждой применимой ветки до реализации нужны контракт данных и пример системного компонента. Тексты выше — предложения визуальной стратегии, окончательная терминология следует продукту.

Декоративная анимация не требуется. Использовать текущие focus/hover и штатные переходы; не добавлять motion dependency. Необязательное движение должно учитывать reduced motion.

## Независимый вход с конфликтующими спецификациями

До уточнения блокируется только способ открытия карточки: drawer и отдельная страница имеют одинаковую заявленную силу и дату. Выбрать один по удобству реализации нельзя. Основание: supplied frontend-design/SKILL.md, Source-authority policy: “stop rather than silently resolve equal-authority conflicts”. Решение принадлежит владельцу требований. Компонование списка, поиск, токены, плотность и reuse таблицы остаются определимыми, как описано выше. Drawer сохраняется в библиотеке; наличие компонента не назначает приоритет спецификации.

## Продолжение по supplied conversation replay

В исходном файле предоставлено второе сообщение: «Выбрана отдельная страница карточки. Продолжай стратегию в этом варианте». Это supplied conversation replay, а не полученный здесь новый ответ. Оно разрешает предыдущий конфликт для этого варианта.

Карточка открывается отдельной страницей из штатного доступного элемента открытия заявки в таблице. Использовать существующий page shell, заголовочную иерархию и компоненты данных. Сначала идентификация заявки, затем существующие группы данных в их принятом порядке. Точный URL, поля, действия и доступ не изобретать; следовать действующим контрактам. Drawer не использовать как конкурирующую карточку и не удалять из библиотеки. Возврат в список и восстановление его состояния следуют существующему navigation-контракту; новый контракт сохранения поиска этим дизайном не вводится. Для доступности реализации потребуются нормальное клавиатурное открытие, осмысленное имя ссылки и управление фокусом по паттерну приложения.

Конфликт способа открытия снят; визуальное направление продолжено. До полного strategy-ready остаются реальные контракты поиска, данных/состояний, маршрута карточки и текущая поверхность компонентов. Это конкретный недостающий материал, а не повод останавливать уже описанную композицию.

После реализации нужны текущие rendered проверки desktop/mobile: поиск и открытие выбранной заявки на отдельной странице, возврат по принятому контракту, применимые loading/empty/error/permission состояния, длинный контент, клавиатура/focus, контраст и touch targets. Эти проверки не выполнялись; стратегия не доказывает работающий интерфейс.
