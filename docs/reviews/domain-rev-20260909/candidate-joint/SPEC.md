# PREVIEW-1: временный сервис предварительного расчёта

## Область и передача исполнителю

Потребитель — владелец реализации Node HTTP/service + PostgreSQL 18.4. Цель: синтетический клиент получает точный предварительный расчёт, сохранённые значения доступны отдельному чтению; вызов очистки по сроку удаляет исходную и экспортную копии. Суммы обозначают commercial fee, без налога и бухгалтерской проводки.

**Handoff: ready for implementation owner для требований S1–S13 и проверок ниже.** Q1 о возвращаемом `removed count` разрешён узким уточнением автора учебного R-I1; блокирующих решений для указанного контура не осталось. Этот документ сам по себе не разрешает запуск или изменение prototype: текущий шаг — спецификация и handoff.

Авторитетные входы: [input.json](input.json), принятые R-F1, R-D1, R-D2, R-I1; [R-I1-count-clarification](count-clarification.json) уточняет только счётчик временного J01 fixture. [Финансовый handoff](finance-handoff.md) и [GDPR handoff](gdpr-handoff.md) объясняют нарушения и необходимые свидетельства; они не заменяют владельцев исходных решений.

Распределение ответственности:

| Владелец | Уже принятое ограничение / дальнейшая обязанность |
| --- | --- |
| Владелец продукта / R-I1 | Временный preview и purge, существующие поля и единицы, наблюдаемый readback; Q1 разрешён R-I1-count-clarification в действующем учебном контракте. Новое PRD не требуется. |
| Владелец архитектуры | Сохранить Node service и PostgreSQL 18.4, две заданные проекции. Новые границы, хранилища или интеграции не нужны; вопрос возвращается сюда только если реализация действительно требует их изменения. |
| Владелец PREVIEW-1 | R-F1: представление, диапазоны, floor, паритет расчётов; повторно оценить финансовые свидетельства. |
| Учебный контролёр / GDPR-владелец | R-D1/R-D2: принятые purpose/basis, проекции, срок, логи; повторно оценить минимизацию и удаление. |
| Исполнитель Node/PostgreSQL | Реализовать точные границы, исправить исходные пути и вернуть фактические результаты обоим предметным владельцам. |

Риск ограничен синтетическим fixture, без production и реальных данных; критичны точность и необратимое удаление, поэтому нужны граничные случаи и реальный readback. Нужен один временный сервисный контур; frontend, общий пакет, постоянный runtime/harness, новые юридические основания, налоговая политика и ledger вне области. Отсутствие третьих сторон, cookies, analytics, operational accounts и backups — входные факты R-D1, а не результат проверки.

## Контракт входа и выхода

`preview(request, now)` и `purge(now)` сохраняют имена и значения из R-I1. `now` — переданный момент сравнения; `expiresAt` и `now` используют одну существующую целочисленную шкалу без преобразования в секунды, миллисекунды или дату. Для временных проверок задаются точные безопасные целые. Нельзя выбирать новую эпоху или единицу вместо принятой.

| Поле request | Допустимое значение | Источник |
| --- | --- | --- |
| `id` | Положительное безопасное целое JSON number | R-I1 |
| `subjectKey` | Строка вида `synthetic-N`, где N — последовательность десятичных цифр; значение сохраняется дословно | R-I1 |
| `unitMinor` | JSON string; `0` либо `-?[1-9][0-9]*` с ASCII `-`; диапазон −9223372036854775808…9223372036854775807 | R-F1; финансовый handoff, canonical decimal |
| `currency` | Строка `EUR` | R-F1 |
| `scale` | JSON number `2` | R-F1 |
| `quantity` | JSON number, целое 1…10 включительно | R-F1 |
| `expiresAt` | Безопасное целое JSON number, строго больше `now` | R-I1 |

Обязательные поля нельзя заменять aliases, `null`, отсутствующими значениями или приведением строки к number. Внешние `netMinor`/`feeMinor` не являются входами расчёта: даже при их наличии единственный источник результата — серверный пересчёт. Дополнительные поля не попадают в persist, export, результат или логи; это требование проекции, без введения новой политики ошибки на любое неизвестное поле.

`preview` возвращает сохранённую и отдельно перечитанную строку `{id,subjectKey,netMinor,feeMinor,expiresAt}`. JSON `netMinor`/`feeMinor` — canonical decimal strings; `id`, `subjectKey`, `expiresAt` равны принятому запросу. EUR/scale 2 — неизменные единицы PREVIEW-1; они не потеряны из-за отсутствия отдельных колонок в принятой проекции.

Существующий путь `exportPreview(row)` сохраняет и позволяет отдельно перечитать `{id,subjectKey,feeMinor}` с точными значениями исходной строки. Это экспортная копия внутри заданного fixture, без передачи третьей стороне. Наличие экспорта проверяется явно; один успешный `preview` без исполнения экспортного пути не доказывает весь lifecycle.

Успешный `purge(now)` возвращает `removed count` и результат отдельного чтения обоих наборов записей. По R-I1-count-clarification count равен числу исходных preview-строк, удалённых этим успешным вызовом; экспортные строки его не увеличивают. До срока и при уже отсутствующих строках count = 0. При сбое вызов выбрасывает ошибку и не возвращает успешный count; после rollback успешный повтор считает действительно удалённые им исходные строки. Отсутствие записей доказывается чтением независимо от count. Формат HTTP envelope/status code, названия SQL-объектов и локальных файлов не предписаны: исполнитель использует существующий service contract, не создавая новый публичный API.

## Проверяемые требования

`explicit` означает прямое правило входа; `derived` — необходимое следствие для соблюдения названного источника. Проверки V1–V5 ниже одновременно являются отрицательными оракулами: нарушение любого указанного результата опровергает соответствующее требование.

| ID | Источник / вывод | Требование | Проверка |
| --- | --- | --- | --- |
| S1 | R-F1, R-I1 / explicit | Сервис MUST отклонять входы вне указанного контракта до записи. | V1, V2 |
| S2 | R-F1 / explicit | Node MUST выполнять арифметику minor units без `Number`; валидированное значение представляется точным bigint. | V1, просмотр затронутого пути |
| S3 | R-F1 / explicit | Расчёт MUST давать `net = unitMinor × quantity`, `fee = floor(net / 2)`. | V1 |
| S4 | R-F1 / explicit | Выход `net` или `fee` за signed int64 MUST приводить к отклонению до записи, даже если другая сумма допустима. | V2 |
| S5 | R-F1, R-I1 / derived: иначе паритет и точность теряются на SQL/JSON переходе | PostgreSQL-расчёт и серверный результат MUST сохранять одинаковые точные значения через запись и перечитывание. | V1 |
| S6 | R-F1, R-I1 / derived: иначе клиент меняет принятую формулу | Сервис MUST получать суммы только серверным пересчётом валидированных `unitMinor`/`quantity`. | V2 |
| S7 | R-D2, R-I1 / explicit | Persist MUST получать только `{id,subjectKey,netMinor,feeMinor,expiresAt}` с точными принятыми значениями. | V1, V3 |
| S8 | R-D2, R-F1 / explicit | Экспорт MUST содержать только `{id,subjectKey,feeMinor}`, совпадающие с исходной строкой. | V1, V3 |
| S9 | R-I1 / explicit | Успешный результат сохранения MUST подтверждаться отдельным чтением из PostgreSQL. | V1, V3 |
| S10 | R-D2 / explicit | Диагностика затронутых успешных и ошибочных путей MUST содержать только `event`, `status`, `count`. | V3, V5 |
| S11 | R-D2 / explicit | При `purge(now)` обе копии записей с `expiresAt <= now` MUST стать недоступны обычному чтению. | V4 |
| S12 | R-D2 / derived: ложный успех или потеря возможности повтора оставляют копию после срока | Сервис MUST сообщать незавершённую очистку при оставшейся копии и сохранять возможность завершить удаление повторным вызовом. | V5 |
| S13 | R-I1-count-clarification / explicit | Успешный purge MUST возвращать число исходных preview-строк, фактически удалённых этим вызовом, без прибавления экспортных строк. | V4, V5 |

Для S2–S5: в Node сначала выполняется точное расширенное умножение, затем проверка net; bigint-деление отрицательного нечётного net корректируется до floor (для −3 результат −2). В PostgreSQL операнд расширяется до exact `numeric` **до** умножения; после проверки диапазонов применяется точный floor и допустимое приведение. Вычисление bigint-умножения SQL до расширения не соответствует требованию отклонения под контролем контракта. SQL/драйвер/JSON не должны промежуточно переводить суммы в двоичный float/number.

Для S7–S10: проекция строится явно вместо spread запроса. `subjectKey` остаётся связанным с пользователем примера, а не объявляется анонимным. `event` обозначает операцию, `status` — её исход, `count` — число в согласованной семантике; значения этих полей не используются для вложенного запроса, идентификаторов, сумм или текста ошибки БД. Логи служат ограниченной диагностике и не заменяют readback.

Для S11–S12: записи с `expiresAt > now` сохраняются. Сервис удаляет экспорт по связи с истёкшей исходной строкой, не теряя эту связь при ошибке. Простейший доступный вариант — существующая транзакция PostgreSQL с удалением обеих копий и rollback при сбое; конкретный SQL остаётся у исполнителя. Нельзя завершить удаление исходной строки, оставить экспорт и затем сделать повтор неспособным найти остаток. Новый фоновый процесс или retry-сервис не требуется. Повтор инициирует вызывающий временный сервис проверяющий исполнитель.

## Минимальные свидетельства при реализации

Общий контур: синтетический request → валидация/точная Node-арифметика → PostgreSQL-расчёт и persist → отдельный readback → JSON строки сумм → export write/readback → purge → независимый readback обоих наборов. Владелец каждого перехода — исполнитель Node/PostgreSQL; потребители результатов — финансовый и GDPR-владельцы. Потеря цифры, лишнее поле либо сохранившаяся истёкшая копия на любом переходе опровергает сквозной результат.

| Проверка | Действие и ожидаемое наблюдение | Требования / получатель |
| --- | --- | --- |
| V1 — точность | Выполнить все успешные fixtures ниже через реальный HTTP/service → PostgreSQL 18.4 write → reread; сравнить Node, SQL, JSON и export fee с фиксированными ожиданиями. | S1–S5, S7–S9; finance + GDPR для проекций |
| V2 — отклонение | Все отрицательные fixtures ниже отклоняются до записи; отдельное чтение подтверждает отсутствие новых/изменённых строк в обоих наборах. Клиентские подставные суммы не влияют на принятый расчёт. | S1, S4, S6; finance + GDPR |
| V3 — минимизация | Добавить в синтетический запрос маркер лишнего поля; проверить фактические поля row/export и выход logger на успехе, отказе валидации и ошибке БД. Ни маркер, ни request, ни `subjectKey`/id/суммы не оказываются в логах. | S7–S10; GDPR, finance для export |
| V4 — срок | Для одной целевой preview-строки с экспортом вызвать purge до срока: count = 0, обе копии доступны. Точно при `now == expiresAt`: count = 1, обе копии отсутствуют. Последующий вызов после срока: count = 0. В отдельном случае первое удаление уже после срока даёт count = 1. Неистёкшая контрольная запись и её экспорт остаются. | S11, S13; GDPR, R-I1 для count |
| V5 — сбой/повтор | Для одной истёкшей preview-строки с экспортом временно вызвать сбой удаления export: вызов выбрасывает ошибку без успешного count; readback фиксирует состояние обеих копий после rollback. Устранить сбой, повторить purge: count = 1; перечитать: обе истёкшие копии отсутствуют, контроль сохранён. Ещё один повтор даёт count = 0. Проверить allowlist логов. | S10–S13; GDPR, R-I1 для count |

Успешные fixtures (остальные поля валидны, каждому случаю выделен отдельный id):

| ID | unitMinor / quantity | netMinor | feeMinor |
| --- | --- | --- | --- |
| N0 | `"0"` / 1 | `"0"` | `"0"` |
| P1 | `"3"` / 1 | `"3"` | `"1"` |
| N1 | `"-3"` / 1 | `"-3"` | `"-2"` |
| N2 | `"-4"` / 1 | `"-4"` | `"-2"` |
| Q10 | `"1"` / 10 | `"10"` | `"5"` |
| EXACT | `"9007199254740993"` / 1 | `"9007199254740993"` | `"4503599627370496"` |
| MAX | `"9223372036854775807"` / 1 | `"9223372036854775807"` | `"4611686018427387903"` |
| MIN | `"-9223372036854775808"` / 1 | `"-9223372036854775808"` | `"-4611686018427387904"` |

Отрицательные fixtures V2: MAX/MIN с quantity 2; unitMinor за обеими границами int64; `""`, `" 1"`, `"+1"`, `"01"`, `"-0"`, `"1.0"`, JSON number `1`; неверные/отсутствующие currency и scale; quantity `0`, `11`, `1.5`, `"1"`; отсутствующие/null обязательные поля; id `0`, дробный или небезопасный; неверный subjectKey; expiresAt дробный, небезопасный, равный now или меньше now. Сравнение состояния до/после ошибки включает уже сохранённую контрольную запись.

Возврат обоим производителям: точный snapshot реализации, команды и версии среды, общие fixture IDs, ожидаемые и фактические значения/ошибки, независимые SQL readback-результаты row/export до и после операций, наблюдения диагностического выхода и результаты сбоя/повтора. Каждая проверка получает `passed`, `failed` либо `not-run` с причиной; материал для повторной предметной оценки передаётся вместе с исходными handoffs. Финансовому владельцу выделяются паритет, int64, floor и экспортная точность; GDPR-владельцу — фактические проекции, логи, срок, обе копии и восстановление. Синтетические readback fixtures в отчёте — свидетельства, их нельзя превращать в runtime-логи с запрещёнными полями.

Нужна минимальная временная проверка существующего контура. Тест mapper, mock БД, схема таблицы, успешный вызов либо один счётчик не закрывают сквозную проверку. Разные случаи не требуют нового пакета или постоянного harness.

## Решение и пределы доказательств

**Q1 — resolved, R-I1-count-clarification:** автор учебного сценария определил count как число исходных preview-строк, удалённых успешным вызовом, без экспортных строк. До срока или после уже выполненного удаления — 0; сбой выбрасывает ошибку без успешного count; после rollback повтор считает фактически удалённые им строки. Решение применяется только к временному J01 fixture и не устанавливает реальную продуктовую, бизнес- или правовую политику. Для S11/S12 остаётся независимый oracle: отсутствие обеих истёкших копий при сохранении контрольных.

Изменение принято ровно относительно показанного prototype: `Number`/`Math.round` → точная PREVIEW-1 арифметика; spread/request logging → заданные проекции; односторонний purge → наблюдаемое удаление обеих копий. Семантика повторного preview с тем же id не расширяется до upsert/idempotency-протокола: в этой временной проверке используются отдельные id, а конкурентные гарантии и replay контракты не заявляются.

Спецификация подготовлена по трём первоначальным входам и узкому уточнению count; код не менялся, runtime и PostgreSQL не запускались. Все V1–V5 сейчас `not-run`. Документ не подтверждает выполненную очистку, финансовую реализацию, юридическую законность реальной обработки или готовность production/release.
