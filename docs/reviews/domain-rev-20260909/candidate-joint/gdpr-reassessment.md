Окончательная ограниченная оценка текущего snapshot: три исходных GDPR finding устранены в проверенном прямом Node service/PostgreSQL-контуре; `COMPLETE_FOR_STATED_SCOPE`. Вывод подтверждён повторной read-only сверкой финальных исходников и фактического evidence после исправления SQL NULL guard. Runtime в этой оценке не запускался; юридическое одобрение и release gate не выдаются.

Источники требований: R-D1/R-D2/R-I1 из исходного входа, GDPR handoff, SPEC S7–S13/V3–V5 и `R-I1-count-clarification`. Последний источник — явное синтетическое решение владельца сценария: count считает исходные строки, удалённые успешным вызовом; экспорт его не увеличивает, сбой не возвращает успешный count. Это закрывает вопрос исходного handoff без изменения обязательства удалить обе копии. Purpose/basis R-D1 остаются принятыми входами учебного примера; техническое наблюдение не заменяет решения контролёра и не доказывает законность реальной обработки.

Карта проверенного потока: синтетический запрос → `preview(request, now)` → таблица preview → отдельный SELECT/readback; `exportPreview(row)` → таблица export → отдельный readback; `purge(now)` → транзакционное удаление обеих копий → чтение обоих наборов. Диагностическая ветвь пишет минимальные события в `logger.jsonl`. Фактический запуск этого локального потока отражён в материалах для Node v24.15.0 и PostgreSQL 18.4; текущая активность среды после запуска повторно не проверялась. Отсутствие внешних получателей, cookies, analytics, operational accounts и backups остаётся ограничивающим фактом R-D1, а не результатом исследования реальной инфраструктуры.

В финальном `evidence.json` независимо пересчитано 160 записей expected/actual без расхождений; это проверка согласованности переданного свидетельства, а не 160 новых runtime-тестов или отдельный финансовый verdict. Проверено сохранение всех прежних evidence-записей в финальном наборе; новые 24 assertions покрывают отказ и readback для каждого из 12 SQL-входов. Финальные V3–V5 actual просмотрены отдельно: проекции, удаление, rollback/recovery соответствуют таблице выше, все 76 logger-записей также перепроверены. `run.mjs` показывает действительные SQL-вызовы и отдельные SELECT, сравнения полных наборов, маркер минимизации и реальный failure trigger, поэтому evidence не сводится к mock или названию теста. `run.stdout` подтверждает 160 assertions / 44 negative service cases и финальное состояние; `run.stderr` пуст. Успешный exit code 0 сообщён финальным runtime-report, самостоятельно процесс в этой оценке не запускался.

Ошибки PostgreSQL с деталями сохраняет проверяющий исполнитель в синтетическом `evidence.json`; они отсутствуют в диагностическом `logger.jsonl`. SPEC явно разделяет эти поверхности. Это не основание разрешать такой сбор production-логов. Отдельный отказ `exportPreview` в наблюдениях не продемонстрирован: его ограниченное логирование видно по коду, но не подтверждено отдельным runtime-сценарием. Данный предел не возвращает закрытое нарушение полного request на показанных путях.

Остаточные границы доказательств: прямой service → PostgreSQL, без HTTP wire/listener, конкурентных операций, падения процесса, production, реальных пользователей, backups и vendors. Планировщик или автономное истечение без вызова purge не заявлены контрактом и не доказаны. Финансовая точность PREVIEW-1 остаётся предметом финансового владельца. Текущая правовая законность, вся организация и отсутствие иной обработки не подтверждаются этим запуском; внешняя правовая проверка для данной сверки с синтетическими решениями не требовалась.
