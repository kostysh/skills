# PREVIEW-1 — временный учебный сервис

## Назначение, источники и передача

**Статус: ready для владельца реализации Node/service + PostgreSQL в синтетическом fixture.** Это спецификация исправления существующего prototype, а не новая продуктовая политика и не свидетельство выполненных контролей. Разрешённый результат этого шага — только данный документ; реализация и runtime не выполнялись.

Потребитель сервиса передаёт запрос в `preview(request, now)`, получает сохранённую строку и её повторное чтение; существующий `exportPreview(row)` сохраняет экспортную копию. Оператор fixture вызывает `purge(now)` и проверяет количество удалённых preview и отсутствие обеих копий. Цель — сохранить точность предварительного расчёта и выполнить согласованные ограничения данных через запись, чтение и удаление.

Авторитетные решения: [input.json](input.json), `authority.R-F1` (PREVIEW-1), `R-D1`, `R-D2`, `R-I1`. Семантика removed count подтверждена автором сценария в [count-clarification.json](count-clarification.json), `R-I1-count-clarification`, исключительно для временного синтетического J01 fixture. Производители специализированных ограничений: [gdpr-handoff.md](gdpr-handoff.md), три finding и входная граница; [finance-handoff.md](finance-handoff.md), пункты 1–5 и fixtures. Handoff уточняют нарушение принятых решений; они не заменяют полномочия владельцев решений.

| Владелец | Принятое решение и применение |
| --- | --- |
| Продуктовый владелец / `prd-engineer` | R-F1/R-I1 уже задают учебный preview, входы, результаты и границы. Новая продуктовая проработка не нужна. Изменение формулы, состава данных или цели потребует решения этого владельца. |
| Учебный контролёр / GDPR-производитель | R-D1 задаёт purpose/basis и исключения fixture; R-D2 — минимизацию и удаление. SPEC переносит ограничения в service/storage и возвращает фактические наблюдения производителю. Правовое основание и consent заново не выбираются. |
| Финансовый производитель | R-F1 задаёт денежное представление и floor; владелец реализации сохраняет их в Node, SQL, JSON и экспорте. Коммерческая fee не является налогом или проводкой. |
| Владелец архитектуры / `architecture-engineer` | R-I1 уже задаёт Node HTTP/service + PostgreSQL 18.4 и существующие операции. Исправления остаются внутри этих границ. Новый компонент, пакет, frontend, очередь, интеграция или постоянный harness не требуются. |
| Владелец реализации Node/service и PostgreSQL | Реализует нижеследующий контракт, выбирает локальный механизм согласованного удаления, предъявляет проверки и возвращает evidence обоим производителям. |

Риск ограничен синтетическим временным сервисом, без реальных пользователей, денег и production: средний для этого задания. Для точности и удаления нужны усиленные отрицательные проверки, но полноценная матрица production-auth/ledger/поставщиков здесь не применима. R-D1 прямо исключает третьих сторон, cookies, analytics, operational accounts и backups. Архитектурные границы наследуются; новый PRD, ASR-регистр или ADR не создаётся.

## Контракт входа и результата

`request` использует имена R-I1; `now` — явно переданный момент сравнения. `expiresAt` и `now` сравниваются в одной существующей единице времени, без смены epoch/единиц или скрытого чтения часов. Для временной проверки передавать безопасные целые значения `now`; не добавлять в API новую временную модель.

| Поле | Допустимое значение | Источник |
| --- | --- | --- |
| `id` | Число: положительное безопасное целое | R-I1 |
| `subjectKey` | Строка формата `synthetic-N`; в fixture N — последовательность десятичных цифр. Не придумывать реальный идентификатор/пользователя | R-I1, GDPR: входная граница |
| `unitMinor` | Строка `0` либо `-?[1-9][0-9]*`, значение от `-9223372036854775808` до `9223372036854775807` включительно | R-F1, finance п. 1 |
| `currency`, `scale` | Строго строка `EUR` и число `2` | R-F1 |
| `quantity` | Число: целое 1..10 включительно | R-F1 |
| `expiresAt` | Число: безопасное целое, строго больше переданного `now`; значение сохраняется без изменения | R-I1, GDPR: входная граница |

Отсутствие обязательного поля, `null`, неверный тип или нарушение диапазона/формата — отказ до записи. Приведение строковых quantity/scale/id/срока к числам не заменяет валидацию. Дополнительные поля не дают полномочий менять результат: клиентские `netMinor`/`feeMinor` не являются источником итогов; любые дополнительные поля запрещено переносить в row, экспорт или logger. Политику HTTP для неизвестных полей этот документ не объявляет существующей.

Разрешённые сохраняемые и перечитываемые значения:

- Основная row — ровно `{id, subjectKey, netMinor, feeMinor, expiresAt}`.
- Экспорт — ровно `{id, subjectKey, feeMinor}`, связь с основной row по сохранённому `id`.
- `netMinor` и `feeMinor` на service/JSON/readback-границах — канонические десятичные строки minor units, фиксированно EUR/scale 2. Физический SQL `bigint` или точный numeric не разрешает преобразование через JavaScript Number.
- `preview(request, now)` возвращает сохранённую row и результат фактического перечитывания; имена полей внешней обёртки/HTTP route исходником не определены. Реализация фиксирует фактическое соответствие существующему транспорту в evidence, сохраняя данные и типы выше.
- `exportPreview(row)` использует серверную row; прочитанная экспортная `feeMinor` совпадает с исходной строкой и единицами.
- `purge(now)` возвращает removed count и результат перечитывания затронутых ID. По `R-I1-count-clarification` count MUST считать основные preview rows, удалённые успешным вызовом purge; экспортные rows к нему не прибавляются. До срока или при уже отсутствующих записях count=0. При сбое вызов MUST выбрасывать ошибку и не иметь успешного count; после rollback повторный успешный вызов считает rows, фактически удалённые этим повторным вызовом. Это прямое подтверждение автора синтетического сценария, не новая бизнес- или правовая политика.

## Инварианты и изменение prototype

В таблице `explicit` означает прямое перенесение принятого решения; `derived` — необходимое техническое следствие для его сохранения. Последний столбец задаёт, какое нарушение допускает удаление требования.

| ID / источник | Обязательное поведение в заданной границе | Основание и фальсификатор |
| --- | --- | --- |
| S1 — R-F1/R-I1; finance 1, GDPR вход | Service MUST валидировать весь обязательный вход до любых записей. Проверяемая SQL-граница MUST применять те же денежные синтаксис, типы, диапазоны и смысл отказа; нельзя использовать мягкий cast как валидатор | explicit; неверная валюта, синтаксис или срок оставляет запись |
| S2 — R-F1; finance 2 | Node MUST вычислять `net=unitMinor*quantity` точно в bigint и отдельно отклонять net вне signed int64 до вычисления принимаемого результата | explicit; `922337203685477581 × 10` принят, потому что fee помещается |
| S3 — R-F1; finance 2–3 | Node и PostgreSQL MUST вычислять `fee=floor(net/2)` математически и проверять signed int64 результата. Для отрицательного нечётного net деление с усечением к нулю корректируется вниз | explicit; net `-3` даёт `-1` вместо `-2` |
| S4 — R-F1; finance 3–4 | SQL MUST вычислять потенциально переполняющее произведение в расширенном точном numeric либо доказанно проверять диапазон до bigint multiplication. Node, SQL и driver/JSON MUST сохранять точное значение, без Number для minor units | derived из exact parity; большое значение меняется при чтении либо SQL переполняется до контрольной проверки |
| S5 — R-D2/R-I1; GDPR finding 2, finance 4–5 | Persistence MUST формировать только разрешённый состав явно; сервер вычисляет суммы, сохраняет `id`, `subjectKey`, `expiresAt` и возвращает фактическое чтение. Экспорт MUST сохранять тот же `id`, `subjectKey`, точную `feeMinor` | explicit; spread оставляет лишнее поле, клиент меняет fee или возвращается только echo вместо чтения |
| S6 — R-F1/R-D2; оба handoff | Ошибка входа/переполнения MUST NOT создавать основную или экспортную запись; отказ MUST быть наблюдаемым, без успешного результата preview | explicit; отрицательная проверка на новом ID находит любую копию |
| S7 — R-D2; GDPR finding 1 | На границе logger MUST быть только `event`, `status`, `count`. Значения event/status описывают операцию/исход и MUST NOT включать интерполированные поля запроса, суммы, subjectKey или сырые ошибки с payload | explicit для состава, derived для значений: разрешённый ключ не должен обходить запрет; маркер запроса появляется в успешном или ошибочном логе |
| S8 — R-D2; GDPR finding 3 | `purge(now)` MUST удалить основные rows с `expiresAt <= now` и связанные экспорты; rows с `expiresAt > now` и их экспорты сохраняются | explicit; на точной границе срока осталась хотя бы одна копия либо раньше срока исчезла row |
| S9 — R-D2; GDPR finding 3 | Purge MUST NOT возвращать успех до подтверждения удаления обеих копий. При отказе удаления экспорта MUST сохраняться возможность завершить удаление по исходным ID при повторном вызове; ложный успех запрещён | derived: потеря связи оставляет неудаляемую копию. Локальная транзакция PostgreSQL допустима; очередь/новый recovery-сервис не требуются |

Основная дельта: `Number` и `Math.round` заменяются точным контрактом; `logger.info(request)` — минимальным событием; spread в insert — явной проекцией; purge основной таблицы — согласованным удалением двух копий с проверяемым исходом. Имена операций, полей, единицы и принятые продуктовые решения сохраняются. Существующий export не превращается в новую внешнюю интеграцию.

## Проверка реализации и возврат evidence

Все проверки ниже — обязательства будущего исполнителя, статус сейчас **not-run**. Достаточна временная проверка через существующие Node HTTP/service и реальный PostgreSQL **18.4**; моки и статическое чтение могут дополнять, но не закрывать эти границы.

Для Node и SQL использовать одинаковые fixture ID и фиксированный oracle из finance-handoff:

| `0` | 1 | `0` | `0` |
| `3` | 1 | `3` | `1` |
| `-3` | 1 | `-3` | `-2` |
| `-4` | 1 | `-4` | `-2` |
| `9007199254740993` | 1 | `9007199254740993` | `4503599627370496` |

В таблице денежные литералы обозначают строки. Для остальных полей брать синтетические валидные значения и новый ID на случай; до/после читать по тому же ID.

| Evidence ID / требования | Действие и наблюдаемый результат | Кому вернуть |
| --- | --- | --- |
| E1 — S1–S4, S6 | Выполнить все финансовые fixtures через Node и SQL, записать команды, версию сервера и наблюдаемые значения/ошибки; сравнить каждый движок с oracle, затем друг с другом | Финансовый производитель |
| E2 — S1, S6 | Буквальные денежные отрицательные входы: unitMinor `9223372036854775808`, `-9223372036854775809`, `+1`, `01`, `-0`, `1.0`, `1e2`, ` 1`, пустая строка, число 1, null/отсутствие; currency `USD`, scale `3`/`"2"`; quantity 0/11/1.5/`"1"`. На обеих денежных границах отказ, затем отсутствие записей | Финансовый производитель; GDPR — отсутствие копий и минимальные логи |
| E3 — S1, S6–S7 | Невалидные id: 0, дробь, строка, небезопасное целое; subjectKey: неправильный формат/тип; expiresAt: равен now, меньше now, дробь, строка, небезопасное целое; обязательное поле отсутствует/null. | E4 — S4–S7 | Полный путь: синтетический запрос → service-валидация/расчёт → PostgreSQL insert → фактическое reread → возвращаемый результат → существующий exportPreview → reread экспорта. Проверить состав и типы обеих копий, сохранность id/subjectKey/expiresAt, большое значение >2^53 и отрицательную нечётную сумму; постороннее поле и подставленная клиентская fee не меняют сохраняемые данные. Снять фактический logger для успеха и отказа | Оба производителя |
| E5 — S7–S9, R-I1-count-clarification | Создать preview и экспорт через существующие операции. При now<expiresAt purge сохраняет обе копии и возвращает count=0. На now=expiresAt удалить обе, count равен числу основных rows, удалённых этим успешным вызовом, без прибавления экспортных rows; выполнить reread обоих хранилищ. Добавить ещё не истёкшую запись: она сохраняется. Повторный purge не находит уже удалённые ID и возвращает count=0 | GDPR-производитель; финансовый — сохранность экспортного значения до удаления |

Исполнитель возвращает **обоим** производителям один компактный пакет: snapshot реализации; окружение/версии; соответствие S1–S9 и E1–E6; точные воспроизводимые вызовы/SQL; expected/actual по fixture ID; service-результат, reread основной и экспортной записей; фактические минимальные логи; ошибки и результаты восстановления; статусы passed/failed/not-run и оставшиеся ограничения. Синтетические fixture-данные допустимы в выделенном evidence, но это не разрешает payload в эксплуатационном logger. Общая зелёная сводка, driver mock или описание redaction не заменяют наблюдения.

## Незакрытые детали и пределы результата

Материальных противоречий продуктовых и доменных решений в переданных источниках нет. HTTP route, имя обёртки результата и error codes не предоставлены: владелец реализации документирует фактическое отображение в существующем сервисе. Обязательное различие здесь — невалидный вход, overflow и storage/purge failure; отказ не считается успехом и не сопровождается запрещёнными записями/логами. Новые публичные коды не объявляются существующим API.

Новая политика повторного preview с тем же ID, auth/session/tenant, фонового scheduler, production-развёртывания или миграции реальных данных не выводится из этого fixture. Семантика count закрыта `R-I1-count-clarification`. Если реализация выявит иной реальный конфликт внешнего контракта, вернуть точное различие владельцу R-I1; при невозможности удалить обе копии в существующей границе — владельцу архитектуры и GDPR с наблюдаемой причиной. Не заменять это общим запросом нового PRD/ADR. Ошибку parity вернуть финансовому производителю с fixture ID и обоими результатами; изменение purpose/basis или формулы требует их исходного владельца.

Данный SPEC не является runtime PASS, юридическим заключением, налоговой политикой, разрешением production-операций или оценкой применённых skills. Приёмка реализации возможна только по будущим наблюдениям E1–E6 в заявленной границе.
