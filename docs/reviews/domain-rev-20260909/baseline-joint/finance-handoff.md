Финансовая часть prototype не соответствует PREVIEW-1: `Number(request.unitMinor)` теряет точность signed int64, а `Math.round(net/2)` не реализует floor. Например, net=3 должен дать fee=1, net=−3 — fee=−2; текущая формула даёт 2 и −1. Анализ выполнен только по joint/input.json; runtime-контроли не выполнялись.

Авторитет: R-F1/PREVIEW-1 задаёт EUR, scale 2, canonical signed decimal int64 для unitMinor, quantity integer 1..10; net=unitMinor×quantity, fee=floor(net/2), обе итоговые суммы signed int64. R-I1 задаёт Node service + PostgreSQL 18.4, preview → запись + повторное чтение. R-D2 задаёт состав строки и экспортной копии. Налоговая применимость и бухгалтерская политика к этой операции не относятся.

Передача владельцам реализации Node/service и PostgreSQL:

1. До арифметики проверить currency=EUR, scale=2, unitMinor как строку canonical signed decimal без дроби/пробелов/экспоненты/ведущего плюса/лишних ведущих нулей/−0; затем signed int64. Quantity должен быть числом integer 1..10. Проверку id, subjectKey, expiresAt и now реализовать по R-I1 в транспортном/сервисном слое.
2. Выполнить net в точном bigint, затем проверить диапазон net отдельно. Нельзя разрешить переполненный net только потому, что fee поместилась бы в int64. После этого вычислить floor(net/2), учитывая отрицательный нечётный остаток, и проверить fee. Деление bigint в Node само по себе округляет к нулю; для отрицательного остатка требуется уменьшение частного на 1.
3. На PostgreSQL стороне сохранить те же синтаксис входа, диапазоны, формулу и ошибки. Использовать widened exact numeric для потенциально переполняющего произведения либо эквивалентную доказанную проверку перед bigint multiplication; приведение после уже переполненного произведения недостаточно. Целочисленное деление PostgreSQL также не заменяет математический floor отрицательных дробей.
4. Вычислять или проверять netMinor/feeMinor на сервере из принятых входов. Не принимать клиентские итоги как авторитет. Сериализовать суммы canonical decimal strings; не превращать их в Number ни в HTTP/JSON, ни при чтении драйвером PostgreSQL.
5. Передать в persistence именно контрактную строку `{id,subjectKey,netMinor,feeMinor,expiresAt}` вместо неограниченного spread запроса. EUR/scale2 должны быть однозначным фиксированным контрактом этой границы; добавлять валютные поля в утверждённый row shape не требуется. Экспортная feeMinor должна дословно сохранять числовое значение и единицы исходной feeMinor. Ошибки входа/переполнения не должны оставлять запись ни в основном хранилище, ни в экспортной копии.
