## Какие дополнительные проверки действительно нужны

**Delete — нужна отдельная bounded live проверка для закрытия исходной P-01 branch.** `P6e` в criteria прямо отличает stipulated решение от MCP state. Existing-library preservation в текущих runs полезен, но Delete не вызывается, поскольку disposable scratch не был создан. Нельзя считать отсутствие удаления успешным исполнением deletion contract. Минимальный отдельный synthetic fixture: current pre-read existing origin/consumer и только task-owned disposable scratch, focused documented Delete лишь scratch, затем inventory/ref-resolution и проверка сохранённого результата. Не добавлять этот шаг задним числом в blind B0/C1; сохранить отдельный exposure и raw record. Permanent harness не нужен.

**Transactional editId — stipulated evidence достаточно для заявленного decision case P2b; live recovery не проверен.** `raw-decision-inputs.json` прямо требует описать repair flow «without calling real tools». Прочитанные ответы и неизменённый API contract поддерживают это решение; B0/C1 raw не содержит transaction failure/editId/repair, а auto-review rejection не является таким событием. В принятом плане live список требует edit/component/readback/visual/export/save; он не превращает специально decision-only P2b в обязательный live error injection. Поэтому новый injected transaction не нужен для закрытия именно этого case. Если итоговый claim включает **фактически выполненный transactional recovery**, нужен отдельный controlled live error→returned editId→documented repair→preserved-state readback; до него эту runtime branch следует оставить unverified, не PASS.

## Оставшиеся действия и итоговый gate

1. Оператор завершает уже запрошенные save/close/reopen intended test `.pen`; исполнитель подтверждает fresh app state и читает прежние A/B IDs/refs. До любых новых Canvas changes сопоставить tree/geometry, screenshots и отдельные refreshed exports с frozen pre-refresh; проверить сохранность обоих outputs. Простое новое соединение не доказывает save или исправление.
2. Восстановить и проверить C1 Edit/Confirm/Applied desktop/mobile visual output по данным refresh; при сохранённом отказе продолжить RCA исходного пути, не слепую серию coordinate patches. Проверить реальные PNG и durability итогового material state. Выполнить отдельный Delete preservation case выше.
3. Передать пригодный final Pencil evidence существующему downstream owner и сверить с текущим UI/behavior authority. Если меняется material design/contract — исправить затронутый app surface и повторить его original-path checks; если меняются только статус/evidence и rendering, достаточно bounded visual comparison/readback, без повторного широкого implementation trial.
4. Заморозить обновлённые evidence и завершить independent bounded Pencil/joint assessment; root обновляет общий log/recovery ledger. Лишь после essential gates возможен единственный предусмотренный acceptance checkpoint. Публикация этим review не разрешена.

Минимальная текущая внешняя зависимость — незавершённый операторский save/reopen. Полный PASS до получения и оценки перечисленного evidence не поддержан. Source remediation заново не открывается без подтверждённой причины; отдельный shadcn C2 standalone PASS и завершённый controlled UI correction сохраняются в своих границах.
