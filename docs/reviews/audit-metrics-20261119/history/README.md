# Как воспроизвести сводку аудита

Оркестратор передаёт генератору JSON одного исследования, массив исследований или несколько файлов. Генератор выводит Markdown в stdout. Для расчёта нужны Node.js и исходные материалы репозитория. Набор исторической кампании и пределы восстановления перечислены в [описи](coverage.md). [Генератор](../../../../scripts/audit-metrics.mjs) · [Регрессионные проверки](../../../../scripts/audit-metrics.test.mjs) · [Утверждённый план](../../../plans/implementation-plan-20261119-1.md)

Из корня репозитория можно проверить один скил, затем все входы. Ссылки в таком выводе отсчитываются от корня репозитория.

```sh
node scripts/audit-metrics.mjs docs/reviews/audit-metrics-20261119/history/02.json
node scripts/audit-metrics.mjs docs/reviews/audit-metrics-20261119/history/*.json
node --test scripts/audit-metrics.test.mjs
```

Чтобы ссылки работали в сохранённом отчёте, запустите команду из каталога самого отчёта. Например, из корня репозитория выполните следующие две команды. Сводку можно заново получить из тех же JSON, сохраняя источник, рубрику и первоначальную оценку каждой работы.

```sh
cd docs/reviews/audit-metrics-20261119
node ../../../scripts/audit-metrics.mjs history/*.json > history-summary.md
```

## Что записывает оркестратор

Полный пример одного исследования находится в [02.json](02.json), пример двух последовательных исследований одного скила — в [05.json](05.json). Сохраняйте варианты, задания, назначенные пары, критерии и снимки в протоколе до исполнения. Затем укажите фактические журналы, ключи после раскрытия и подписанные ответы оценщиков. Во входе достаточно идентификаторов, контрольных сумм и относительных ссылок на уже сохранённые объекты.

| Поле | Содержание |
| --- | --- |
| `skill, study, model, effort, source` | Имя скила, идентификатор исследования, назначенные модель и режим исполнителя, ссылка на протокол с замороженными входами. `base` задаёт общий префикс путей от корня репозитория. Без него пути отсчитываются от корня. `kind: "policy"` выводит правила отдельно от числа скилов. |
| `runs[runId]` | Один состоявшийся запуск. Запишите `task, variant, sha256, source, ratings`. Хеш относится к исходному потоку событий, ссылка ведёт на полную запись или опись с ключом. У свежего повторного исполнения свой хеш и `repeatOf` с идентификатором исходной работы. |
| `runs[runId].ratings[ratingId]` | Одно полученное до раскрытия мнение. Поля `assessor, rubric, packet, score, source` обозначают оценщика, версию рубрики, выданные свидетельства, общий исход работы и подписанное основание. Значения `score` — `PASS`, `FAIL`, `INCONCLUSIVE`. В `label` можно сохранить нейтральный код выдачи. Новое мнение о прежней записи получает свой `ratingId`. |
| `series[]` | `id, comparison, phase, rubric, packet, pairs`. В `comparison` укажите проверяемую редакцию слева, контроль справа, например `full/absent`, `A/B`, `C/B`, `C/A`. Оба имени должны совпадать с `variant` в запусках. В `source` можно указать фиксацию назначения, в `limit` — область вывода. |
| `series[].pairs[]` | `id, task, left, right`. Сторона пары имеет вид `["runId", "ratingId"]`. Без исполнения поставьте `null`, при состоявшемся исполнении без оценки — `["runId", null]`. Поле `reason` у серии или пары фиксирует причину непригодности. Упомянутое в плане, но сорванное сравнение сохраняет место в знаменателе. |
| `bRemoval` и `runs[runId].behavior` | На серии или конкретной паре укажите `complete`, если до исполнения сверены все доступные выдачи B и удалены равнозначные подсказки. `partial` отмечает известную оставшуюся подсказку, `unknown` — отсутствие подтверждения. Значение пары уточняет значение серии. Для каждого наблюдаемого действия B запишите `result` (`done`, `missed` или `unknown`), `note` и `source`. |
| `technicalStarts[]` | `id, reason, source` для сбоя до открытия сессии исполнителя. Ошибка после начала действий остаётся в `runs` со ссылкой на фактический результат. |
| `taskSet` | Одинаковый ключ укажите в документах, а при необходимости в серии, только когда протокол подтверждает тот же набор заданий, например для двух моделей. Иначе имена заданий локальны внутри исследования. |

Назначьте фазу `primary` исходному сравнению, `planned-repeat` заранее запланированному свежему повтору, `diagnostic` диагностике, `confirmation` проверке принятой формулировки и `holdout` отдельному отложенному заданию. Фаза `regrade` показывает, как оценки изменились на прежних работах. Она имеет собственную строку и отдельный счётчик. Когда изменение рубрики или состава предъявленных свидетельств даёт новое основание для оценки, заведите другую серию с его идентификатором. Для проверки согласия двух оценщиков `packet` должен обозначать одинаково предъявленные свидетельства именно этой работы. Хеша всего многострочного файла, содержащего работы обоих вариантов, для этого вывода недостаточно.

В каждой серии `PASS/FAIL` даёт «лучше», `FAIL/PASS` — «хуже», `PASS/PASS` — «обе прошли», `FAIL/FAIL` — «обе ошиблись». Неполная или испорченная пара, неприменимая рубрика и неразрешённое разногласие дают «недостаточно». Знаменатель включает все назначенные пары этой серии. Итоговый счёт объединяет серии для сверки до каждой строки. Вывод о правке относится к сравнимым случаям своего исследования. Даже общий PASS работы B сам по себе ничего не сообщает о выполнении выбранного действия без подсказки. В этом столбце учитывается отдельное наблюдение при подтверждённом полном изъятии и пригодных условиях.

## Согласие и события процесса

Для заранее отобранной работы добавьте элемент в `agreement`. Укажите `run, rubric, packet, ratings: ["первое", "второе"]`. Отсутствующее мнение можно записать как `null`. Два определённых исходных мнения разных оценщиков по одинаковым свидетельствам образуют знаменатель согласия. Если они расходятся, независимый третий оценщик получает ту же выдачу. Его `ratingId` запишите в `resolution`. Сводка показывает обе исходные оценки, ожидание решения или подписанный исход разбора, в том числе `INCONCLUSIVE`. Новое выполнение задания из-за разногласия к согласованности оценщиков прежней работы не относится.

Для документарного аудита допустимы пустые `runs` и `series`. Укажите в протоколе, почему поведенческие пары неприменимы. Одна формальная передача аудитору добавляет строку в `attempts`. Обязательны `id, snapshot, source`. Ещё идущая проверка имеет пустой `verdict`. Первый возврат сохраняет своё заключение. Для нескольких документов одной цепочки укажите одинаковый `audit` и порядковый `order` либо однозначные времена передач.

| Данные события | Что появится в отчёте |
| --- | --- |
| `handed, started, decided` в UTC, `verdict` | Ожидание до проверки, время проверки, интервал от возврата до следующей передачи, весь аудит от первой передачи до последнего вердикта. Каждая медиана сообщает число полных наблюдений. |
| `active: [{kind, start, end}]` | Сумма записанных интервалов `review` или `repair` без пауз. Незарегистрированные интервалы остаются неизвестными. |
| `returned: {primary, finding, source}` | Замечание, снимок, основная причина (`skill`, `rubric`, `fixture`, `evidence`), ссылки на сопутствующие причины в исходном журнале. Отдельно учитываются требовавшие повтора скилы, состоявшиеся повторные передачи и открытые возвраты, включая ожидание второго вердикта. |
| `observation: {version, accepted, released, through, systematic, defects, source}` | Окно наблюдения принятой версии. Если выпуск к концу окна отсутствовал, укажите `released: null`, если его дата неизвестна, пропустите поле. Подтверждённый дефект получает `id, at, rule, covered, source` со ссылкой на issue или журнал. Один ID на скил и версию учитывается один раз. Отчёт различает находки до выпуска, после выпуска и без известной даты выпуска. При неполном наблюдении отсутствие записей остаётся неизвестным. |

Повторная передача того же файла даёт тот же результат. Генератор отклоняет конфликт под одним ключом исследования, одинаковый хеш исходных событий у двух разных работ и повторное назначение той же пары как двух исполнений. Оркестратор вручную проверяет идентичность исходных объектов, назначение вариантов, пригодность свидетельств и причину ограничения. Формальный вердикт, решение о тексте правила и обобщение на другие задания остаются за владельцами аудита.
