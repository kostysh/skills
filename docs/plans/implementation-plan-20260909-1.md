## 3. Проверить поведение и получить семь независимых PASS

Корректировка оператора 2026-09-09: сократить расход токенов и использование агентов. Для новых запусков reasoning medium по умолчанию; отдельные агенты только для обязательной независимости и изолированных behavioral cases. Подготовку и обычные проверки выполнять координатором, результаты оценивать пакетами. Уже снятый high baseline сохраняется; дальнейшие запуски используют medium. Сравнение high baseline с medium candidate не является контролируемым сравнением влияния только скилла; эти настройки и предел вывода фиксируются явно.

Baseline и candidate получают одинаковые входы, критерии, fixtures, полномочия и версии инструментов. Исполнители — свежие контексты GPT-6 Astra без fork; reasoning регулируется корректировкой оператора выше. Им доступны задача и необходимые active surfaces, но недоступны диагнозы, критерии оценки, предыдущие вердикты и раскрывающая ответы история. Сохранять состав экспозиции, назначенные настройки, реальные команды, выходы, изменения и состояния. Ограничения telemetry и shared filesystem фиксировать явно. Ассессор изучает исходные результаты и критерии; он не автор candidate и не выдаёт собственному исполнению независимую оценку.

Отдельно проверять:

- Выбор из каталога: собственные и смежные запросы с descriptions/UI metadata.
- Исполнение после загрузки: достаточные запросы и версионно-зависимые задачи каждого скилла.
- Сложные входы: отсутствующие и конфликтующие сведения, уточнения пользователя, недостаточные полномочия, недоступный сосед, частичные свидетельства.
- Технические изменения: obsolete API/command, изменённый default, несовместимые версии, старый поддерживаемый проект без незапрошенного upgrade.

Распределение случаев обосновывается покрытием; риск одного скилла нельзя закрыть нерелевантным тестом другого.

| Контур | Наблюдаемый результат |
|---|---|
| Hono → Supabase | Реальные HTTP success/validation/error и middleware behavior; разрешённая запись, отказ чужой роли и повторное чтение состояния. Node adapter и Workers local runtime — для затронутых платформенных правил. |
| Next → Supabase | Production build/start и browser-проверки SSR, login/logout, cookies/auth, cache/revalidation/navigation; reload подтверждает доступность своих данных и отсутствие чужих. |
| Payload-migration → Payload → Next | Импорт relationships/media/rich text/locales, частичная ошибка и повторный запуск; сверка дублей, ID и содержимого через БД, API и страницу после reload. Отдельно access denial и hook/transaction rollback на поддерживающем транзакции адаптере. |
| Electron | Реальный Linux запуск main/preload/renderer, IPC success и отказ неверному sender/input, lifecycle/permissions; package и запуск того же artifact. Signing, updates и другие ОС — полная официальная сверка и проверка отсутствия ложной готовности без целевых свидетельств. |
| Docusaurus → documentation | Build и раздача production output; browser-проверки routes/baseUrl/assets/MDX/version/i18n. Потребитель проверяет инструкции на том же результате; команды CI-шаблона выполняются в fixture. |

По карте исправлений добавить минимальные реальные проверки остальных затронутых executable claims, включая сервисы и адаптеры. Эти контуры не ограничивают обязательную техническую сверку и не требуют искусственного приложения из семи платформ.

Среда по умолчанию — Linux, доступный Docker и временные данные. GUI/Xvfb и дополнительные runtime размещаются только во временной среде. Глобальная среда, продуктовые репозитории и удалённые сервисы не изменяются. Недоступное обязательное runtime evidence оставляет зависимый verdict незавершённым; документация, mock или build его не заменяют.

Ресурсы: до трёх параллельных лёгких агентов и один тяжёлый build/DB/GUI-контур одновременно. Для тяжёлого контура установить доступными средствами предел до 4 CPU/16 GiB; для CI — workspace concurrency1, доступные CPU и пониженный приоритет. После архивирования удалить только созданные задачей временные ресурсы, сохранив worktree и evidence.

Обязательные gates:

- Авторский Audit instruction quality, compiler lint/regenerate/check, isolated compile/readback, ссылки, переносимость и metadata.
- Применимые пакетные проверки, включая существующий Hono docs-contract.
- pnpm test:ci на финальном снимке в disposable copy: проверки compiler могут пересобирать файлы.
- Стабильный hash snapshot после авторских проверок; семь отдельных независимых skill-reviewer PASS и подтверждение прямого interop.
- Проверка reviewers охватывает полноту официальной сверки, а не только изменённые строки.

Каждый P1/P2 связывается с причиной, исправлением и свидетельством закрытия. Повторный связанный FAIL требует RCA исходного пути, затем ограниченного повторного аудита. Изменение проверенной поверхности инвалидирует соответствующий PASS.

## Приёмка, риски и откат

Предъявить семь точных версий и снимков, независимые PASS, полную карту источников с датами, baseline/candidate и catalog-результаты отдельно, реальные взаимодействия, compiler/package/CI evidence и пределы по ОС и сервисам.

Приёмка возможна, когда нет открытых P1/P2, неразобранных deprecated/removed рекомендаций и существенных непроверенных утверждений, выданных за актуальные. Все обязательные gates завершены; иначе результат остаётся incomplete/blocked без запроса приёмки.

Откат ограничивается собственными изменениями относительно baseline. Соседние worktrees сохраняются. Commit, push, PR и merge в этот план исполнения не входят.
