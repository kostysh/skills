# План ревизии правил и 38 скилов под GPT‑6.2

**Результат для оркестратора.** Провести 39 ревизий. Сначала принять общие правила, затем базовый аудитор `skill-reviewer`. Для каждого скила установить, какие указания нужны GPT‑6.2 Sol для надёжного решения его задач, и проверить актуальность предметных рекомендаций. У каждого пункта ниже есть вход, короткое поручение и наблюдаемый результат для приёмки.

- Исходный снимок — `fd0f519922a37d272b31e87d8015bad6d1c80e4a`. В [каталоге](../../skills/) 38 пар `skill.yaml` и `SKILL.md`. Порядок выведен из разделов взаимодействия, описаний входов и результатов в самих скилах. Перед стартом оркестратор сверяет перечень и изменившиеся связи с рабочей версией. Внешние скилы, включая `skill-creator`, участвуют в своих ролях. Объекты ревизии перечислены в таблицах.

Для каждого скила проверь ясность результата, свободу выбора способа, границы самостоятельных решений и способ подтвердить завершение. Сохраняй точный порядок действий там, где от него зависит результат. Модельные особенности, описанные для Astra, проверяй на Sol перед переносом в скил. ## Как оркестратор выдаёт и принимает работу

1. **Открыть отдельную рабочую сессию по строке таблицы.** Передать исполнителю строку, общие условия ниже, ревизию репозитория, путь к пакету, применимые `AGENTS.md`, принятые входы соседей и разрешённые изменения. Критерий конкретной строки дополняет общую приёмку. Один владелец меняет один пакет. Общие правила ведёт владелец 00. Соседи могут напрямую согласовать вход, выход и случай для совместной проверки. Оркестратор фиксирует принятое решение и снимки обеих сторон.
2. **Проверить инструкции и актуальность.** Владелец сверяет манифест, реально поставляемый `SKILL.md`, активные ссылки, метаданные выбора, примеры, команды и ресурсы, влияющие на поведение. Для предметных утверждений указывает применимую версию, официальный источник или фактическую справку установленного инструмента, дату и вывод. Проверяет расхождения с поддерживаемыми версиями, устаревшие команды и замены. Для методических скилов сверяет действующие полномочия, критерии и передачу результата. Недоступный интерфейс ограничивает конкретный вывод.
3. **Получить поведенческие свидетельства.** Каждая ревизия, включая 00, 01 и ревизию без правок, содержит слепое сравнение по протоколу ниже. Владелец перечисляет существенные правила и решения по ним. У каждого обоснованного сокращения есть своё сравнение. При необходимости изменить пакет автор применяет `skill-creator` и `skill-source-compiler`, редактирует объявленный источник и регенерирует результат. Оправданный итог ревизии — также принятие исходной версии с доказательствами.
4. **Принять стабильную версию.** При существенной правке автор выполняет самопроверку из этапа [Audit instruction quality](../../skills/skill-source-compiler/SKILL.md#workflow-stage-audit-instruction-quality). Независимый рецензент проверяет фактически поставляемую редакцию по [методике](../../skills/skill-reviewer/references/methodology.md). Оркестратор принимает результат с предметными источниками, исходами слепых прогонов, полученными артефактами, границами проверки и заключением по тому же снимку. Для 00 действует процедура проверки общих правил. При `P1/P2` автор исправляет причину, рецензент проверяет исходный путь ошибки и затронутые стыки до `PASS`. Однотипный повторный отказ требует разобраться в причине. Изменение общего контракта открывает только зависимые проверки.

**Разрешение оператора.** Субагенты для слепых исследований уже разрешены на всю эту ревизию, включая повторные и совместные прогоны. Оркестратор передаёт это разрешение рабочим сессиям. Его можно использовать без повторного запроса. Для внешних действий и публикации действуют обычные полномочия задачи.

## Слепое сравнение одного правила

Дополнение к действующему [слепому forward-testing](../../skills/skill-reviewer/references/forward-testing.md). У карточек ниже аудитория — оркестратор и владельцы скилов. Тестируемый исполнитель видит только рабочее задание своего варианта.

| Роль | Модель и доступная информация |
| --- | --- |
| Исследователь | Готовит случаи и закрытые критерии, фиксирует варианты и их соответствие кодам. Может использовать более высокий уровень рассуждения, в том числе на Sol. |
| Тестируемый исполнитель | Только `gpt-6.2-sol`, уровень `low` или `medium`. Один и тот же уровень для всех вариантов одного сравнения. В каждой сессии выполняет обычное задание с выданной версией инструкций. |
| Оценщик результатов | В отдельной сессии получает критерии и обезличенные действия и результаты в перемешанном порядке. Может использовать более высокий уровень рассуждения. Ключ соответствия вариантов получает после выставления оценок. |
| Независимый аудитор этого плана | `gpt-6.2-astra`. Проверяет обоснованность и исполнимость плана. Это отдельное поручение. |

1. **До правок** исследователь выбирает реальное решение, на которое может влиять правило. Фиксирует исходный текст, наблюдаемый критерий успеха, допустимые побочные эффекты и ошибку, которая опровергнет успех. Берёт обычный достаточный случай и случай, различающий правильное и ошибочное решение. Для заявления о выборе скила использует также соседний запрос и один и тот же каталог до загрузки тела скила. Принудительная загрузка проверяет выполнение после выбора.
2. Готовит **A** с исходным правилом и **B** с изъятым только этим правилом. Фиксирует точную разницу в доступных исполнителю материалах. Бизнес-условия, инструменты, исходные данные, соседние скилы и остальные инструкции совпадают. Проверяет возможные подсказки в запросе, глобальных правилах, метаданных и ссылках. Если требование продублировано независимым источником, отмечает, что B доказывает избыточность в данном окружении. При необходимости проверить переносимость использует отдельный чистый комплект скила. Действующие полномочия среды сохраняются во всех случаях.
3. Запускает варианты в отдельных свежих сессиях без истории автора, ключей, предыдущих заключений и доступа к результатам соседнего прогона. Передаёт нейтральные имена и только нужные файлы. Проверяет фактическую границу доступа в общей файловой системе. Фиксирует назначенные модель и уровень, доступное подтверждение среды, снимки, вход, сырой ответ, существенные действия и состояние результата. Прогон с раскрывшейся подсказкой сохраняет как таковой и повторяет в чистой сессии. Если назначение модели или уровня установить нельзя, прогон остаётся вне вывода о поведении Sol в заданном режиме.
4. Оценщик ставит `PASS`, `FAIL` или `INCONCLUSIVE` каждому случаю по заранее зафиксированным критериям. Исследователь раскрывает ключ, сопоставляет случаи и передаёт решение автору. Объём текста и единичный успех сами по себе не обосновывают сокращение.

| Наблюдение | Действие автора |
| --- | --- |
| B устойчиво выполняет требование на обычном и различающем случаях | Заменить подробную инструкцию **кратчайшим положительным указанием на нужное действие (C)**. Сравнить C с A при тех же условиях и проверить C на свежем случае, отложенном до выбора формулировки. Если исходное указание уже минимально, зафиксировать совпадение C с A. Сохранить полномочия, явные обязательства проекта и существенные исключения. |
| A проходит, после изъятия в B возникает ошибка | Сохранить конкретику, от которой зависит правильное действие. Проверить её на исходном пути ошибки после любых правок. |
| Ошибается исходная версия A | Зафиксировать исходный дефект, исправить его и сравнить кандидат на исходном и свежем случаях. Если B при этом устойчиво проходит, проверить минимальный положительный вариант. |
| Результаты противоречат друг другу | Проверить конкретную гипотезу повтором или вариацией случая. До разрешения расхождения оставить вывод о необходимости правила открытым. |

## Совместная приёмка

Вход для старта — принятая локальная версия контракта предшественника. Итог по общему сценарию можно получить позднее, когда готовы оба участника. Поэтому взаимная ссылка не образует цикл ожидания. На стыке оркестратор передаёт фактический результат одного агента другому, фиксирует версии и наблюдает, сможет ли получатель завершить свою задачу. Один случай может одновременно закрывать несколько карточек, если сохранены критерии, данные и независимость по каждой. При несовместимости оркестратор называет владельца решения и возвращает ему конкретный пример.

| Участники | Что проверить на одном исходном примере |
| --- | --- |
| 00 ↔ 01 ↔ 02 ↔ 03 | Разрешённое действие, настоящий обязательный останов и предел структурной проверки одинаково интерпретируются правилами, аудитором, авторской самопроверкой и исполнителем. |
| 04 ↔ 14 → 15 → 23 → 32 | Проследить подтверждённое решение и его открытый остаток до спецификации и задания агенту. По артефактам следующая сессия определяет, что можно начать и что понадобится для приёмки. |
| 17 ↔ 24 ↔ 33, затем 30 → 38 | На одном изменении различить качество кода, соответствие спецификации и достижение цели пользователя. Передать установленный дефект на исправление, а свидетельства исправления — на ретроспективу. |
| 07 ↔ 08 → 17, 11 ↔ 12 → 21 | Для PR сверить Git ref и GitHub head. Для доступа к данным сопоставить инженерный вывод о правах, вывод о потоке данных и фактическую роль в БД. Это два отдельных случая. |
| 05 ↔ 06 ↔ 16 → 29, 29 → 13 → 31 | На установленной локальной CLI отличить типы, выполнение и тест. Затем проверить, что пользователь проходит инструкцию через опубликованный в локальной сборке маршрут документации. |
| 09 ↔ 19 ↔ 20, 10 ↔ 25 ↔ 26 | Передать один сценарий формы из UX в дизайн и реализацию. На отрисованной форме проверить сохранение, клавиатуру и восстановление. Для Pencil отдельно подтвердить сохранение проекта. |
| 18 ↔ 26 ↔ 27 → 34, 26 ↔ 35 | На компоненте проверить, какие решения принимает владелец компонента, а какие — SPA, Next.js или Electron. Проверять только заявленные среды и затронутые передачи. |
| 23 ↔ 28 ↔ 21, 21 ↔ 22 | Проследить контракт запроса до Hono и роли в Supabase. Для финансовой записи передать принятую формулу и сверить сохранённое значение с расчётом в заявленных слоях. |
| 27 ↔ 36 ↔ 37 | Передать принятые схему, права и версию адаптера от владельца CMS в импорт, затем перечитать итог через штатный интерфейс. |

Эти случаи покрывают основные передачи. Для другого материально изменённого стыка владельцы указывают его потребителя и проверяют именно затронутый вход и выход. При обновлении нескольких пакетов оркестратор объединяет изменения в рабочей копии и принимает совместный результат на одних и тех же версиях.

## Проверки, учёт и откат

- Для изменённого исходного комплекта запускать из корня `node skills/skill-source-compiler/scripts/skill-source-compiler.mjs regenerate skills/<имя>`, затем `check` с тем же путём. Проверить фактический состав поставки и чтение нужных файлов из автономной копии. Для интеграционной проверки есть локальная команда `pnpm --filter @kostysh/skills pack:skills --out <абсолютный-временный-каталог> --release skills-local-review`. Упаковщик и состав архива определены в [коде поставки](../../cli/src/pack.ts). Проверить правила версионирования затронутого пакета. При изменении генератора также проверить его работу на собственном пакете и на отличающемся потребителе.
- Использовать тесты пакета там, где они объявлены. У `code-reviewer`, `hono-engineer`, `security-reviewer` и `typescript-test-engineer` есть тесты документационных контрактов, у компилятора — тесты CLI. Для интегрированной редакции использовать применимые обязательные проверки репозитория, включая `pnpm test:ci` из [CI](../../.github/workflows/test.yml). Проверки, способные писать файлы, проводить в расходной копии. Заявление об интеграции с сервисом требует проверки соответствующей реальной границы или явной отметки о том, что осталось непроверенным.
- Оркестратор ведёт общий журнал реализации в `docs/reviews/` по [шаблону журнала](../templates/IMPLEMENTATION_LOG_TEMPLATE.md) и связывает его с этим планом при создании. Для каждой строки сохраняет снимок, проверенные предметные источники, точные различия A/B/C, случаи и условия доступа, ссылки на сырые результаты и заключение, решение и затронутые стыки. Для созданной записи отдельного скила обновляет его `docs/README.md`. Ключи и оценки хранит отдельно от комплекта тестируемого исполнителя.
- При регрессии изолировать кандидат и использовать последнюю принятую версию. Исправление проверять на исходном случае и затронутом стыке. Оркестратор сохраняет результаты неудачных прогонов и работу соседних сессий. Если отсутствуют обязательные свидетельства, строка остаётся открытой с конкретной причиной. Другие независимые строки продолжаются.
- **Готовность всей ревизии.** Реестр сверен с фактическим каталогом. У общих правил и у каждого скила есть предметный вывод, слепое сравнение с вариантом без правила и независимое решение о приёмке на определённом снимке. Для сокращённых указаний подтверждён вариант C. Затронутые совместные сценарии пройдены на согласованных версиях. Оркестратор сообщает число принятых и открытых строк, существенные изменения и пределы доказательств.
